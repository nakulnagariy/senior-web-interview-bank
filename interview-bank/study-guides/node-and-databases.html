Node.js runtime and event loop

“How does Node.js work? Explain the event loop phases, libuv and the thread pool, non-blocking I/O, streams, buffers, CommonJS versus ES modules, and when Node is a poor fit.”

Say this first (30 seconds)

“Node.js runs JavaScript on V8 outside the browser, with a single main thread and an event-driven, non-blocking I/O model implemented by libuv. When my code starts an I/O operation such as a file read or a network call, libuv hands it to the operating system or a small thread pool, and the callback or promise resolves later through the event loop, so one thread can serve thousands of concurrent connections. The event loop cycles through phases: timers, pending callbacks, poll for I/O, check for setImmediate, and close callbacks, with microtasks and process.nextTick drained between them. Node is excellent for I/O-heavy APIs, real-time and tooling; it is a poor fit for CPU-bound work on the main thread, which blocks every request, unless moved to worker threads or other services.”

Details interviewers probe

  • Single-threaded, but not single-process: the JavaScript runs on one thread; libuv and the OS do I/O work in parallel; worker_threads give additional JavaScript threads with message passing and SharedArrayBuffer; the cluster module or process managers (PM2, containers) run one process per core.
  • Blocking versus non-blocking: fs.readFileSync blocks the loop; fs.promises.readFile does not. Synchronous APIs are acceptable at startup (config loading) but not in request handlers. CPU work such as large JSON parsing, crypto hashing (use async crypto.scrypt/argon2 libraries that use the pool), image processing and regex backtracking can freeze the server (J14).
  • Streams: process data in chunks without loading it all: Readable, Writable, Duplex, Transform. pipeline() from stream/promises handles errors and cleanup; backpressure signals (write() returns false, drain event) prevent memory blowup. Use for file uploads, large downloads, compression, and proxying; HTTP request and response objects are streams.
  • Buffers: raw binary data (Buffer, a Uint8Array subclass) for files, network and crypto; allocate with Buffer.alloc; encoding conversions (utf8, base64, hex).
  • Modules: CommonJS (require, synchronous, cached, module.exports) and ES modules (import, static, async, "type": "module" or .mjs); interop caveats: require of ESM is limited (improving in newer versions verify), ESM lacks __dirname (use import.meta.dirname/url), file extensions required, top-level await available (J15).
  • Process and environment: process.env, process.argv, signals (SIGTERM for graceful shutdown), uncaughtException and unhandledRejection handlers (log and exit, do not continue), exit codes, process.memoryUsage().
  • Built-in modules worth knowing: http/https, fs, path, os, events (EventEmitter), stream, crypto, url, util.promisify, child_process, worker_threads, perf_hooks, async_hooks/AsyncLocalStorage for request context, and a built-in test runner (node:test) and fetch in recent versions.
  • EventEmitter: the base of many APIs (observer pattern, J28); remember to remove listeners, handle the 'error' event (an unhandled error event throws), and watch for listener leak warnings.
  • Error handling: callbacks use error-first convention; promises and async/await are the norm; wrap route handlers so rejected promises reach error middleware (Express 5 does this natively); distinguish operational errors (expected) from programmer errors (bugs) (J21).
  • Versions and LTS: use even-numbered LTS releases in production; check the end-of-life schedule; manage versions with nvm/fnm/Volta; pin in .nvmrc and Docker images.
  • When Node fits: API gateways and BFFs, real-time (WebSockets), microservices with I/O-bound work, SSR, build tooling, serverless functions. When not: heavy computation, machine learning training, long-lived CPU-bound batch processing (use Go, Java, Rust, Python) unless offloaded.
  • Performance tips: avoid sync calls in handlers, reuse connections (HTTP keep-alive agents, DB pools), cache hot data, stream large payloads, profile with --inspect/clinic, and watch event-loop lag (perf_hooks.monitorEventLoopDelay).

Traps

  • Saying Node is “single-threaded” without mentioning libuv, the thread pool and workers.
  • Running CPU-heavy work in a request handler and wondering why latency spikes for everyone.
  • Using synchronous filesystem or crypto calls in handlers.
  • Letting an unhandledRejection go unnoticed in older Node versions, or continuing after uncaughtException.
  • Ignoring backpressure when piping streams manually.

Likely follow-ups

setImmediate versus setTimeout(0) versus nextTick?
nextTick runs before the loop continues (before promise microtasks); setImmediate runs in the check phase after poll; setTimeout(0) runs in the timers phase after at least one millisecond; their order from the main module is non-deterministic.
How do you use all CPU cores?
Run multiple processes (cluster, PM2, containers behind a load balancer) or worker threads for CPU work.
What is backpressure?
A signal from a slow consumer telling the producer to pause so buffers do not grow without bound; pipeline handles it.
How do you find event-loop blocking?
Measure event-loop delay, CPU profile with --cpu-prof, and look for long synchronous functions.

Express and middleware

“How does Express work? Explain middleware, the request lifecycle, routing, error handling, async errors, validation and project structure. What are alternatives like Fastify, NestJS and Hono?”

Say this first (30 seconds)

“Express is a minimal web framework built around middleware: functions that receive the request, the response and next, run in the order they were registered, and either end the response or call next to pass control on. A request flows through global middleware such as logging, security headers, body parsing and authentication, then the matching route handler, and errors flow to error-handling middleware with four arguments. The order matters. I structure apps in layers: routes, controllers, services and data access, validate input with a schema, centralise error handling, and keep configuration and secrets in the environment. Alternatives include Fastify for speed and schema-based validation, NestJS for opinionated structure with dependency injection, and Hono for edge runtimes.”

Details interviewers probe

  • Middleware types: application-level (app.use), router-level, error-handling (four parameters), built-in (express.json(), express.static), and third-party (helmet, cors, morgan/pino-http, compression, express-rate-limit, cookie-parser, multer). Order: security and parsing first, then auth, routes, 404 handler, error handler last.
  • Routing: methods and path patterns, route parameters (/users/:id), query strings, express.Router() for modular routes, route-level middleware, path-to-regexp rules (changed in Express 5), and a catch-all 404.
  • Request and response: req.params, req.query, req.body, req.headers, res.status().json(), res.set, streaming with res.write or pipe. Always send exactly one response; “headers already sent” errors mean double responses.
  • Error handling: create typed errors (AppError with status and code), throw or next(err), a single error middleware that logs full details but returns safe messages (no stack traces in production), and handle 404 separately. For async code in Express 4 use an asyncHandler wrapper or express-async-errors; Express 5 handles promise rejection natively.
  • Validation: validate body, query and params with Zod, Joi or Ajv at the boundary; return 400/422 with field errors; never trust client data; sanitise where output encodes (T11, E6).
  • Security middleware: helmet (security headers), cors with an allowlist, rate limiting, request size limits (express.json({ limit })), disabling X-Powered-By, HTTPS and secure cookies behind proxies (trust proxy), CSRF protection for cookie sessions, input validation, parameterised queries (P5, P6, P7).
  • Configuration: twelve-factor: config from environment, validated at startup; no secrets in code; separate dev and production behaviour; NODE_ENV=production enables optimisations.
  • Project structure: by feature (users/ with routes, controller, service, schema, tests) scales better than by technical type; keep controllers thin; services independent of Express for testability; dependency injection manually or with a container.
  • Static files and SPA hosting: express.static with cache headers; history fallback to index.html; in production prefer a CDN or reverse proxy for static content.
  • Alternatives: Fastify (high performance, JSON-schema validation and serialisation, plugin encapsulation, built-in logging with pino); NestJS (TypeScript, decorators, modules, DI, guards, pipes, interceptors, Angular-like structure, good for large teams); Koa (minimal, async middleware); Hono (tiny, runs on edge and Node, Bun, Deno); tRPC for typed RPC (E9). Choose by team size, structure needs and performance targets.
  • Testing: export the app separately from listen; use supertest for HTTP-level tests; mock dependencies at service boundaries; test error paths and auth (D11).
  • Graceful shutdown: on SIGTERM stop accepting connections (server.close), finish in-flight requests, close DB pools, then exit; set a timeout.
  • Health and readiness endpoints: /healthz (liveness) and /readyz (dependencies ready) for orchestrators.

Traps

  • Registering the error handler before routes, or body parsers after routes, so they never apply.
  • Forgetting return after sending a response and then calling next() or sending again.
  • Unhandled promise rejections in async handlers on Express 4.
  • Returning stack traces and internal error messages to clients.
  • Accepting unlimited body sizes or unvalidated input.

Likely follow-ups

What does next() do?
Passes control to the next matching middleware; next(err) skips to the error handlers.
How do you handle errors consistently?
Typed application errors, one error-handling middleware that maps them to status codes and a standard JSON shape, plus structured logging.
Why choose NestJS or Fastify?
NestJS for structure and DI in large teams; Fastify for performance and schema-driven validation.
How do you structure a growing Express codebase?
By feature modules with layered controllers, services and repositories, shared infrastructure, and tests per layer.

REST API design

“How do you design a good REST API? Resources, verbs, status codes, pagination, filtering, versioning, idempotency, errors, rate limiting, documentation. When do you pick GraphQL or gRPC instead?”

Say this first (30 seconds)

“A good REST API models resources with nouns in URLs, uses HTTP methods for actions and status codes for outcomes, and is predictable: consistent naming, pagination, filtering and error format. GET reads and is safe, POST creates, PUT and PATCH update, DELETE removes, with idempotency respected so clients can retry safely. I return consistent JSON with problem-details errors, support cursor pagination for large collections, version deliberately, protect with authentication, authorisation and rate limiting, and document with OpenAPI so clients and tests can be generated. I would choose GraphQL when many different clients need flexible aggregated data, and gRPC for internal service-to-service calls.”

Details interviewers probe

  • REST constraints: client-server, stateless requests, cacheable responses, uniform interface (resources, representations, self-descriptive messages), layered system; HATEOAS (links in responses) is the least adopted. In practice “REST-ish JSON over HTTP” with sound conventions is the goal.
  • Naming and modelling: nouns, plural collections, hierarchical relationships only one or two levels deep, filter by query parameters (?status=active&sort=-createdAt), field selection (?fields=), consistent casing (camelCase JSON), ISO 8601 UTC timestamps, string ids for large numbers.
  • Methods semantics: safe (GET, HEAD), idempotent (GET, PUT, DELETE), non-idempotent (POST, usually PATCH); design retries around that; support HEAD and OPTIONS where useful (P1).
  • Pagination: offset/limit (simple, can skip or duplicate on changing data, slow for deep pages), cursor/keyset (use an indexed column, stable and fast), page tokens; include next/prev links or cursors; return total counts only if cheap (counts are costly on big tables). Cap limit.
  • Filtering and sorting: allow-list sortable and filterable fields (avoid injection and unindexed scans); document operators; consider search endpoints for complex queries.
  • Idempotency and concurrency: Idempotency-Key for POST; optimistic concurrency with ETag/If-Match (412 on mismatch) or version fields to prevent lost updates; return 409 for conflicts.
  • Errors: a consistent shape with machine-readable code, human message and field details (RFC 9457 problem details); correct status codes; do not leak internals; include a request/trace id for support.
  • Caching and conditional requests: ETags and Cache-Control for GET; 304 responses; Vary (P3).
  • Bulk and long-running operations: batch endpoints with partial-success reporting; asynchronous jobs return 202 Accepted with a status URL; webhooks or polling for completion; file uploads via presigned URLs.
  • Security: authentication (bearer tokens), authorisation per resource, rate limiting by key and IP, input validation, CORS allowlists, no sensitive data in URLs, TLS, and audit logging (P8, D4).
  • Documentation and contracts: OpenAPI/Swagger spec as the contract; generate docs (Swagger UI, Redoc), client SDKs and mocks; contract tests; keep spec and code in sync (code-first with decorators or schema-first).
  • Versioning and compatibility: additive changes are compatible; removing or changing fields requires a new version; support old versions for a deprecation window; communicate with changelog and Deprecation/Sunset headers.
  • GraphQL versus REST versus gRPC: GraphQL for diverse clients and nested data (watch N+1, caching, query cost limits); gRPC for typed, streaming service-to-service calls; REST for public, cache-friendly APIs (E9, P4).
  • Frontend-friendly APIs: stable shapes, predictable errors, pagination consistent across endpoints, partial responses, enums as strings, no ambiguous nulls, ids as strings, and time zone clarity — all reduce frontend complexity.

Traps

  • Verbs in URLs everywhere (/getUsers) and inconsistent naming.
  • Returning 200 for failures, or 500 for client mistakes.
  • Offset pagination on huge, frequently changing tables.
  • Breaking changes without versioning or a deprecation path.
  • No idempotency story for payments or order creation.

Likely follow-ups

PUT versus PATCH?
PUT replaces the full representation and is idempotent; PATCH applies partial changes (JSON Patch or merge patch).
Why cursor pagination?
It uses an indexed position instead of skipping rows, so it is fast and stable under inserts and deletes.
How do you make POST safe to retry?
Accept an idempotency key, store the first result for that key, and return the same response for repeats.
How do you version an API without breaking clients?
Prefer additive changes, introduce /v2 only for breaking ones, run both with a deprecation timeline.

Authentication and authorisation in Node

“How do you implement authentication and authorisation in a Node API? Password hashing, sessions versus JWT, refresh tokens, role-based access control, rate limiting and common vulnerabilities.”

Say this first (30 seconds)

“Authentication verifies who the caller is, authorisation decides what they can do. For credentials I hash passwords with Argon2id or bcrypt and never store them reversibly. For browser clients I prefer server sessions in an HttpOnly cookie, or short-lived access tokens with rotated refresh tokens; JWTs suit service-to-service and stateless verification but are hard to revoke. In Express, an auth middleware verifies the session or token and attaches the user to the request, and a second layer checks permissions: roles, or better, ownership and attribute-based rules, enforced in the service layer. I add rate limiting, account lockout protection, input validation, secure cookie flags and CSRF protection, and I use an identity provider where possible rather than building everything.”

Details interviewers probe

  • Password handling in Node: argon2 or bcrypt (cost tuned to about 100 to 500 ms), per-user salt (built in), optional pepper from a secrets manager, minimum length and breached-password checks, constant-time comparison, no logging of credentials (P9).
  • Sessions in Express: express-session with a store (Redis via connect-redis), cookie: { httpOnly, secure, sameSite, maxAge }, trust proxy behind a load balancer, regenerate the session id after login, destroy on logout, idle and absolute timeouts.
  • JWT implementation: jose or jsonwebtoken; asymmetric keys (RS256/ES256) for multi-service verification; validate iss, aud, exp; pin algorithms; short expiry; keep claims minimal; rotate signing keys via JWKS; do not put secrets in the payload (P8).
  • Refresh tokens: opaque random values stored hashed server-side, bound to device, rotated on each use with reuse detection (reuse means theft: revoke the family), sent in an HttpOnly cookie for browsers.
  • OAuth and SSO: use Passport.js strategies, Auth.js, or provider SDKs; authorisation code with PKCE; verify ID tokens; map external identities to local accounts safely (verify email ownership). Prefer managed identity (Auth0, Cognito, Entra, Clerk, Supabase Auth, Keycloak) for MFA, recovery, breach detection and compliance.
  • Authorisation design: centralised policy functions, tested thoroughly, applied in the service layer so every entry point (REST, GraphQL, jobs) is protected; multi-tenancy requires a tenant id on every query (or database row-level security, D7); log denied access attempts.
  • API keys and service accounts: hash stored keys, scope them, support rotation and revocation, rate-limit per key, prefix for identification; machine-to-machine through OAuth client credentials.
  • Rate limiting and abuse: express-rate-limit with a shared store (Redis) so limits hold across instances; stricter on login, registration, password reset, OTP; combine IP and account keys; add CAPTCHA or proof-of-work selectively; return 429 with Retry-After.
  • CSRF and CORS: cookie-based sessions need CSRF defences (SameSite, tokens such as csrf-csrf, Origin checks); bearer-token APIs do not; CORS with an allowlist (P5, P6).
  • Common vulnerabilities: IDOR, mass assignment (binding request bodies directly into models; use explicit allowlists), NoSQL/SQL injection, SSRF, path traversal in file serving, JWT alg:none/confusion, insecure password reset links, verbose errors, missing authorisation on secondary endpoints, privilege escalation through role fields in updates.
  • Security hygiene: helmet, HTTPS only, dependency audits, secrets in environment or vault, least-privilege DB users, audit logs for sensitive actions, and security tests in CI (P10).
  • Testing auth: test each role against each endpoint (matrix), test unauthenticated access, expired and tampered tokens, and ownership boundaries.

Traps

  • Checking only that a user is logged in, not that they own the resource.
  • Binding req.body straight into a model update, letting clients set role or isAdmin.
  • Rate limiting in memory on a multi-instance deployment, so limits are per instance.
  • Storing refresh tokens in plain text or never rotating them.
  • Building custom auth when a managed identity provider would be safer.

Likely follow-ups

Session or JWT for a SPA with a Node API?
Server session in an HttpOnly cookie (often via a BFF) for simplicity and revocation; JWTs when stateless verification across services is needed.
What is mass assignment?
Letting a client set fields it should not by passing the whole request body to a create or update; fix with explicit allowlists or DTOs.
How do you revoke access immediately?
Delete the server session or refresh token family; for JWTs use short expiry plus a deny list.
How do you support multiple tenants safely?
Tenant id on every row and query via a mandatory scope, ideally enforced by database row-level security as well.

SQL versus NoSQL, ACID, CAP, ORMs

“How do you choose between a relational and a NoSQL database? What are ACID and BASE, the CAP theorem and consistency models? What do ORMs such as Prisma, Drizzle and Mongoose give you and cost you?”

Say this first (30 seconds)

“Relational databases store data in tables with a fixed schema, enforce relationships and constraints, and offer ACID transactions and powerful querying with SQL, which suits structured, related data like orders and accounts. NoSQL covers several models, document stores like MongoDB, key-value stores like Redis, wide-column and graph databases, which trade some relational features for flexible schemas, horizontal scaling or specialised access patterns. ACID means transactions are atomic, consistent, isolated and durable; many distributed NoSQL systems favour availability and eventual consistency, sometimes called BASE. The CAP theorem says during a network partition you must choose between consistency and availability. My default is a relational database such as PostgreSQL, and I add specialised stores when the access pattern clearly needs them.”

Details interviewers probe

  • When relational fits: structured data with relationships, need for transactions (payments, inventory), ad-hoc queries and reporting, strong integrity constraints, mature tooling. PostgreSQL covers JSON, full-text search, geospatial and queues in one system, which reduces moving parts.
  • When document stores fit: hierarchical data read as a whole (profiles, content, catalogs with varying attributes), rapid schema evolution, horizontal scaling by sharding. Risks: duplication, weaker joins, consistency across documents, and “schemaless” meaning the schema lives in your code.
  • Key-value and caches: Redis/Memcached for sessions, rate limits, queues, leaderboards (D9); DynamoDB for massive scale with predictable single-digit-millisecond lookups and careful access-pattern design.
  • ACID and isolation levels: read committed (default in PostgreSQL), repeatable read, serializable; anomalies: dirty read, non-repeatable read, phantom read, lost update, write skew. Higher isolation costs concurrency and may need retries (D6).
  • BASE and eventual consistency: basically available, soft state, eventually consistent. Acceptable for feeds, counters, search indexes; not for balances. Design UIs for it (optimistic updates, “saved” indicators) and use read-your-writes where needed.
  • CAP in practice: CAP is about behaviour during partitions; latency trade-offs are better described by PACELC (else latency versus consistency). Single-node relational databases sidestep partitions; replicated systems choose per operation (quorum reads and writes).
  • Replication and scaling: read replicas (eventually consistent reads), sharding/partitioning (by key), connection pooling, caching, and vertical scaling first. Relational databases scale far with good indexes and replicas before sharding.
  • Schema design principles: normalise to avoid anomalies (third normal form), denormalise deliberately for read performance, use proper types and constraints, surrogate keys (UUIDv7 or bigint), foreign keys with cascades chosen carefully, and migrations tracked in version control.
  • ORMs and query builders: Prisma (schema-first, type-safe client, migrations), Drizzle (SQL-like, lightweight, type-safe), TypeORM and Sequelize (classic ORMs), Knex/Kysely (query builders), Mongoose (MongoDB schemas and validation). Benefits: productivity, type safety, migrations, parameterised queries. Costs: hidden N+1 queries, leaky abstractions, performance surprises, harder complex SQL; drop to raw SQL for reports and hot paths.
  • N+1 problem: fetching a list and then one query per item; fix with joins/includes, batching (DataLoader), or prefetching related data; detect with query logging and APM.
  • Migrations: versioned, reviewed, applied automatically in CI/CD; backward-compatible changes (expand then contract) so old and new code run together during rollout; avoid long locks on large tables (A6).
  • Data modelling for APIs: map DB rows to DTOs; never expose internal ids or sensitive fields; paginate; use transactions for multi-step writes; keep money in integers or decimals, not floats (J13).
  • Backups and recovery: automated backups, point-in-time recovery, tested restores, RPO and RTO targets, replicas in other zones, and migration rehearsals.
  • Decision guidance for the interview: state the access patterns, consistency requirement, scale and team context, then recommend (usually PostgreSQL) and name the trade-offs and what would change your mind.

Traps

  • “NoSQL scales, SQL does not.” Relational databases scale a long way; NoSQL scale needs careful data modelling.
  • Choosing MongoDB for highly relational data and then reimplementing joins in application code.
  • Believing “schemaless” removes the need for a schema; it just moves it.
  • Misusing CAP as a label for databases instead of a statement about partitions.
  • Using floating-point numbers for money.

Likely follow-ups

How would you pick a database for an e-commerce app?
PostgreSQL as the system of record for orders and inventory with transactions, Redis for sessions and caching, search engine for catalogue search if needed.
What is eventual consistency?
Replicas converge to the same value if updates stop, but reads may be stale in between.
What is write skew?
Two concurrent transactions each read overlapping data and write different rows, together violating an invariant; prevented by serializable isolation or explicit locks.
Why avoid ORMs for reports?
Complex aggregations and joins are clearer and faster in SQL; ORMs generate inefficient queries for them.

SQL essentials: joins, indexes, transactions

“Explain SQL joins, indexes, query plans, normalisation, transactions and isolation levels. How do you find and fix a slow query? What is the N+1 problem?”

Say this first (30 seconds)

“Joins combine rows from tables: an inner join returns matches only, left join keeps all rows from the left table with nulls where nothing matches, and so on. An index is a sorted data structure, usually a B-tree, that lets the database find rows without scanning the whole table, at the cost of extra storage and slower writes; composite indexes follow the leftmost-prefix rule. To fix a slow query I run EXPLAIN ANALYZE, look for sequential scans on large tables, bad row estimates and expensive sorts, then add or adjust indexes, rewrite the query or reduce the data. A transaction groups statements atomically; isolation levels trade anomalies for concurrency. Normalisation removes redundancy, and I denormalise only with a measured reason.”

Details interviewers probe

  • Core SQL: SELECT, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT/OFFSET, aggregates, DISTINCT, subqueries, CTEs (WITH), set operations (UNION), CASE; window functions (ROW_NUMBER(), RANK(), SUM() OVER (PARTITION BY …)) for rankings and running totals; EXISTS versus IN; NULL semantics (three-valued logic; = NULL never true, use IS NULL).
  • Keys and constraints: primary key, foreign key (referential integrity, ON DELETE behaviour), unique, not null, check constraints; let the database enforce invariants rather than only application code. Composite and surrogate keys; UUID versions and index locality.
  • Index types: B-tree (default), hash, GIN (arrays, JSONB, full-text), GiST/SP-GiST (geospatial), BRIN (huge ordered tables), partial indexes (WHERE active), covering indexes (INCLUDE) enabling index-only scans, unique indexes. Primary-key indexes are clustered in some engines (MySQL InnoDB) but not in PostgreSQL heap tables.
  • Query plans: EXPLAIN (ANALYZE, BUFFERS) shows scan types (Seq Scan, Index Scan, Index Only Scan, Bitmap), join algorithms (Nested Loop, Hash Join, Merge Join), estimated versus actual rows, sort and aggregate costs. Out-of-date statistics (ANALYZE) cause bad plans.
  • Slow query workflow: find via slow query log or pg_stat_statements; reproduce with real parameters; read the plan; fix with an index matching filter and sort, rewrite to avoid functions on indexed columns, reduce rows early, paginate with keyset, avoid SELECT *, check lock waits and connection pool saturation; verify improvement and monitor regression.
  • Pagination performance: OFFSET 100000 scans and discards rows; use keyset pagination (WHERE (created_at, id) < ($1, $2) ORDER BY … LIMIT) with a matching index (D3).
  • Transactions: BEGIN … COMMIT/ROLLBACK, savepoints; use for multi-statement invariants (transfer money); idempotent retries on serialization failures or deadlocks; avoid long transactions and holding them across network calls.
  • Locking and concurrency: MVCC lets readers not block writers in PostgreSQL; row locks (FOR UPDATE, SKIP LOCKED for work queues), advisory locks, optimistic concurrency with version columns; deadlocks arise from inconsistent lock ordering.
  • N+1 and query counts: one query for a list plus one per row; fix with joins, IN batching, ORM include, or DataLoader; log queries per request in development.
  • Aggregations and reporting: pre-aggregate with materialised views or summary tables, use read replicas for heavy reports, and consider OLAP stores for analytics.
  • Data types: timestamptz for time (store UTC), numeric for money, text with constraints, enums or lookup tables for fixed sets, JSONB for flexible attributes (indexed with GIN).
  • Migrations and safety: add nullable columns first, backfill in batches, add constraints after (NOT VALID then validate), create indexes CONCURRENTLY, avoid table rewrites during peak, and make changes backward compatible.
  • Security: parameterised queries (never string concatenation) to prevent SQL injection; least-privilege roles; encrypt sensitive columns where required; audit logging.

Traps

  • Building SQL with string concatenation from user input.
  • Adding an index on every column “just in case”, slowing writes.
  • Putting a function on an indexed column in WHERE so the index cannot be used.
  • Confusing WHERE and HAVING, or using COUNT(*) with a left join and getting 1 for no matches.
  • Holding a transaction open while calling an external API.

Likely follow-ups

Why is the order of columns in a composite index important?
The index is sorted by the first column, then the second, so it helps queries that filter on a leftmost prefix.
What does EXPLAIN ANALYZE tell you?
The chosen plan with real timings and row counts, so you can spot scans, bad estimates and expensive operations.
What is MVCC?
Multi-version concurrency control: each transaction sees a snapshot, so reads do not block writes.
How do you handle a deadlock?
Keep transactions short, lock rows in a consistent order, and retry the failed transaction.

PostgreSQL and Supabase

“What is Supabase and how is it built? Explain its Postgres foundation, Auth, Row Level Security, Realtime, Storage and Edge Functions. How do you use it from a frontend, and what are its limits?”

Say this first (30 seconds)

“Supabase is an open-source backend platform built around PostgreSQL. It gives you a managed Postgres database plus an auto-generated REST and GraphQL API through PostgREST, authentication, file storage, realtime subscriptions to database changes, and serverless Edge Functions. The security model is the key idea: because the client can talk to the database API directly with a public key, authorisation is enforced inside Postgres with Row Level Security policies that use the authenticated user’s JWT, for example ‘a row is visible only if its user_id equals auth.uid()’. That lets a frontend team move fast, but it means policies must be designed and tested carefully, and complex business logic still belongs in database functions, Edge Functions or a separate backend.”

Details interviewers probe

  • PostgreSQL strengths: mature, standards-compliant, extensible; JSONB with GIN indexes, full-text search, arrays, range types, CTEs and window functions, partitioning, logical replication, row-level security, extensions (PostGIS, pgvector for embeddings, pg_cron, pg_trgm), MVCC and robust transactions.
  • Supabase components: Postgres (managed), PostgREST (REST API derived from tables and views, using the caller’s role), GoTrue (Auth: email/password, magic links, OAuth providers, phone, MFA, SSO in higher plans), Realtime (Elixir service broadcasting database changes from the WAL, Broadcast and Presence channels), Storage (buckets with RLS-like policies, signed URLs, image transformations), Edge Functions (Deno/TypeScript at the edge), and Studio dashboard.
  • Client usage: createClient(url, anonKey); supabase.from('notes').select('*, tags(name)').eq('user_id', id) with relationship expansion; insert, update, delete, rpc('fn') for database functions; auth.signInWithPassword/OAuth; channel().on('postgres_changes', …) for realtime; generated TypeScript types from the schema (supabase gen types) (T11).
  • RLS design: enable per table; write policies for each operation (select, insert, update, delete) with using (existing rows) and with check (new rows); use helper functions for roles and tenancy (auth.jwt() claims, membership tables); index the columns used in policies; test policies with different users (pgTAP or Supabase test helpers); remember that policies add query cost, so keep them simple and indexed.
  • Roles and keys: anon (unauthenticated), authenticated (logged in), and service_role (bypasses RLS, server only). The anon key is public by design; safety comes from RLS and grants. Misconfigured RLS (disabled, or overly permissive policies like using (true)) is the most common Supabase security flaw.
  • Server-side use: Next.js with @supabase/ssr for cookie-based sessions in server components and route handlers; use the service role only in server code; validate input; combine with Server Actions (N6).
  • Business logic: use Postgres functions (plpgsql/SQL) and triggers for data integrity and transactions (via rpc), Edge Functions for webhooks, third-party APIs and secrets, and scheduled jobs with pg_cron or Edge schedules. Avoid putting multi-step critical logic purely in client code.
  • Realtime caveats: database change streams respect RLS but have throughput and payload limits; use Broadcast for ephemeral messages; plan for reconnect and missed events (P4).
  • Migrations and environments: manage schema as SQL migrations with the Supabase CLI in Git, separate projects for dev, staging, production (or branching), seed data, and CI to apply migrations.
  • Limits and trade-offs: vendor-managed service with quotas and pricing tiers; connection limits (use the pooler, Supavisor/PgBouncer, in serverless); complex domain logic may outgrow the client-centric model; vendor lock-in is lower than most BaaS because it is Postgres, and self-hosting is possible but operationally heavy; compare with Firebase (NoSQL, proprietary), Appwrite, and custom Node + Postgres.
  • Performance and operations: indexes, query plans, connection pooling, read replicas on higher plans, caching at the edge, monitoring with the dashboard and pg_stat_statements, backups and point-in-time recovery on paid plans.
  • Security checklist: RLS on all tables, no service key in clients, least-privilege grants, validate uploads with Storage policies, restrict OAuth redirect URLs, enable email confirmation, rate limit auth, and review Security Advisor warnings in the dashboard.
  • When to choose it: MVPs, internal tools, apps with user-owned data and straightforward authorisation, teams strong in frontend and SQL; less ideal for heavy bespoke backend workflows or strict compliance needing custom infrastructure.

Traps

  • Shipping tables without RLS because “the anon key is hidden”. It is public by design.
  • Using the service_role key in browser code or public repos.
  • Writing RLS policies that perform slow subqueries without indexes.
  • Putting complex multi-step business rules only in the client.
  • Calling Supabase “a Firebase clone”; it is relational, SQL-first and open source.

Likely follow-ups

How does a Supabase client query get authorised?
The request carries the user’s JWT; PostgREST sets the database role and claims, and RLS policies decide which rows are visible or writable.
What is the difference between using and with check?
using filters existing rows for select, update and delete; with check validates rows being inserted or updated.
Where do you put logic that must not run in the browser?
In Postgres functions or Edge Functions on the server, using the service role where required.
Supabase versus building a Node API?
Supabase accelerates CRUD, auth and realtime with RLS; a custom API gives full control over workflows, integrations and complex rules.

MongoDB

“How does MongoDB work? When do you embed versus reference? Explain indexes, the aggregation pipeline, transactions, replica sets, sharding, write concern and Mongoose. What are its pitfalls?”

Say this first (30 seconds)

“MongoDB is a document database storing BSON documents, JSON-like records with nested arrays and objects, in collections without a fixed schema. Modelling is driven by access patterns: I embed data that is read together and bounded in size, such as an order’s line items, and reference data that is shared, large or changes independently, such as users. Indexes, including compound and TTL indexes, are essential for performance. The aggregation pipeline transforms and analyses data in stages. Replica sets provide high availability with a primary and secondaries, and sharding scales horizontally by a shard key. Multi-document transactions exist but are costlier than single-document atomicity, so good modelling avoids needing them. Mongoose adds schemas, validation and middleware in Node.”

Details interviewers probe

  • Document model: BSON types (ObjectId, Date, Decimal128, arrays, embedded documents), _id primary key, flexible schema within a collection, 16 MB document limit. Schema validation rules ($jsonSchema) and Mongoose schemas add structure.
  • CRUD operations: insertOne/Many, find with filters and projections, updateOne with operators ($set, $inc, $push, $pull, $addToSet), findOneAndUpdate (atomic), deleteOne, bulk writes, upserts. Updates to a single document are atomic.
  • Query operators: comparison ($gt, $in), logical ($and, $or), element, array ($elemMatch), regex, text search; arrays match any element by default, a common source of confusion.
  • Indexing strategy: every frequent query needs an index; compound index order follows equality then sort then range (ESR); too many indexes hurt writes and memory; covered queries return from the index alone; use explain('executionStats') to see COLLSCAN versus IXSCAN and docs examined versus returned; TTL indexes expire sessions and logs; unique indexes enforce constraints.
  • Transactions: multi-document ACID transactions across a replica set or sharded cluster (since 4.0/4.2) using sessions; they add overhead and limits, so prefer single-document designs; use them for multi-collection invariants such as transfers.
  • Replication and consistency: replica sets with automatic failover; write concern (w: 1 versus majority) and read concern/preference determine durability and staleness; reading from secondaries can return stale data; use causal consistency sessions for read-your-writes.
  • Sharding: horizontal partitioning by shard key (ranged, hashed, zoned); a good key has high cardinality, even distribution and supports targeted queries; poor keys cause hot shards and scatter-gather queries; resharding is possible but heavy, so plan ahead.
  • Aggregation: pipeline of stages for transformations, grouping, joins ($lookup), faceting, and computed fields; put $match and $limit early to use indexes; Atlas Search and vector search extend it.
  • Mongoose: schemas with types and validators, models, middleware (hooks), virtuals, population (populate performs separate queries, like a join in application code), lean queries for speed, timestamps, indexes defined in schemas (build in production carefully). Gotchas: unbounded populate, N+1, schema drift, buffering when disconnected, and version conflicts (__v optimistic concurrency).
  • Common pitfalls: unbounded arrays, treating Mongo like a relational DB with many joins, missing indexes, large skip-based pagination, no schema discipline, weak durability settings, and unbounded growth of collections without TTL or archiving.
  • Operations: MongoDB Atlas (managed) for backups, monitoring and scaling; connection pooling in the driver (reuse a single client; in serverless cache the connection); monitoring slow queries with the profiler; security: authentication on, least-privilege roles, network restrictions, TLS, field-level encryption where needed, and never expose the database to the public internet.
  • Injection risks: NoSQL injection through operators in user input ({ "$ne": null } in a login body); validate and coerce types, use schema validation, and sanitise operator keys (express-mongo-sanitize).
  • When to choose MongoDB: varied or evolving document shapes, content and catalogue data, event or log storage with bucketing, rapid prototyping, horizontal scale needs; choose relational when data is highly interrelated with strong transactional needs.

Traps

  • Embedding unbounded arrays that grow forever until hitting the document limit.
  • Modelling everything as references and then doing client-side joins.
  • Reading from secondaries and assuming up-to-date data.
  • Accepting raw query objects from clients, enabling operator injection.
  • Choosing a shard key such as a monotonically increasing id, creating a hot shard.

Likely follow-ups

How do you model a blog with comments?
Embed a bounded recent subset of comments for quick display and store all comments in a separate collection referenced by post id for scale.
How do you do a join in MongoDB?
$lookup in an aggregation, or Mongoose populate; better to design documents to avoid frequent joins.
What does w: "majority" ensure?
The write is acknowledged after a majority of replica set members have it, so it survives a primary failover.
How do you check why a query is slow?
Run explain('executionStats'), check for collection scans and high documents-examined ratio, and add or adjust a compound index.

Caching and Redis

“What is Redis and what do you use it for? Explain cache-aside, write-through and write-behind, TTLs, eviction, cache invalidation, sessions, rate limiting, pub/sub and distributed locks.”

Say this first (30 seconds)

“Redis is an in-memory data structure store used as a cache, session store, rate limiter, message broker and queue backend. It offers strings, hashes, lists, sets, sorted sets, streams and more, with sub-millisecond reads. The most common pattern is cache-aside: the application checks the cache, on a miss reads the database, then stores the result with a TTL; on writes it updates the database and deletes or updates the cached entry. The hard parts are invalidation, stampedes on expiry, and consistency. I choose TTLs by how stale data may be, set a memory limit and an eviction policy such as LRU, and treat the cache as disposable: the system must still work, more slowly, if Redis is empty or down.”

Details interviewers probe

  • Data structures: strings (with INCR, SETEX), hashes, lists, sets, sorted sets, bitmaps, HyperLogLog, geospatial, streams (consumer groups), JSON (modules). Commands are atomic because Redis executes them on a single thread; use pipelines and Lua scripts or transactions (MULTI/EXEC) for multi-step atomicity.
  • TTL and eviction: set expiry for cache keys; configure maxmemory and a policy (allkeys-lru for caches, noeviction for data you cannot lose); avoid unbounded key growth; use key naming conventions (app:entity:id).
  • Cache invalidation approaches: TTL expiry (simple, bounded staleness), explicit delete on write (consistent but race-prone), event-driven invalidation (publish on change), key versioning/namespace bump, tags via sets of keys. “There are only two hard things in computer science.”
  • Races and consistency: read-then-write races can leave stale values (a slow reader repopulates after a writer deleted); mitigate with short TTLs, delete-after-write plus delayed double delete, or version checks. Accept bounded staleness explicitly.
  • Cache stampede (thundering herd): many requests rebuild an expired hot key; use request coalescing, a short lock (SET lock NX PX), stale-while-revalidate in the application, TTL jitter, and pre-warming (F7).
  • Cache penetration and negative caching: repeated requests for non-existent keys hit the database; cache “not found” briefly, validate inputs, or use Bloom filters.
  • Sessions in Redis: shared across instances, TTL equals session timeout; secure the instance and consider persistence if logging everyone out on restart is unacceptable (D4).
  • Rate limiting: fixed window (INCR with expiry), sliding window (sorted set of timestamps), token bucket (Lua script); keyed by IP, user or API key; return 429 (D3, D4).
  • Distributed locks: SET key value NX PX ttl with a unique token and a safe release script; leases can expire mid-work (use fencing tokens); Redlock across nodes is debated; prefer database constraints or queues for correctness-critical mutual exclusion.
  • Pub/Sub versus Streams: Pub/Sub is fire-and-forget (messages lost if no subscriber); Streams persist with consumer groups and acknowledgements for reliable processing.
  • High availability: replication (async), Sentinel for failover, Cluster for sharding by hash slots; managed services (ElastiCache, Upstash, Redis Cloud); persistence settings trade durability for speed; lost writes are possible on failover.
  • Client-side and HTTP caching: Redis caches server-side; combine with CDN and HTTP caching (P3) and client caches (E4) in layers.
  • Other caches: in-process memory (LRU, per instance, fastest, inconsistent across instances), Memcached (simple key-value, multi-threaded), CDN edge caches, database query caches.
  • Node usage: ioredis or the official redis client with connection reuse, timeouts and error handlers; handle disconnects (fail open for caches, fail closed for rate limiters and locks as appropriate); serialise JSON carefully and compress large values.
  • What not to do: store large blobs or unbounded lists, use KEYS * in production (use SCAN), treat Redis as the only copy of important data, or cache user-specific data under shared keys.

Traps

  • Caching without a strategy for invalidation and then serving stale data indefinitely.
  • Same TTL on many keys causing synchronised expiry and a stampede.
  • Using KEYS or large O(N) commands on a busy instance.
  • Relying on a distributed lock for money-critical correctness.
  • Letting the application fail hard when Redis is unavailable for a pure cache.

Likely follow-ups

Cache-aside versus write-through?
Cache-aside lets the app populate on demand and is simple; write-through updates cache on every write for fresher data at higher write cost.
How do you prevent a stampede?
Coalesce concurrent rebuilds with a lock, serve stale while refreshing, and jitter TTLs.
How would you implement rate limiting with Redis?
A per-key counter with expiry (fixed window) or a sorted set of timestamps (sliding window), checked atomically with a Lua script.
Redis persistence options?
RDB snapshots (compact, can lose recent writes) and AOF logging (more durable, larger); both can be combined.

Background jobs and messaging

“When do you use queues and background jobs? Explain producers and consumers, retries, idempotency, dead-letter queues, scheduling, event-driven architecture and the differences between RabbitMQ, SQS and Kafka.”

Say this first (30 seconds)

“A queue decouples work from the request: the API accepts a request, puts a message on a queue and responds immediately, while workers process it asynchronously. I use this for slow or unreliable tasks such as sending email, image processing, report generation, webhooks and integrations. Reliability depends on at-least-once delivery, so consumers must be idempotent; failed jobs are retried with backoff, and permanently failing ones go to a dead-letter queue for inspection. For simple Node jobs I use BullMQ on Redis; for cloud messaging, SQS or RabbitMQ; and for high-throughput event streaming and replay, Kafka. Event-driven designs publish facts that other services react to, which reduces coupling but adds complexity in ordering, duplicates and observability.”

Details interviewers probe

  • When to go asynchronous: work slower than a request should wait (over a second), needs retries (third-party APIs), is bursty (spikes), is scheduled, or must not block the user (emails, exports, thumbnails, notifications, webhook delivery, AI processing). Keep synchronous what the user needs immediately.
  • Delivery semantics: at-most-once (may lose), at-least-once (may duplicate; the common default), exactly-once (achieved effectively through idempotent processing and transactional outbox, rarely true end to end). Design consumers to tolerate duplicates and out-of-order messages.
  • Idempotency techniques: deduplicate by message id in a table with a unique constraint, make operations naturally idempotent (set rather than increment), use idempotency keys to external APIs, and record processed ids with a TTL.
  • Retries and failure handling: exponential backoff with jitter, max attempts, distinguishing retryable (timeouts, 5xx) from permanent errors (validation), poison messages moved to a dead-letter queue, alerts on DLQ depth, and tooling to inspect and replay.
  • BullMQ in Node: queues, workers, delayed and repeatable jobs (cron), priorities, concurrency, rate limiting, job events, flows (dependencies), UI dashboards (Bull Board); requires Redis persistence considerations. Alternatives: Agenda (Mongo), pg-boss/Graphile Worker (Postgres-based queues), cloud schedulers.
  • Scheduling: cron in a single place (one scheduler, not one per instance), distributed locks or queue repeatable jobs to prevent duplicate runs; cloud schedulers (EventBridge, Cloud Scheduler); time zones and daylight-saving handling.
  • Event-driven architecture: services publish domain events (OrderPlaced) and others subscribe; benefits: loose coupling, scalability, extensibility; challenges: eventual consistency, debugging flows, schema evolution (versioned events, schema registry), ordering, and duplicate handling. Distinguish events (facts) from commands (requests).
  • Patterns: outbox (reliable publishing), saga (distributed transactions with compensation), CQRS (separate read and write models), event sourcing (state as a log of events), competing consumers, fan-out, and claim-check (store large payloads externally).
  • Webhooks and real-time to the frontend: a worker finishes and notifies the client through WebSocket, SSE or polling a job-status endpoint; update caches (E4, P4).
  • Streams in Node: large data processing through Node streams or Kafka consumers with backpressure; keep consumers light, batch where possible.
  • Observability: metrics (queue depth, age of oldest message, processing time, failure rate), tracing across async boundaries (propagate trace ids in message headers), structured logs with job ids, and alerting on lag.
  • Capacity and ordering: scale workers horizontally by queue depth; partitions or message groups preserve per-entity order; avoid global ordering requirements.
  • Frontend relevance: understand job status UX (pending, running, done, failed), idempotent client retries, and how eventual consistency affects what a user sees after submitting.

Traps

  • Assuming messages are delivered exactly once, then double-charging or double-emailing.
  • Infinite retries on a poison message that blocks or floods the queue.
  • Publishing an event after the DB commit without an outbox, losing events on crash.
  • Running a cron job on every instance, executing it several times.
  • No monitoring of queue depth or dead-letter queues.

Likely follow-ups

How do you make a job idempotent?
Use a unique job or business key and check or record processing atomically, or design the operation so repeating it has the same effect.
What is the outbox pattern?
Insert the event into an outbox table in the same transaction as the data change; a relay publishes it to the broker, giving reliable delivery.
Kafka versus RabbitMQ?
Kafka is a replayable partitioned log for streaming at scale; RabbitMQ is a flexible message broker for routing and task distribution where messages are consumed and removed.
How do you give the user progress for a long job?
Return 202 with a job id; the client polls a status endpoint or listens over SSE/WebSocket for updates.

Testing, logging and observability

“How do you test a Node API? Unit, integration and contract tests. How do you do logging, metrics and tracing? What is a health check? What are the twelve-factor principles?”

Say this first (30 seconds)

“I test an API in layers: fast unit tests for business logic, integration tests that run the real app against a real database in a container with a library like supertest, contract tests to protect consumers, and a few end-to-end tests. For observability I use structured JSON logs with request ids, metrics for rate, errors and latency, and distributed traces with OpenTelemetry, so I can follow a request across services. Health endpoints let orchestrators route traffic and restart unhealthy instances. I follow twelve-factor ideas: config in the environment, stateless processes, logs to stdout, disposable processes with graceful shutdown, and parity between environments. The goal is to detect problems before users do and diagnose them quickly.”

Details interviewers probe

  • Unit tests: isolate business rules from HTTP and DB; inject dependencies (repositories, clock, mailer) so they can be faked; keep tests deterministic; use property-based tests for tricky logic. Avoid mocking everything: mocks that mirror implementation tests nothing.
  • Integration tests: start the real app (export app, not listen) and call it with supertest; use a real database via Docker/Testcontainers and migrations; seed minimal data; test auth, validation, transactions, pagination and error responses; run in CI in parallel with isolated schemas or databases.
  • Contract and API tests: validate responses against the OpenAPI spec; consumer-driven contracts (Pact) catch breaking changes between frontend and backend; schema registries for events; run provider verification in CI.
  • Load and resilience testing: k6/Artillery for throughput and latency under load, soak tests for leaks, chaos experiments for dependency failure; set performance budgets (p95 latency) and test them before big releases.
  • Structured logging: JSON logs with level, timestamp, message, request id, user id (not PII), route, duration, and error stack; pino (fast) or winston; log to stdout and let the platform ship them; levels used consistently; never log secrets or full personal data; sample noisy logs.
  • Request context: generate or accept a correlation id (x-request-id), store it in AsyncLocalStorage, include it in every log line and downstream call, and return it in responses and error bodies for support.
  • Metrics: expose Prometheus metrics (prom-client) or push to Datadog/CloudWatch; RED (rate, errors, duration) for services, USE (utilisation, saturation, errors) for resources; also Node-specific: event-loop lag, heap usage, GC pauses, active handles, DB pool usage. Use histograms for latency percentiles (p50, p95, p99).
  • Tracing: OpenTelemetry SDK with auto-instrumentation for http, express, pg, mongodb, redis; export to Jaeger, Tempo, Datadog; propagate traceparent headers across services and message queues; link frontend RUM traces to backend traces.
  • Alerting and SLOs: alert on symptoms (error rate, latency, saturation) rather than causes; define SLIs/SLOs and error budgets; page only for actionable alerts; dashboards per service; runbooks linked from alerts (DevOps guide).
  • Error tracking: Sentry or similar with release tags and source maps; group errors; track unhandled rejections; sample to control cost.
  • Health checks: liveness (restart if failing: do not check dependencies), readiness (remove from load balancer when dependencies are down or draining), startup probes for slow boots; keep them cheap.
  • Configuration and twelve-factor: validate environment variables at startup, separate config from code, backing services as URLs, stateless processes (no local session state or files), disposability (fast start, graceful shutdown), dev/prod parity, admin tasks as one-off processes.
  • Graceful shutdown and robustness: handle SIGTERM, stop accepting new connections, finish requests, close pools; timeouts on all outbound calls; circuit breakers (opossum) and retries with backoff for dependencies; bulkheads to isolate failures.
  • Debugging in production: trace and log correlation, feature flags for safe rollout, canary releases, heap snapshots and CPU profiles on demand, and feature toggles for kill switches.

Traps

  • Integration tests against a mocked database that hides real SQL or driver behaviour.
  • Logging unstructured text or sensitive data.
  • Liveness probes that check the database, causing restarts during a database outage.
  • Alerting on every error instead of user-impacting symptoms.
  • Tests that depend on shared state or ordering.

Likely follow-ups

What do you put in a readiness check?
Quick checks of critical dependencies (database ping, cache) and startup completion, so traffic is only sent when the instance can serve it.
How do you trace a request across services?
Propagate W3C traceparent headers and instrument each service with OpenTelemetry; view the combined trace in a backend.
What is a good logging strategy?
Structured JSON with consistent fields and correlation ids, appropriate levels, no secrets, shipped centrally and searchable.
How do you test an endpoint that calls a third-party API?
Stub it at the HTTP level (nock/MSW), test success, failure and timeout paths, and run occasional contract checks against a sandbox.

Scaling and hardening a Node service

“How do you scale a Node API? Horizontal scaling, load balancing, statelessness, connection pooling, clustering, profiling and memory leaks, backpressure, graceful degradation. How do you harden it for production?”

Say this first (30 seconds)

“I scale Node horizontally: stateless instances behind a load balancer, one process per core via containers or a process manager, with sessions, files and jobs moved out to Redis, object storage and queues. Before scaling out I find the actual bottleneck with profiling and metrics: it is usually the database, so I add indexes, connection pooling, caching and read replicas, and I keep the event loop free of CPU work. I protect the service with timeouts, rate limits, circuit breakers, bulkheads and backpressure so a slow dependency does not take everything down. For production hardening: security headers and input validation, least-privilege credentials, dependency scanning, graceful shutdown, health checks, structured logs and alerts, and a rollback plan.”

Details interviewers probe

  • Statelessness: no in-memory sessions, uploaded files on local disk, or per-instance caches that must be consistent; use Redis, object storage, and a database. This allows adding or removing instances freely.
  • Using all cores: cluster module, PM2, or (preferably) one container per core under an orchestrator (Kubernetes, ECS) with autoscaling on CPU, memory, or request rate; set CPU and memory limits and tune --max-old-space-size to container memory.
  • Load balancing: round robin, least connections; health checks remove unhealthy instances; connection draining on deploy; sticky sessions only when unavoidable (WebSockets with in-memory state); keep-alive tuning between balancer and Node (keepAliveTimeout longer than the balancer’s idle timeout to avoid resets).
  • Database scaling: connection pooling (pool size sensible; PgBouncer for many instances), indexes and query tuning, read replicas for read-heavy workloads (replication lag), caching, partitioning, archiving, then sharding as a last resort.
  • Profiling and finding bottlenecks: CPU profiles and flame graphs (--cpu-prof, clinic.js, 0x), event-loop delay metrics, heap snapshots for leaks, APM traces for slow spans, database slow query logs; load test with realistic data.
  • Memory leaks in Node: growing heap from unbounded caches, listeners never removed, global maps, closures holding request objects, unclosed streams or timers; symptoms: climbing RSS, GC pressure, OOM kills; diagnose with heap snapshots and comparison; mitigate with bounded LRU caches and restart policies as a safety net, not a fix (J24, J25).
  • Concurrency limits and backpressure: limit concurrent outbound calls and DB queries; use bounded queues; reject quickly with 429/503 when overloaded rather than building unbounded backlogs; stream large responses.
  • Request handling limits: body size limits, timeouts (server.requestTimeout, headers timeout), maximum connections, slowloris protection at the proxy, upload limits and streaming to storage.
  • Security hardening checklist: helmet, CORS allowlist, validation and sanitisation, parameterised queries, rate limiting, secrets in a manager, non-root container user, minimal base image, read-only filesystem where possible, dependency and image scanning, HTTPS termination, WAF, audit logging, regular patching of Node (LTS) and packages (P10, P11).
  • Deployment safety: rolling or canary deployments with health checks, database migrations compatible with old and new versions, feature flags, quick rollback, and connection draining so in-flight requests finish (A6).
  • Cost and efficiency: right-size instances, cache aggressively, offload static files to CDN, use serverless for spiky workloads (cold starts, connection limits, 15-minute caps), and measure cost per request.
  • Serverless Node considerations: stateless by design; reuse connections across invocations; use a database proxy/pooler; mind cold starts and bundle size; limits on execution time and concurrency; local state is ephemeral.
  • Capacity planning: derive from load tests and traffic patterns: peak requests per second, per-request CPU and DB cost, headroom (target around 60 to 70% utilisation), and autoscaling policies with sensible cooldowns.
  • Failure modes to rehearse: database failover, Redis outage, dependency slowdown, traffic spike, bad deploy, certificate expiry; document runbooks and test them (game days).

Traps

  • Scaling out Node instances when the database is the bottleneck.
  • Pool size times instance count exceeding the database’s connection limit.
  • No timeouts on outbound calls, so one slow dependency exhausts all workers.
  • Relying on restarts to hide a memory leak.
  • Sticky sessions and local state that prevent autoscaling or rolling deploys.

Likely follow-ups

How would you scale an API from 100 to 10,000 requests per second?
Profile first; add caching and indexes, pool connections, make it stateless and scale horizontally behind a load balancer, move slow work to queues, add read replicas, and test with load profiles.
What is a circuit breaker?
A guard that stops calls to a failing dependency after a threshold, failing fast and probing periodically for recovery.
How do you handle a traffic spike you cannot absorb?
Shed load gracefully with rate limits and 503/429 responses, serve cached or degraded content, and scale or queue the rest.
Why must keepAliveTimeout exceed the load balancer’s idle timeout?
Otherwise Node may close a connection just as the balancer reuses it, causing intermittent 502 errors.

How to answer backend questions as a frontend lead

  • Show working depth and good judgement rather than trying to be a DBA: state the access pattern, the consistency requirement and the trade-off, then recommend.
  • Connect backend choices to frontend consequences: pagination style, error shapes, eventual consistency in the UI, auth cookies versus tokens, long-job status UX.
  • Lead with defaults and reasons: PostgreSQL as the system of record, Redis for caching, queues for slow work, stateless services behind a load balancer.
  • Name failure modes (duplicates, stampedes, retries, slow dependencies) and the pattern that handles each.
  • Be explicit about security: authorisation at the data layer, parameterised queries, least privilege, never trusting client input.
  • The interview is theoretical: expect “explain”, “compare”, “how would you design” and “what are the trade-offs”, not live coding.
