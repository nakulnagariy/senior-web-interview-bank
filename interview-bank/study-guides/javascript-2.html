The event loop, tasks and microtasks

“JavaScript is single-threaded. How does it handle asynchronous work? Explain the call stack, the task queue, the microtask queue and the event loop. Where do rendering and requestAnimationFrame fit?”

Say this first (30 seconds)

“JavaScript runs your code on one thread, with one call stack. Asynchronous work such as timers, network and user events is handled by the host environment, the browser or Node, outside that thread. When it finishes, the host queues a callback. The event loop repeats one cycle: take one task from a task queue and run it to completion, then drain the entire microtask queue, which holds promise reactions and await continuations, then, if a frame is due, render: run requestAnimationFrame callbacks, style, layout and paint. Because a task runs to completion, a long task blocks rendering and input. And because microtasks run before the next task or render, an endless chain of microtasks can starve the page.”

Details interviewers probe

  • Who does the waiting? The JavaScript engine (V8) has only the stack and heap. Timers, network, storage and DOM events are provided by the host (Web APIs in a browser, libuv in Node), which run in other threads or the OS and post a callback back to the event loop.
  • Task versus microtask: a task is a unit of work scheduled by the host (timer, event, message, I/O). A microtask is a short follow-up scheduled by the language itself, run as soon as the stack is empty, before the next task. Promise reactions, await continuations, queueMicrotask and MutationObserver callbacks are microtasks.
  • Why promises beat setTimeout(fn, 0) for “run this soon”: the microtask runs before rendering and before any other task, so state is consistent. setTimeout yields to the browser, so rendering and input can happen first, and it has a minimum delay (J22).
  • Rendering is not a task, it is a step: the browser decides at the end of a loop turn whether a frame is due (display refresh, visibility). It may skip rendering for several turns. requestAnimationFrame callbacks run just before style and layout in that step, which is the right place for visual updates, so they happen once per frame.
  • Layout thrashing: reading layout (offsetHeight) after writing styles forces a synchronous layout inside your task. Batch reads, then writes; or write in requestAnimationFrame.
  • Yielding to keep the page responsive: split long work into chunks and give the loop a turn between chunks with setTimeout, MessageChannel, or scheduler.yield() verify support. React’s scheduler uses the same idea for time slicing.
  • await in terms of the loop: the code after await becomes a microtask continuation once the awaited promise settles. The function returns to its caller at the first await.
  • Order guarantees: synchronous code first; then microtasks in the order queued; then the next task. Between two setTimeout calls with equal delay, the first queued runs first.
  • Node specifics: process.nextTick has its own queue that runs before promise microtasks, and recursive nextTick can starve I/O. setImmediate runs in the check phase, after the poll phase.

Traps

  • Saying “JavaScript is asynchronous”. The language is single-threaded and synchronous; the environment provides asynchrony.
  • Saying “setTimeout(0) runs immediately”. It queues a task after the current one and after all microtasks, and browsers clamp nested timers to at least 4 ms.
  • Describing only “callback queue” and “microtask queue” and forgetting the rendering step, which is where most real-world jank questions go.
  • Claiming async code runs in parallel. Callbacks never run at the same time as your other JavaScript; only workers give real parallelism (J23).

Likely follow-ups

Why can a long loop freeze the UI?
The task runs to completion on the same thread that renders and handles input. Nothing can interrupt it.
How do you process a million items without freezing the page?
Chunk the work and yield between chunks, move it to a Web Worker, or use virtualisation so you never process everything.
What is a microtask starvation?
Microtasks that keep scheduling more microtasks keep the drain loop busy, so rendering and other tasks never run.
Where do MessageChannel and postMessage fit?
They queue a task with no 4 ms clamp, which is why schedulers use them to yield quickly.
How does this relate to Core Web Vitals?
Long tasks delay input handling and hurt INP. Keeping tasks under 50 ms is the practical target.

Promises

“What is a promise? Explain its states, chaining, and error propagation. What is the difference between Promise.all, allSettled, race and any? Why were promises introduced?”

Say this first (30 seconds)

“A promise is an object representing the eventual result of an asynchronous operation. It starts pending and settles exactly once, either fulfilled with a value or rejected with a reason, and a settled promise never changes. You attach handlers with then, catch and finally; each returns a new promise, which is what makes chaining work, and handlers always run asynchronously as microtasks. A rejection skips then handlers until a catch handles it. Promises fixed callback hell and inconsistent error handling, and gave a composable value for combinators: all waits for everything and fails fast, allSettled waits and reports each outcome, race takes the first to settle, and any takes the first to fulfil.”

Details interviewers probe

  • Why promises: callbacks invert control (you hand your continuation to someone else, who may call it twice, late or never), nest into pyramids, and make errors manual. A promise is a first-class value: composable, always asynchronous, settled once.
  • The executor runs synchronously: new Promise((resolve, reject) => …) runs the function immediately; only the handlers are async. Throwing inside the executor rejects the promise.
  • Chaining rules: whatever a handler returns becomes the next promise’s value; returning a promise (or any “thenable”) makes the chain wait for it; throwing becomes a rejection; returning nothing passes undefined. Forgetting to return inside a then is the most common chaining bug: the chain does not wait.
  • catch and recovery: catch(fn) is then(undefined, fn). If the handler returns normally, the chain continues fulfilled. finally runs on both outcomes, receives no argument and passes the original value or reason through (unless it throws).
  • Promise.resolve(x): wraps a plain value, or returns x itself if it is already a native promise. Resolving with another promise adopts its state, which costs extra microtask ticks.
  • Unhandled rejections: a rejection with no handler fires unhandledrejection on window (browser) or terminates the process by default in Node 15 and later. Always end a chain with catch or handle it in await with try/catch.
  • Combinator choice: all for “need everything”, allSettled for dashboards and batch jobs, race for timeouts, any for redundancy. None of them cancel the losers; the other requests keep running unless you use an AbortController (J22).
  • Newer helpers: Promise.withResolvers() (ES2024) returns { promise, resolve, reject } verify; Promise.try() (ES2025) starts a chain from a function that may throw or return synchronously verify.
  • Promises are eager and not cancellable: creating one starts the work. Cancellation is a separate concern, handled with AbortSignal.
  • Promisifying callbacks: wrap in new Promise and call resolve or reject in the callback; in Node use util.promisify.

Traps

  • Nesting then inside then (“promise hell”) instead of returning and flattening.
  • Forgetting return, so the next then runs before the inner work is done.
  • Putting catch in the middle of a chain and then continuing as if the step succeeded (it did, as far as later handlers can tell).
  • Calling Promise.all on a list where one failure should not discard the other results.
  • Believing race cancels the slower promises. It does not.

Likely follow-ups

What is a thenable?
Any object with a then method. Promise resolution assimilates it, which is how libraries interoperate.
How would you add a timeout to a request?
Promise.race against a timer, or better AbortSignal.timeout(ms) passed to fetch, which actually cancels the request.
How would you limit concurrency to five requests at a time?
Keep a pool of five workers that each pull the next item from a shared queue, or use a library such as p-limit. Explain the idea; do not rebuild it from memory.
Promise versus Observable?
A promise is one value, eager and not cancellable. An observable is a stream of values over time, lazy and cancellable by unsubscribing (RxJS, common in Angular).

async / await

“How does async/await work under the hood? How do you run requests in parallel? How do you handle errors? What are the common pitfalls, for example in loops?”

Say this first (30 seconds)

“async/await is syntax over promises. An async function always returns a promise. await pauses that function, not the thread, until the awaited promise settles, and the rest of the function resumes as a microtask. The caller gets control back at the first await. It makes asynchronous code read like synchronous code and lets me use try/catch for rejections. The main pitfall is accidental serialisation: awaiting independent requests one after another is slow, so I start them together and await Promise.all. Others are using await inside forEach, which does not wait, and forgetting that an unawaited promise can fail silently.”

Details interviewers probe

  • Mechanism: an async function is a state machine, similar to a generator driven by promises. Each await x wraps x with Promise.resolve, subscribes a continuation and returns. Modern V8 needs only one microtask tick to resume after awaiting a native promise.
  • Return values: returning a value resolves the promise with it; throwing rejects it. return await p versus return p: inside try/catch you need the await for the catch to see the rejection; elsewhere it is redundant.
  • Error handling: wrap in try/catch/finally, or call .catch on the returned promise. Wrap only what can fail and keep the try block small so unrelated bugs are not swallowed. Handle errors at a boundary that can do something useful (retry, show message, report).
  • Loops: for…of with await runs items one at a time (correct when order matters or you must limit load). array.forEach(async …) fires everything and does not wait; map(async …) returns promises you can pass to Promise.all. For controlled concurrency use a pool or a library.
  • Fire and forget: calling an async function without await or catch loses its errors (they become unhandled rejections). Lint rule: no-floating-promises.
  • for await…of: consumes async iterables, such as streams, paginated APIs and async generators. Each iteration awaits the next value.
  • Top-level await: allowed in ES modules (ES2022). It makes the module’s evaluation asynchronous, so importers wait for it; it can delay startup, so avoid it on the critical path.
  • Async in non-obvious places: constructors cannot be async (use a static factory), useEffect callbacks must not be async (declare an inner async function), array callbacks like sort cannot await.
  • Race conditions: a slower earlier request can overwrite a newer result (typeahead, route changes). Fix with an abort signal, a request id or a “latest only” guard, which is what TanStack Query and useEffect cleanup patterns do.
  • Retry and backoff: wrap an operation, retry only idempotent calls, use exponential backoff with jitter, cap attempts, and respect AbortSignal.

Traps

  • “await blocks the thread.” It suspends only the function; the event loop keeps running.
  • Awaiting independent calls in sequence, then claiming “async is slow”.
  • Using forEach with await and assuming the code after it runs afterwards.
  • A try/catch around a call that is not awaited: the rejection escapes it.
  • Making a function async just so it returns a promise, hiding that it is synchronous and adding an extra tick.

Likely follow-ups

Is async/await faster than promises?
No. It is syntax; performance is about the same. The benefit is readability and error handling.
How do you run tasks in parallel but limit concurrency?
A fixed set of worker loops that each take the next job from a shared iterator, or a library. Promise.all alone starts everything at once.
What happens to an error in an un-awaited promise?
It becomes an unhandled rejection: an event in the browser, a crash by default in Node.
Async generators?
async function* yields values asynchronously; consume with for await. Good for pagination and streaming.

Error handling

“How do you handle errors in JavaScript? Synchronous versus asynchronous errors, custom errors, global handlers, and how would you design error handling for a production frontend?”

Say this first (30 seconds)

“Errors are objects, normally instances of Error, thrown with throw and caught with try/catch/finally. Synchronous throws use try/catch; promise rejections use catch or try/catch around await. I create custom error classes that extend Error, set a name and a code, and use the cause option to keep the original error. For anything that escapes, there are global handlers: window.onerror and unhandledrejection in the browser. In a production app I add layers: validation near the source, typed errors, a boundary that shows a fallback, such as a React error boundary, and reporting to a service like Sentry with source maps. I do not swallow errors silently.”

Details interviewers probe

  • Built-in types: Error, TypeError (wrong type, calling undefined), ReferenceError (undeclared name or TDZ), SyntaxError, RangeError (out-of-range value, stack overflow), URIError, EvalError, AggregateError (from Promise.any).
  • try / catch / finally: finally always runs, even after return or throw, and a return in finally overrides the earlier one. The catch binding is optional (catch { }).
  • Throw Error objects, not strings: only Error carries a stack trace. Anything can be thrown, so in TypeScript catch (e) is unknown and you must narrow it.
  • Custom errors: class ApiError extends Error { constructor(msg, { status, cause }) { super(msg, { cause }); this.name = 'ApiError'; this.status = status; } }. They let callers branch with instanceof or a code field. Preserve the original with cause (ES2022), and avoid relying on message strings.
  • fetch does not reject on HTTP errors: it rejects only on network failure. Check response.ok and throw. Parsing JSON can also fail.
  • Global handlers: window.addEventListener('error', …) for uncaught sync errors (and resource load failures in capture phase); 'unhandledrejection' for promise rejections. Node: process.on('uncaughtException') and 'unhandledRejection'; treat them as “log and exit”, not “continue”.
  • React: error boundaries (class components, or react-error-boundary) catch errors in rendering, lifecycle and constructors of descendants. They do not catch event handlers, async code, SSR or errors in the boundary itself. In Next.js use error.js and global-error.js.
  • Operational errors versus programmer errors: expected failures (network, validation, 404) are handled and shown to the user; bugs (TypeError from undefined) should be reported and fixed. Do not catch bugs just to hide them.
  • Result / either style: return { ok, value | error } for expected failures instead of throwing; common in TypeScript for validation and parsing.
  • Production practice: user-friendly message plus a retry; no stack traces shown to users; structured logging; release tagging and source maps for readable stacks; alert on error rate; sanitise personal data before reporting.

Traps

  • Empty catch blocks. If you must ignore an error, say why in a comment.
  • Catching an error, logging it and returning undefined, so the caller continues with bad data.
  • Rethrowing a new error without cause, which loses the original stack.
  • Expecting try/catch to catch errors inside setTimeout or un-awaited promises.
  • Assuming an error boundary covers everything.

Likely follow-ups

Why do cross-origin script errors show as “Script error.”?
The browser hides details for scripts from another origin unless they are served with CORS and loaded with crossorigin.
How do you make minified stack traces readable?
Upload source maps to the error service at build time, keep them off the public site or restrict access, and tag each release.
Retry or fail?
Retry transient, idempotent failures with backoff and a cap; fail fast on validation or auth errors.
How do you test error paths?
Assert on error types and codes, mock failing dependencies, and test that the boundary renders a fallback.

Timers, scheduling, debounce, throttle and cancellation

“Explain setTimeout, setInterval and requestAnimationFrame. What is the difference between debounce and throttle, and when do you use each? How do you cancel an in-flight request?”

Say this first (30 seconds)

“setTimeout schedules a task after at least the delay, not exactly after it, because the loop must be free. setInterval repeats and can drift or stack up if the callback is slow, so I prefer a self-rescheduling timeout for work with variable length. requestAnimationFrame runs before the next paint and is the right tool for visual updates. Debounce waits until events stop for a given time and then fires once, which suits search-as-you-type and resize-end. Throttle lets a function run at most once per interval, which suits scroll, mousemove and drag. To cancel a request I use an AbortController and pass its signal to fetch; aborting rejects with an AbortError, which I ignore.”

Details interviewers probe

  • Timer guarantees: the delay is a minimum. A busy main thread, nested timers (clamped to at least 4 ms after five levels) and background tabs (throttled to about once per second, more aggressively when the tab is hidden for long) all delay callbacks. Never use timers for accurate timekeeping; compare Date.now() or performance.now().
  • setInterval issues: if the callback takes longer than the interval, runs queue up back to back and drift accumulates. A recursive setTimeout that schedules the next run after finishing keeps a stable gap. Always store the id and clear it (clearInterval) on cleanup, such as in a React effect.
  • requestAnimationFrame: runs once per frame, paused in background tabs, so it saves battery and avoids useless work. Use it for animations and for batching DOM writes. Pass the timestamp it gives you to compute progress instead of counting frames. It is not for non-visual work.
  • requestIdleCallback: runs low-priority work when the main thread is idle, with an optional timeout. Not available in Safari verify; polyfill with a timeout. scheduler.postTask() and scheduler.yield() give prioritised scheduling in Chromium verify.
  • Debounce implementation idea (explain, do not code): keep a timer id in a closure; on each call clear it and set a new one; when it finally fires, call the function with the latest arguments. Options: leading versus trailing edge, cancel() and flush().
  • Throttle implementation idea: remember the last run time or a “waiting” flag; ignore calls until the interval passes; optionally run once more at the end (trailing).
  • In React: create the debounced function once (useMemo/useRef) or debounce the value with a hook; a debounced function recreated on every render never debounces. Clean up on unmount. useDeferredValue and transitions are alternatives for rendering cost.
  • Prefer CSS or passive listeners where possible: { passive: true } scroll listeners, IntersectionObserver instead of scroll polling, CSS scroll-snap and position: sticky.
  • Cancellation: const ctrl = new AbortController(); fetch(url, { signal: ctrl.signal }); ctrl.abort(); The promise rejects with DOMException named AbortError. AbortSignal.timeout(ms) aborts after a delay; AbortSignal.any([a, b]) combines signals verify. Signals also work with addEventListener ({ signal } removes the listener on abort) and in many Node APIs.
  • Aborting does not undo server work: the request may already have been processed. Mutations need idempotency keys.
  • Promises themselves cannot be cancelled; design your own APIs to accept an AbortSignal and check signal.aborted or listen to its abort event.

Traps

  • Mixing up debounce and throttle, or saying “throttle ignores the last event” without mentioning trailing calls.
  • Debouncing a handler inside a component body so a new debounced function is created each render.
  • Forgetting to clear timers and abort requests on unmount, causing updates on unmounted components and leaks.
  • Treating an AbortError as a real failure and showing an error toast.
  • Relying on setInterval for a clock or countdown instead of computing from real time.

Likely follow-ups

How do you avoid showing results from an older request?
Abort the previous request when a new one starts, or tag requests with an id and ignore stale responses. Libraries such as TanStack Query handle this.
requestAnimationFrame versus setTimeout(…, 16)?
rAF is synchronised with the display, paused when hidden and passes a precise timestamp; the timer is not synchronised and drifts.
When would you choose requestIdleCallback?
Analytics beacons, prefetching, non-urgent caching: work that must not compete with input and rendering.
Debounce delay choice?
Around 200 to 300 ms for typing; shorter for resize; measure with real users. Always show immediate feedback so the UI never feels dead.

Workers and concurrency

“JavaScript is single-threaded. How do you do CPU-heavy work without blocking the UI? What are Web Workers, Service Workers and SharedArrayBuffer? What are the trade-offs?”

Say this first (30 seconds)

“Each JavaScript thread has its own event loop, heap and stack, so the main thread can be blocked by heavy computation. A Web Worker runs a script on a separate thread with no access to the DOM, and communicates by postMessage, which copies data with the structured clone algorithm, or transfers ownership of buffers without copying. SharedArrayBuffer with Atomics lets threads share memory, but needs cross-origin isolation headers. A Service Worker is a different thing: an event-driven proxy between the page and the network, used for offline support, caching and push. I use workers for parsing, image processing, crypto and large data transforms, and avoid them for small tasks, because startup and message copying have a cost.”

Details interviewers probe

  • Why workers, not async: async only helps with waiting (I/O). CPU-bound work still occupies the thread. A worker moves that computation off the main thread.
  • Communication: messages are copied with structured clone, which supports most data types (objects, arrays, Map, Set, Date, typed arrays) but not functions or DOM nodes. Large payloads are expensive; use transferable objects (ArrayBuffer, MessagePort, ImageBitmap, OffscreenCanvas) to move them without copying.
  • Ergonomics: raw postMessage is event-based. Libraries such as Comlink wrap a worker as an async RPC object. Module workers (new Worker(url, { type: 'module' })) support import. Bundlers (Vite, webpack 5) handle worker URLs.
  • Costs: thread startup (tens of milliseconds), memory per worker, message copying, and debugging complexity. Reuse a pool of workers; do not spawn one per task. Limit to navigator.hardwareConcurrency or fewer.
  • Good use cases: parsing big JSON or CSV, search indexing, image and video processing, compression and crypto, syntax highlighting or Markdown rendering, running WebAssembly, offscreen canvas rendering, heavy diffing.
  • SharedArrayBuffer and Atomics: shared memory plus atomic operations (add, compareExchange, wait, notify) to avoid data races. It needs a cross-origin isolated page (Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp), a requirement introduced after Spectre. Use only when copying is the bottleneck.
  • Service Worker: runs in its own thread with a lifecycle (install, activate, fetch), intercepts network requests for the pages it controls, needs HTTPS, and is terminated when idle, so it must not keep state in memory. Caching strategies: cache-first, network-first, stale-while-revalidate. Details in the PWA guide.
  • Alternatives to a worker: chunk and yield (J18), move work to the server, virtualise lists, use requestIdleCallback, use CSS or the GPU, or avoid doing the work at all (memoise, paginate).
  • Node.js: worker_threads for CPU work, cluster or multiple processes for scaling across cores, and the libuv thread pool for file system and DNS. I/O-heavy servers need no workers.
  • Concurrency versus parallelism: concurrency is interleaving tasks (event loop); parallelism is running at the same instant (workers, processes).

Traps

  • “Web Workers can update the DOM.” They cannot; the result must go back to the main thread.
  • Confusing Service Workers with Web Workers; their purposes and lifecycles differ.
  • Sending huge objects back and forth on every keystroke and making things slower than before.
  • Using workers for I/O-bound work, where fetch is already non-blocking.
  • Reaching for SharedArrayBuffer first. Message passing is safer; shared memory brings race conditions.

Likely follow-ups

How do you terminate a worker?
worker.terminate() from outside, or self.close() from inside. Always do it on component unmount.
Can a worker start another worker?
Yes, in modern browsers (nested workers), but a pool managed from one place is simpler.
What is OffscreenCanvas for?
Rendering canvas or WebGL in a worker so heavy drawing does not block the UI.
How does React’s concurrent rendering relate?
It is still single-threaded: it slices rendering work and yields to the loop so input stays responsive. It is not workers.

Memory management and garbage collection

“How does memory management work in JavaScript? How does garbage collection decide what to free? What is the difference between the stack and the heap, and what are WeakRef and FinalizationRegistry?”

Say this first (30 seconds)

“JavaScript manages memory automatically. Primitives and call frames live on the stack, and objects, arrays and closures live on the heap. The garbage collector frees heap objects that are no longer reachable from the roots: the global object, the current stack and active closures. Modern engines such as V8 use mark-and-sweep, not reference counting, so cycles are collected. V8 is generational: new objects go into a small young generation that is collected often and cheaply, and survivors are promoted to the old generation, collected less often with incremental, concurrent and parallel marking to keep pauses short. I cannot force a collection, so the practical job is to avoid keeping references to things I no longer need.”

Details interviewers probe

  • Lifecycle: allocate (when you create a value), use, release (when it becomes unreachable). You never call free; you only drop references.
  • Stack versus heap: the stack holds call frames, local primitives and references, and is freed when functions return. The heap holds objects, arrays, strings of non-trivial size and closures, and is collected by the GC. (Engines optimise this; treat it as a mental model.)
  • Reachability: an object is alive if a chain of references connects it to a root. Roots include globals, the stack, active timers, registered event listeners and pending promise reactions.
  • Old approach: reference counting frees an object when its count hits zero but cannot free cycles; some old browsers leaked DOM cycles this way. Modern engines use tracing.
  • V8 (Orinoco project) techniques: generational collection, parallel (several threads at once), incremental (small slices between tasks) and concurrent (on a background thread while JavaScript runs) marking, write barriers to track old-to-new references, idle-time GC, and compaction. Pauses are mostly well under a few milliseconds but a large heap can still cause jank.
  • What triggers GC: allocation pressure, not a timer. Creating many short-lived objects in a hot loop (animations, mapping huge arrays on scroll) triggers frequent scavenges and can drop frames.
  • Reduce garbage: reuse objects and arrays in hot paths (object pools), avoid allocating in requestAnimationFrame loops, prefer typed arrays for numeric data, stream or paginate large data instead of loading all of it.
  • Off-heap memory: ArrayBuffer contents, WebAssembly memory, GPU textures and canvases are not in the JS heap; they have their own limits and release rules.
  • WeakMap / WeakSet: hold keys weakly, so an entry does not keep the key alive. Good for per-object metadata and private data (J11).
  • WeakRef and FinalizationRegistry: a WeakRef lets you point to an object without keeping it alive (ref.deref() returns it or undefined). A registry runs a callback after an object is collected. Behaviour is non-deterministic and may never run, so use them only for caches and cleanup of external resources, never for program logic.
  • Manual control: global.gc() exists only with --expose-gc in Node, for testing. In browsers you cannot call it in production code.
  • Limits: V8’s default old-space limit depends on the version and system memory; in Node set it with --max-old-space-size. Mobile browsers kill tabs at much lower memory, so web apps must be careful on low-end devices.

Traps

  • “Setting a variable to null frees memory.” It only drops that reference; the object is freed when nothing reaches it, at the collector’s discretion.
  • “JavaScript uses reference counting.” Modern engines trace reachability.
  • “Garbage collection is a pause that freezes everything for a long time.” Modern V8 mostly does the work incrementally and concurrently.
  • Using FinalizationRegistry for essential cleanup such as closing connections.

Likely follow-ups

Does a closure cause a leak?
Not by itself. A closure keeps its captured variables alive as long as the closure itself is reachable, so a long-lived closure over large data retains that data (J25).
Why are strings and arrays special for memory?
String concatenation can build rope structures, and sparse or holey arrays use different representations. Large arrays of numbers are far smaller as typed arrays.
How do you see memory use?
DevTools Performance monitor and Memory panel (heap snapshots, allocation timeline); in Node process.memoryUsage() and --inspect.
Why might memory not drop after you release data?
The collector has not run yet, something still references it, or the engine keeps freed pages for reuse.

Memory leaks in the browser

“What are common causes of memory leaks in a web app, how do you detect them, and how do you prevent them in a single-page app?”

Say this first (30 seconds)

“A leak is memory that is still reachable but no longer needed, so the garbage collector cannot free it. In single-page apps the usual causes are event listeners and timers that are never removed, subscriptions that are never cancelled, detached DOM nodes still referenced from JavaScript, closures that capture large objects, unbounded caches and accidental globals. I detect them in Chrome DevTools: the Performance monitor shows heap growing in a staircase pattern, and the Memory panel lets me take heap snapshots before and after repeating an action, then compare to see which objects survive and what retains them. I prevent them by always pairing setup with cleanup: in React, return a cleanup function from useEffect; in general, use AbortController signals, weak collections and bounded caches.”

How to investigate (explain this sequence)

  • Confirm: open DevTools, Performance monitor (JS heap size), and repeat the suspect action (open and close a dialog 20 times, navigate between routes). A rising floor means a leak.
  • Three-snapshot technique: take a heap snapshot, do the action, force GC (trash can icon), snapshot again, repeat, then use the “Objects allocated between Snapshot 1 and 2” filter. Objects that appear in every cycle are leaking.
  • Read the snapshot: search for “Detached” DOM nodes, sort by retained size, and follow the Retainers panel up to the root that holds them.
  • Allocation timeline/sampling: shows which function allocates memory that is never released.
  • Node.js: node --inspect with Chrome DevTools, process.memoryUsage(), heap snapshots, and production APM to watch RSS and heap over days.
  • Prevent: a lint rule for effect cleanups, unmount tests in CI, memory budgets in end-to-end tests with repeated navigation, and error reporting that includes performance data.

Traps

  • Describing a “leak” as high memory use. A leak is growth that does not stabilise, not a big but steady footprint.
  • Only knowing the textbook “forgot to remove a listener” and nothing about detection tools.
  • Forgetting that caching is a deliberate leak unless it has a bound.
  • Assuming React prevents leaks. It cleans up its own state; your subscriptions are your responsibility.

Likely follow-ups

Does removing a DOM node free it?
Only if no JavaScript references remain. Removed but referenced nodes are “detached” and retained.
How do you leak-test in CI?
A scripted loop in Playwright or Puppeteer that repeats a flow, forces GC through the DevTools protocol and compares heap sizes against a threshold.
What does “retained size” mean?
The memory that would be freed if this object were removed, including everything only it keeps alive.
Is the WeakRef a fix?
For specific caches, yes. For lifecycle bugs the fix is cleanup, not weak references.

V8 internals and JIT-friendly code

“How does V8 execute JavaScript? What are the interpreter and the optimising compiler, hidden classes and deoptimisation? How does that affect the way you write code?”

Say this first (30 seconds)

“V8 parses source into an AST and compiles it to bytecode, which the Ignition interpreter runs immediately for fast startup. While running, V8 collects feedback about the types it sees. Hot functions are compiled to optimised machine code by TurboFan, which makes assumptions based on that feedback, for example that an object always has the same shape. Objects with the same properties added in the same order share a hidden class, which lets property access become a fast fixed-offset load with inline caching. If an assumption breaks, V8 deoptimises back to bytecode. So predictable code is fast code: consistent object shapes, stable types in hot paths, and no changing structures after creation. But I do not micro-optimise before measuring; algorithms and avoiding unnecessary work matter far more.”

Details interviewers probe

  • Why a JIT: JavaScript is dynamic, so ahead-of-time compilation cannot know types. A JIT observes real behaviour and generates specialised code, falling back if it was wrong. The tiers exist because compiling everything with the heavy optimiser would delay startup.
  • Pipeline: lazy parsing (inner functions are pre-parsed and only fully compiled when first called), Ignition bytecode, then Sparkplug (fast baseline compiler), Maglev (mid-tier optimiser added in recent Chrome versions) and TurboFan verify tier names for the Chrome version in question. The details change between versions; the principle does not.
  • Inline caches and feedback: each property access or call site records the shapes and types it has seen. Optimised code assumes that profile.
  • Deoptimisation: if an optimised function meets a value that breaks an assumption (a different shape, a number where a string was always seen, an out-of-bounds read), V8 discards the optimised code and returns to bytecode, then may re-optimise. Repeated cycles are visible in the profiler.
  • Numbers: small integers (Smi) are stored directly; other numbers are boxed heap numbers, which is slower. Mixing integers and floats in an array changes its “elements kind”, and the engine does not go back.
  • Arrays have elements kinds: packed integers, packed doubles, packed generic, and holey variants. Holes (new Array(100), delete arr[i], writing far past the end) make arrays “holey” and slower; very sparse arrays fall back to dictionary mode.
  • Practical guidance: initialise all properties in the constructor in the same order; do not add or delete properties later (use undefined/null or a Map); keep function parameters and return types consistent; avoid mixing types in arrays; use classes or factory functions for objects of the same kind; avoid arguments leaking and with/eval in hot code.
  • Measure first: use the DevTools Performance panel, flame charts, and Node’s --prof/--cpu-prof. Check that you are not optimising something that takes 1% of the time. Most real slowness is network, rendering, too much DOM or too much JavaScript shipped, not property shapes.
  • Startup costs: parse and compile time grows with bundle size; code caching (V8 caches bytecode for scripts that are reused), splitting bundles and deferring unused code help. Fewer bytes of JavaScript is the best optimisation.
  • WebAssembly: compiled ahead of time to a compact binary format with predictable performance; useful for compute-heavy modules (codecs, games, Figma, image processing), not for DOM-heavy UI.
  • Security link: Spectre mitigations (site isolation, reduced timer precision, cross-origin isolation) came from speculative execution attacks and shaped SharedArrayBuffer rules (J23).

Traps

  • Treating hidden classes as something you tune daily. Know the concept and the two or three habits it implies; do not recommend rewriting code for them without a profile.
  • “JavaScript is interpreted.” Modern engines compile to bytecode and machine code at run time.
  • “Using delete is always bad.” It is harmful in hot paths with many objects; in normal app code the effect is negligible.
  • Quoting engine tier names with certainty. They change; say “baseline and optimising tiers” if unsure.

Likely follow-ups

What is the difference between Ignition and TurboFan?
Ignition interprets compact bytecode for quick start and gathers type feedback. TurboFan compiles hot functions to speculative, optimised machine code.
Why is a class with fields initialised in the constructor faster than adding fields later?
All instances follow one shape-transition path and share one hidden class, so access sites stay monomorphic.
What is code caching?
The browser stores compiled bytecode for a script so repeat visits skip parsing and compilation. Stable file URLs and content help.
How do you find a performance problem in JavaScript?
Record a profile, read the flame chart for long tasks and hot functions, fix the biggest, and measure again. Use real devices, not only a fast laptop.

Events, delegation and observers

“Explain event bubbling and capturing. What is event delegation and why use it? What is the difference between stopPropagation and preventDefault? What are the Observer APIs?”

Say this first (30 seconds)

“When an event fires on an element, it travels in three phases: capture, from the window down to the target; the target phase; then bubble, back up to the window. Listeners run in the bubble phase by default; passing capture: true listens on the way down. Event delegation puts one listener on a common ancestor and uses event.target, usually with closest(), to find which child was hit. It uses less memory and works for elements added later. stopPropagation stops the event travelling further; preventDefault cancels the browser’s default action, such as following a link or submitting a form; they are independent. For observing changes without polling, I use IntersectionObserver, ResizeObserver and MutationObserver.”

Details interviewers probe

  • addEventListener(type, fn, options): options are capture, once (auto remove), passive (promise not to call preventDefault, so scrolling is not blocked) and signal (remove when the signal aborts). To remove a listener you need the same function reference and same capture flag.
  • Delegation benefits: one listener rather than thousands (memory), handles dynamically added children, simpler cleanup. Limits: events that do not bubble (focus, blur, mouseenter, mouseleave, load; use focusin/focusout, mouseover/mouseout or capture), and a handler that must run before ancestors’ handlers.
  • this in listeners: in a regular function it is currentTarget; in an arrow function it is the lexical this (J5).
  • Cancelable and default actions: not every event is cancelable (event.cancelable). Passive listeners for touchstart, wheel make scrolling smooth; calling preventDefault inside one is ignored with a console warning.
  • Custom events: el.dispatchEvent(new CustomEvent('item:add', { detail, bubbles: true, composed: true })) for component communication; composed lets it cross Shadow DOM boundaries. EventTarget can be used as a lightweight event bus.
  • Shadow DOM: events are retargeted so outside listeners see the host as target; event.composedPath() gives the real path for open shadow roots.
  • Framework note: React attaches listeners at the root container and dispatches its own synthetic events (a delegation mechanism); since React 17 events are attached to the root, not document. Mixing native and React handlers can lead to ordering surprises with stopPropagation.
  • Event timing and INP: slow handlers delay the next paint; do light work in the handler and defer the rest (J18, J22). Prefer pointer events over separate mouse/touch handlers.
  • IntersectionObserver: reports when an element enters or leaves the viewport (or another root) by a threshold; used for lazy loading, infinite scroll, analytics visibility and sticky headers, without scroll listeners.
  • ResizeObserver: notifies when an element’s box changes size; used for responsive components, charts and virtual lists; avoid changing size inside the callback in a loop.
  • MutationObserver: watches DOM changes (children, attributes, text); callbacks run as microtasks; used by extensions and libraries; always disconnect() when done.
  • PerformanceObserver: receives performance entries (long tasks, LCP, layout shift, event timing) for monitoring.

Traps

  • Using event.target directly in a delegated handler when the click may land on an inner icon or span; use closest.
  • Calling stopPropagation to “fix” things, breaking analytics, dropdown-close logic and delegation elsewhere. Prefer checking event.target.
  • Removing an anonymous listener: a new function is a different reference and nothing is removed.
  • Saying preventDefault stops bubbling, or the reverse.
  • Forgetting that return false in an inline handler does both, but not in addEventListener.

Likely follow-ups

Which events do not bubble?
Mainly focus, blur, mouseenter, mouseleave, load, unload, scroll on elements (document scroll bubbles to window), and media events.
Why use { passive: true }?
The browser can scroll immediately instead of waiting to see whether you call preventDefault.
Delegation in a React app?
Usually unnecessary: React already delegates. Use it for large lists of native DOM or non-React widgets.
How would you implement lazy-loading images?
loading="lazy" first; IntersectionObserver when you need control (placeholders, thresholds).

Design patterns in JavaScript

“Which design patterns do you use in JavaScript and where? Explain the module, singleton, factory, observer, strategy, decorator and proxy patterns. What are the SOLID principles in a frontend context?”

Say this first (30 seconds)

“Patterns are named, reusable solutions to recurring design problems. JavaScript’s first-class functions, closures and modules make many of them lighter than in class-based languages. The ones I use most are the module pattern, now ES modules, for encapsulation; factory functions to create objects; observer or publish/subscribe for decoupled communication, which is how events, stores and RxJS work; strategy, passing behaviour as a function; decorator, wrapping a function to add behaviour such as logging or caching; and middleware, a chain of responsibility, as in Express and Redux. I choose a pattern to solve a concrete problem, not to show I know it, and I prefer composition over inheritance.”

Principles worth mentioning

  • SOLID in frontend terms: single responsibility (a component or hook does one thing; split fetching, state and presentation); open/closed (extend via props, slots and composition rather than editing the component); Liskov (a replacement component honours the same contract); interface segregation (pass components only the props they need, not whole objects); dependency inversion (depend on abstractions like a repository or hook, so you can swap or mock the API layer).
  • Composition over inheritance: combine small functions and objects; deep class hierarchies are rigid. React moved from mixins and HOCs to hooks for this reason.
  • DRY, KISS, YAGNI: duplication is cheaper than the wrong abstraction; add a pattern when the third use appears.
  • Separation of concerns: data access, business rules and UI in different layers, which is also what enables testing.
  • State architecture patterns: Flux/Redux (one-way data flow), observer-based stores (Zustand, MobX), state machines (XState) for complex flows.
  • Anti-patterns: god objects, deep inheritance, global mutable state, callback pyramids, premature abstraction, patterns used for their own sake.

Traps

  • Reciting a list of Gang of Four names without a real example from your own work. Prepare two: say where you used one and what it improved.
  • Calling every shared module a “singleton” without noting the downside: global state that complicates tests and server rendering (state shared between requests).
  • Over-engineering with patterns where a plain function would do.
  • Confusing observer with pub-sub: in observer, subjects know their observers; in pub-sub a broker sits between them.

Likely follow-ups

Observer versus pub-sub?
Observer: subject holds and notifies its observers directly. Pub-sub: publishers and subscribers only know the broker and topic names, so they are fully decoupled.
Why are ES modules good singletons?
The module is evaluated once and cached; every importer sees the same instance. On a server, the cache is shared across requests, so do not keep per-user data there.
Which pattern is Redux?
Command (actions), observer (subscribe), mediator (central store), with a reducer as a pure function.
What pattern is React’s children and render props?
Composition, a form of strategy: the parent provides the rendering behaviour.

JavaScript security

“What are the main security risks in a JavaScript frontend? Explain XSS, CSRF, prototype pollution and supply-chain risk, and how you defend against them. Where should you store tokens?”

Say this first (30 seconds)

“The biggest frontend risk is cross-site scripting: untrusted data ends up executed as code in my origin, so an attacker can read tokens and act as the user. I prevent it by treating all external data as text, using framework auto-escaping, avoiding innerHTML, eval and dangerouslySetInnerHTML unless the HTML is sanitised with DOMPurify, and adding a strict Content Security Policy, with Trusted Types where possible. CSRF abuses the browser sending cookies automatically; I defend with SameSite cookies and anti-CSRF tokens. Prototype pollution comes from merging untrusted keys such as __proto__. Dependencies are a supply-chain risk, so I use lockfiles, audits and minimal packages. The client is never trusted: authorisation always lives on the server.”

Threats and defences

  • XSS sinks to avoid: innerHTML, outerHTML, insertAdjacentHTML, document.write, eval, new Function, string arguments to setTimeout, javascript: URLs in href, and React’s dangerouslySetInnerHTML. Safe by default: textContent, framework interpolation, setAttribute with validated values.
  • URLs are a sink too: validate scheme (http, https, mailto) before putting user data in href or src; guard open redirects (?next= parameters).
  • Content Security Policy: an HTTP response header telling the browser which sources of script, style, images and frames are allowed. A strict policy uses nonces or hashes with strict-dynamic and avoids unsafe-inline and unsafe-eval. Start with report-only to see violations. frame-ancestors prevents clickjacking.
  • Trusted Types verify browser support: forces dangerous sinks to accept only values created by approved policies, which turns DOM XSS into a compile-time-like error in supported browsers.
  • Token storage: localStorage is readable by any script on the page, so an XSS steals the token. An HttpOnly cookie cannot be read by JavaScript but is sent automatically, so it needs CSRF protection (SameSite=Lax/Strict, anti-CSRF token). A common recommendation: short-lived access token in memory, refresh token in an HttpOnly cookie, or a backend-for-frontend that keeps tokens server-side. There is a trade-off; be ready to explain it, not claim a single right answer.
  • CSRF: a malicious site makes the user’s browser send an authenticated request. Defences: SameSite cookies, CSRF tokens (synchroniser or double-submit), checking Origin/Referer, requiring custom headers or JSON content type on state-changing requests. Not an issue for APIs that use Authorization headers from JavaScript rather than cookies.
  • CORS is not a security feature for your server: it relaxes the browser’s same-origin policy for reads. It does not stop non-browser clients, and misconfiguration (* with credentials, reflecting any origin) creates holes.
  • Prototype pollution: a merge, clone or path-set function that accepts keys like __proto__, constructor or prototype from untrusted JSON modifies Object.prototype for the whole app, enabling logic bypass or even XSS gadgets. Defences: reject those keys, use Object.create(null) or Map for dictionaries, validate with schemas, Object.freeze(Object.prototype) in controlled environments, keep libraries patched (J6).
  • Supply chain: a malicious or hijacked npm package runs with your app’s power at build and at run time. Mitigate with lockfiles and npm ci, pinned versions, npm audit/Dependabot/Renovate, fewer dependencies, review install scripts (--ignore-scripts), package provenance, Subresource Integrity (integrity attribute) for CDN scripts, and a vetted internal registry.
  • Third-party scripts: tags and widgets run with full page privileges. Load them in sandboxed iframes where possible, or use a tag manager with governance.
  • ReDoS: a regular expression with nested quantifiers on user input can take exponential time and freeze the thread (J14). Use linear-time patterns, input length limits, or a safe engine.
  • postMessage: always check event.origin against an allowlist and never send secrets to *.
  • Iframes: use the sandbox attribute for untrusted content, rel="noopener" on external links (default in modern browsers), and frame-ancestors or X-Frame-Options against clickjacking.
  • Secrets: anything shipped to the browser is public: API keys in bundles, source maps with comments, environment variables exposed by the build tool prefix (VITE_, NEXT_PUBLIC_). Keep real secrets on the server.
  • Sensitive data: avoid putting tokens or personal data in URLs, logs and analytics; clear caches on logout; set Cache-Control: no-store on sensitive responses.

Traps

  • “React is safe from XSS.” It escapes interpolated text, but dangerouslySetInnerHTML, href with javascript:, server-rendered HTML and third-party libraries remain risks.
  • Believing “we sanitise on input” is enough. Encode at output for the right context.
  • “Put the token in localStorage because it is simple” without acknowledging XSS exposure, or “cookies are always safer” without mentioning CSRF.
  • Treating CORS errors as something to silence with *.
  • Client-side role checks as the only access control.

Likely follow-ups

Stored versus reflected versus DOM XSS?
Stored: payload persisted on the server and served to many users. Reflected: payload in the request echoed in the response. DOM-based: client-side code reads attacker-controlled data (URL hash, postMessage) and writes it to a sink.
What does SameSite do?
Controls whether cookies are sent on cross-site requests: Strict never, Lax only on top-level navigations (the modern default), None always (requires Secure).
How would you secure a CDN script?
Subresource Integrity hash plus crossorigin, a CSP that allows only that host, and ideally self-hosting a pinned copy.
What is the OWASP Top 10 relevance for frontend?
Injection (XSS), broken access control, vulnerable and outdated components, security misconfiguration (CSP, CORS), and identification failures (token handling).

Network, streams and storage APIs

“How do you make network requests in the browser? Compare polling, Server-Sent Events and WebSockets. What are the client-side storage options and when do you use each?”

Say this first (30 seconds)

“For requests I use fetch, which returns a promise, does not reject on HTTP errors, and exposes the body as a stream. I control it with AbortSignal, credentials and cache options. For live updates I choose by direction and cost: polling is simplest, Server-Sent Events give one-way server push over plain HTTP with automatic reconnect, and WebSockets give a full-duplex channel for chat, collaboration and games. For storage: cookies for small server-visible data such as sessions, localStorage for small synchronous preferences, sessionStorage per tab, IndexedDB for large structured data and offline apps, and the Cache API for request and response pairs used by Service Workers. Everything is per origin and can be evicted.”

Fetch in depth

  • Basics: fetch(url, { method, headers, body, signal, credentials, cache, mode, redirect, keepalive }) returns a promise for a Response. It rejects only on network failure or abort; check response.ok or status. Read the body once with json(), text(), blob() or arrayBuffer(); use clone() to read twice.
  • credentials: same-origin (default) sends cookies only to your origin; include sends them cross-origin (the server must allow it explicitly with CORS); omit never.
  • mode and CORS: cross-origin reads need CORS headers from the server. Non-simple requests trigger a preflight OPTIONS. no-cors returns an opaque response you cannot read; it is rarely what you want.
  • Cache control: the cache option (default, no-store, reload, force-cache) interacts with HTTP caching headers; the real policy belongs on the server.
  • Streams: response.body is a ReadableStream. You can process large or incremental responses chunk by chunk (progress bars, NDJSON, LLM token streaming) through getReader() or for await, and pipe through TextDecoderStream or CompressionStream. Streaming request bodies need HTTP/2 or newer and duplex: 'half' verify support.
  • Fire-and-forget on page exit: navigator.sendBeacon(url, data) or fetch(..., { keepalive: true }) survive page unload; use for analytics and logs. Do not use unload handlers; they block back/forward caching.
  • Helpers: URL and URLSearchParams build and parse URLs safely (never concatenate query strings by hand); FormData for forms and file uploads (do not set the multipart Content-Type yourself); Blob, File and URL.createObjectURL for local previews (revoke when done); Headers, Request, Response; TextEncoder/TextDecoder.
  • Progress and uploads: fetch has no upload progress event; use XMLHttpRequest (upload.onprogress) or streaming uploads.
  • Production concerns: timeouts (AbortSignal.timeout), retries with backoff for idempotent calls, deduplication and caching (TanStack Query), error mapping (J21), and request ids for tracing.

  • Feature detection, not browser detection: if ('IntersectionObserver' in window), if (navigator.share), CSS.supports(). User-agent sniffing breaks as browsers change.
  • Progressive enhancement: the core task works without the API; the API improves it (share sheet, instant transitions, offline mode).
  • Baseline: a shared definition (web.dev, MDN) of features that work in all current major browsers; “Baseline widely available” is safe, “newly available” needs a check against your audience. Use browserslist and analytics to decide your support matrix.
  • Polyfills versus ponyfills: a polyfill patches the global; a ponyfill exports a function without touching globals. Polyfill only what your targets lack, loaded conditionally; tools: core-js with useBuiltIns, or a polyfill service.
  • Secure contexts and permissions: many APIs need HTTPS and a user gesture; handle denial and unavailability gracefully.
  • Origin trials and flags: experimental features may change or disappear; keep them behind detection and never as a hard dependency.
  • Page lifecycle events: visibilitychange (hidden), pagehide (leaving, bfcache-safe), pageshow (restored), freeze/resume (Chromium); avoid beforeunload except for real unsaved-changes warnings and unload entirely.
  • Privacy and consent: geolocation, camera and notifications are sensitive; ask in context, explain why, and have a fallback.

Traps

  • “Just use it, everyone has Chrome.” Your audience may include Safari on iOS, which sets the floor for many APIs.
  • Calling a permission API on page load, so users deny it before understanding why.
  • Using unload or beforeunload for analytics and killing the back/forward cache.
  • Shipping a polyfill bundle to every browser rather than conditionally.
  • Using Math.random() for tokens or ids that need to be unguessable.

Likely follow-ups

How do you decide whether you can use a new API?
Check Baseline and Can I Use against the support matrix from real analytics, feature-detect, provide a fallback, and decide whether the enhancement justifies the maintenance.
What is the difference between visibilitychange and pagehide?
visibilitychange fires when the tab is hidden or shown, including switching tabs; pagehide fires when the page is being navigated away from or closed. Use the first as the main save signal, the second as a backup.
Why does bfcache matter for performance?
A restored page skips the network and script startup, so back navigation is instant and improves real-user metrics.
Which API would replace a scroll listener for lazy loading?
IntersectionObserver, or the native loading="lazy" attribute.

How to answer runtime and engine questions at L4

  • Start with the one-sentence model (“one task, then all microtasks, then render”), then go one level deeper only if asked. Interviewers reward a clear mental model over a memorised list.
  • Always attach a production consequence: a long task hurts INP, a missing cleanup leaks memory, a floating promise loses an error, a stale response overwrites a newer one.
  • Name trade-offs, not just features: workers cost startup and copying, throttling costs freshness, a strict CSP costs integration effort, localStorage tokens cost XSS exposure.
  • For engine internals (V8 tiers, GC details) state the principle confidently and say “I would check the exact version details” for the specifics.
  • Connect to React and tooling: effect cleanup, concurrent rendering as scheduling, error boundaries, bundle size and parse cost.
  • The interview is theoretical: expect “explain”, “compare”, “how would you debug”, and “what are the trade-offs”, not code puzzles.
