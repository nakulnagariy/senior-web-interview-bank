The JVM and how Java runs

“How does Java run? What are the JDK, JRE and JVM? Explain bytecode, the JIT compiler, memory (heap, stack), garbage collection and the Java release model. How does this compare with JavaScript and V8?”

Say this first (30 seconds)

“Java source is compiled by javac into platform-independent bytecode, which the Java Virtual Machine loads and executes, interpreting it first and using a just-in-time compiler to turn hot code into optimised machine code, so the same class files run on any operating system with a JVM. The JDK contains the compiler and tools; the JRE is the runtime; the JVM is the engine. Objects live on the heap, managed by a garbage collector such as G1 or ZGC; each thread has a stack for method calls and local variables. Java is statically typed and compiled ahead to bytecode, unlike JavaScript which is dynamically typed and compiled at run time, but both use JIT compilation and garbage collection. Oracle releases a new Java version every six months, with long-term support releases such as 17 and 21 used in production.”

Details interviewers probe

  • Compilation and execution: javac produces .class files; jar packages them with metadata (MANIFEST.MF); the JVM’s class loader loads classes lazily; the bytecode verifier checks safety; execution starts in the interpreter, and tiered JIT compilation (C1 quick, C2 aggressive) optimises hot code; warm-up explains slower initial requests after startup.
  • Garbage collection: automatic reclamation of unreachable objects; generational hypothesis (most objects die young). Collectors: Serial, Parallel, G1 (default, balanced pause times), ZGC and Shenandoah (low latency, concurrent). Tuning knobs: heap size, pause goals; symptoms of trouble: long pauses, OutOfMemoryError, memory leaks from static collections and listeners (similar causes to JS leaks, J24, J25).
  • Stack and heap: primitives and references in stack frames; objects in the heap; passing arguments is always by value (object references are copied), like JavaScript’s “call by sharing” (J1).
  • Release model and LTS: a feature release every six months; LTS every few years (8, 11, 17, 21, 25) supported longer; enterprises standardise on LTS and upgrade periodically; features arrive as preview before finalising (records, sealed classes, virtual threads, pattern matching) verify the current LTS.
  • Native images and startup: GraalVM native image compiles ahead of time for fast startup and low memory (useful for serverless), with trade-offs in build time and reflection constraints; Spring Boot supports it. CRaC and class data sharing also reduce startup.
  • Tooling: Maven or Gradle for builds, IDEs (IntelliJ IDEA), JFR (Java Flight Recorder) and VisualVM for profiling, jstack thread dumps, jmap heap dumps, Mission Control, and APM agents (Datadog, New Relic) attach as -javaagent.
  • Platforms beyond Java: Kotlin and Scala run on the JVM and interoperate; many “Java shops” use Kotlin for new services.
  • Why enterprises use Java: mature ecosystem, strong typing and tooling, performance, long-term compatibility, a huge talent pool, and robust frameworks (Spring, Jakarta EE); good for large, long-lived systems and teams.
  • What frontend leads should take away: Java services have slower cold starts and heavier memory but strong throughput; response times may vary after deploys until JIT warm-up; heap sizing and GC affect latency (visible as slow outliers in your API calls).
  • Containers: modern JVMs respect container memory and CPU limits; set max heap as a percentage; OOM kills in Kubernetes appear as exit code 137 (A8, A9).

Traps

  • Saying Java is “interpreted” or “compiled to native code” without explaining bytecode and JIT.
  • Confusing Java and JavaScript beyond the name.
  • Believing Java’s garbage collection means memory leaks are impossible.
  • Ignoring warm-up when benchmarking or diagnosing slow first requests.

Likely follow-ups

JDK versus JRE versus JVM?
The JDK includes development tools and the JRE; the JRE includes the JVM and standard libraries; the JVM executes bytecode.
Why do Java services seem slow right after deployment?
The JVM is still interpreting and profiling; JIT compilation optimises hot code after warm-up.
What does the garbage collector do?
Finds objects no longer reachable and frees their memory, in generations, concurrently with the application in modern collectors.
What is an LTS release?
A Java version with extended vendor support, preferred for production.

Core language and OOP essentials

“Explain the core Java language concepts a non-Java developer should recognise: classes, interfaces, inheritance, encapsulation, polymorphism, immutability, records, enums, generics, exceptions, equals/hashCode, Optional and modern features.”

Say this first (30 seconds)

“Java is a statically typed, class-based object-oriented language. Everything lives in classes; interfaces define contracts that classes implement; inheritance lets a class extend one parent, and polymorphism means a reference of the parent or interface type can hold different implementations. Fields are private and exposed through methods, which is encapsulation. Java has primitives and wrapper objects, strings are immutable, and modern Java adds records for immutable data carriers, sealed classes, pattern matching, text blocks, var and enhanced switch. Exceptions are either checked, which must be handled or declared, or unchecked. Collections of objects rely on equals and hashCode being consistent. I can read Java code comfortably because the concepts map to TypeScript classes, interfaces and generics.”

Details interviewers probe

  • Types: eight primitives (int, long, double, boolean, char, byte, short, float) and reference types; wrapper classes (Integer, Long) with autoboxing; null is a valid reference value (the source of NullPointerException); String is immutable (like JavaScript strings); == compares references for objects, so .equals() compares content.
  • Classes and encapsulation: fields usually private with getters and setters (JavaBeans convention); constructors; static members; access modifiers (package-private is the default); packages and imports organise code; one public class per file.
  • Inheritance and polymorphism: single inheritance of classes, multiple interfaces; @Override; abstract classes; super; interfaces can have default methods; favour composition over inheritance (J28, S8). Dynamic dispatch means the runtime class decides which method runs.
  • Immutability and records: final fields, immutable classes, and record Point(int x, int y) {} (compact immutable data carrier with accessors x(), equals, hashCode); records are popular for DTOs in APIs.
  • Enums and sealed types: enums are full classes with fields, constructors and methods; sealed hierarchies with pattern-matching switch give exhaustive handling similar to TypeScript discriminated unions (T4).
  • Generics: compile-time type safety (List<String>), wildcards (? extends, ? super), and type erasure: generic information is removed at runtime, so you cannot do instanceof List<String>; similar erasure exists in TypeScript.
  • Exceptions: Throwable splits into Error (JVM problems), checked Exception (must be caught or declared with throws) and unchecked RuntimeException (programming errors such as NullPointerException, IllegalArgumentException); try-with-resources closes resources; Spring commonly translates exceptions into HTTP responses (JV6).
  • equals and hashCode: must be consistent: equal objects must have equal hash codes, otherwise HashMap and HashSet misbehave; records and IDE generation handle it.
  • Optional<T>: a container signalling a value may be absent, used for return types (not fields or parameters); methods map, orElse, orElseThrow, ifPresent; avoids returning null but is not a general nullability solution; annotations (@Nullable) and static analysis help.
  • Annotations: metadata like @Override, @Deprecated, and framework annotations (@RestController, @Entity, @Autowired, @Valid) that drive behaviour via reflection at runtime or annotation processing at compile time.
  • Lambdas and functional interfaces: x -> x * 2 implements single-method interfaces (Function, Predicate, Consumer, Supplier); method references String::trim; used with streams and callbacks, like JavaScript arrow functions (J8).
  • Naming and style: classes PascalCase, methods and variables camelCase, constants UPPER_SNAKE_CASE, packages lowercase; JSON property names often need mapping (@JsonProperty) when the frontend uses different casing.
  • Date and time and numbers: java.time (Instant, LocalDate, ZonedDateTime, Duration) is the modern API; BigDecimal for money; long ids can exceed JavaScript’s safe integer range (J13) (JV6).

Traps

  • Comparing strings or boxed numbers with == in Java.
  • Overriding equals without hashCode.
  • Treating Optional as a replacement for all null handling or using it for fields.
  • Assuming generics exist at runtime.
  • Using floating-point types for money instead of BigDecimal.

Likely follow-ups

Interface versus abstract class?
Interfaces define contracts (and default methods) with multiple implementation; abstract classes share state and code with single inheritance.
Checked versus unchecked exceptions?
Checked must be handled or declared; unchecked represent programming errors and need not be.
What is a record?
A concise immutable data class with generated accessors, equals, hashCode and toString.
What is type erasure?
The compiler removes generic type arguments, so they are not available at run time.

Collections, generics and streams

“What are the Java collections: List, Set, Map and their implementations? How does HashMap work? What are streams and how do they compare with JavaScript array methods? What is immutability in collections?”

Say this first (30 seconds)

“The Java Collections Framework provides interfaces and implementations for groups of objects: List is an ordered sequence, usually ArrayList; Set holds unique elements, such as HashSet or the ordered LinkedHashSet and TreeSet; Map stores key-value pairs, usually HashMap. A HashMap computes a bucket from the key’s hashCode and uses equals to find the entry, giving average constant-time lookups. The Stream API processes collections declaratively with operations like filter, map and collect, similar to JavaScript’s array methods but lazy and able to run in parallel. Collections are mutable by default; List.of creates immutable ones, and concurrent collections exist for multi-threaded use.”

Details interviewers probe

  • Choosing a collection: ArrayList by default for lists; LinkedList almost never; HashSet for uniqueness; TreeMap/TreeSet when sorted order matters; LinkedHashMap for insertion order or LRU caches; ArrayDeque for queues and stacks; PriorityQueue for ordering by priority.
  • Big-O awareness: ArrayList get O(1), add amortised O(1), insert middle O(n); HashMap/HashSet O(1) average; TreeMap O(log n); contains on a list is O(n). Interview-level understanding, similar to JavaScript data structure costs (J10, J11).
  • HashMap internals: array of buckets, key hash spread, collisions resolved by chaining (linked list converting to a balanced tree when long), resize doubling; null keys allowed in HashMap but not in ConcurrentHashMap; iteration order is unspecified.
  • Equality and ordering: equals/hashCode for hash-based collections; Comparable (natural ordering) and Comparator (external ordering) for sorting and tree collections.
  • Immutability and defensive copies: List.of, Set.of, Map.of, Collections.unmodifiableList (a view), List.copyOf; modifying immutable collections throws UnsupportedOperationException; return copies from APIs to protect internal state.
  • Streams: sources (collections, arrays, ranges), intermediate operations (filter, map, flatMap, distinct, sorted, limit), terminal operations (collect, forEach, reduce, count, anyMatch, findFirst); keep them side-effect free; avoid overusing for complex logic; debugging is harder than loops.
  • Collectors: groupingBy (like building a map of arrays), partitioningBy, toMap (watch duplicate keys), joining, counting, summarizingInt.
  • Generics with collections: compile-time safety, bounded types and wildcards; raw types (List without type) are legacy and unsafe.
  • Concurrent collections: ConcurrentHashMap, CopyOnWriteArrayList, blocking queues for producer-consumer; plain collections are not thread-safe; Collections.synchronizedList is coarse.
  • Iteration: enhanced for-loop, iterators, forEach with lambdas; modifying a collection while iterating throws ConcurrentModificationException (use iterator removal or removeIf).
  • Relevance to the frontend: API responses are often serialised collections; ordering guarantees (a HashSet or HashMap has no stable order, so the JSON array or object order may vary), pagination of lists, and large result sets affecting response size and latency.

Traps

  • Using mutable objects as HashMap keys and changing them after insertion.
  • Relying on iteration order of a HashMap/HashSet.
  • Reusing a stream after a terminal operation.
  • Thinking Collections.unmodifiableList makes a copy; it is a read-only view.
  • Using parallel streams without understanding thread pool sharing.

Likely follow-ups

ArrayList versus LinkedList?
ArrayList is array-backed with fast random access and is the default; LinkedList has fast inserts at known nodes but poor cache locality and slow indexed access.
How does HashMap handle collisions?
Entries in the same bucket are chained (list, or tree when long) and distinguished using equals.
What is a lazy stream?
Intermediate operations are not executed until a terminal operation runs, allowing optimisations and short-circuiting.
Stream or for loop?
Streams for declarative transformations; loops for complex control flow or performance-critical code.

Concurrency versus the JavaScript model

“How does concurrency work in Java? Threads, executors, synchronisation, volatile, CompletableFuture and virtual threads. How does it differ from the single-threaded JavaScript event loop, and what do race conditions mean for an API?”

Say this first (30 seconds)

“Java has real multithreading: multiple threads execute code simultaneously and share heap memory, so correctness depends on synchronisation. A web server typically handles each request on a thread from a pool, so many requests run in parallel, and shared mutable state needs protection with locks, synchronized, atomic classes or concurrent collections; volatile ensures visibility of changes across threads. Higher-level tools include executors and CompletableFuture for asynchronous composition, similar to promises, and from Java 21 virtual threads, which make blocking code cheap to scale. JavaScript instead runs one thread with an event loop, so data races on shared memory do not occur, but CPU work blocks everything. For a frontend lead the relevance is that concurrent requests can race on the server, so operations need idempotency, transactions and optimistic locking.”

Details interviewers probe

  • Threads and executors: creating raw Threads is discouraged; use ExecutorService thread pools (Executors.newFixedThreadPool, ForkJoinPool); servlet containers (Tomcat) assign a pool thread per request; pool sizing affects throughput and latency (too small queues requests, too large wastes memory).
  • Synchronisation: synchronized blocks provide mutual exclusion and visibility; ReentrantLock adds features; volatile guarantees visibility, not atomicity of compound operations; AtomicInteger/LongAdder for lock-free counters; immutable objects and thread-confined data avoid locking.
  • Common problems: race conditions, deadlocks (lock ordering), starvation, memory visibility bugs, thread leaks, and thread-unsafe shared singletons such as a SimpleDateFormat instance (legacy pitfall).
  • CompletableFuture: composes async tasks (supplyAsync, thenApply, thenCompose, thenCombine, allOf, exceptionally), conceptually like Promise chains (J19); pay attention to which executor runs each stage.
  • Reactive stacks: Spring WebFlux and Project Reactor (Mono, Flux) offer a non-blocking event-loop model similar to Node, with backpressure; higher complexity; mostly justified for very high concurrency or streaming. Virtual threads (Java 21) give most of the scalability benefit with the simple blocking style verify adoption status.
  • Virtual threads: lightweight threads scheduled by the JVM onto carrier threads; blocking calls park the virtual thread rather than an OS thread; allow thread-per-request designs at huge scale; supported in Spring Boot 3.2+ with a configuration flag.
  • Transactions and concurrency control: database isolation levels (D6), pessimistic locking (SELECT … FOR UPDATE, JPA PESSIMISTIC_WRITE), optimistic locking with a @Version column leading to OptimisticLockException mapped to 409; these protect business invariants from lost updates (JV7).
  • Idempotency and retries: servers must handle duplicate requests from retries and double clicks; frontends should send idempotency keys for creation and disable repeated actions (D3).
  • Scheduled and async work: @Scheduled jobs, @Async methods, message queues (Kafka, RabbitMQ) for background processing; frontends see eventual consistency and job status endpoints (D10).
  • Timeouts and resilience: thread pools exhausted by slow downstream calls cause cascading latency; use timeouts, circuit breakers (Resilience4j), bulkheads; as a frontend lead you will see this as intermittent 503s or timeouts (A11, D12).
  • Thread dumps and diagnosis: jstack shows blocked threads and deadlocks; useful when a service hangs; ask backend colleagues for thread dumps during incidents.

Traps

  • Assuming volatile makes compound operations such as count++ atomic.
  • Sharing mutable state in singleton beans without synchronisation.
  • Thinking Java is slow at concurrency because JavaScript “is async”; they are different models.
  • Ignoring that two quick frontend requests can interleave on the server.
  • Believing parallel streams are free speedups.

Likely follow-ups

How can two requests corrupt data?
They run concurrently on different threads and interleave reads and writes; protect with transactions, atomic updates, locking or versioning.
CompletableFuture versus Promise?
Both represent a future result and support chaining; CompletableFuture runs on thread pools and can be blocked on with get.
What are virtual threads?
Cheap JVM-managed threads that let blocking-style code scale to many concurrent tasks without OS thread limits.
What is optimistic locking?
Detecting concurrent modification via a version number at update time and failing (409/412) rather than holding locks.

Spring Boot and dependency injection

“What is Spring and Spring Boot? Explain inversion of control, dependency injection, beans, annotations like @RestController, @Service and @Autowired, auto-configuration, profiles and the typical layered structure.”

Say this first (30 seconds)

“Spring is the dominant Java application framework; Spring Boot adds convention-based auto-configuration, starter dependencies, an embedded server and production features such as actuator endpoints, so a service can start with a single command. Its core is inversion of control with dependency injection: instead of creating dependencies myself, I declare them, usually through constructor parameters, and the Spring container creates and wires beans, objects it manages, with scopes such as singleton. Annotations mark roles: @RestController for HTTP endpoints, @Service for business logic, @Repository for data access, @Configuration for bean definitions. Services are layered controller to service to repository, configuration comes from properties and profiles per environment, and this is very similar in spirit to Angular’s dependency injection or NestJS.”

Details interviewers probe

  • Inversion of control and DI: the framework controls object creation and wiring; constructor injection is preferred (immutable fields, easy tests); field injection with @Autowired is discouraged; interfaces allow swapping implementations (@Primary, @Qualifier); beans are singletons by default (shared across threads, so keep them stateless), with request or prototype scopes available.
  • Component scanning and configuration: @SpringBootApplication combines @Configuration, @EnableAutoConfiguration and @ComponentScan; stereotype annotations @Component, @Service, @Repository, @Controller; explicit beans with @Bean methods in @Configuration classes.
  • Auto-configuration: Boot inspects the classpath and properties and configures beans (data source, Jackson, web server) conditionally (@ConditionalOnClass), which you override with your own beans or properties; debug with --debug reports.
  • Configuration and profiles: application.properties/.yml, profile-specific files (application-prod.yml), environment variables override, @ConfigurationProperties binds typed settings, secrets from vaults or the platform; same twelve-factor approach as Node (D11).
  • Web layer: Spring MVC (servlet-based, thread per request) with @GetMapping, @PostMapping, @RequestBody (JSON via Jackson), @PathVariable, @RequestParam, ResponseEntity; Spring WebFlux for reactive; filters and interceptors for cross-cutting concerns (logging, auth, CORS).
  • AOP and proxies: annotations like @Transactional, @Cacheable, @Async, @PreAuthorize work through proxies wrapping beans; a pitfall: calling an annotated method from within the same class bypasses the proxy (“self-invocation”).
  • Spring Security (awareness): filter chain handling authentication and authorisation; common setups: session cookies with CSRF protection, or stateless JWT/OAuth2 resource server validating bearer tokens; method security (@PreAuthorize); CORS configuration; configuration complexity is notable (P6, P8).
  • Testing: JUnit 5, Mockito for mocks, @SpringBootTest for integration tests, @WebMvcTest for controller slices with MockMvc, Testcontainers for real databases, WireMock for external services; contract tests with Spring Cloud Contract or Pact (D11).
  • Actuator and observability: health and readiness endpoints for Kubernetes, metrics via Micrometer (Prometheus), tracing with OpenTelemetry, structured logging (Logback, SLF4J) (A10).
  • Alternatives: Quarkus and Micronaut (fast startup, native images), Jakarta EE, Dropwizard, Vert.x; for frontend leads the choice rarely matters, the contract does.
  • Compared with Express/NestJS: Spring Boot is more opinionated and heavier with richer built-in capabilities; NestJS imitates its DI and decorators in TypeScript (D2).
  • Microservices with Spring: Spring Cloud for config, discovery, gateway and resilience (Resilience4j); many teams use Kubernetes-native alternatives instead.

Traps

  • Storing request-specific state in singleton beans.
  • Expecting @Transactional to work on self-invoked or private methods.
  • Field injection everywhere, making tests and immutability awkward.
  • Exposing entities directly in APIs instead of DTOs.
  • Believing Spring is only for “old” systems; modern Spring Boot 3 is current practice.

Likely follow-ups

What is a bean?
An object created, wired and managed by the Spring container.
Constructor versus field injection?
Constructor injection makes dependencies explicit and objects immutable and testable; field injection hides dependencies.
What does Spring Boot add to Spring?
Auto-configuration, starters, an embedded server, externalised configuration and production-ready features.
How does Spring’s DI compare with Angular’s?
Both inject dependencies from a container using types and annotations or decorators; Spring uses a global container with scopes, Angular a hierarchical injector.

REST APIs: what the frontend sees

“How are REST APIs built in Spring and what do frontend developers need to know? DTOs, validation, error handling, pagination, CORS, dates and numbers in JSON, versioning, OpenAPI, file upload and authentication.”

Say this first (30 seconds)

“In Spring, controllers map HTTP requests to methods, bind JSON bodies to Java objects with Jackson, validate them with annotations, and return DTOs rather than database entities. Errors are translated into HTTP responses by exception handlers, and pagination, sorting and filtering follow Spring Data conventions. From the frontend side the details that cause bugs are contract details: how dates and times are serialised, whether large long ids exceed JavaScript’s safe integer range, how nulls and empty collections appear, enum representation, error response shape, pagination parameters and CORS configuration. I work with backend colleagues on an OpenAPI contract, generate typed clients, validate at the boundary and agree on error formats and versioning early.”

Details interviewers probe

  • Controllers and mapping: @RestController (controller + response body), @RequestMapping, @GetMapping, @PostMapping, @PutMapping, @PatchMapping, @DeleteMapping; request binding: @PathVariable, @RequestParam, @RequestBody, @RequestHeader; responses via return values or ResponseEntity with explicit status and headers (201 Created + Location).
  • Jackson serialisation: maps objects to JSON; configuration for naming strategy, date formats (JavaTimeModule, WRITE_DATES_AS_TIMESTAMPS), @JsonProperty, @JsonIgnore, @JsonInclude(NON_NULL), unknown properties handling; version differences produce subtle contract changes, so test serialised output.
  • DTO versus entity: entities represent persistence; DTOs represent API contracts. Exposing entities leaks internal fields (passwords, relations), couples the API to the schema, causes lazy-loading and cyclic serialisation problems, and invites mass-assignment vulnerabilities (D4). Map with MapStruct or manually.
  • Validation: @Valid on @RequestBody triggers Bean Validation; violations produce MethodArgumentNotValidException mapped to 400/422 with field errors; custom validators for cross-field rules; server validation is authoritative (E6, T11).
  • Error handling: @ControllerAdvice/@RestControllerAdvice with @ExceptionHandler methods returning a consistent error body (RFC 9457 ProblemDetail in Spring Framework 6); do not leak stack traces; include a correlation id; map domain exceptions (not found, conflict, forbidden) to proper statuses (D3).
  • Pagination and filtering: Spring Data’s Pageable (?page=0&size=20&sort=createdAt,desc) and Page<T> (content, totalElements, totalPages); frontends must know that pages start at 0 and the exact response shape; keyset pagination for large data; specifications or QueryDSL for dynamic filters; whitelist sortable fields.
  • CORS and security headers: configure allowed origins, methods, headers and credentials centrally (CorsConfigurationSource with Spring Security) rather than per controller; CSRF settings for cookie sessions; common frontend symptom is a failing preflight caused by security filters rejecting OPTIONS (P5).
  • Dates and time zones: use Instant or OffsetDateTime in UTC for timestamps and LocalDate for dates without time; document the format; avoid LocalDateTime without zone for events; frontends convert to the user’s locale with Intl (J13).
  • Large numbers and money: Long ids above 2^53 − 1 lose precision in JavaScript JSON.parse; serialise as strings (@JsonSerialize(using = ToStringSerializer.class)) or use UUIDs; represent money as BigDecimal serialised as string or as integer minor units.
  • File upload and download: MultipartFile for uploads (size limits configured), streaming responses with StreamingResponseBody, Content-Disposition headers; large files often go via presigned URLs to object storage (N6).
  • OpenAPI: springdoc-openapi generates a spec from controllers; frontends generate TypeScript clients (openapi-typescript, Orval); contract-first alternative designs the spec first and generates server stubs; fail CI on breaking changes with spec diff tools.
  • Versioning and compatibility: URL versions (/api/v1), headers, or additive evolution; Jackson’s lenient handling of unknown fields keeps clients compatible when the backend adds fields; communicate deprecations.
  • Authentication in practice: bearer JWTs validated by Spring Security’s resource server, or cookie sessions via a gateway/BFF; token refresh flows and 401 handling in the client (P8, E9).
  • GraphQL and other styles: Spring for GraphQL, gRPC and messaging exist; REST/JSON is the default for browser clients.

Traps

  • Assuming a Java long id survives JSON in JavaScript.
  • Ambiguous date-time formats and time zones between backend and frontend.
  • Depending on an undocumented error shape or field presence.
  • Exposing JPA entities directly and leaking fields or triggering lazy-loading errors.
  • Blaming the frontend for CORS failures caused by server security filters.

Likely follow-ups

Why DTOs instead of entities?
They decouple the API from the database schema, control exposed fields, avoid lazy-loading and cyclic JSON issues, and prevent mass assignment.
How does Spring validate input?
Bean Validation annotations on DTO fields, triggered by @Valid, with violations translated into 400/422 error responses.
What do you check when a CORS error appears with a Spring backend?
Allowed origins and headers, credentials setting, and whether the security filter chain permits preflight OPTIONS requests.
How do you keep frontend types in sync with the Java API?
Publish an OpenAPI spec from the backend, generate TypeScript types or clients in CI, and add contract checks.

Persistence, JPA and transactions

“How do Java backends talk to databases? JDBC, JPA, Hibernate and Spring Data. What are entities, relationships, lazy loading, the N+1 problem, @Transactional, connection pools and migrations? What should a frontend lead ask about performance?”

Say this first (30 seconds)

“Java applications access relational databases through JDBC at the lowest level and, more commonly, through JPA with Hibernate as the ORM, usually via Spring Data repositories where I declare an interface and the framework generates queries. Entities are classes mapped to tables, with relationships such as one-to-many. Hibernate loads related data lazily by default, which can cause the N+1 query problem when a list triggers one extra query per row, solved with fetch joins, entity graphs or projections. @Transactional demarcates transactions so multiple operations commit or roll back together. A pooled set of connections, typically HikariCP, serves requests, and schema changes are managed by migration tools like Flyway or Liquibase. From the frontend side, slow lists and timeouts often come from these layers, so I ask about queries, indexes, pagination and payload size.”

Details interviewers probe

  • JDBC and pools: JDBC is the low-level API (connections, statements, result sets); PreparedStatement parameters prevent SQL injection; HikariCP (Spring Boot default) pools connections; pool size must fit the database limit across all instances (D12).
  • JPA and Hibernate: JPA is the specification; Hibernate is the dominant implementation. The persistence context tracks entity changes (dirty checking) and flushes updates on commit. EntityManager underlies repositories. First-level cache per transaction; second-level cache optional.
  • Spring Data JPA: repository interfaces with derived queries (findByEmailAndActiveTrue), @Query for JPQL or native SQL, paging and sorting, specifications for dynamic filters; projections to DTOs reduce loaded columns.
  • Relationships and fetching: @OneToMany, @ManyToOne, @ManyToMany; lazy loading (default for collections) versus eager; bidirectional associations and cyclic serialisation when entities are returned directly (use DTOs); cascade types and orphan removal need care.
  • N+1 and performance diagnosis: enable SQL logging in development, use p6spy or Hibernate statistics, APM traces showing many repeated queries; fix via fetch joins or entity graphs, @BatchSize, projections, or separate queries; combine with pagination (note fetch join with collections and pagination in memory pitfall).
  • Indexes and query tuning: backend team adds indexes for filters and sorts; ask for EXPLAIN plans when an endpoint is slow; avoid SELECT * through projections; pagination with keyset for large tables (D6).
  • @Transactional: proxy-based; applies to public methods called from outside the bean; rollback by default on unchecked exceptions; readOnly = true optimises reads; isolation level and propagation (REQUIRED, REQUIRES_NEW) determine nested behaviour; keep transactions short and do not call slow external services inside.
  • Optimistic and pessimistic locking: @Version detects concurrent updates and throws OptimisticLockException (map to 409); PESSIMISTIC_WRITE locks rows for critical sections; choose by contention and invariants; frontends should handle 409 by refetching and retrying (JV4).
  • Migrations: Flyway or Liquibase versioned scripts run at deploy; backward-compatible changes (expand/contract) so old and new versions can coexist (A6); ddl-auto=update is unsafe in production.
  • Other persistence options: jOOQ and MyBatis for SQL-centric designs, Spring Data MongoDB/Redis/Elasticsearch for other stores, event-sourced designs, read models for queries (CQRS).
  • Data volume and API design: large collections in JSON slow both server and client; paginate, limit nested expansions, and allow field selection; backend and frontend agree on maximum page sizes.
  • Caching on the Java side: Spring Cache with Caffeine or Redis, Hibernate second-level cache, HTTP caching with ETags; frontends benefit from Cache-Control headers set correctly (P3, D9).
  • Questions to ask the backend team: which queries does this endpoint run, are there indexes, is the result paginated, how long can it take at p95, what happens on concurrent updates, and how are migrations deployed.

Traps

  • Assuming ORMs remove the need to understand SQL and query plans.
  • Returning entities with lazy relations and hitting LazyInitializationException or infinite recursion.
  • Expecting @Transactional to roll back on checked exceptions by default.
  • Long transactions that include HTTP calls.
  • Letting a list endpoint load full object graphs for each row.

Likely follow-ups

What is Hibernate?
The leading JPA implementation: an ORM that maps objects to tables, generates SQL and tracks entity changes.
What causes N+1 queries and how do you fix them?
Lazy loading a relation per item in a loop; fix with fetch joins, entity graphs, batching or DTO projections.
How do you handle two users editing the same record?
Optimistic locking with a version field, returning 409 so the client can refetch and merge or retry.
Why might an endpoint be fast in dev and slow in production?
Larger data volumes, missing indexes, N+1 behaviour, cold caches and concurrent load.

Build, deploy and operate Java services

“How are Java services built and deployed? Maven versus Gradle, JAR packaging, Docker images, JVM options, logging, monitoring, microservice patterns and how a Java release pipeline compares with a frontend one.”

Say this first (30 seconds)

“Java projects are built with Maven or Gradle, which resolve dependencies from repositories, compile, run tests and package an executable JAR containing the application and an embedded server. In CI the pipeline runs unit and integration tests, static analysis such as SonarQube, builds a container image, scans it and deploys to Kubernetes or a cloud service, much like a frontend pipeline. Operationally I would expect health endpoints from Spring Actuator, structured logs through SLF4J and Logback, metrics via Micrometer, and JVM settings for heap and garbage collection tuned to the container. Many systems are split into microservices behind an API gateway, communicating over REST or messaging, which affects how the frontend calls the backend and handles partial failures.”

Details interviewers probe

  • Build tools: Maven (XML pom.xml, convention over configuration, lifecycle phases compile, test, package, verify) and Gradle (Groovy/Kotlin DSL, faster incremental builds, flexible); dependency management with BOMs and version catalogues; repositories (Maven Central, Artifactory, Nexus); multi-module projects similar to monorepos (A3).
  • Packaging: Spring Boot “fat” JAR (java -jar app.jar) with an embedded Tomcat/Netty; layered JARs and Buildpacks or Jib create efficient container images without a Dockerfile; WAR deployment to application servers is legacy; GraalVM native images for fast startup (JV1).
  • JVM options in containers: -XX:MaxRAMPercentage, -Xmx, GC choice (-XX:+UseG1GC, ZGC), heap dumps on OOM (-XX:+HeapDumpOnOutOfMemoryError), and JFR flags; set requests and limits in Kubernetes accordingly; monitor GC pauses and heap usage (A9).
  • Logging: SLF4J API with Logback or Log4j2; JSON logs for aggregation; MDC (mapped diagnostic context) adds request and trace ids to every line; log levels per package; the Log4Shell vulnerability (2021) shows the need to patch logging libraries quickly.
  • Monitoring: Spring Boot Actuator (/actuator/health, /metrics, /prometheus), Micrometer metrics, OpenTelemetry tracing, APM agents, JMX; dashboards for latency, error rate, GC and thread pools (A10, D11).
  • Quality tooling: JUnit 5, Mockito, AssertJ, Testcontainers, JaCoCo coverage, SonarQube for smells and security hotspots, Checkstyle/SpotBugs, ArchUnit for architecture rules, OWASP Dependency-Check or Snyk for vulnerabilities.
  • Microservices and gateways: Spring Cloud Gateway, Kong, API Gateway (AWS) for routing, auth and rate limits; service discovery in Kubernetes via DNS; resilience with Resilience4j (circuit breaker, retry, bulkhead, rate limiter); distributed tracing across services; saga and outbox patterns for consistency (D10, A11).
  • Configuration and secrets: Spring profiles, ConfigMaps and Secrets in Kubernetes, vault integrations; never commit credentials; feature toggles through flags (A7).
  • Release and compatibility: backward-compatible API changes, versioned endpoints, deprecation notices, database migrations coordinated with application versions, rolling and canary deployments (A6).
  • Java versions and upgrades: upgrade LTS to LTS (for example 11 → 17 → 21), update Spring Boot major versions (Boot 3 requires Java 17 and the jakarta.* namespace migration), use OpenRewrite recipes for automated upgrades; security patch cadence for JDK and libraries.
  • Legacy realities: many enterprise systems still run Java 8/11, WAR files on application servers (WebLogic, JBoss/WildFly), SOAP/XML services and monoliths; the frontend lead often integrates with these through adapters or a BFF.
  • Performance characteristics: high throughput after warm-up, higher memory use than Node, slower cold start (mitigated by native images or CRaC); autoscaling should consider warm-up time.

Traps

  • Assuming Java services start as quickly as Node services when planning autoscaling.
  • Deploying with default JVM memory settings in containers and getting OOM kills.
  • Skipping database migration coordination in rolling deployments.
  • Leaving outdated logging or framework libraries unpatched.
  • Treating microservices as free: every hop adds latency and failure modes.

Likely follow-ups

Maven or Gradle?
Maven is standard and declarative; Gradle is more flexible and faster for large builds; both are widely used and either is fine.
What is a fat JAR?
An executable archive including the app, its dependencies and an embedded server, started with java -jar.
How does an API gateway help the frontend?
It provides a single entry point with authentication, routing, aggregation and rate limiting across backend services.
Why might a new Java instance be slow at first?
Cold JIT and cold caches; warm-up before sending full traffic or use readiness checks and gradual rollout.

Working with a Java team as a frontend lead

“How do you collaborate effectively with Java backend engineers? How do you negotiate API contracts, handle errors and versioning, debug cross-team issues, and decide between consuming Java services directly or through a BFF?”

Say this first (30 seconds)

“Effective collaboration starts with a shared contract. I agree the API in OpenAPI before or alongside implementation, with examples, error shapes, pagination, nullability and date and ID formats spelled out, and I use mock servers and generated clients so frontend and backend work in parallel. I set up contract tests so breaking changes are caught in CI, agree on versioning and deprecation, and align on non-functional needs such as latency budgets and payload sizes. When problems occur I debug together using correlation ids across logs and traces and reproduce with real requests. If backend APIs are too granular or shaped for other consumers, I propose a backend-for-frontend or an aggregation endpoint. I treat the Java team as partners and learn enough of their stack to ask the right questions.”

Details interviewers probe

  • Contract-first versus code-first: contract-first designs the OpenAPI spec first and generates server stubs and client types; code-first generates the spec from annotations (springdoc). Either way, the spec is reviewed in pull requests and published; frontends generate types (openapi-typescript) and mocks so work is parallel (E9, T11).
  • Backend-for-frontend: when microservices expose fine-grained or domain-oriented APIs, a BFF (Node or Java) aggregates and shapes responses for the UI, hides tokens, handles sessions and reduces round trips; weigh the cost of another service and who owns it; sometimes a gateway aggregation endpoint suffices (A1).
  • Error handling alignment: agree on a standard error body (problem details with code, message, field errors, trace id), distinguish validation (400/422), authentication (401), authorisation (403), not found (404), conflict (409), rate limit (429) and server errors (5xx), and map codes to UI messages; avoid leaking technical messages.
  • Versioning and change management: backward-compatible additions by default; breaking changes via new versions with a deprecation window; changelog and notifications; feature flags to coordinate rollouts; contract tests (Pact) verify consumers still pass before releases.
  • Environments and test data: stable staging with realistic data, shared seeded datasets, sandbox integrations, and the ability to reset; mocks or MSW for UI development and tests; avoid blocking on backend availability (R12).
  • Performance conversations: share frontend needs (p95 latency per endpoint, payload size, pagination size), request field selection or compact representations, ask for ETags and caching headers, and collaborate on N+1 and index fixes using traces (JV7, P3).
  • Security collaboration: agree on authentication flows (OAuth2/OIDC, cookie sessions with CSRF, token refresh), CORS allowlists, input validation on both sides, authorisation on the server, and secret handling; participate in threat modelling (P8, P11).
  • Learning enough Java: read controllers, DTOs and OpenAPI; understand Spring annotations and the request lifecycle; know how to run the service locally in Docker; read logs and traces; ask informed questions (“is this lazy-loaded?”, “which transaction covers this?”).
  • Building credibility and rapport: deliver precise bug reports (request, response, expected, trace id), propose concrete contract changes with examples, respect backend constraints, share frontend context and priorities, and celebrate joint wins.
  • Handling friction: misaligned priorities, “works on my machine” disputes, blame about who caused a bug; address with shared dashboards, joint post-incident reviews, and clear ownership boundaries; escalate cross-team blockers early with data.
  • Interview angle: show you can work across the stack without pretending to be a Java expert: explain how you align on contracts, ask good questions, debug across layers and reduce integration risk.
  • Career and architecture view: understand trade-offs between Java and Node for the BFF and services, and where each shines (heavy domain logic and transactions in Java; UI-oriented aggregation in Node/TypeScript) (D12).
  • Checklist for kicking off a feature with the backend: user story and acceptance criteria, API draft in OpenAPI, error cases, data volume expectations, performance targets, security considerations, test data plan, feature flag plan, and release coordination.

Traps

  • Waiting for the backend to finish before starting UI work, instead of building against a mock of the agreed contract.
  • Undocumented or inconsistently shaped errors that force brittle UI parsing.
  • Changing a response shape without notice or contract tests.
  • Treating backend teams as a black box and filing vague “it is slow” bugs.
  • Building heavy client-side aggregation when a BFF or endpoint would be simpler and faster.

Likely follow-ups

How do you start a feature when the API does not exist yet?
Agree an OpenAPI draft with the backend, generate types and a mock, and build and test the UI against it while the real implementation is developed.
When would you propose a BFF?
When the UI needs aggregated or reshaped data from several services, when tokens and sessions should be handled server-side, or when mobile and web need different payloads.
How do you protect against breaking API changes?
Contract tests in both pipelines, a deprecation policy, versioned endpoints and generated types that fail the build on incompatible changes.
How do you report a backend issue effectively?
Provide the exact request and response, timestamp, environment, trace id, expected versus actual behaviour, and the impact.

How to answer Java questions as a frontend lead

  • Be candid: you are a frontend specialist who works well with Java teams. Show you understand the runtime, the framework layers and the contract details that affect the UI.
  • Map concepts to what you know: Spring DI to Angular DI and NestJS, streams to array methods, CompletableFuture to promises, DTOs to API types, Maven or Gradle to npm scripts.

  • Mention the failure modes you have watched for: N+1 queries, slow warm-up, thread pool exhaustion, concurrent updates, cascading failures between microservices.
  • The interview is theoretical: expect “how would you work with”, “what would you check” and “what are the trade-offs”, not Java coding.
