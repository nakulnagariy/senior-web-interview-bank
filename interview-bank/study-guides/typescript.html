How TypeScript works

“What is TypeScript and why use it? What happens at compile time versus run time? What is structural typing? Is TypeScript sound?”

Say this first (30 seconds)

“TypeScript is JavaScript with a static type system. The compiler checks types, then erases them and emits plain JavaScript, so there is no type information at run time and no performance cost. The type system is structural: compatibility depends on the shape of a value, not on its declared name, so two unrelated types with the same members are interchangeable. It is intentionally not fully sound; it favours usability, so there are escape hatches such as any and assertions. The value is catching mistakes before they ship, safer refactoring across a large codebase, editor tooling such as autocomplete and rename, and types as living documentation. It does not validate data at run time, which is why I still validate at system boundaries.”

Details interviewers probe

  • Superset of JavaScript: any valid JavaScript is valid TypeScript syntax (types may be inferred as any or error under strict settings). TypeScript adds a type layer and a few syntax extensions (enums, parameter properties, decorators, namespaces) that need transformation.
  • Type inference: you do not annotate everything. The compiler infers from initialisers, return values, contextual typing (a callback’s parameter types come from where it is passed), and control-flow analysis. Annotate public boundaries (exported functions, props, API responses) and let inference handle locals.
  • Gradual typing: you can adopt it file by file (T13). any opts out of checking for a value.
  • Structural typing consequences: a function accepting { id: string } accepts any object with an id: string, including bigger ones. Excess properties are only flagged on fresh object literals (T3). To get nominal-like safety use branded types (T11).
  • Soundness: a sound type system never lets a value of the wrong type through. TypeScript deliberately is not sound; known holes include any, type assertions, array and method-parameter variance, index access without noUncheckedIndexedAccess, and mutation through aliases (T12). Its goal is to be useful and catch most bugs, not to prove correctness.
  • Erasure implications: no instanceof against an interface, no overload by type at run time, no reflection on generics. Use discriminant fields, type guards and schemas instead. Enums and decorators are the exceptions that emit code.
  • Tooling: the compiler API powers the language server (autocomplete, go to definition, safe rename, auto-imports), which is a main productivity benefit, plus typescript-eslint for type-aware lint rules.
  • Trade-offs: build and config complexity, learning curve, slower builds on huge projects, time spent on types for dynamic code, and types that drift from reality when they describe external data. The payoff grows with team size and codebase lifetime.
  • Compiler evolution: modern versions added satisfies, const type parameters, standard decorators, and using. A native (Go) port of the compiler for much faster builds has been announced verify current status.

Traps

  • “TypeScript checks types at run time.” It does not; data from the network is whatever it is.
  • “TypeScript makes code faster.” It has no run-time effect; it prevents bugs.
  • Claiming it is sound or “type-safe” without qualification.
  • Treating TypeScript as Java-style nominal typing and reaching for classes and instanceof everywhere.
  • Saying Babel/esbuild “compile TypeScript”. They strip types; they do not check them.

Likely follow-ups

Why use TypeScript on a team?
Contracts between modules are checked, refactors are safer, new developers learn the code by reading types, and many bugs (undefined access, wrong arguments, missing cases) are caught before review.
How do you type data from an API?
Declare the type, but verify it at the boundary with a schema validator (T11); the type alone is a promise, not a check.
What does tsc emit for older browsers?
Controlled by target and lib. In most apps a bundler or Babel handles transpilation and polyfills; tsc is used for checking and for emitting libraries and .d.ts files.
What is the difference between TypeScript and Flow?
Both add static types; TypeScript won on ecosystem, tooling and community, and nearly all libraries ship TypeScript types.
T2Added

Basic and special types

“What is the difference between any, unknown and never? What are literal types, tuples and enums? When do you use as, ! and satisfies?”

Say this first (30 seconds)

“any turns off type checking for a value and spreads silently, so I avoid it. unknown is the type-safe top type: it accepts anything, but I must narrow it before using it, so it is what I use for data I do not control. never is the bottom type: no value exists, used for functions that never return and for exhaustiveness checks. void is a function that returns nothing useful. Literal types such as 'GET' | 'POST' narrow a type to exact values, and as const freezes an object into literal readonly types. For enums I prefer a union of string literals or an as const object. An assertion with as overrides the compiler and can lie, so I prefer narrowing; satisfies validates a value against a type while keeping its precise inferred type.”

Details interviewers probe

  • any versus unknown: with any you can call it, index it and assign it anywhere with no error. With unknown you can assign anything to it but cannot use it until you narrow with typeof, instanceof, a guard or a schema. Use unknown for catch variables (useUnknownInCatchVariables), JSON.parse results, message payloads and generic “I do not know yet” values.
  • never: the return type of functions that throw or loop forever; the type of an impossible branch after exhaustive narrowing, which gives you compile-time exhaustiveness (T4); the result of impossible intersections such as string & number.
  • void versus undefined: void on a function type means “ignore the return value”, so a callback typed () => void may legally return something. undefined is an actual value type.
  • null and undefined: with strictNullChecks (part of strict) they are distinct types that must be handled. Always enable it. Optional chaining ?. and nullish coalescing ?? are the idioms.
  • Primitive wrapper types: use string, number, boolean; never String, Number, Object. object means any non-primitive; {} means any non-null value (including primitives), which surprises people.
  • Literal types and widening: const x = 'a' has type 'a'; let x = 'a' widens to string. Object properties widen too unless you write as const. as const makes everything deeply readonly with literal types, and is the standard way to define fixed lists: const ROLES = ['admin','user'] as const; type Role = typeof ROLES[number];
  • Union and intersection: A | B is “either” (you can use only what both share until narrowed); A & B is “both” (combines members; conflicting property types collapse to never).
  • Tuples: fixed-length arrays with positional types, optional and rest elements, and labels: type Range = [start: number, end?: number]. Used for useState-like returns. readonly tuples for constants.
  • Enums: numeric enums have a reverse mapping and accept any number (loose); string enums are nominal and emit run-time objects; const enum is inlined but problematic with isolatedModules and libraries. Many teams prefer type Status = 'idle' | 'loading' or an as const object plus a derived union, which emit nothing, work with erasable-syntax-only tooling, and interoperate easily with JSON.
  • Assertions: value as T tells the compiler “trust me”; it only allows sufficiently overlapping types (otherwise as unknown as T, a red flag). x! asserts non-null. Both are unchecked, so prefer narrowing, defaults, or guards; use assertions at proven boundaries and comment why.
  • satisfies: const config = { port: 3000, mode: 'dev' } satisfies Config checks the value against Config (catching typos and wrong values) but keeps the narrow inferred type, so config.mode is 'dev', not string. Annotation (: Config) widens; assertion (as Config) skips checking. TypeScript 4.9 verify.
  • Definite assignment: let x!: number and class field ! tell the compiler a value will be set later; use sparingly.

Traps

  • Using any “temporarily” and leaving it. It disables checks for everything it flows into.
  • Saying unknown and any are the same because both accept anything.
  • Using Object, Function or {} as general-purpose types; they are much looser than they look.
  • Assuming enums are free. They add run-time code and numeric enums accept arbitrary numbers.
  • Using as to silence an error, which hides a real mismatch.

Likely follow-ups

How do you get a union type from an array of values?
Declare the array as const and use typeof ARR[number].
Why use unknown in a catch clause?
Anything can be thrown, not only Error. You narrow with instanceof Error before reading message.
What is the difference between readonly and const?
const prevents rebinding a variable; readonly is a compile-time modifier on properties and arrays. Neither freezes at run time.
When is the non-null assertion acceptable?
When an invariant guarantees presence that the compiler cannot see (for example, a DOM element your template always renders), ideally with a runtime check or a comment.
T3Added

Objects: type versus interface

“What is the difference between type and interface? When do you use each? What are optional, readonly and index-signature properties, and what are excess property checks?”

Say this first (30 seconds)

“Both describe the shape of an object and are interchangeable in most cases. An interface can be extended with extends and can be reopened and merged by declaring it again, which is how libraries are augmented. A type alias can name anything, not just objects: unions, tuples, primitives, mapped and conditional types, but it cannot be merged. My rule is to use interface for public object shapes that others may extend, and type for unions, utility compositions and everything else, and to be consistent within the codebase. Excess property checking flags unknown properties only on fresh object literals, which is a common surprise because the type system is structural.”

Details interviewers probe

  • Optional versus | undefined: a?: string may be missing or undefined; a: string | undefined must be present. With exactOptionalPropertyTypes the difference is enforced.
  • readonly: shallow and compile-time only: it does not freeze the object, and a readonly-typed object can still be mutated through a mutable alias. Readonly<T> and ReadonlyArray<T> help express intent (props and state treated as immutable).
  • Index signatures: { [key: string]: number } or Record<string, number> for dictionaries. All known properties must match the value type. With noUncheckedIndexedAccess, reads become number | undefined, which is safer. Prefer Map when keys are dynamic.
  • Function types: type Fn = (a: number) => string or an interface with a call signature; add properties to model callable objects.
  • Extending and combining: interface B extends A, type B = A & { extra: string }; use Omit first if you need to change a property’s type.
  • Implements: class X implements Y only checks that X conforms; it does not inherit anything or change X’s type.
  • Excess property checks catch typos in options objects ({ colour: 'red' }). To allow extras intentionally add an index signature or build the object in a variable first.
  • Weak type detection: assigning an object with no matching properties to a type whose properties are all optional is an error.
  • Global augmentation: declare global { interface Window { … } } inside a module file; for libraries use declare module 'lib' { … } (T9).

Traps

  • “Interfaces are for objects, types are for everything; they are completely different.” They overlap heavily; know the real differences (merging, unions, mapped types).
  • Believing readonly makes data immutable at run time.
  • Expecting the excess property check to run on any assignment.
  • Building huge intersections of intersections, which slow the compiler and produce unreadable errors.
  • Typing a dictionary as object or {} and then being unable to index it.

Likely follow-ups

Why might you prefer interface in a library?
Consumers can augment it through declaration merging, and it gives clearer errors and better caching.
Why does an object with extra props pass in one place and fail in another?
Fresh-literal excess property checking applies only to direct literal assignment, not to variables.
How do you type an object whose keys are dynamic but values are fixed?
Record<string, V>, an index signature, or a Map<string, V>.
Can a class implement a union type?
No, only object types with statically known members.

Narrowing and type guards

“What is type narrowing? Explain type guards, discriminated unions, user-defined guards and how you make a switch exhaustive.”

Say this first (30 seconds)

“Narrowing is how TypeScript refines a broad type, such as a union, to a more specific one inside a branch, using control-flow analysis. The built-in guards are typeof, instanceof, in, equality and truthiness checks. For objects the best pattern is a discriminated union: each member has a literal tag such as kind, so a switch on the tag narrows to the exact member. When built-in checks are not enough I write a user-defined type guard that returns x is T, or an assertion function. To guarantee I handle every case, I assign the leftover value to never in the default branch, so adding a new variant produces a compile error where it is unhandled.”

Details interviewers probe

  • Built-in guards: typeof x === 'string' (primitives; typeof null is 'object'), instanceof (classes, not interfaces), 'prop' in obj (checks presence of a property to pick a union member), equality narrowing, truthiness narrowing (beware 0 and ''), Array.isArray.
  • Discriminated unions: a shared literal-typed property (the discriminant) such as kind, type, or status. Ideal for Redux actions, useReducer, API results ({ status: 'ok', data } | { status: 'error', error }), state machines and AST nodes. It beats optional-property bags such as { data?: T; error?: E; loading: boolean }, which allow impossible states.
  • User-defined type guards: function isUser(x: unknown): x is User { … }. The compiler trusts the predicate, so it is only as safe as your check; a wrong body is an unchecked lie. Inferred type predicates arrive in newer versions verify (5.5).
  • Assertion functions: function assert(c: unknown, msg?: string): asserts c and asserts x is T narrow the value after the call (used by testing and validation libraries).
  • Exhaustiveness: assign to never in a default branch, or write an assertNever(x: never): never helper that also throws at run time. Alternatively use a Record<Union, …> lookup, which forces a key for every variant, or the satisfies operator.
  • Narrowing with generics and unknown: validate unknown input step by step, or hand it to a schema library (T11) that returns a typed result.
  • Limits: narrowing is lost across function boundaries (a guard on a property does not persist into a callback if it may change), for let variables reassigned later, and on mutable property access after a function call. Copy to a const first.
  • Branching on type at run time is impossible for interfaces or generics because types are erased, so models carry a run-time discriminant.
  • Optional chaining and narrowing: a?.b yields undefined when a is nullish; after if (a?.b) the compiler knows a is defined.

Traps

  • Writing a type guard whose body does not actually verify the shape: return true or only checking one field. It turns a lie into compiler-approved code.
  • Modelling variants with many optional fields and booleans instead of a tagged union.
  • Forgetting never exhaustiveness, so a new variant silently falls through.
  • Using typeof x === 'object' without excluding null.
  • Relying on narrowing after the variable is captured by a closure and reassigned.

Likely follow-ups

How would you type an async request state?
A discriminated union: idle | loading | { status: 'success'; data: T } | { status: 'error'; error: Error }, so data exists only in the success branch.
What is the difference between a type guard and an assertion function?
A guard returns a boolean and narrows in the branch; an assertion function throws on failure and narrows for the rest of the scope.
How does in narrowing work?
'swim' in animal narrows to the union members that have (or may have) that property.
Why is exhaustiveness valuable in a lead’s codebase?
It turns “find every place this enum is used” into a compiler error list when requirements change.

Generics

“What are generics and why use them? Explain constraints, defaults, inference and keyof. How would you type a reusable function or a generic React component?”

Say this first (30 seconds)

“Generics are type parameters: they let a function, type or class work with many types while keeping the relationship between input and output types, instead of falling back to any. For example, first<T>(items: T[]): T | undefined returns the same element type it receives. Usually the compiler infers T from the arguments, so callers do not write it. I add constraints with extends when the function needs certain members, such as T extends { id: string }, and defaults when a parameter is usually the same. keyof and indexed access types let me write type-safe property accessors. The rule I follow is that a type parameter should appear at least twice, otherwise it is not relating anything and a plain type would do.”

Details interviewers probe

  • Where generics appear: functions, type aliases and interfaces (ApiResponse<T>), classes (Repository<T>), and built-ins (Array<T>, Promise<T>, Map<K, V>).
  • Inference: the compiler infers from arguments, from the return position (contextual), and from defaults. If it cannot infer, it falls back to the constraint or unknown. Specify type arguments explicitly only when inference fails.
  • Constraints: T extends U limits what can be passed; multiple parameters can reference each other (K extends keyof T). You can constrain to a shape ({ length: number }), a union, or a function type.
  • Defaults: type State<T = unknown>. Required parameters must precede defaulted ones.
  • Generic constraints with const: function f<const T>(x: T) infers literal, readonly types without the caller writing as const verify (5.0). NoInfer<T> stops a parameter from contributing to inference verify (5.4).
  • Generic components and hooks: function Table<T>({ rows, render }: { rows: T[]; render: (row: T) => ReactNode }). In .tsx arrow functions write <T,> or <T extends unknown> to avoid being parsed as JSX. A custom hook useFetch<T>(url): { data: T | null } shows the caller’s type, but remember the type is not validated at run time (T11).
  • Generic classes and variance: a Box<Dog> is usually assignable to Box<Animal> if T is only read (covariant), not if it is also written. Variance annotations in and out exist for explicitness and performance verify (4.7).
  • Avoid over-generalising: a generic with one use of T (f<T>(x: T): void) adds nothing. Too many type parameters make signatures unreadable and slow type checking; prefer a few well-named ones (TItem, TKey) or an options type.
  • Generics versus overloads versus unions: use generics when output depends on input type; overloads (T8) when distinct signatures differ in arity or specific mappings; unions when the function treats alternatives uniformly.
  • Type-safe patterns built on generics: typed event emitters (on<K extends keyof Events>(name: K, cb: (p: Events[K]) => void)), a typed fetch wrapper, repository and store factories, builder APIs, Result<T, E>.

Traps

  • Writing function f<T>(x: T): T and then casting inside with as any. If you need a cast, the signature probably lies.
  • Explaining generics as “just a way to avoid any” without mentioning that they preserve relationships between types.
  • Forgetting the <T,> trick in .tsx files.
  • Returning T from a function that actually fetches unvalidated data. It looks safe and is not.
  • Giant generic signatures that no one can read; prefer simpler, concrete types for application code.

Likely follow-ups

What does T extends keyof U mean?
T must be one of the property names of U; it is the standard way to accept a key safely.
How do you type a function that returns the same type as its argument but wrapped in a Promise?
function wrap<T>(x: T): Promise<T> or, for async input, Awaited<T>.
Generic default versus constraint?
A constraint restricts what is allowed; a default supplies a type when none is given or inferred. They can be combined.
How would you type a data table component?
Generic over the row type, columns keyed by keyof Row, render callbacks receiving typed values.
T6Added

Utility types

“Which built-in utility types do you use? Explain Partial, Pick, Omit, Record, Exclude, ReturnType and Awaited. How would you derive types instead of duplicating them?”

Say this first (30 seconds)

“Utility types are generic helpers built into TypeScript that derive new types from existing ones, so I define a shape once and derive the variants. For object shapes: Partial makes everything optional, Required the opposite, Readonly freezes properties, Pick and Omit select or drop keys, and Record builds a dictionary. For unions: Exclude, Extract and NonNullable. For functions: ReturnType, Parameters, and Awaited to unwrap promises. Deriving types keeps one source of truth: for example, a form’s update payload is Partial<Omit<User, 'id'>> and an action type can come from typeof a value.”

Details interviewers probe

  • Derive, do not duplicate: type Props = ComponentProps<typeof Button>, type State = ReturnType<typeof store.getState>, type Role = typeof ROLES[number], type Keys = keyof typeof config. When the source changes, derived types follow.
  • Omit is not distributive over unions and does not check that keys exist (its key parameter is keyof any), so a typo in the key silently omits nothing. Pick does check. A stricter custom StrictOmit is common.
  • Partial is shallow: nested objects stay required. A DeepPartial needs a recursive mapped type (T7).
  • Record with a union key forces completeness (every key must be present), which makes it an exhaustiveness tool for configuration maps. With string keys it is just a dictionary.
  • Practical combos: Partial<Omit<User, 'id'>> for updates; Pick<User, 'id' | 'name'> for list items; Required<Pick<Options, 'a' | 'b'>> to make some options mandatory; Readonly<Record<…>> for constant lookup tables.
  • Overuse: deeply nested utility chains become unreadable; name intermediate types and add a short comment.

Traps

  • Believing Omit validates keys. Use Pick or a strict variant when typos matter.
  • Expecting Partial or Readonly to be deep.
  • Reaching for utility types when a separate small interface would be clearer.
  • Duplicating an interface and slightly editing the copy instead of deriving, so types drift apart.

Likely follow-ups

Difference between Pick and Omit?
Pick keeps listed keys, Omit removes them. Prefer the one with the shorter list; Pick additionally validates that the keys exist.
How do you get the type of an array’s items?
T[number] for an array type T, or (typeof arr)[number] for a value.
How do you get the type of a function’s resolved value?
Awaited<ReturnType<typeof fn>>.
Write Partial yourself in words.
A mapped type over keyof T that adds ? to every property and keeps the value type: { [K in keyof T]?: T[K] }.
T7Added

Mapped, conditional and template literal types

“Explain mapped types, conditional types, infer and template literal types. What is a distributive conditional type? When is advanced type-level code worth it?”

Say this first (30 seconds)

“These are the building blocks of type-level programming. A mapped type iterates over keys to create a new object type, { [K in keyof T]: … }, and can add or remove modifiers and rename keys. A conditional type chooses between two types, T extends U ? X : Y, and with infer it can extract a type from within another, such as a function’s return type. Conditional types distribute over unions when the checked type is a naked type parameter. Template literal types build string types, like on${Capitalize<K>}, so event names and route strings can be type-checked. I use them to build well-typed library APIs and helpers, but in application code I keep types simple, because clever types are expensive to read, slow to compile and hard to debug.”

Details interviewers probe

  • Mapped types: { [K in keyof T]: Transform<T[K]> } is homomorphic (preserves optional and readonly modifiers of T). -? removes optionality, +readonly adds it, and as renames or filters keys (as never drops a key). They power Partial, Readonly, Pick, Record.
  • Conditional types: evaluated when the type is known; deferred while generic. The extends check is assignability, not equality. Branches can be nested and recursive.
  • Distribution: happens only when the checked type is a bare type parameter. never distributes to never (empty union), a known gotcha; wrap in a tuple to avoid it.
  • infer: introduces a type variable inside the extends clause: element type of an array (T extends (infer U)[]), Promise payload, first parameter, props of a component. Constraints on infer (infer U extends string) exist verify (4.7).
  • Template literal types combine with unions to produce the Cartesian product, and with infer to parse strings: extract route parameters from '/users/:id' to type a router’s params. Beware union explosion in big combinations.
  • Recursive types: type Json = string | number | boolean | null | Json[] | { [k: string]: Json }; DeepPartial, DeepReadonly, path types ('a.b.c'). Recursion depth is limited, and deep recursion is slow.
  • typeof, keyof, indexed access, as const: the everyday toolkit to derive types from values: type Action = ReturnType<typeof actions[keyof typeof actions]>.
  • Real examples: typed Object.keys wrapper, typed event emitters, form libraries inferring field names from a schema, ORM query builders, tRPC and Zod inference, typed i18n keys, styled-system props.
  • When it is worth it: in shared libraries and design-system code used by many teams, where a good type prevents widespread misuse. Avoid in feature code: prefer simple explicit types, comments and runtime checks. Type-level code is code: it needs tests (T13), naming and a maintainer.
  • Costs: slow compile and editor latency, unreadable error messages, brittle behaviour across TypeScript versions. If a type needs a PhD to read, simplify the design.

Traps

  • Forgetting distribution and being surprised that a conditional type returns a union of results.
  • Using extends thinking it means equality; string extends 'a' is false but 'a' extends string is true.
  • Over-engineering application types for the sake of cleverness.
  • Skipping tests for type utilities, then breaking consumers on a version upgrade.

Likely follow-ups

How would you implement Pick?
{ [P in K]: T[P] } where K extends keyof T.
How do you extract the element type of an array type?
T extends (infer U)[] ? U : never, or T[number].
How would you type route params from a path string?
A recursive template literal type that splits on / and maps segments starting with : to keys. Mention the compile-time cost and use it only in the router library.
What does keyof typeof obj give?
The union of the object value’s property names, derived from the value so it cannot drift.
T8Added

Functions, overloads, classes and decorators

“How do you type functions, optional and rest parameters, this, and overloads? How do TypeScript classes differ from JavaScript classes? What are access modifiers, abstract classes and decorators?”

Say this first (30 seconds)

“Functions are typed by their parameters and return type; I annotate exported functions and let inference handle the rest. Optional, default and rest parameters have their own syntax, and a this parameter can declare what this must be. Overloads let one function expose several call signatures with different parameter and return types; callers see only the overload signatures, not the implementation signature. TypeScript classes add public, protected and private (compile-time only), readonly, parameter properties, abstract classes and override; for true privacy at run time use JavaScript’s #private fields. Decorators are functions that annotate or wrap classes and members; the standard version arrived in TypeScript 5, while Angular still uses the older experimental form.”

Details interviewers probe

  • Function typing: optional (x?: T, must come after required), default (x = 1, type inferred), rest (...args: number[] or a tuple), return type inference versus an explicit annotation (explicit on exported functions improves errors and speed). (a: number) => string is a function type; void return means “ignored”.
  • Contextual typing: callback parameter types are inferred from the expected function type, so inline arrow functions need no annotations.
  • Parameter bivariance: with strictFunctionTypes, function-type parameters are checked contravariantly, but method shorthand declarations remain bivariant, which is a known unsoundness (T12).
  • Overload design: overloads give precise mappings ((el: 'a'): HTMLAnchorElement); a conditional or generic return type is an alternative. Callers do not see the implementation signature. Do not write overloads that differ only in trailing optional parameters.
  • Type predicates and assertion signatures are function return types too (T4).
  • TypeScript class features: property declarations, access modifiers, parameter properties, readonly, abstract, override (with noImplicitOverride to catch accidental shadowing), index signatures, implements for interface conformance, generics. Classes are both a value and a type.
  • Class fields and run time: with useDefineForClassFields (default for modern targets) fields use define semantics, which affects initialisation order with inheritance and parameter properties. strictPropertyInitialization requires fields to be assigned in the constructor or marked !.
  • Interfaces versus abstract classes: interfaces are erased and carry no code; abstract classes can share implementation and exist at run time (usable with instanceof). Prefer composition and functions in frontend code; classes mainly appear in Angular, NestJS and domain models.
  • Decorators: TypeScript 5 supports the standard (TC39 stage 3) decorators; experimentalDecorators enables the older form used by Angular, NestJS and TypeORM (with emitDecoratorMetadata). They are different, incompatible APIs verify the framework’s current requirement. Use cases: dependency injection, validation metadata, logging, routing.
  • Other non-erasable syntax: enums, namespaces, parameter properties and (legacy) decorators generate code. erasableSyntaxOnly and Node’s type-stripping mode reject them verify (5.8, Node 22.6+ and later).
  • this types: a method can return this for fluent APIs, which keeps subclass types.
  • Explicit resource management: using and await using with Symbol.dispose for cleanup verify (5.2).

Traps

  • Believing private prevents access at run time. It does not; use # for real privacy.
  • Writing many overloads when a generic or union signature expresses the same thing.
  • Calling implements inheritance. It checks shape only.
  • Mixing the two decorator systems or assuming experimentalDecorators works with the standard syntax.
  • Using enums, namespaces or parameter properties in a project that must work with type stripping.

Likely follow-ups

Interface versus abstract class?
Interface: pure type, erased. Abstract class: type plus shared implementation and a run-time value.
What does override add?
With noImplicitOverride the compiler errors if you override without the keyword or the base member no longer exists, catching renames.
How do you type a function that accepts a callback with a variable number of arguments?
A generic over a tuple: function call<A extends unknown[], R>(fn: (...a: A) => R, ...a: A): R.
Why do some TypeScript features break with Babel or esbuild?
They transpile file by file; const enum, namespaces merging across files and decorator metadata need whole-program knowledge or special support.

Modules, declaration files and tsconfig

“How does TypeScript find types for a JavaScript library? What are .d.ts files and @types? Which tsconfig options matter, and what does strict include?”

Say this first (30 seconds)

“When I import a package, TypeScript resolves types in order: the package’s own bundled types from the types or exports fields, then @types/name from DefinitelyTyped, then any ambient declare module in my project; otherwise under noImplicitAny it is an error. Declaration files, .d.ts, contain only types and describe JavaScript that exists elsewhere. In tsconfig.json the key choices are strict: true, which turns on a family of checks including strictNullChecks and noImplicitAny; target and lib for emitted syntax and available APIs; module and moduleResolution to match the bundler or Node; and isolatedModules or verbatimModuleSyntax so every file can be transpiled alone. In large repos I use project references and an incremental build.”

Details interviewers probe

  • Declaration files: .d.ts has types only and no code. A library publishes them next to its JavaScript (tsc --declaration) so consumers get types. Ambient declarations (declare const, declare function, declare module 'x') describe things that exist at run time but were not written in TypeScript, such as a global injected by a script.
  • Global and module augmentation: in a module file, declare global { interface Window { analytics: Analytics } } adds a global; declare module 'express-serve-static-core' { interface Request { user?: User } } extends a library type. A file is a module if it has a top-level import or export; otherwise its declarations are global.
  • Typing an untyped library: check @types first; otherwise write a minimal declare module with only the functions you use, and contribute upstream if it is widely used. Prefer a typed alternative if one exists.
  • package.json and types: libraries use "types" and, for modern resolution, conditional "exports" with "types" first. Dual ESM/CJS packages need matching declarations (.d.mts/.d.cts); tools such as publint and arethetypeswrong check this.
  • strict bundle: strictNullChecks, noImplicitAny, strictFunctionTypes, strictBindCallApply, strictPropertyInitialization, noImplicitThis, alwaysStrict, useUnknownInCatchVariables. New projects should start strict. Extra flags worth knowing: noUncheckedIndexedAccess (index reads may be undefined), exactOptionalPropertyTypes, noImplicitOverride, noImplicitReturns, noFallthroughCasesInSwitch, noUnusedLocals/noUnusedParameters (often left to ESLint).
  • target and lib: target sets emitted syntax (ES2022 and so on); lib declares which built-in APIs exist for the type checker (DOM, ES2023). Setting lib does not add polyfills.
  • module and moduleResolution: bundler for apps built with Vite, webpack or esbuild (allows extensionless imports and exports); node16/nodenext for Node ESM and libraries (requires file extensions and honours package.json type); older node/classic are legacy verify option names for your TypeScript version.
  • Transpile-per-file safety: isolatedModules flags code that cannot be compiled without other files (re-exporting types without export type, const enum). verbatimModuleSyntax keeps imports and exports as written and forces import type for types, so emit is predictable. import type { X } is erased entirely.
  • Paths and baseUrl: paths only affects type checking; the bundler or runtime needs matching aliases (Vite resolve.alias, vite-tsconfig-paths, Jest moduleNameMapper, Node subpath imports).
  • Other options: jsx (react-jsx), esModuleInterop and allowSyntheticDefaultImports for CJS interop, resolveJsonModule, skipLibCheck (skips checking .d.ts in dependencies: faster, can hide conflicts), noEmit when a bundler emits, declaration/declarationMap for libraries, incremental and composite for speed.
  • types and typeRoots: by default every @types/* package is loaded globally; restrict with "types": ["node"] to avoid global type pollution (for example Jest globals appearing in app code).
  • Type-only imports and circularity: import type avoids run-time circular imports caused only by types.

Traps

  • Thinking lib or target polyfills missing APIs. They only tell the compiler what exists.
  • Setting paths and forgetting the bundler alias, so code type-checks and then fails at run time.
  • Leaving strict off “for now” in a new project.
  • Using skipLibCheck without understanding it hides type errors inside dependencies.
  • Installing @types/* with a version unrelated to the library version, causing mismatched APIs.

Likely follow-ups

Difference between tsc and the bundler?
tsc type-checks (and can emit); the bundler resolves, bundles and minifies. Many projects use only tsc --noEmit for checking.
How do you add a property to Express’s Request?
Module augmentation in a .d.ts included by tsconfig.
What does declare do?
It states that something exists without implementing it; it emits no code.
How do you speed up type checking on a large repo?
Project references with composite, incremental, skipLibCheck, narrower include, explicit return types on exported functions, and avoiding extreme type-level code (T13).

TypeScript with React

“How do you type React components, props, children, state, refs, events and context? How do you type generic components and custom hooks? Is React.FC still recommended?”

Say this first (30 seconds)

“I type props with an interface or type and annotate the parameter directly, function Button({ label }: ButtonProps), instead of React.FC, which adds little and used to inject implicit children. children is typed as React.ReactNode. State uses inference, with an explicit generic when the initial value does not show the full type, like useState<User | null>(null). For complex state I use useReducer with a discriminated union of actions. Events use types like React.ChangeEvent<HTMLInputElement>, and I extend native element props with React.ComponentProps<'button'>. Reusable components are generic, for example a list over T. Context needs a null default plus a hook that throws, so consumers get a non-null type.”

Details interviewers probe

  • Props: interface or type; optional props with ? and defaults via destructuring; callbacks typed precisely (onSelect: (id: string) => void). Avoid any in props and avoid Function.
  • React.FC: older versions added implicit children; it also hampers generics and defaults. The community default is to annotate the props parameter. Either works; be consistent and know why.
  • Children and return types: children: React.ReactNode (anything renderable); React.ReactElement or JSX.Element for a single element; PropsWithChildren is a helper. Do not annotate component return types unless needed.
  • Native element props: React.ComponentProps<'input'> or ComponentPropsWithoutRef plus Omit for conflicts, to wrap native elements in a design system and still accept aria-*, onClick and so on.
  • Refs: useRef<HTMLDivElement>(null) gives a read-only current that is null until mounted; mutable value refs use useRef<number>(0). React 19 passes ref as a regular prop; before that use forwardRef<El, Props> verify version.
  • Events: React.MouseEvent<HTMLButtonElement>, ChangeEvent, FormEvent, KeyboardEvent; the generic is the element type. e.currentTarget is typed to the element you attached to; e.target is a broader EventTarget and needs narrowing.
  • State and reducers: model state as a discriminated union (loading, success, error) and actions as a union with a type tag, so the reducer’s switch is exhaustive.
  • Context: createContext<Value | null>(null) with a useValue() hook that throws if the provider is missing, so consumers see a non-null type.
  • Custom hooks: generic over data (useQuery<TData>); return tuples with as const or typed tuples, or objects. Typing useFetch<T> does not validate T.
  • Polymorphic components: an as prop typed with a generic over ElementType and ComponentPropsWithoutRef<E>; powerful but heavy. Use it in design systems only.
  • HOCs: hard to type; hooks and composition replace most uses.
  • Frameworks: Next.js gives typed route handlers, Metadata and typed params; React Query infers data types from the query function; Redux Toolkit uses RootState/AppDispatch and typed hooks useAppSelector; forms libraries infer from a schema (React Hook Form with Zod).
  • as const and satisfies for configuration: route tables, theme tokens and variant maps keep literal types and are checked against a shape.
  • JSX typing: the jsx setting (react-jsx) and the JSX namespace; types come from @types/react (matching React’s major version).

Traps

  • Trusting useState<User> or useFetch<User> as validation of server data.
  • Passing a mutable-typed value where props are treated as immutable and then mutating it.
  • Using any for event handlers or refs instead of the right element type.
  • Declaring generic arrow components in .tsx without <T,>.
  • Over-engineering polymorphic prop types in application code.

Likely follow-ups

How do you type default props?
Use default parameter values in destructuring; the prop stays optional in the type and is non-optional inside.
How do you type children that must be a function?
children: (value: T) => ReactNode (a render-prop pattern).
How do you extend a button’s native props?
interface Props extends React.ComponentProps<'button'> { variant: Variant }, using Omit when overriding a native prop.
Typing Redux Toolkit?
Infer RootState and AppDispatch from the store, export typed hooks and use them everywhere.

Types at the boundary: validation and APIs

“TypeScript types disappear at run time, so how do you make sure data from an API or user input matches your types? What are branded types, zod, and end-to-end type safety?”

Say this first (30 seconds)

“Types are a compile-time promise, but network responses, localStorage, query strings and form input are untrusted at run time. At those boundaries I treat the value as unknown and validate it with a schema library such as Zod, Valibot or ArkType. The schema is the single source of truth: it validates at run time and I infer the static type from it, so they cannot drift. Inside the validated core I rely on types. For stronger domain safety I use branded types to separate values like UserId and OrderId that are both strings. For API contracts I prefer generating types from an OpenAPI or GraphQL schema or using tRPC, so client and server share a contract instead of hand-copying interfaces.”

Details interviewers probe

  • Why assertions are unsafe: as User on any or unknown data tells the compiler to believe you. A backend change then produces a run-time undefined far from the cause.
  • Schema libraries: Zod (popular, rich API), Valibot (smaller, tree-shakable), ArkType (type-syntax based), Yup, io-ts. Features: transforms, defaults, coercion, discriminated unions, error formatting, safeParse returning a result instead of throwing. Cost: bundle size and parse time on very large payloads; validate at the edge once.
  • Forms: React Hook Form plus a Zod resolver reuses the same schema for field validation and the submitted type. Share schemas between client and server where possible.
  • Environment variables and config: parse process.env or import.meta.env at startup with a schema so missing values fail early with a readable message.
  • Branded (opaque) types: type UserId = string & { readonly __brand: 'UserId' } with a constructor function that validates. They stop mixing up ids, validated and unvalidated strings, or currencies, at zero run-time cost. They are a convention, not enforced by the language.
  • Result types: type Result<T, E> = { ok: true; value: T } | { ok: false; error: E } for expected failures makes error handling explicit and exhaustive (J21 explains throwing versus returning).
  • End-to-end type safety options: OpenAPI with a generator (openapi-typescript, orval) for REST; GraphQL Code Generator for typed queries; tRPC when client and server are both TypeScript in a monorepo (types flow without a schema file); Protobuf/gRPC-web for contracts. Generated types still need run-time validation if the server is not fully trusted or versions can drift.
  • Data fetching libraries: TanStack Query infers the data type from the query function; pair the function with a parse step so the cache holds validated data.
  • Serialisation gaps: JSON turns Date into a string, drops undefined and functions, and cannot carry Map or bigint. A type claiming createdAt: Date for parsed JSON is wrong; schemas with transforms (z.coerce.date()) fix it.
  • Versioning: when APIs evolve, make new fields optional in the client schema, use unions for versioned payloads, and keep the contract in one place.
  • Security link: validation at the boundary also guards against malformed input and prototype pollution style payloads (J29), but the server must still validate and authorise.

Traps

  • Writing interfaces by hand to “match” an API and treating them as guaranteed.
  • Validating in many places instead of once at the boundary, or not at all.
  • Thinking a TypeScript type on a request body validates it on the server.
  • Declaring Date fields for JSON data without conversion.
  • Using a branded type but creating values with unchecked casts everywhere, which defeats it.

Likely follow-ups

How do you keep frontend types in sync with the backend?
Generate them from the API schema in CI, or share a schema package in a monorepo, and fail the build on drift. Add run-time parsing for external data.
What is the difference between a type guard and a schema parse?
A hand-written guard checks only what you coded; a schema is a declarative description that checks, reports errors and derives the type.
Where exactly do you validate in a React app?
In the fetch layer (or query function) before data enters state or the cache, and in form handlers before submission.
What do branded types cost?
No run-time cost, but a helper to create values; they add discipline rather than enforcement.

Soundness and common pitfalls

“Where does TypeScript’s type system lie? What are common mistakes teams make? Explain variance, any leakage and why Object.keys returns string[].”

Say this first (30 seconds)

“TypeScript is deliberately unsound in a few places so that common JavaScript patterns type-check. any disables checking and spreads to everything it touches. Assertions and non-null ! are unchecked claims. Arrays are covariant, so a Dog[] can be used as an Animal[] and then polluted with a cat. Method parameters are bivariant even under strict mode. Index access returns the element type without undefined unless noUncheckedIndexedAccess is on. readonly is shallow and compile-time only. And Object.keys returns string[] because objects can have more properties than their type says. My mitigations are strict flags, banning any with lint, schemas at boundaries, and treating every assertion as a code-review flag.”

Details interviewers probe

  • Variance in one minute: covariant positions (read, outputs) allow a subtype where a supertype is expected; contravariant positions (function parameters) work the other way. Correct typing makes function parameters contravariant. TypeScript does this for function-typed properties under strictFunctionTypes, but treats method-shorthand parameters bivariantly, and treats arrays as covariant, trading safety for convenience.
  • Object.keys and for…in: return string[]/string because a value of type { a: number } may have more keys at run time. Use a typed helper with a documented cast, Object.entries carefully, or Record/Map structures when keys are known.
  • Unchecked index access: enable noUncheckedIndexedAccess so arr[0] and dict[key] include undefined, then handle it. It forces many small checks but removes a common source of run-time errors.
  • Widening surprises: let x = 'a' is string; object literal properties are widened ({ mode: 'dev' } has mode: string) so passing it to a function expecting 'dev' | 'prod' fails. Use as const, satisfies or annotate.
  • Enum quirks: numeric enums accept any number; reverse mappings add noise; const enum can break across packages. Use unions of literals.
  • {}, object, Object: three different things; avoid {} and Object.
  • Optional versus undefined versus null: choose a convention (often undefined for “missing” and null for “explicitly empty”, mirroring APIs) and use ?? and ?..
  • Overly broad return types: returning any from helper functions or leaving inferred any[] in an array (const a = [] evolving types) hides problems.
  • Unsafe casts: as unknown as T is a loud red flag; @ts-ignore hides errors for the whole next line, while @ts-expect-error fails when the error disappears, so use it with a reason.
  • Type-only dependencies: mixing runtime and type imports creates cycles; use import type.
  • Mutation: TypeScript does not prevent mutation; immutability still needs discipline, readonly types, or libraries like Immer.
  • Promise pitfalls: a () => void callback accepts an async function, so a returned promise (and its errors) is ignored; the no-misused-promises and no-floating-promises lint rules catch this.
  • Team anti-patterns: using any to unblock a deadline and never returning, duplicating types by hand, giant “God” types, deeply clever generics, interface and type chosen randomly, ignoring compile errors in CI.

Traps

  • Claiming “TypeScript guarantees no run-time type errors”. It does not.
  • Answering the variance question with definitions only; give the array and callback examples.
  • Silencing errors with @ts-ignore or as any instead of fixing the type.
  • Believing readonly or as const freeze data at run time (use Object.freeze, J9, if needed).

Likely follow-ups

What is the difference between @ts-ignore and @ts-expect-error?
Both suppress the next line’s error. @ts-expect-error becomes an error itself once the underlying problem is fixed, so stale suppressions are found.
Why is strictFunctionTypes not enough for methods?
Methods are intentionally exempt, because common patterns such as Array<T> assignability rely on bivariance.
How do you stop any entering the codebase?
noImplicitAny, @typescript-eslint/no-explicit-any and the no-unsafe-* rules, wrapped JSON/fetch helpers returning unknown, and review.
Is as const the same as Object.freeze?
No: as const affects the types only; Object.freeze changes run-time behaviour (shallowly).

Adopting TypeScript at scale

“How would you migrate a large JavaScript codebase to TypeScript? How do you keep type checking fast, enforce quality in CI, and test types? How do you set conventions for a team?”

Say this first (30 seconds)

“I migrate incrementally, never with a big-bang rewrite. First allow JavaScript and TypeScript to coexist with allowJs, add TypeScript to the build and CI, and start with strict off or per-directory. Then type the most shared and highest-risk modules first: API clients, domain models, shared utilities. Tighten flags one at a time, until strict is on, and block new any with lint. I separate transpilation from checking: a fast tool such as esbuild or swc emits code, and tsc --noEmit runs in CI and the editor. For performance in large repos I use project references, incremental builds and avoid very expensive types. I add conventions, templates and a short guide, and I measure progress, for example the percentage of files migrated and the count of any.”

Details interviewers probe

  • Planning: inventory the codebase, choose a pilot team and module, agree on tsconfig and conventions, decide who reviews types, and set exit criteria. Communicate the benefit (fewer incidents, easier refactors) and the cost.
  • Tactics: allowJs/checkJs with // @ts-check and JSDoc to get value from JavaScript files without renaming; automated codemods (ts-migrate, jscodeshift) to rename and insert temporary suppressions; @ts-expect-error with a ticket reference as migration debt; strictness per directory via multiple tsconfig files; ratchet scripts that fail CI if the count of any or suppressions increases.
  • Order of work: shared types and API layer first (biggest payoff), then state management, utilities, then leaf components. Leave volatile, soon-to-be-deleted code for last.
  • Tooling split: bundlers do not type-check. Run tsc --noEmit (or vue-tsc/framework equivalents) in CI as a required check, in a pre-push hook, and keep the IDE check on. Use typescript-eslint with type-aware rules: no-explicit-any, no-floating-promises, no-misused-promises, consistent-type-imports, no-unnecessary-condition, switch-exhaustiveness-check.
  • Performance: measure with tsc --extendedDiagnostics and --generateTrace. Remedies: project references with composite and incremental, narrow include/exclude, skipLibCheck, explicit return types on exported functions (and isolatedDeclarations where applicable verify (5.5)), prefer interface extends to large intersections, avoid giant unions and deeply recursive conditional types, and reduce @types globals. A native compiler port promises large speedups verify status.
  • Testing types: type-level tests with expectTypeOf (Vitest), tsd, dtslint, or // @ts-expect-error lines that prove misuse fails; satisfies in fixtures; compile checks for public API changes in libraries. Run-time tests still cover behaviour; types do not replace them.
  • Library authors: ship .d.ts (and maps), verify the packaging with publint and arethetypeswrong, keep public types stable (types are part of the semver contract), avoid exposing internal types, document generics.
  • Conventions to agree on: interface versus type rule, unknown over any, no enums (or only string enums), naming (TItem for generics, no I prefix), where to put shared types, assertion policy (comment required), file organisation, how to handle null and undefined, error and result types.
  • Monorepos: a base tsconfig, per-package configs, project references, shared types package, consistent TypeScript version, and dependency checks (syncpack, workspace protocols).
  • Upgrading TypeScript: pin the version, upgrade regularly in small steps, read breaking changes, and run the full check in CI; type-level utilities are the usual breakage.
  • Measuring success: percentage of files in TypeScript, number of any and suppressions over time, type-check duration, and production error rates for typed modules. Tie it to outcomes, not coverage numbers alone.
  • Culture: pair on the first conversions, review types in PRs as carefully as logic, and keep types simple. Over-typing slows teams more than it helps.

Traps

  • Proposing a stop-the-world rewrite to TypeScript.
  • Turning on strict for the whole repo in one commit, producing thousands of errors and a flood of any.
  • Assuming the bundler checks types. A green build does not mean types are valid.
  • Letting @ts-ignore and any accumulate without a ratchet.
  • Optimising type-checking speed by weakening types rather than measuring where time goes.

Likely follow-ups

What would you convert first?
The shared API layer and domain models, because they are imported everywhere and their types give the most downstream safety.
How do you stop regressions during a long migration?
A ratchet in CI: new files must be TypeScript, the count of any and suppressions may not grow, and converted directories enable strict.
How do you justify the effort to stakeholders?
Point to defect classes eliminated (undefined access, wrong arguments), faster onboarding and safer refactors; propose a pilot with measurable results.
What is your position on any?
Forbidden by default, allowed with a comment at boundaries or in tests, and tracked.
