Choosing a state management approach

“How do you manage state in a large React application? When do you use local state, context, Redux, Zustand or a data-fetching library? How do you decide?”

Say this first (30 seconds)

“I first separate kinds of state, because each has a best tool. Local UI state, such as an open dropdown or a form field, stays in the component with useState. Server state, data that lives on a server and is cached on the client, belongs in a data library like TanStack Query or RTK Query, which handle caching, refetching and invalidation. URL state, such as filters and pagination, lives in the URL. Shared client state, such as a shopping cart, theme or wizard progress, goes into context for low-frequency values or a store like Zustand or Redux Toolkit when many components read and update it. Form state belongs in a form library. Most apps need much less global state than teams assume once server state is handled separately.”

Details interviewers probe

  • Kinds of state: UI state (ephemeral), form state, server cache state, URL state, global client state (rare but real), and persistent client state (localStorage, IndexedDB). Name which applies before naming a library.
  • Context is not a state manager: it is a dependency-injection mechanism that avoids prop drilling. Every consumer re-renders when the value changes (R5), so use it for values that change rarely (theme, locale, auth user, feature flags), split contexts, and memoise values. Fast-changing shared state needs a store with selectors.
  • Store selection criteria: boilerplate and learning curve, TypeScript support, devtools and time travel, ecosystem and middleware, performance with selectors, SSR and Server Component compatibility, team familiarity, testing story, community and maintenance.
  • Redux Toolkit: structure, predictable flow, excellent devtools, large ecosystem, RTK Query; good for big teams and complex, auditable state. Zustand: minimal API, little boilerplate, selectors, works outside React, small. Jotai/Recoil-style atoms: fine-grained derived state. MobX: mutable observable model with automatic tracking. XState: explicit state machines for workflows (E3).
  • Server state characteristics: asynchronous, shared ownership, can become stale, needs caching, deduplication, retries, background refresh, pagination, invalidation. Libraries built for it do these well; hand-rolled useEffect plus Redux rarely does.
  • URL as state: shareable, bookmarkable, supports back/forward. Use search params for filters, sorting and pagination; validate them (Zod) because users can edit the URL.
  • Derived data: compute from sources with selectors or during render; do not store it (R3). Normalise entities in stores that hold relational data (createEntityAdapter).
  • Anti-patterns: putting everything in global state, duplicating server data in a store, storing derived values, mutating state, giant reducers, using context for high-frequency updates, one store with no module boundaries, and choosing a library by trend.
  • Server Components change the picture: initial data is fetched on the server and passed as props, so client state shrinks to interaction state (R11, N3). Per-request stores are required for SSR to avoid sharing state between users.
  • Migration paths: adopt a query library first for server data, then reassess how much global state remains. Replace old Redux slices gradually; both can coexist.
  • Persistence and sync: use middleware (persist) or storage hooks for small preferences; IndexedDB for large offline data; handle versioning and migrations of persisted shapes.
  • Testing: test through the UI with real stores created per test; keep pure reducers and selectors unit-tested; avoid mocking the store.
  • Decision records: document the chosen approach and the reasons so the team applies it consistently (an ADR; see the engineering practices guide).

Traps

  • Answering “Redux” (or “Zustand”) before asking what kind of state it is.
  • Saying context replaces Redux. It lacks selectors, batching of reads and tooling, and re-renders all consumers.
  • Copying API data into a global store and writing loading and error reducers by hand.
  • Using global state for data only two siblings share.
  • Treating the choice as permanent; state architecture should evolve.

Likely follow-ups

When is Redux still the right choice?
Large teams and complex client-side workflows where strict structure, middleware, devtools and auditability pay off, or when the codebase already uses it with RTK Query.
Why not put everything in Context?
Context re-renders every consumer on any change and has no selector mechanism; it suits configuration, not frequently updated data.
What state would you put in the URL?
Anything the user might share, bookmark or navigate back to: filters, sort, pagination, selected tab, search query.
How do you avoid prop drilling without a store?
Composition (slots, children) and colocated state; context only for truly cross-cutting values.

Redux Toolkit and RTK Query

“Explain Redux and Redux Toolkit. How does the data flow work? What are slices, thunks, selectors and middleware? What is RTK Query? Why was Redux criticised and what is modern Redux?”

Say this first (30 seconds)

“Redux keeps application state in one store, changed only by dispatching plain action objects that pure reducers turn into new state, which gives a predictable, traceable one-way data flow with excellent devtools. Redux Toolkit, RTK, is the official way to use it: configureStore sets up middleware and devtools, createSlice generates actions and reducers and lets me write ‘mutating’ code that Immer turns into immutable updates, and createAsyncThunk handles async flows. Components read state with useSelector, ideally memoised selectors, and dispatch with useDispatch. RTK Query adds data fetching and caching on top. The old complaints were boilerplate and over-use for everything; RTK removed most boilerplate, and the modern guidance is to use Redux only for state that really is shared and complex, and RTK Query for server data.”

Details interviewers probe

  • Core concepts: store, action (plain object with type), reducer (pure function), dispatch, selector, middleware. State is immutable and updated by returning new objects; Redux checks references to decide which components re-render.
  • Redux Toolkit API: configureStore (adds thunk middleware, devtools, and dev-time immutability and serialisability checks), createSlice (name, initialState, reducers → action creators and reducer), createAsyncThunk (lifecycle actions pending, fulfilled, rejected handled in extraReducers), createEntityAdapter (normalised collections with CRUD reducers and selectors), createListenerMiddleware (side effects reacting to actions), createSelector (memoised, from Reselect).
  • Immer: lets reducers “mutate” a draft; Immer produces a new immutable state. Either mutate or return a new value, never both. Draft proxies cannot be stored outside.
  • Selectors: useSelector(state => state.cart.items.length) re-runs on every dispatch and re-renders when the result changes by reference. Return primitives or memoised results; do not create new objects or arrays inside a selector without memoisation. Colocate selectors with slices; derive data (totals, filtered lists) with createSelector.
  • TypeScript: infer RootState and AppDispatch from the store; export typed hooks (useAppSelector, useAppDispatch); PayloadAction<T> for reducer actions (T10).
  • Async logic: thunks are functions dispatched like actions, receiving dispatch and getState; createAsyncThunk standardises loading states and error handling; listener middleware or sagas handle complex flows; RTK Query replaces most data-fetching thunks.
  • RTK Query: declare endpoints; hooks manage fetching, caching (keyed by endpoint and arguments), subscription-based lifetime (keepUnusedDataFor), refetch on focus/reconnect, polling, tags for invalidation, optimistic updates with onQueryStarted, streaming updates, and code generation. It is comparable to TanStack Query but integrated with the Redux store and devtools.
  • Redux versus context: Redux has selectors, middleware, devtools, serialisable state and structure; context is built in and simple for low-frequency values.
  • Why Redux was criticised: boilerplate (action types, creators, switch reducers), indirection, putting all state (including form and fetch state) into the store, and misuse in small apps. RTK and the official style guide address these.
  • Best practices (official style guide): keep state minimal and serialisable, one store, slices by feature, put logic in reducers rather than components, model actions as events (“what happened”), normalise, avoid storing form state or derived data, use RTK Query for server data.
  • Middleware ecosystem: redux-persist for storage (watch migrations), redux-saga (generator-based, heavier; legacy codebases), redux-observable (RxJS), logger, analytics middleware.
  • SSR and Next.js: create a new store per request and provide it through a client component provider; never use a module-level store on the server (shared across users).
  • Testing: unit-test reducers and selectors as pure functions; test components with a real store created per test; test thunks with mocked APIs or MSW.

Traps

  • Describing Redux without Toolkit, as if you still write action constants and switch statements.
  • Selectors returning new arrays or objects every time, causing re-render on every dispatch.
  • Putting non-serialisable values (class instances, promises, functions) in state.
  • Mutating state outside Immer-managed reducers.
  • Using Redux for form fields or every boolean toggle.

Likely follow-ups

Why must reducers be pure?
So state transitions are predictable, testable, replayable (time travel) and safe to run more than once.
RTK Query versus TanStack Query?
Both cache server state; RTK Query integrates with Redux (shared store, devtools) and generates endpoint hooks; TanStack Query is framework-agnostic, has a richer ecosystem and does not need Redux.
How do you optimise Redux performance?
Narrow selectors, memoised derived data, normalised state, React.memo on list items, and avoiding large frequently updated slices.
Thunk versus saga?
Thunks are simple async functions; sagas use generators for complex orchestration (cancellation, races, debouncing). RTK’s listener middleware covers many saga use cases.

Zustand, Jotai, MobX, XState

“What alternatives to Redux do you know? Compare Zustand, Jotai, MobX and XState. How do they avoid unnecessary re-renders? When would you pick each?”

Say this first (30 seconds)

“Zustand is a small store: I create it with a function, read slices with selector hooks so components only re-render when their slice changes, and it works outside React with almost no boilerplate. Jotai models state as small independent atoms with derived atoms, which gives fine-grained updates and suits state that is naturally graph-shaped. MobX uses observable mutable objects and automatically tracks which components read what, which is productive but implicit and a different mental model. XState models behaviour as explicit state machines and statecharts, which I use for complex workflows such as multi-step flows, so impossible states cannot occur. I pick based on the shape of the problem and team conventions, not trend.”

Details interviewers probe

  • Zustand: create((set, get) => ({ count: 0, inc: () => set(s => ({ count: s.count + 1 })) })). Components call the hook with a selector; the default equality is reference equality, so return primitives or use useShallow for objects. No provider needed. Middleware: persist, devtools, immer, subscribeWithSelector. Actions live in the store; you can read and write outside React (store.getState()), which helps with non-React code.
  • Zustand with SSR/Next.js: a global module-level store is shared across requests on the server. Create the store per request (createStore) and provide it by context, and avoid hydration mismatches with persisted state.
  • Jotai: atom(0), useAtom, derived atoms atom(get => get(a) + get(b)), async atoms with Suspense, atomWithStorage, scoped providers. Re-renders are as fine-grained as atom subscriptions. Recoil (Meta) pioneered the idea; its maintenance status has been reported as discontinued verify before using.
  • MobX: observable state, computed values, actions, and observer components (MobX-react). Mutable style is concise but implicit: harder to trace without devtools, and conventions matter. Strong in complex domain models and legacy enterprise code; mobx-state-tree adds structure. Valtio offers a proxy-based similar model with a smaller API.
  • XState: explicit states, events, guards, actions, invoked services and actors; visual editor (Stately); typed; works with React via useMachine/useActor. Benefits: eliminates impossible states, documents flows, testable by path generation. Cost: more upfront structure; overkill for simple toggles.
  • Signals: fine-grained reactive primitives (Preact signals, Solid, Angular signals) update DOM without re-rendering components. React has no built-in signals; integration libraries exist but fight the model. Angular guide covers signals.
  • Re-render control: in every library the rule is the same: subscribe to the smallest slice, return stable values, and derive in selectors. Zustand and Redux use selectors, Jotai uses atom granularity, MobX uses tracked access.
  • React built-ins as stores: useSyncExternalStore is how these libraries integrate safely with concurrent rendering (R6); you can write a tiny store with it for small needs.
  • Comparison table to keep in mind: boilerplate (Redux > Zustand), structure (Redux/XState high, Zustand/Jotai low), debugging (Redux best), learning curve (MobX different), bundle size (Zustand and Jotai tiny), ecosystem (Redux largest).
  • Interop and migration: stores can coexist; migrate slice by slice; do not mix two global stores for the same data.
  • Guideline for teams: pick one default store and one server-state library, document usage patterns (where actions live, naming, selectors), and allow state machines for specific complex flows.

Traps

  • Using Zustand’s hook without a selector (useStore()) and re-rendering on every change.
  • A module-level store on the server leaking user data across requests.
  • Treating MobX mutation as free: unclear ownership of writes causes bugs.
  • Using XState for trivial boolean state, or ignoring state machines where booleans multiply (isLoading && isError).
  • Picking a library because of popularity without considering maintenance status.

Likely follow-ups

Why do people choose Zustand over Redux?
Far less ceremony and a tiny API with selector-based performance; Redux gives more structure, tooling and conventions for large teams.
How do atoms differ from a store?
Atoms are independent pieces composed by derivation, with no central object; a store is one object with slices.
When is a state machine worth it?
When the same flow has several statuses, guarded transitions and side effects, so booleans would allow impossible combinations.
How would you persist part of a store?
Persist middleware with a whitelist, versioning and migrations, avoiding storing secrets or server data that can be refetched.

TanStack Query and server state

“What is server state and why use TanStack Query? Explain query keys, staleTime, cacheTime (gcTime), refetching, mutations, optimistic updates and invalidation. How does it compare with SWR?”

Say this first (30 seconds)

“Server state is data owned by the server that the client only caches: it is asynchronous, shared, and can become stale. TanStack Query manages it declaratively. A query is identified by a key, and the library caches the result, dedupes simultaneous requests, retries failures, and refetches in the background when data is stale, such as on window focus or reconnect. staleTime says how long data counts as fresh, and gcTime how long unused data stays in memory. Mutations change server data, and afterwards I invalidate related query keys so they refetch, or update the cache optimistically and roll back on error. It replaces most hand-written fetch effects and loading flags, and works with SSR by prefetching and hydrating.”

Details interviewers probe

  • Queries: useQuery({ queryKey, queryFn }) returns data, status (pending, error, success), isFetching (background fetch indicator), and error. Distinguish isPending (no data yet) from isFetching (any request in flight). placeholderData and keepPreviousData behaviour give smooth pagination.
  • Query keys: arrays that uniquely describe the data and all variables the query depends on. Changing a key triggers a new query. Hierarchical keys enable targeted invalidation. Do not put non-serialisable values in keys.
  • Freshness and cache: staleTime and gcTime (renamed from cacheTime in v5) verify version. refetchOnWindowFocus is what makes apps feel “live”; disable or tune it where it is wasteful.
  • Dependent and parallel queries: enabled option for dependencies, useQueries for dynamic parallel sets, and prefetching to avoid waterfalls.
  • Mutations: useMutation({ mutationFn, onSuccess }). After success, invalidate affected keys (simple, one extra request) or update the cache with setQueryData (no request, but you must replicate server logic). Optimistic updates add instant feedback with rollback on error.
  • Pagination and infinite lists: useInfiniteQuery with getNextPageParam and cursors; combine with IntersectionObserver for infinite scroll (R14).
  • Error handling and retries: default exponential backoff; do not retry 4xx; global handlers via QueryCache onError; error boundaries with throwOnError; Suspense with useSuspenseQuery.
  • SSR and Server Components: prefetch on the server with prefetchQuery, dehydrate the cache and hydrate it on the client with HydrationBoundary; set staleTime above zero to avoid an immediate refetch after hydration. Create one QueryClient per request on the server.
  • Select and transformation: the select option derives data and enables fine-grained re-renders; keep raw server data in the cache and derive views from it, rather than copying data into component state.
  • Devtools: inspect keys, status, timings, cache contents; invaluable for debugging staleness.
  • SWR versus TanStack Query: SWR (Vercel) is minimal: key + fetcher with stale-while-revalidate, smaller API. TanStack Query has richer mutation, pagination, devtools, offline and persistence support. RTK Query suits teams already on Redux. Apollo/urql fit GraphQL with normalised caches.
  • Anti-patterns: copying query data into useState, using useEffect to call refetch on state changes (put the variable in the key instead), manual loading flags, very short staleTime with aggressive focus refetching, giant queries that mix unrelated data.
  • Offline and persistence: persist the cache to storage (persister plugins) and use networkMode to pause mutations offline.
  • Testing: wrap components in a fresh QueryClientProvider per test with retry: false; mock the network with MSW (R12).

Traps

  • Leaving staleTime at 0 and being surprised by repeated refetches on every mount and focus.
  • Forgetting variables in the query key, so different inputs share one cache entry.
  • Syncing query data into local state with an effect.
  • Confusing isLoading and isFetching or showing a full-page spinner during background refetch.
  • Sharing one QueryClient across requests on the server.

Likely follow-ups

How do you refetch when a filter changes?
Put the filter in the query key; the key change triggers a new fetch automatically, no effect needed.
Invalidate or update the cache after a mutation?
Invalidate when the server computes the result or when simplicity matters; setQueryData when you know the exact new value and want to skip a round trip.
How do you prevent request waterfalls?
Prefetch in the route or on the server, run independent queries in parallel, and avoid chaining child-component queries that depend on parent data.
How do you handle auth token refresh?
In the fetch layer (interceptor/wrapper): on 401 refresh once, retry the request, and redirect on failure; keep it outside components.

Routing: React Router and TanStack Router

“How does client-side routing work? Explain React Router’s data APIs (loaders and actions), nested routes, protected routes and code splitting. How does TanStack Router differ?”

Say this first (30 seconds)

“A client-side router maps the URL to a component tree using the History API, so navigation changes the view without a page reload while keeping back and forward working. React Router defines nested routes, where each route renders into its parent’s Outlet, so layouts persist. Since version 6.4 the data router adds loader functions that fetch data before rendering a route, action functions that handle form submissions, pending states through useNavigation, and per-route error elements; React Router 7 merges this with Remix into a framework mode with server rendering. TanStack Router focuses on fully type-safe routes, params and search params. I split code per route with lazy loading, treat the URL as state, and guard routes by checking authentication in loaders or layouts, with the real check on the server.”

Details interviewers probe

  • History API basics: pushState, replaceState and the popstate event let routers change the URL without reload. Hash routing (#/path) works without server configuration; browser routing needs the server to return index.html for unknown paths (SPA fallback).
  • React Router concepts: createBrowserRouter with route objects; <RouterProvider>; <Link>/<NavLink> (active styling); useParams, useSearchParams, useNavigate, useLocation; nested routes with <Outlet>; index routes; layout routes without a path; * splat for 404.
  • Loaders and actions: loader returns data (or a response or promise) and is read with useLoaderData; action handles non-GET submissions through <Form> or useFetcher (mutations without navigation). After an action, loaders revalidate. defer/streaming promises plus <Await> allow showing the shell while slower data loads verify API in your version.
  • Using a query library with loaders: call queryClient.ensureQueryData in the loader so data starts early and lands in the TanStack Query cache; the component then uses useQuery with the same key.
  • Error handling: errorElement per route (like an error boundary), useRouteError; throw responses for 404/401 to render dedicated UI.
  • Protected routes: check auth in a layout route or loader and redirect('/login?next=…'); store the intended destination; avoid flashing protected content; remember this is UX only and the API must enforce access. Role-based UI hides links but cannot replace server checks.
  • Code splitting: route-level lazy (React Router’s lazy route property or React.lazy) with Suspense; prefetch on hover or intent; keep shared layouts in the main chunk; verify chunk sizes with a bundle analyser.
  • URL as state: keep filters, tabs and pagination in search params so links are shareable; parse and validate with a schema; update with setSearchParams using replace for incremental changes to avoid polluting history.
  • Scroll and focus: restore scroll (<ScrollRestoration>), manage focus and document title on navigation for accessibility (R13).
  • React Router 7: merges Remix, offers library mode (the familiar router) and framework mode (file or config routes, SSR, type-safe route modules, Vite-based) verify current structure. Existing v6 apps upgrade with small changes.
  • TanStack Router: fully type-safe links and params inferred from the route tree, search-param schemas with validation, route-level loaders with caching and stale-while-revalidate, code-splitting by file convention. Strong for TypeScript-heavy SPAs; smaller ecosystem than React Router.
  • Framework routers: Next.js App Router, Remix, and Expo Router use file-based routing with server features (N2). Pick them when SSR and SEO matter; pick a library router for client-only apps.
  • Testing routes: render with createMemoryRouter and the route config, assert on navigation results; test loaders as functions.

Traps

  • Fetching data in useEffect inside the page when a loader would start earlier and avoid waterfalls.
  • Treating client-side route guards as security.
  • Forgetting server fallback to index.html, so deep links return 404 on refresh.
  • Pushing every keystroke into history instead of replacing.
  • Lazy loading every tiny component, creating many small chunks and waterfalls.

Likely follow-ups

Why do deep links 404 on refresh in a SPA?
The server looks for a file at that path; configure a fallback to index.html so the client router handles it.
How do you preserve scroll position and focus?
Scroll restoration from the router and explicit focus management on the new heading plus title updates.
Loader versus useEffect fetching?
Loaders start on navigation, in parallel for nested routes, and integrate with pending and error states; effects start after render, creating waterfalls.
When would you choose TanStack Router?
When end-to-end type safety of paths, params and search params matters and you are building a client-side app in TypeScript.

Forms and schema validation

“Which libraries do you use for forms and validation, and why? Compare React Hook Form, Formik and TanStack Form. How do Zod, Yup and Valibot work, and how do you share validation between client and server?”

Say this first (30 seconds)

“I use React Hook Form for most forms: it registers inputs as uncontrolled, so typing does not re-render the whole form, it handles touched and dirty state, field arrays and submission, and it takes a schema resolver. For validation I define a schema with Zod, Valibot or Yup: it describes the shape and rules once, validates at run time, and with Zod or Valibot infers the TypeScript type, so the form values, the API payload and the server validation share one source of truth. Formik is older and re-renders more; TanStack Form is a newer, type-safe, headless option. I show errors accessibly, validate on blur then on change, and never trust client validation alone.”

Details interviewers probe

  • React Hook Form mechanics: register attaches a ref and handlers so the DOM holds values; handleSubmit validates then calls your function; formState (errors, isDirty, isSubmitting) is subscribed lazily through a proxy so only used parts cause renders; Controller/useController wraps controlled UI components (MUI, custom selects); useFieldArray for repeating rows; watch re-renders, getValues does not; reset for editing existing entities.
  • Controlled vs uncontrolled trade-off: uncontrolled is faster for large forms; controlled gives instant access to values for dependent UI. Use useWatch narrowly to avoid root re-renders (R8).
  • Schema design: compose schemas, use refine/superRefine for cross-field rules (password confirmation), transforms and coercion (strings to numbers and dates from inputs), discriminated unions for conditional sections, localisable error messages, and separate input and output types (z.input, z.output).
  • Async validation: username availability via debounced checks that do not block typing, with the server as the final judge.
  • Server-side validation and errors: return structured field errors (problem details) and map to setError; handle generic failures at form level; preserve user input on failure.
  • Accessibility: labels, aria-invalid, aria-describedby linking error text, focus the first invalid field on submit, live-region announcement of the error summary (R13).
  • UX patterns: validate on blur first (mode: 'onTouched'), then on change after the first error (reValidateMode); do not show errors for untouched fields; disable submit only during submission, not for invalid state; preserve drafts for long forms.
  • Multi-step forms: one form state across steps (provider) or per-step forms merged at the end; validate each step with its own schema fragment; persist in URL or storage; review step before submit.
  • File uploads: uncontrolled file inputs with size and type validation, previews with URL.createObjectURL (revoke later), direct-to-storage uploads with progress.
  • Bundle and performance: Zod is larger than Valibot (which tree-shakes); on tight budgets validate on the server or lazy-load heavy validators. Large forms: avoid watching the entire form, memoise field components.
  • Type safety: infer form values from the schema; avoid duplicating interfaces; ensure defaults match the schema type.
  • Server Actions and frameworks: with Next.js use the same schema inside the action and return errors through useActionState; libraries like conform bridge progressive enhancement and schemas.

Traps

  • Validating only on the client.
  • Duplicating validation rules and types by hand in three places.
  • Using watch() at the root of a big form and re-rendering on every keystroke.
  • Showing all errors immediately before the user has interacted.
  • Forgetting that number and date inputs return strings and need coercion.

Likely follow-ups

Why does React Hook Form re-render less?
It leaves values in the DOM (uncontrolled) and subscribes to form state selectively, so keystrokes do not trigger React state updates.
How do you validate dependent fields?
Schema-level refine with a path for the error, or trigger on the dependent field when the source changes.
How do you handle server validation errors?
Return field-keyed errors and apply them with setError; show a general error for the rest.
Zod versus Yup?
Zod is TypeScript-first with inference and a modern API; Yup is older with a JS-first design and weaker inference.

Styling approaches

“How do you style a React application? Compare CSS Modules, Tailwind, CSS-in-JS (styled-components, Emotion) and zero-runtime options. How do you handle theming, dark mode and design tokens?”

Say this first (30 seconds)

“There are four broad families. Plain CSS or CSS Modules give scoped class names with no runtime cost and use standard CSS. Utility-first CSS such as Tailwind builds styles from small classes in markup, which is fast to write, consistent through a design-token config, and ships very small CSS. Runtime CSS-in-JS like styled-components and Emotion colocates styles with components and supports dynamic props, but adds JavaScript cost and has friction with Server Components. Zero-runtime CSS-in-JS such as vanilla-extract, Panda CSS, Linaria or StyleX gives typed, colocated styles compiled to static CSS. I choose by team skills, performance and server-rendering needs, and I drive theming through CSS custom properties and design tokens so dark mode and brands are data, not code.”

Details interviewers probe

  • CSS Modules: file-scoped class names (styles.button becomes a hashed class), no collisions, plain CSS features, works everywhere. Compose with composes, Sass, PostCSS. Dynamic styling by switching class names or CSS variables.
  • Tailwind CSS: utility classes generated from the content you use (tiny CSS), config for design tokens (colours, spacing, breakpoints), variants (hover:, md:, dark:), plugins, and typography. Pros: speed, consistency, no naming. Cons: noisy markup, learning the vocabulary, needs component abstraction for reuse, runtime-dynamic values need care (full class names, not string concatenation, so the scanner sees them), accessibility not automatic. clsx/cva/tailwind-merge manage variants and conflicts. Newer versions use CSS-first configuration verify (v4).
  • Runtime CSS-in-JS: styled-components and Emotion generate and inject CSS at run time, enabling props-based styles and theming through context. Costs: bundle size, extra render work, style recalculation, SSR style collection, and incompatibility with Server Components (they need client components). Some libraries moved to maintenance mode verify the status of styled-components.
  • Zero-runtime options: vanilla-extract (TypeScript style files compiled to CSS), Panda CSS (token-driven, recipes), Linaria, StyleX (Meta’s atomic CSS compiler), and CSS Modules + design tokens. They preserve the colocated authoring model without runtime cost.
  • Modern CSS reduces the need for libraries: custom properties, :has(), container queries, cascade layers, nesting, color-mix(), logical properties (CSS guide).
  • Theming and dark mode: define semantic tokens (--color-surface) mapped to raw palette values per theme; use prefers-color-scheme and a data-theme attribute; set the theme before first paint to avoid a flash (inline script or server cookie); color-scheme for native controls; test contrast in both themes.
  • Design tokens: single source for visual decisions, exported to CSS variables and platform formats; versioned with the design system (next guide).
  • Performance concerns: prefer static CSS extracted at build; avoid style recalculation storms from huge dynamic style injection; keep critical CSS small; remove unused CSS; use content-visibility and avoid layout thrash.
  • Server Components compatibility: CSS Modules, Tailwind, and zero-runtime libraries work in server components; runtime CSS-in-JS requires 'use client'.
  • Organisation: component-level styles beside the component, global styles for resets and tokens, avoid deep specificity, naming conventions (BEM) for plain CSS, lint with Stylelint.
  • Choosing: content or marketing sites with a design system and RSC: Tailwind or CSS Modules. Design-system libraries: CSS variables with zero-runtime or CSS Modules. Legacy apps already on styled-components: keep it but plan the migration path.
  • Migration strategy: introduce tokens as CSS variables first, then new components in the target approach, and migrate by feature; do not rewrite styles wholesale.

Traps

  • Building Tailwind class names dynamically (`text-${color}-500`) so they never reach the output.
  • Picking runtime CSS-in-JS for a Server Component app and then wrapping everything in client boundaries.
  • Flashing the wrong theme because it is applied after hydration.
  • Hard-coding colours and spacing in components instead of tokens.
  • Rewriting all styles at once instead of migrating incrementally.

Likely follow-ups

How do you implement dark mode?
Semantic CSS variables swapped under a theme attribute or media query, user preference stored in a cookie or storage, theme applied before first paint, and accessible contrast checked.
Why is Tailwind popular despite verbose markup?
Speed, constraint through tokens, no naming and dead-code elimination; reuse is handled by components rather than CSS classes.
What is wrong with runtime CSS-in-JS?
It adds render-time work and bundle size, needs SSR plumbing and does not run in Server Components.
How do you share styles across micro-frontends?
Shared tokens as CSS variables and a design-system package; avoid shared global class names.

Component libraries and headless UI

“How do you choose a UI component library? Compare MUI, Ant Design, Chakra, shadcn/ui, Radix and React Aria. What is a headless component and when do you build your own?”

Say this first (30 seconds)

“Libraries sit on a spectrum from fully styled to fully headless. Styled systems such as MUI, Ant Design and Mantine give a complete, themeable set of components quickly, at the cost of a recognisable look, bundle size and customisation limits. Headless libraries, Radix Primitives, React Aria, Headless UI and Ark UI, provide behaviour and accessibility, such as focus management, keyboard handling and ARIA, with no styling, so I can match any design. shadcn/ui is a pattern, not a package: it copies accessible Radix-based components styled with Tailwind into my repo so I own the code. I choose by design requirements, accessibility needs, bundle size, customisation depth, maintenance health, and whether we have a design system team. Building accessible widgets such as comboboxes or date pickers from scratch is rarely worth it.”

Details interviewers probe

  • MUI (Material UI): large, mature, Material Design look, deep theming, many components (data grid and date pickers have paid tiers), Emotion-based styling (runtime; zero-runtime options evolving) verify. Fast for internal tools; customising away from Material costs effort.
  • Ant Design: enterprise component set (tables, forms, tree, pickers) with a distinctive style; heavy; strong in admin dashboards.
  • Chakra UI and Mantine: developer-friendly, style props and hooks, good accessibility; Chakra v3 moved to Ark UI/Panda-based architecture verify; Mantine ships many components and hooks.
  • Radix Primitives: unstyled, accessible building blocks (Dialog, Dropdown, Popover, Tabs, Select) with composition via asChild. React Aria / React Aria Components (Adobe): the most thorough accessibility and internationalisation (dates, numbers, drag and drop). Headless UI (Tailwind Labs) and Ark UI (Zag state machines, multi-framework) are alternatives.
  • shadcn/ui: a CLI that copies component source into your project (Radix + Tailwind + class-variance-authority). You own and edit the code: no version-lock, but also no upstream updates and you take on maintenance. Popular for fast, customisable results; assess accessibility and tailor tokens.
  • When to build your own: simple presentational components (buttons, cards, badges) are fine; complex interactive widgets (combobox, date picker, data grid, rich text editor, modals with focus management) are costly to build accessibly, so wrap a headless library.
  • Wrapping third-party components: create your own thin wrapper layer in the design system so you can swap implementations, enforce tokens and defaults, and limit API surface.
  • Bundle and performance: check tree shaking (ESM, per-component imports), CSS strategy (runtime styles add cost), icon libraries (optimizePackageImports, individual imports), and use code splitting for heavy widgets (data grid, charts).
  • Accessibility due diligence: test keyboard, screen reader and focus behaviour of candidates; read the library’s accessibility statements and issues; prefer ones following WAI-ARIA Authoring Practices (R13).
  • Theming and branding: how deeply can tokens, typography and component variants be customised without forking? Does it support CSS variables, dark mode and multiple brands?
  • Server Components: many libraries need 'use client'; check for RSC-compatible exports and hydration behaviour (N3).
  • Long-term risk: maintenance activity, bus factor, breaking-change history, paid tiers, community size; plan a migration path and avoid deep coupling to library-specific props throughout the app.
  • Documentation and Storybook: publish your wrapped components in Storybook with usage and a11y notes (design systems guide).

Traps

  • Choosing a library by looks in the demo without checking accessibility or bundle size.
  • Building a custom dropdown or modal and missing focus trap, Escape handling or screen-reader semantics.
  • Overriding a styled library with !important and deep selectors rather than using its theming system, or picking a headless library without capacity to style everything.
  • Importing the whole library or icon set into the bundle.
  • Using shadcn/ui as if it were a dependency and never reviewing or updating the copied code.

Likely follow-ups

What is the difference between headless and styled libraries?
Headless supplies behaviour and accessibility with no visual styling; styled libraries include both and impose a look and a theming API.
How would you introduce a component library to an existing project?
Wrap it in design-system components, adopt tokens, migrate feature by feature, and track coverage of old versus new components.
Why wrap third-party components?
To control the API, enforce tokens and accessibility defaults, and make replacing the library a local change.
How do you evaluate a data grid?
Virtualisation, sorting, filtering, grouping, accessibility, server-side data support, licensing, bundle cost, and customisation.

API layers: REST, GraphQL, tRPC

“How do you structure the API layer of a React app? Compare REST, GraphQL and tRPC. fetch versus Axios. How do you handle auth tokens, errors, retries and real-time data?”

Say this first (30 seconds)

“I keep all network code behind a thin API layer: a typed client with the base URL, auth headers, error mapping and retry rules, and feature-level functions or hooks that components call, so components never build URLs or parse responses. For the protocol: REST is simple, cacheable and universal; GraphQL lets clients request exactly the fields they need in one round trip and gives a typed schema, at the cost of caching complexity and server work; tRPC gives end-to-end type safety when client and server are both TypeScript in one repo. I use fetch (or a small wrapper) or Axios for interceptors, AbortSignal for cancellation, a query library for caching, and I handle 401 with one refresh-and-retry path. For real-time I choose polling, SSE or WebSockets by need.”

Details interviewers probe

  • fetch versus Axios: fetch is built in, streaming-capable, works in browsers, Node and edge, but does not reject on HTTP errors, has no interceptors or automatic JSON handling, and needs AbortController for timeouts. Axios offers interceptors, automatic JSON, timeouts, upload progress and cancellation, at extra bundle cost. Ky, ofetch and wretch are small wrappers over fetch. Whichever you use, wrap it once (J30).
  • Auth tokens: keep access tokens short-lived; prefer HttpOnly cookies set by the server (a backend-for-frontend can hold tokens) over localStorage; on 401 refresh once (single-flight so concurrent requests share one refresh) and retry; on refresh failure log out. CSRF protection is required for cookie-based flows (J29).
  • Error handling: normalise errors into one shape (status, code, message, field errors, request id); distinguish network, 4xx (user-fixable), 5xx (retry or report); surface friendly messages; report unexpected ones (J21). Use RFC 7807 “problem details” on the server.
  • Retries and timeouts: retry only idempotent requests (GET, PUT with idempotency) with exponential backoff and jitter; set timeouts via AbortSignal.timeout; never retry a payment POST without an idempotency key.
  • Pagination styles: offset (simple, unstable with inserts), cursor (stable, best for feeds), page tokens; expose in the API function and map to infinite-query hooks.
  • REST design basics for consumers: predictable resources and verbs, correct status codes, filtering/sorting/pagination parameters, ETags and conditional requests, versioning, and OpenAPI documentation. Generate typed clients (openapi-typescript, Orval) and validate at run time where trust is limited (T11).
  • GraphQL in React: Apollo Client (normalised cache, hooks, devtools), urql (lighter), Relay (fragment colocation, compiler, strong at scale). Use codegen for typed hooks. Trade-offs: cache invalidation, over-complex queries, persisted queries, file uploads, error handling with partial data, N+1 on the server (DataLoader), and security hardening (depth, complexity limits, disabling introspection in production).
  • tRPC: procedures with Zod input validation, inferred output types, React Query integration; ideal for full-stack TypeScript monorepos (Next.js). Not suited when other consumers need a stable public API.
  • Backend for frontend (BFF): a server layer tailored to a client that aggregates services, hides secrets and tokens, shapes data and handles sessions; reduces client complexity and chattiness.
  • Real-time: polling (simple), Server-Sent Events (one-way), WebSockets (two-way), or libraries (Socket.IO, Ably, Pusher, Supabase Realtime); merge real-time updates into the query cache (setQueryData); handle reconnect and missed events (J30).
  • Mocking and contracts: MSW for development and tests; contract tests (Pact) or shared schemas to detect drift; Storybook with mocked handlers.
  • Performance: batch or combine requests carefully, cache with HTTP headers and the query cache, compress, use HTTP/2 multiplexing, avoid waterfalls, prefetch likely navigations.
  • Environment and config: base URLs per environment through build or runtime config; never ship secrets in the client; CORS configured on the server for browser calls.
  • Request cancellation and race conditions: pass abort signals from the query library to fetch; ignore stale responses (J22).

Traps

  • Scattering fetch calls with hand-built URLs and ad hoc error handling across components.
  • Refreshing the token separately in many parallel requests, causing a refresh storm or logout loop.
  • Choosing GraphQL to “reduce requests” without the capacity for schema governance and caching.
  • Storing tokens in localStorage without accounting for XSS.
  • Retrying non-idempotent requests blindly.

Likely follow-ups

REST or GraphQL for a new product?
REST with OpenAPI by default for simplicity and caching; GraphQL when many clients need flexible, aggregated data or the schema-first workflow pays off; tRPC for a TypeScript-only full-stack app.
How do you handle token refresh with concurrent requests?
A single in-flight refresh promise that queued requests await, then retry once with the new token.
How do you keep client types in sync with the API?
Generate from OpenAPI or GraphQL schemas in CI, fail on drift, and validate responses at the boundary.
What does a BFF solve?
It hides tokens, aggregates backend calls into client-shaped responses, and lets frontend teams own an API tailored to their UI.

Testing and Storybook toolchain

“What testing tools and workflow do you use for a React project? Jest versus Vitest, Testing Library, MSW, Playwright, Storybook. How do you set up CI and quality gates?”

Say this first (30 seconds)

“My toolchain has layers. Vitest, or Jest in older projects, runs unit and component tests with Testing Library for user-centric queries and MSW to mock the network. Playwright runs end-to-end tests across browsers for critical flows. Storybook documents and develops components in isolation, with interaction tests and an accessibility addon, and visual regression through Chromatic or Playwright screenshots. Static checks, TypeScript, ESLint and Prettier, run first. In CI every pull request runs type check, lint, unit and component tests with coverage thresholds, builds Storybook, and runs end-to-end tests against a preview deployment; flaky tests are treated as bugs. The goal is fast feedback and confidence, not a coverage number.”

Details interviewers probe

  • Vitest versus Jest: Vitest reuses the Vite config and transforms, runs quickly with ESM and TypeScript support, has a Jest-compatible API, watch mode and a browser mode; Jest is the long-standing default with a huge ecosystem, needs Babel or SWC transforms and has more friction with ESM. New Vite-based projects choose Vitest; existing Jest suites rarely justify a rewrite.
  • Testing Library ecosystem: @testing-library/react, user-event, jest-dom (toBeVisible, toHaveAccessibleName), and renderHook. Provide a custom render wrapper with providers (R12).
  • MSW: handlers describe the API for tests, Storybook and local development; supports REST and GraphQL; the same handlers can power tests and a mock dev server; keep handlers close to API types.
  • Playwright: multi-browser, auto-waiting locators, network interception, tracing and video, parallel sharding, component testing, API testing, authentication state reuse, and visual comparisons. Keep end-to-end tests few and stable: login, checkout, core CRUD; run against a preview or staging environment with seeded data.
  • Storybook: component workshop and documentation. Stories (CSF) double as test fixtures; play functions simulate interaction and assert; the a11y addon runs axe; Chromatic or Playwright snapshots detect visual regressions; MDX docs and controls help designers and QA. Autodocs generate prop tables from TypeScript.
  • Visual regression: baseline screenshots per story, reviewed in PRs; reduce flakiness with fixed viewport, fonts, animation disabled, deterministic data.
  • Contract and API tests: schema checks from OpenAPI, Pact consumer-driven contracts, or generated mocks, to detect drift between frontend and backend.
  • Coverage: use thresholds on changed lines (diff coverage) rather than a high global number; look at what is untested. Mutation testing (Stryker) measures test strength on critical logic.
  • Static checks: TypeScript strict, ESLint with react-hooks, jsx-a11y, @typescript-eslint type-aware rules (T13), Prettier for formatting, Knip or depcheck for unused code and dependencies, Husky and lint-staged for pre-commit speed (full checks stay in CI).
  • CI practices: cache dependencies and build outputs, run jobs in parallel, shard end-to-end tests, retry flaky tests only as a diagnostic (and fix them), publish reports and traces as artifacts, require checks before merge, and keep the default branch green.
  • Performance and bundle budgets: size-limit or bundle analysers in CI, Lighthouse CI for key pages, Web Vitals budgets.
  • Test data and environments: factories/builders, seeded databases for end-to-end, isolated test users, cleanup, and no dependence on production data.
  • Culture: tests as part of the definition of done, reviews check test quality, quarantine flaky tests with an owner and deadline, track flake rate and pipeline time as engineering metrics.

Traps

  • Large end-to-end suites that are slow and flaky, replacing faster component tests.
  • Updating visual snapshots without looking at the diff.
  • Mocking modules and hooks instead of the network, so tests no longer cover real wiring.
  • Running every check only in CI with slow feedback, or only in pre-commit hooks that developers bypass.
  • Treating coverage percentage as the quality target.

Likely follow-ups

Playwright or Cypress?
Playwright for multi-browser, speed, parallelism and tracing; Cypress has a strong developer experience and ecosystem and suits teams already invested in it.
How do you keep a test suite fast?
Prefer component tests over end-to-end, parallelise, cache, avoid heavy setup per test, and run only affected tests locally.
What do you do with a flaky test?
Reproduce with traces, fix the cause (race, shared state, timing), quarantine with an owner while fixing, and track the flake rate.
How does Storybook help beyond documentation?
Isolated states for development, interaction and accessibility tests, visual regression, and a shared language with designers.

Everyday libraries and choosing dependencies

“Which libraries do you reach for to build tables, charts, animations, dates, drag and drop and rich text? How do you decide whether to add a dependency, and how do you manage dependency risk and upgrades?”

Say this first (30 seconds)

“For common needs I have default choices: TanStack Table with TanStack Virtual for data grids, Recharts, Visx, ECharts or D3 for charts depending on complexity, Motion (Framer Motion) for animation, date-fns or Day.js for dates with Intl for formatting, dnd-kit for drag and drop, and Tiptap or Lexical for rich text. Before adding any dependency I evaluate need versus cost: maintenance activity, bundle size and tree shaking, TypeScript types, accessibility, licence, security record, and how deeply it would couple to our code. I prefer the platform and small utilities when they are enough, wrap third-party libraries behind our own interfaces, and manage upgrades with automated pull requests, lockfiles and audits.”

Details interviewers probe

  • Tables and grids: TanStack Table is headless (you render markup and styles, it supplies sorting, filtering, grouping, pagination and column state); AG Grid and MUI X Data Grid are full-featured with commercial tiers. Combine with virtualisation for thousands of rows, server-side pagination for large datasets, and semantic <table> markup or proper grid roles for accessibility.
  • Charts: Recharts (declarative, simple), Visx (low-level D3 primitives for React), ECharts and Chart.js (feature-rich, canvas), D3 (maximum control; use for maths and scales, let React render). Consider accessibility (data table alternative, labels), canvas versus SVG performance, and bundle size.
  • Animation: prefer CSS transitions and the Web Animations API for simple effects; Motion (formerly Framer Motion) for layout animation, gestures and exit transitions; respect prefers-reduced-motion; animate transform and opacity for compositor performance (CSS guide).
  • Dates: avoid Moment.js (large, mutable, legacy). Use date-fns (functional, tree-shakable) or Day.js (small, Moment-like); Luxon for time zones; the platform Intl.DateTimeFormat for formatting and the Temporal proposal for the future verify status (J13). Store UTC, convert for display, and test around daylight-saving changes.
  • Drag and drop: dnd-kit (accessible, modular, keyboard support), Pragmatic drag and drop (Atlassian), react-beautiful-dnd is deprecated. Native HTML5 drag and drop has poor touch and accessibility support.
  • Rich text and editors: Tiptap (ProseMirror), Lexical (Meta), Slate; Monaco/CodeMirror for code. Editors are huge: lazy-load them and plan for sanitisation of output (J29).
  • Utilities: import per-function (lodash-es) or use native methods and structuredClone; many lodash helpers are redundant (J10, J16). Check for duplicates in the bundle.
  • Maintenance health signals: last release date, commit activity, open issues and response time, number of maintainers (bus factor), sponsorship or company backing, semver discipline, changelog quality, migration guides.
  • Bundle cost: check minified+gzip size, ESM and sideEffects: false for tree shaking, and what it pulls in; analyse with the bundle analyser; lazy-load heavy libraries on the routes that need them.
  • Security and supply chain: audit new packages (typosquatting, install scripts, maintainers), pin versions with lockfiles, use npm audit/Dependabot/Renovate/Socket, review transitive dependencies, restrict postinstall scripts, and consider provenance (J29).
  • Licences: MIT/Apache are permissive; GPL/AGPL and some “source-available” licences may constrain commercial use; check with legal for anything unusual; track with a licence checker in CI.
  • Upgrades: automate with Renovate or Dependabot, group minor updates, run the full CI, read changelogs for majors, use codemods, upgrade frameworks regularly in small steps, and keep a policy for security patches versus feature updates.
  • Wrapping and boundaries: encapsulate libraries behind your components or functions (a formatDate utility, a Chart component) so swapping is a local change and conventions stay consistent.
  • Monorepo tooling: pnpm workspaces, Turborepo or Nx for caching and task orchestration, shared configs and consistent versions (build and tooling guide).
  • Decision records: record why a library was chosen and the alternatives considered so future maintainers can reassess.

Traps

  • Adding a large library for one small function.
  • Choosing by GitHub stars alone, ignoring maintenance and accessibility.
  • Spreading library-specific APIs across the whole codebase so removal is impossible.
  • Deferring upgrades for years, then facing a risky mass migration.
  • Ignoring transitive dependencies and install scripts.

Likely follow-ups

Build or buy a data grid?
Buy or adopt a headless base for anything beyond a simple table; sorting, virtualisation, keyboard navigation and accessibility are expensive to build.
How do you decide between two similar libraries?
Prototype the hardest use case, compare maintenance, bundle size, accessibility and migration cost, and record the decision.
How do you keep dependencies from rotting?
Automated update PRs with CI, scheduled upgrade time, removal of unused packages, and ownership of each critical dependency.
Why avoid Moment.js today?
It is in maintenance mode, large, mutable and not tree-shakable; modern alternatives and Intl cover the needs.
