R1Added

What React is and how it renders

“What is React and what problem does it solve? What is the virtual DOM? Explain what happens from a state change to the screen updating: the render phase and the commit phase.”

Say this first (30 seconds)

“React is a library for building user interfaces from components. You describe what the UI should look like for the current state, and React works out how to update the DOM. That is the declarative model: UI is a function of state. A component is a function that returns React elements, which are plain objects describing the UI; React keeps this tree of elements, sometimes called the virtual DOM, compares the new tree with the previous one, and applies only the differences to the real DOM. Updating has two phases. The render phase calls my components to compute the new tree and must be pure. The commit phase applies changes to the DOM, runs layout effects, and then the browser paints; passive effects from useEffect run afterwards.”

Details interviewers probe

  • Declarative versus imperative: with jQuery you write the steps to change the DOM; with React you describe the result for each state and let React reconcile. This removes a class of bugs where UI and data drift apart.
  • JSX: syntax sugar for createElement calls (the modern transform compiles to jsx() from the runtime, so no import React is needed). It is JavaScript with expressions in braces: { } accepts expressions, not statements. Attributes use camelCase (className, htmlFor). Values are escaped by default, which protects against injection.
  • Elements versus components versus instances: an element is an immutable description ({ type, props, key }). A component is a function (or class) that returns elements. React creates and tracks the instances; you never hold them.
  • Virtual DOM: not magic and not always faster than hand-written DOM updates. Its benefit is a simple programming model with good-enough performance. Svelte and Solid avoid it with compile-time or fine-grained reactivity; React’s answer to cost is smart scheduling and the compiler (R5, R9).
  • Render phase purity: no mutation of external variables, no network calls, no Math.random() or Date.now() in the output, no DOM access. React may call a component multiple times (StrictMode in development, concurrent rendering, discarded renders), so side effects belong in event handlers or effects.
  • Commit phase details: React applies DOM mutations, attaches refs, runs useLayoutEffect synchronously (before paint), then schedules passive effects (useEffect) after paint. Layout effects can read layout and re-render synchronously, at the cost of delaying paint.
  • What triggers a render: the initial render, a state update in the component, a parent re-render (by default all children re-render), and a context value change for consumers. Props changing is a consequence of a parent rendering, not a separate trigger.
  • One-way data flow: data flows down through props; events flow up through callbacks. State lives in the closest common owner. This makes data flow traceable.
  • Fiber: React’s internal reconciler data structure (a linked tree of units of work). It lets rendering be split, paused, prioritised and resumed (R9). Know the name and the idea, not the internals.
  • Strict Mode: in development it renders components twice and runs effects twice on mount (mount, unmount, mount) to expose impure renders and missing cleanup. It does nothing in production.
  • React is a library, not a framework: it renders UI. Routing, data fetching, bundling and SSR come from the ecosystem or a framework such as Next.js, Remix or React Router framework mode.
  • Why React is popular: component model, huge ecosystem, hiring pool, backing from Meta, and a stable programming model across web and native.

Traps

  • “React re-renders the whole DOM.” It re-calls components and then updates only changed DOM nodes.
  • “The virtual DOM makes React fast.” It makes updates simple; speed comes from skipping unnecessary work.
  • Putting side effects such as fetch or mutations directly in the component body.
  • Confusing “rendering” with “updating the DOM”. A component can render without any DOM change.
  • Believing useEffect runs before paint. It normally runs after.

Likely follow-ups

Why must components be pure?
React can render a component several times, out of order or discard the result. Purity makes that safe and enables concurrent features.
What is the difference between an element and a component?
An element is a plain-object description of what to show; a component is the function that produces elements.
How does React know what changed?
By comparing the new element tree with the previous one in reconciliation (R2).
Why does JSX need a single root?
A function returns one value; use a fragment <>…</> to group siblings without an extra DOM node.

Reconciliation and keys

“How does React’s diffing algorithm work? Why are keys needed in lists? Why is using the array index as a key a problem? What causes a component to remount?”

Say this first (30 seconds)

“Reconciliation compares the previous element tree with the new one to decide the minimum DOM work. React uses heuristics to stay linear: elements of different types produce different trees, so a type change destroys the old subtree and mounts a new one; the same type at the same position is updated in place and its state is kept; and in lists, key identifies items so React can match, move or remove them correctly rather than relying on position. Keys must be stable and unique among siblings, such as a database id. Using the index breaks state and DOM identity when items are inserted, removed or reordered: inputs keep the wrong text and animations attach to the wrong item. A changed key forces a remount, which is also a deliberate way to reset state.”

Details interviewers probe

  • Two heuristics: (1) different element types give different trees (React tears down the old tree and builds the new one); (2) the key prop hints which children are stable across renders. These assumptions make diffing linear.
  • Same type, same position: React keeps the instance and its state, updates props and recurses into children. DOM elements update only the attributes that changed.
  • Keys: must be unique among siblings (not globally), stable across renders, and not generated on render. Do not use Math.random() (remounts every time) or the index for dynamic lists. When no stable id exists, create one when the data is created.
  • Fragments with keys: <Fragment key={id}> when mapping to several siblings per item. The key is not passed as a prop; read it from another prop if needed.
  • Resetting state with a key: changing the key of a component remounts it with fresh state. It is the cleanest way to reset a form when the edited entity changes, instead of an effect that copies props into state.
  • State is tied to position in the tree, not to the component function. Moving a component to a different position or wrapping it differently (for example conditional wrapper elements) resets its state.
  • Components defined inside components create a new component type per render, causing remounts: the classic cause of inputs losing focus on every keystroke.
  • Conditional rendering patterns: {cond && <X/>} (beware 0 && rendering “0”), ternaries, early returns. Switching which branch renders at the same position with the same type preserves state; different types reset it.
  • Reconciliation versus rendering: reconciliation is the diff. A re-render calls your function; the diff then decides DOM work. A child that re-renders but returns the same output produces no DOM change.
  • Performance consequences: stable keys let React move nodes instead of recreating them; big lists still cost render time, so virtualise when long (R14).
  • Hydration and keys: server and client must render the same tree and keys, otherwise hydration mismatches appear (Next.js guide).

Traps

  • “Keys are for performance only.” They are about identity and correctness of state; performance is a side effect.
  • Using index as a key “because it works”, in a list with inputs, checkboxes, animations or reordering.
  • Generating keys during render with random values or timestamps.
  • Defining components inside other components and then fighting remount bugs with memoisation.
  • Not knowing that key changes reset state; using it by accident or ignoring it as a tool.

Likely follow-ups

Is it ever fine to use the index as key?
For static, never reordered, never filtered lists with no local state in items, such as a fixed menu.
How do you reset a component’s state when a prop changes?
Give it a key that changes with the identity (like userId). Avoid syncing state from props with effects.
What is the complexity of React’s diff?
Linear, O(n), because of the type and key heuristics; a general tree diff would be cubic.
Does a re-render always change the DOM?
No. If the new elements equal the old ones, nothing in the DOM changes.

State, batching and snapshots

“How does useState work? Is setState synchronous? What is batching? Why use a functional update? How do you structure state, and what is derived state?”

Say this first (30 seconds)

“State is component memory that survives re-renders. Each render sees a snapshot: inside one render, count has a fixed value, and calling setCount does not change it in the current function; it schedules a re-render with the new value. React batches multiple updates in the same event into one render; since React 18 this is automatic, including in promises, timeouts and native events. When the next state depends on the previous one, I use a functional update, setCount(c => c + 1), because the queued updates run in order against the latest value. State must be treated as immutable: I create new objects and arrays instead of mutating, so React can detect changes by reference. I keep state minimal, derive everything else during render, and lift state up to the nearest common parent.”

Details interviewers probe

  • useState mechanics: returns [value, setter]. React stores state in the fiber, by call order (R6). The setter queues an update; if the new value is Object.is-equal to the current one, React skips the re-render.
  • Lazy initial state: useState(() => expensive()) runs the function once; useState(expensive()) calls it on every render and discards it.
  • Batching: before React 18 only updates inside React event handlers were batched. With createRoot, all updates are batched automatically (promises, timeouts, native handlers). flushSync forces a synchronous render for the rare cases that need DOM results immediately.
  • Functional updates: use them whenever the next value depends on the previous (counters, toggles, appending to arrays). They also let callbacks avoid listing the state as a dependency.
  • Immutability: never mutate state objects or arrays (push, sort, obj.x = 1). Use spread, map, filter, toSorted, or Immer for nested updates. Mutations are invisible to Object.is, so React does not re-render, and shared references cause subtle bugs (J1, J9).
  • Principles for structuring state: group related values, avoid contradictory states (use one status union instead of isLoading and isError booleans), avoid redundant state, avoid duplicated state, avoid deeply nested state (normalise).
  • Derived state: compute values from props or state during render (const total = items.reduce(…)) instead of storing them and syncing in an effect. Storing derived data creates two sources of truth. If the computation is expensive, useMemo (R5).
  • Copying props into state is only right when you want an initial value that then diverges (name it initialX). Otherwise it goes stale when the prop changes; use a key to reset or derive instead.
  • Lifting state up: when two components need the same data, move the state to their closest common parent and pass it down with callbacks. Colocation is the reverse rule: keep state as close as possible to where it is used, so fewer components re-render.
  • State versus ref versus variable: state triggers re-renders and persists; a ref persists without re-rendering (timers, DOM nodes, previous values); a local variable resets each render.
  • useReducer: consolidate complex transitions in one pure function ((state, action) => state); good for multi-field state, related updates and testable logic (R6).
  • State between renders and the DOM: inputs hold DOM state unless controlled (R8). State resets when the component unmounts or its key changes.
  • External state: for state outside React (stores, URL, server cache) use useSyncExternalStore or a library (Redux, Zustand, TanStack Query: ecosystem guide).

Traps

  • “setState is asynchronous.” More precisely, the value in the current render does not change; the update is applied in the next render.
  • Reading state right after the setter and expecting the new value.
  • Mutating an array or object in state and calling the setter with the same reference.
  • Storing values that can be computed from other state or props, then keeping them in sync with effects.
  • Using the state variable inside a setTimeout or setInterval without a functional update, and seeing stale values.

Likely follow-ups

Why does a state setter not update the variable immediately?
The variable belongs to the current render’s snapshot. React re-renders the component with the new value; that is what keeps renders predictable and batchable.
What if you set state to the same value?
React bails out and usually does not re-render the children (it may render the component once more before bailing out).
How would you model a fetch state?
A discriminated union (idle | loading | success | error) or a data library, not several independent booleans.
When use useReducer over useState?
When next state depends on several fields or many actions, when transitions need names and tests, or to pass dispatch (stable) down instead of many callbacks.

Effects and synchronisation

“How does useEffect work? Explain the dependency array and cleanup. When should you not use an effect? What is the difference between useEffect and useLayoutEffect? Why do effects run twice in development?”

Say this first (30 seconds)

“An effect synchronises a component with something outside React, such as a subscription, a timer, a network connection or a non-React widget. useEffect runs after the commit and paint. Its dependency array lists the reactive values it reads; React re-runs the effect when any of them changed, after running the previous cleanup. An empty array means ‘only on mount’, but that is a consequence, not the goal. The cleanup function must undo the setup, which is what prevents leaks and race conditions. Effects are not for transforming data for rendering or for responding to user events: derive during render, and put event logic in handlers. useLayoutEffect runs before paint and blocks it, for measuring layout. In development Strict Mode mounts, unmounts and re-mounts once to reveal missing cleanup.”

Details interviewers probe

  • Dependency array: [] run after the first render only; [a, b] run when a or b changed (by Object.is); omitted means after every render. All reactive values used inside (props, state, values derived from them, functions defined in the component) must be listed; the exhaustive-deps lint rule enforces this. Do not suppress the rule; restructure the code.
  • Stale closures and loops: a missing dependency makes the effect read old values. An object or function created in render changes every time, re-running the effect; stabilise it (move it outside, memoise with useMemo/useCallback, or depend on primitive fields).
  • Cleanup: returns a function that runs before the next effect run and on unmount. Use it to unsubscribe, clear timers, abort fetches (AbortController), disconnect observers, and destroy third-party widgets (J25).
  • Data fetching in effects: works but is easy to get wrong (race conditions, no caching, no deduplication, waterfalls, double fetch in Strict Mode). Use an ignore flag or abort in cleanup, or better a data library (TanStack Query, SWR) or framework data loading (Server Components, route loaders).
  • You might not need an effect: transform data for display during render; handle user events in event handlers; reset state with a key; adjust state during render only in rare, guarded cases; compute derived values; notify a parent from the event that caused the change, not from an effect watching state; lift state instead of syncing two states with effects.
  • Effects are for external synchronisation: subscriptions (addEventListener, WebSocket), timers, imperative widgets (maps, charts), analytics on mount, document title, focus management, logging page views. Or use useSyncExternalStore for external stores.
  • useLayoutEffect: runs synchronously after DOM mutation and before paint. Use for measuring DOM and positioning tooltips to avoid flicker. It blocks paint, so keep it short. It does not run on the server and warns in SSR, so guard or use useEffect when no layout read is needed.
  • useInsertionEffect: for CSS-in-JS libraries to inject styles before layout; library authors only.
  • Order: child effects run before parent effects; cleanups of the previous run happen before new setups; layout effects run before passive effects.
  • Why Strict Mode double-invokes: to surface missing cleanup and impure render logic. A correct effect behaves the same after one extra setup/cleanup cycle. It is also preparation for features like Offscreen/Activity that preserve and remount state.
  • Event handlers versus effects: the question is “why does this code run?” If because the user clicked, it belongs in the handler. If because the component should stay connected to something while visible, it is an effect.
  • Effect events: a way to read latest props or state inside an effect without making it a dependency (useEffectEvent) verify stable status in your React version.
  • Server rendering: effects do not run on the server; do not rely on them for SEO-critical data.

Traps

  • Lying to the dependency array (omitting values) to “run once”.
  • Updating state in an effect that depends on that state, creating an infinite loop.
  • Using an effect to derive state from props or other state.
  • Fetching without cleanup, so a slow old response overwrites a new one.
  • Adding a ref or a guard to make an effect run once in Strict Mode, hiding the real bug.
  • Making the effect callback itself async. It returns a promise, not a cleanup function; declare an inner async function.

Likely follow-ups

How do you fetch data safely in an effect?
Start the request, keep an ignore flag or AbortController, set state only if still current, and clear in cleanup. Prefer a data library for caching and deduplication.
What happens if you omit the dependency array?
The effect runs after every render, which is rarely intended.
useEffect versus useLayoutEffect?
Passive after paint versus synchronous before paint; use layout only for measurements or preventing visual flicker.
Why do you get “Cannot update an unmounted component” type bugs?
An async callback sets state after the component left; cleanup must cancel or ignore it.

Re-renders and memoisation

“Why does a component re-render? How do you prevent unnecessary re-renders? Explain React.memo, useMemo and useCallback, and when they help or hurt. What does the React Compiler change? How do you profile?”

Say this first (30 seconds)

“A component re-renders when its state changes, when its parent re-renders, or when a context it consumes changes. By default, a parent re-render re-renders all its children, which is usually fine because renders are cheap and the DOM only changes if output differs. I optimise only when the profiler shows a real problem. First I restructure: move state down, lift expensive parts up, or pass them as children so they are not recreated. Then I use memoisation: React.memo skips a component when its props are shallowly equal, useMemo caches a computed value, and useCallback caches a function so props stay referentially stable. Overusing them adds cost and complexity. The React Compiler automates most of this memoisation at build time.”

Details interviewers probe

  • Why a component renders: its own state or reducer update, a parent render, a context change, or a store subscription via useSyncExternalStore. Props changing alone does not cause a render; a parent rendering does.
  • React.memo: wraps a component so that, if props are shallow-equal (Object.is per prop), React reuses the last result. A custom comparison function is possible but rarely worth it. State and context changes inside the memoised component still re-render it.
  • useMemo: caches a calculation between renders until dependencies change. Use for expensive computations (filter and sort of large data) and to keep object identity stable for memoised children or effect dependencies. React may discard the cache, so it is a performance hint, not a semantic guarantee.
  • useCallback: useCallback(fn, deps) equals useMemo(() => fn, deps); keeps the function identity stable for memoised children, effect dependencies, and context values.
  • Costs of memoisation: comparison work, memory, code noise, and bugs from wrong dependencies. It helps only when the skipped work is bigger than the comparison, and when props really are stable.
  • Structural fixes first: colocate state; split a component so the changing part is small; children as a prop (the elements are created by the parent that is not re-rendering, so React keeps them); avoid creating components in render; move static data outside the component.
  • Context re-renders: every consumer re-renders when the context value changes, even if it uses only a part and even if wrapped in memo. Mitigate: split contexts by update frequency (state and dispatch separately), memoise the provider value, keep fast-changing values out of context, or use a selector-based store (Zustand, Redux, use-context-selector).
  • Lists: long lists are costly because of many items, not because of one render. Virtualise (react-window, TanStack Virtual), paginate, and memoise row components with stable props.
  • Transitions: for slow renders caused by input (filtering a big list while typing), useTransition or useDeferredValue keep typing responsive (R9).
  • React Compiler: a build-time tool (Babel plugin/SWC integration) that analyses components that follow the Rules of React and inserts memoisation automatically, so manual memo, useMemo and useCallback become mostly unnecessary. Components that break the rules are skipped. Stable in recent versions verify release status and framework support.
  • Profiling: React DevTools Profiler (record, flamegraph, “why did this render?”), the browser Performance panel, <Profiler> component for programmatic timing, why-did-you-render, and measuring real user interactions (INP). Measure before and after; fix the slow commits, not every render.
  • Other costs: large bundles and hydration, layout thrash, huge DOM size, expensive effects, and network waterfalls often matter more than re-renders.
  • Keep values stable on purpose: pass primitives rather than objects when possible; derive inside the child; lift constants out of the component.

Traps

  • Wrapping everything in memo/useCallback “for performance” without measuring.
  • Memoising a component but passing it inline objects or functions, so the memo never hits.
  • Thinking useMemo guarantees the value is never recomputed.
  • Putting frequently changing state in a single large context.
  • Saying re-renders are bad. They are normal; unnecessary expensive ones are the problem.

Likely follow-ups

How do you find out why a component re-rendered?
React DevTools Profiler with “record why each component rendered”, which shows props, state, hooks or context changes.
When is useCallback actually useful?
When the function is passed to a memoised child, used in a dependency array, or provided through context. Otherwise it adds cost.
What is the “children as props” optimisation?
Elements passed as children were created by an ancestor that did not re-render, so React reuses them when the wrapper’s state changes.
How would you optimise a slow table with 10,000 rows?
Server-side pagination or filtering, virtualisation, memoised rows with stable props, transitions for filtering, and avoiding per-row context or heavy effects.

Hooks: rules and the built-in set

“What are hooks and why were they introduced? What are the rules of hooks and why do they exist? Explain useRef, useReducer, useContext, useId and custom hooks.”

Say this first (30 seconds)

“Hooks let function components use state, lifecycle-like behaviour and other React features, and let me extract and reuse stateful logic as custom hooks without wrapper components or class inheritance. They replaced classes, HOCs and render props for most logic reuse. The two rules are: call hooks only at the top level, never in conditions, loops or nested functions, and call them only from function components or other hooks. The reason is that React identifies each hook by the order of calls in a component, kept as a list on the fiber; changing the order between renders would mismatch the stored state. The built-ins I use constantly are useState, useReducer, useEffect, useRef, useContext, useMemo and useCallback, plus useId, useTransition and useSyncExternalStore when needed.”

Details interviewers probe

  • Why hooks: classes made logic reuse hard (HOCs created wrapper hell, render props nested deeply), split related logic across lifecycle methods, confused with this, and optimised poorly. Hooks group logic by concern and compose by calling functions.
  • useRef: a mutable box { current } that persists for the component’s lifetime and does not trigger re-renders when changed. Uses: DOM nodes, timer ids, the previous value, the latest callback or value (to avoid stale closures), instance-like variables. Do not read or write ref.current during render (except lazy initialisation) because it breaks purity.
  • useReducer: [state, dispatch] = useReducer(reducer, initial). The reducer is pure and returns new state for an action. Benefits: all transitions in one place, easy unit tests, stable dispatch identity for context and memoised children, and clearer modelling of related fields. Redux uses the same idea.
  • useContext: reads the nearest provider value for a context. All consumers re-render when the value changes (R5). Provide a sensible default or throw in a custom useX() hook if the provider is missing. React 19 also lets you render <Context value=…> directly verify version.
  • useId: generates a stable unique id that matches on server and client, for linking label htmlFor and aria-* attributes. Do not use it for list keys.
  • useImperativeHandle: customise what a parent gets through a ref (expose focus(), reset()) instead of the raw DOM node. Rare; prefer props and state.
  • useSyncExternalStore: subscribe to an external store safely with concurrent rendering (no tearing); used by libraries such as Redux, Zustand, and for matchMedia or navigator.onLine.
  • use (React 19): reads a promise or a context during render; with a promise it integrates with Suspense. Unlike other hooks it may be called conditionally verify.
  • Custom hooks: functions whose names start with use and that call other hooks. They share logic, not state: each call has its own state. Examples: useDebounce, useLocalStorage, useMediaQuery, useOnClickOutside, useFetch. Design them with a clear input and output, stable returned references where they matter, cleanup for subscriptions, and no hidden global state.
  • Testing custom hooks: renderHook from Testing Library, or test through a component that uses them.
  • Class lifecycle mapping: see R10. Hooks do not map one-to-one; think “synchronise with values” rather than “on mount/update”.
  • Common mistakes: hooks in conditions or loops, hooks after an early return, stale closures, missing dependencies, creating a custom hook that only wraps one useState with no logic, over-abstracting.

Traps

  • Saying hooks “do not work in conditions because of magic”. State the call-order reason precisely.
  • Calling a hook after an early return, which makes the number of hooks vary between renders.
  • Believing custom hooks share state between components. They share code, not instances.
  • Writing to ref.current during render, or expecting a ref change to re-render.
  • Using useRef for data that should drive the UI; that is state.

Likely follow-ups

Difference between useRef and useState?
State updates re-render and are for UI data; refs do not re-render and are for mutable values outside the render output, such as DOM nodes and timers.
How do you get the previous value of a prop?
Store it in a ref updated in an effect, or restructure so you do not need it; a custom usePrevious hook does exactly this.
Can hooks be used in classes?
No. Use a function component or a wrapper; classes remain supported but are not recommended for new code.
How do you share state between components using a custom hook?
Hooks do not share state. Lift state, use context or a store, and have the hook read from it.

Composition and component patterns

“How do you share logic and UI between components? Explain props, children, higher-order components, render props, compound components and controlled versus uncontrolled components. How do you avoid prop drilling?”

Say this first (30 seconds)

“React favours composition over inheritance. I build components that accept children or render slots and compose them, instead of extending classes. For sharing logic I write custom hooks; for sharing UI structure, children and slots. Older patterns still appear in codebases: a higher-order component wraps a component and injects props or behaviour, render props pass a function that returns UI. Compound components, like <Tabs> with <Tabs.List> and <Tabs.Panel>, share implicit state through context so the consumer controls layout. To avoid prop drilling I first restructure with composition, passing the rendered element down as children; if many distant components need the data, I use context or a store. I also design components to be controlled or uncontrolled, following native inputs.”

Details interviewers probe

  • Props and children: children is just a prop; you can also pass named slots as props (header, footer) that hold elements. This inverts control and avoids drilling.
  • Higher-order component (HOC): a function that takes a component and returns a new one (withAuth(Page)). Costs: wrapper hell, prop name collisions, hard typing and debugging, static method loss (use hoist-non-react-statics), and refs need forwarding. Still used for cross-cutting concerns in older code and libraries (Redux connect, withRouter).
  • Render props: a component takes a function prop that returns UI (<Mouse render={pos => …} /> or children as a function). Flexible but nests deeply. Hooks replaced most uses; they remain useful for libraries that need to control when and where to render (virtualised lists, Formik, Downshift).
  • Compound components: a parent with subcomponents attached (Menu.Item) sharing state through context (or cloneElement in old code, which is brittle). Gives flexible markup with coordinated behaviour. Headless libraries are built this way.
  • Controlled versus uncontrolled: controlled components take state from props and report changes; uncontrolled keep their own. Make design-system inputs support both, and warn when switching modes (the native input warning “changing an uncontrolled input to be controlled”).
  • Container and presentational split: separate data logic from rendering. Hooks make a lighter version: the component calls a hook for logic and renders markup. It improves testability and Storybook stories.
  • Prop drilling: passing props through components that do not use them. Acceptable for one or two levels; beyond that use composition or context. Do not reach for global state first.
  • Context best practice: for low-frequency values (theme, locale, auth user); split state and dispatch contexts; memoise the value; provide a custom hook with a helpful error; avoid using context for rapidly changing data (R5).
  • Polymorphic components: an as prop that changes the rendered element (<Button as="a" href>), or asChild (Radix Slot) that merges props onto a child. Useful in design systems; typing is complex (T10).
  • Lists, keys and slots in libraries: prefer APIs that accept render functions for items (renderItem) or children, instead of data-only configuration, to avoid reinventing every option.
  • Composition with hooks: compose small hooks (useDebounce + useFetch → useSearch) instead of growing one large hook.
  • API design principles: small surface, sensible defaults, escape hatches (className, ...rest forwarded to the DOM element, ref), accessible by default, consistent naming (onChange, isOpen, defaultOpen), avoid boolean prop explosion (use variants or composition).
  • Inheritance: React recommends against class inheritance for components; composition covers every case.

Traps

  • Jumping straight to global state or context to avoid passing a prop through two levels.
  • Putting fast-changing data in context and wondering why the whole tree re-renders.
  • Building components with dozens of boolean props instead of composition or variants.
  • Using cloneElement or Children.map tricks for implicit communication in new code; context is more robust.
  • Describing HOCs as obsolete without knowing where they still appear and why they were replaced.

Likely follow-ups

HOC versus hook: when would you still use a HOC?
When you must wrap and alter rendering or props of a component you do not control, apply a cross-cutting concern uniformly (instrumentation), or support class components.
How would you build a reusable modal?
A controlled open/onClose API, rendered in a portal with focus trap, Escape handling, scroll lock, ARIA roles, and slots for header, body and footer (R10, R13).
What are headless components?
Components or hooks that provide behaviour and accessibility with no styling (Radix, React Aria, Downshift), leaving markup and style to you.
How do you decide where state lives?
Start local, lift to the nearest common parent when shared, move to context or a store only when many distant components need it.

Forms, controlled inputs and actions

“How do you handle forms in React? Controlled versus uncontrolled inputs, validation, and the form libraries. What are Actions, useActionState, useFormStatus and useOptimistic in React 19?”

Say this first (30 seconds)

“A controlled input keeps its value in React state and updates through onChange, so React is the single source of truth and I can validate, format and conditionally disable on every change. An uncontrolled input keeps its value in the DOM, and I read it on submit with a ref or FormData, which means fewer re-renders and less code. For small forms either works; for large, complex forms I use a library such as React Hook Form, which uses uncontrolled inputs under the hood for performance, with a schema validator like Zod. React 19 adds form Actions: pass a function to the form’s action, and React handles pending state, errors and resets with useActionState, useFormStatus and useOptimistic, which also work with Server Actions.”

Details interviewers probe

  • Controlled input rules: always pair value with onChange (or readOnly); never let a controlled value become undefined (use ''), or React warns about switching between uncontrolled and controlled. For checkboxes use checked; for selects use value on <select>; <input type="file"> is always uncontrolled.
  • One handler for many fields: use the input’s name and e.target.value with a computed key and an immutable update, or useReducer.
  • Validation strategy: validate on blur or submit first, then on change after the first error; show errors near fields with aria-invalid and aria-describedby; use schema validation shared with the server (Zod, Yup, Valibot); the server must always validate too.
  • Debouncing and expensive validation: validate asynchronously (username availability) with debounce and cancellation (J22).
  • React Hook Form: minimal re-renders, register, Controller for controlled UI components, resolvers for Zod, field arrays, formState. Formik is older and re-renders more; TanStack Form is a newer typed alternative.
  • Native features first: HTML constraint validation (required, pattern, type="email"), autocomplete attributes, correct type and inputMode for mobile keyboards, and a real <form> with a submit button so Enter works.
  • React 19 Actions: an action is a function (sync or async) passed to <form action> or called inside a transition. React tracks pending state, handles errors, and resets uncontrolled form fields on success. useActionState(fn, initialState) returns [state, formAction, isPending]. useFormStatus() (from react-dom) gives pending to a child of the form, such as a submit button. useOptimistic(state, reducer) shows a temporary value while an action is in flight and reverts it if the action fails verify names and semantics for the installed React version.
  • Server Actions: functions marked 'use server' that the client calls like a function, executed on the server (Next.js guide). They are public HTTP endpoints: validate and authorise inside them.
  • Progressive enhancement: forms using Actions can work before hydration when the action is a server action.
  • Accessibility: every input has a visible <label> (htmlFor/useId), errors are announced (role="alert" or aria-live), focus moves to the first invalid field on submit, and disabled buttons are not the only feedback (R13).
  • Large forms and wizards: split into sections or steps, keep per-step validation, persist drafts (URL or storage), and model the flow as a state machine.
  • Preventing double submit: use pending state to disable the button and an idempotency key on the server.

Traps

  • Setting value without onChange, creating a read-only field.
  • Initialising controlled state as undefined and triggering the controlled/uncontrolled warning.
  • Re-rendering a huge form on every keystroke with all fields in one state object; split fields or use an uncontrolled library.
  • Trusting client-side validation as security.
  • Using placeholders as labels, or errors that are not associated with fields.

Likely follow-ups

Why is a file input uncontrolled?
Browsers do not let scripts set its value for security; you read files from the DOM or FormData.
How do you validate on the client and the server without duplicating rules?
Share a schema package (Zod) used by both, and map server errors back to fields.
What does useOptimistic solve?
Instant UI feedback (a like, a new message) while the request is pending, with automatic rollback if it fails.
Controlled or uncontrolled for a design-system input?
Support both: value/onChange for control and defaultValue for uncontrolled, forwarding native props and refs.

Concurrent rendering and Suspense

“What is concurrent rendering in React 18? Explain transitions, useDeferredValue, Suspense, lazy loading and streaming. How does React keep the UI responsive?”

Say this first (30 seconds)

“Concurrent rendering means React can prepare a new UI in the background, pause, resume or abandon it, and keep the screen responsive to urgent input. It is still single-threaded; React splits rendering into small units and yields to the browser between them. I mark updates as urgent or non-urgent: typing is urgent, filtering a large list in response is not, so I wrap that update in startTransition or use useDeferredValue; React keeps showing the old UI until the new one is ready and interrupts the slow render if the user types again. Suspense lets a component declare that it is waiting, for code from React.lazy or for data, and shows a fallback until it resolves; with streaming server rendering the shell is sent first and slower parts stream in later.”

Details interviewers probe

  • What “concurrent” means: rendering is interruptible and prioritised. React 18 enables it through createRoot and features that opt in (transitions, useDeferredValue, Suspense). Existing code behaves as before unless it uses them. JavaScript is still single-threaded; React cooperates with the event loop (J18) and yields between small chunks.
  • Priorities (lanes): discrete events (clicks, input) are highest, continuous events (scroll, mouse move) next, transitions lower, and offscreen work lowest. A higher-priority update can interrupt a lower-priority render; the render phase must be pure for that to be safe (R1).
  • useTransition and startTransition: mark state updates as non-urgent. isPending lets you show a subtle indicator. If a transition suspends, React keeps the current UI instead of showing the fallback again (no “flash of loading”). A transition callback must be synchronous in older versions; React 19 supports async actions inside transitions verify.
  • useDeferredValue: returns a value that lags behind during urgent updates; pass the deferred value to the slow child (often memoised) so typing stays fast. Use it when you do not control where the update starts (a prop from a parent or a library).
  • Suspense: a boundary that shows fallback while any child is suspended. It works with React.lazy, framework data loading (Next.js, Relay), and libraries that integrate (TanStack Query suspense mode). With React 19 the use(promise) API reads a promise created outside render. Do not create the promise inside the same component render, because it would be recreated each time.
  • Code splitting: const Page = lazy(() => import('./Page')) wrapped in Suspense; split by route first, then by heavy widgets (editors, charts, modals); prefetch on hover or idle.
  • Streaming SSR: the server sends the HTML shell with fallbacks, then streams completed Suspense boundaries as they resolve; selective hydration lets React hydrate the parts the user interacts with first, rather than blocking on the whole page (Next.js guide).
  • Avoid waterfalls: fetching in nested components that each suspend one after another is slow. Start requests in parallel at the route level or use server components and preloading.
  • Boundaries design: place them at meaningful UI regions with matching skeletons that do not shift layout; avoid a single giant boundary and avoid a boundary around every component.
  • Tearing and external stores: concurrent rendering can read an external mutable store at two moments; useSyncExternalStore prevents inconsistency (R6).
  • Offscreen/Activity verify availability: keeps hidden UI mounted with preserved state and lowered priority, useful for tabs and back navigation.
  • Measuring: use the Profiler and real interaction metrics (INP); transitions help interaction responsiveness, not raw render cost.
  • Pitfalls: side effects in render break under interruption; transitions do not defer effects; wrapping the controlled input value in a transition makes typing feel laggy.

Traps

  • Saying concurrent React is multi-threaded or uses Web Workers. It time-slices on the main thread.
  • Putting the input’s own state update in startTransition. The input must update urgently.
  • Using Suspense as a data-fetching tool by itself; it only coordinates waiting.
  • Wrapping the whole app in one Suspense boundary so any lazy part blanks the page.
  • Believing transitions reduce CPU work. They only reorder and allow interruption.

Likely follow-ups

How would you keep a search box responsive while filtering 20,000 items?
Keep the input state urgent, defer the filter with useDeferredValue or a transition, memoise the list, and virtualise rendering; consider server-side filtering.
useTransition versus useDeferredValue?
Transition wraps the setter where you own the update; deferred value wraps the value when you only receive it.
What happens to the old UI during a suspended transition?
It stays visible (with isPending true) until the new tree is ready.
How does Suspense relate to error boundaries?
Suspense handles “not ready yet”; error boundaries handle “failed”. They are used together around async parts.

Error boundaries, portals, refs and class lifecycle

“How do error boundaries work and what do they not catch? What is a portal and how do events behave? How do refs work? How do class lifecycle methods map to hooks?”

Say this first (30 seconds)

“An error boundary is a class component that catches errors thrown while rendering its descendants, in lifecycle methods and constructors, and shows a fallback instead of unmounting the whole app. It does not catch errors in event handlers, async code, server rendering or in itself, so those need their own try/catch and reporting. A portal renders children into a different DOM node, such as document.body, for modals, tooltips and dropdowns, while keeping them in the React tree, so context and event bubbling still work as if they were nested. Refs give direct access to a DOM node or a mutable value without re-rendering; I use them for focus, measurement and integrating non-React libraries. Class lifecycle methods map loosely to hooks, but effects are about synchronisation, not lifecycle events.”

Details interviewers probe

  • Writing an error boundary: a class with static getDerivedStateFromError(error) (return state to render the fallback) and componentDidCatch(error, info) (log, report). No hook equivalent exists; use the react-error-boundary package for function-component ergonomics (reset on key change, onReset, useErrorBoundary to bubble async errors).
  • Strategy: a top-level boundary as a safety net; boundaries per route or major widget so one failure does not blank the app; reset the boundary when the user retries or navigates; report to Sentry with component stack and release; show helpful messages and a retry action. Next.js provides error.js and global-error.js.
  • Bridging async errors: catch the error and rethrow in state (setState(() => { throw err })) so a boundary handles it, or use useErrorBoundary.
  • Portals: createPortal(children, domNode). Use for modals, popovers, tooltips, toasts. Events bubble through the React tree (not the DOM tree), so a click in a portal reaches React ancestors’ onClick. Context works. CSS inheritance follows the DOM, so styles of the original parent do not apply. Accessibility needs explicit work: focus trap, aria-modal, inert on the rest, return focus on close (R13). The native <dialog> and Popover API reduce the need.
  • Refs: useRef for a DOM node (<input ref={ref}/>) or mutable value. Callback refs (ref={node => …}) run on attach and detach; React 19 allows returning a cleanup function from a ref callback verify. Refs are set after commit, so read them in effects or event handlers, not during render.
  • Passing refs to components: function components cannot receive ref as a special prop before React 19; wrap with forwardRef. In React 19 ref is a regular prop, and forwardRef is being phased out verify. useImperativeHandle limits what the parent can call.
  • When to use refs: focus management, text selection, scrolling, measuring (with getBoundingClientRect), media playback, integrating libraries (D3, maps, editors), storing timers or previous values. Avoid using refs to read or write data that should be state or props.
  • Class lifecycle review: mounting (constructor, render, componentDidMount), updating (shouldComponentUpdate, render, getSnapshotBeforeUpdate, componentDidUpdate), unmounting (componentWillUnmount), errors (getDerivedStateFromError, componentDidCatch). Legacy componentWillMount/Receive/Update are unsafe under concurrent rendering and deprecated.
  • Class versus function components: both supported; function components with hooks are preferred. Classes remain for error boundaries and legacy code. Migrating is incremental; interop works both ways.
  • Fragments and strict structure: <></> avoids extra DOM nodes; keyed fragments for lists.
  • flushSync and unstable_batchedUpdates: escape hatches for integrating with the DOM synchronously; rarely needed.
  • Hydration errors: mismatches between server HTML and the first client render (dates, random values, browser-only checks) cause warnings or re-renders; render client-only values in an effect or use suppressHydrationWarning for known cases.

Traps

  • Assuming an error boundary catches errors in event handlers or fetch callbacks.
  • One global boundary only, so every failure shows the same blank error page.
  • Believing portal content escapes React events or context. It does not.
  • Reading ref.current during render and getting null on the first pass.
  • Forgetting focus management after opening and closing a portal-based modal.

Likely follow-ups

Why must error boundaries be classes?
The error-catching lifecycle methods have no hook equivalent yet; the API is class-only, though wrappers hide that.
How do events work with portals?
React synthetic events bubble through the React component tree, even though the DOM nodes live elsewhere.
How would you recover from a boundary error?
Provide a retry that resets the boundary (changing its key or calling reset), optionally after refetching data.
What replaces componentDidUpdate comparisons of previous props?
An effect with dependencies, or a ref storing the previous value, or deriving during render.

Server Components and React 19

“What are React Server Components? How do they differ from SSR? What does 'use client' mean? What is new in React 19?”

Say this first (30 seconds)

“React Server Components are components that run only on the server, ahead of time or per request. They can read databases and files directly, are never shipped to the browser, and so add no JavaScript to the bundle. They send a serialised description of the rendered tree to the client, which React merges with interactive parts. This is different from SSR, which renders the same components to HTML on the server and then hydrates them in the browser. Components are server components by default in frameworks like the Next.js App Router; a 'use client' directive marks a boundary where components, and everything they import, become client components that can use state, effects and browser APIs. React 19 stabilised this model and added Actions, use, useOptimistic, ref as a prop, document metadata support, and improved error reporting.”

Details interviewers probe

  • Why Server Components: smaller bundles (heavy libraries like Markdown parsers or date libraries stay on the server), direct and secure data access without an API layer, fewer client-side waterfalls, and automatic code splitting at the boundary. Trade-offs: new mental model, server infrastructure needed, constraints on what can cross the boundary, and framework dependence.
  • Rules: server components can be async and await data; they cannot use state, effects, event handlers, browser APIs or context consumers. Client components ('use client' at the top of a file) can use all hooks. A client component cannot import a server component, but can receive one as children or a prop, which keeps it server-rendered.
  • Boundary rules: 'use client' marks a module boundary: the file and its imports are client code. Put it as deep (as leaf) as possible to keep most of the tree on the server. Props crossing the boundary must be serialisable (primitives, plain objects, arrays, Dates, promises in React 19, server actions), not functions or class instances.
  • Server Actions: async functions with 'use server' callable from the client; they run on the server, are exposed as endpoints, and need input validation and authorisation (R8). Used as form actions or inside transitions; they can revalidate caches in the framework.
  • Data fetching pattern: fetch where the data is needed in server components; run independent requests in parallel (Promise.all); pass data down; use Suspense to stream slow parts; keep client-side fetching for interactive, user-driven data (TanStack Query).
  • Context and state: server components cannot read context; providers are client components wrapping children. Global client state lives in client components; avoid request-scoped state in module variables on the server (shared across requests).
  • React 19 highlights verify against the release notes: Actions (async functions in transitions, with pending, error and optimistic handling), useActionState, useFormStatus, useOptimistic, use (read promises and context), ref as a prop (and cleanup functions for ref callbacks), <Context> as a provider, built-in support for <title>, <meta> and <link> hoisting, stylesheet and script resource APIs (preload, preinit), better hydration errors, custom elements support, and ref/cleanup improvements. The React Compiler is a separate build tool (R5).
  • Who implements RSC: Next.js App Router is the main production implementation; others include Waku, Parcel and Redwood experiments, and bundler plugins. Plain Vite/CRA apps do not have RSC.
  • Mixing with existing apps: migrate gradually: new routes in the App Router, client components for existing interactive parts, shared libraries marked with 'use client' where needed.
  • Security: server-only code must not leak: use server-only package markers, never pass secrets or full database rows as props, and treat actions like public APIs (J29). Recent versions had RSC-related vulnerabilities; keep React and the framework patched verify advisories.
  • Caching: frameworks add caching layers for server component data (Next.js guide); understand revalidation to avoid stale data.

Traps

  • “Server Components are SSR.” They are different: SSR renders client components to HTML and still hydrates them; RSC code never reaches the browser.
  • Marking a high-level layout 'use client' and making the whole tree client-side.
  • Passing functions, class instances or secrets across the boundary.
  • Expecting useState or useEffect in a server component.
  • Treating server actions as private functions instead of public endpoints.

Likely follow-ups

Can a client component render a server component?
Not by importing it, but it can receive it as children or another prop from a server component parent, and React renders it on the server.
How do you share state between server and client?
The server passes serialisable props; the client manages its own state afterwards. For data that changes, refetch or revalidate.
Do Server Components replace data libraries?
For initial data, often yes; for interactive client-side data (polling, optimistic updates, infinite scroll) a library still helps.
What does the React Compiler do and is it related?
It memoises client components at build time; it is independent of Server Components.

Testing React applications

“How do you test React applications? What is the testing philosophy of React Testing Library? How do you test async behaviour, hooks and API calls? What do you test at each level?”

Say this first (30 seconds)

“I test behaviour the way a user experiences it, not implementation details. React Testing Library renders a component and queries it by accessible roles and labels, then interacts with user-event; if I refactor internals the tests still pass. I layer tests: unit tests for pure logic and hooks, component and integration tests with Testing Library and Vitest or Jest, network calls mocked at the HTTP level with MSW so the real fetching code runs, and a smaller set of end-to-end tests with Playwright for critical journeys. I avoid snapshot tests of big trees and tests that assert on state or internal calls. I test loading, error and empty states, accessibility basics, and keep tests fast and deterministic.”

Details interviewers probe

  • React Testing Library (RTL): renders into a real DOM (jsdom or a browser runner), exposes queries mirroring user perception, and discourages testing component instances, state or hooks directly. Use userEvent (realistic event sequences) over fireEvent; await its calls in v14.
  • Async behaviour: use findBy* or waitFor for things that appear later; do not use arbitrary sleeps; fake timers (vi.useFakeTimers) for debounce and timeouts. act warnings mean updates happened outside the test’s awareness; usually fixed by awaiting the right query.
  • Mocking the network: MSW intercepts requests at the network layer, so components use the real fetch/axios code and tests describe responses (success, 500, slow). It also works in the browser for development and Storybook. Avoid mocking fetch or modules per test; it couples tests to implementation.
  • What to mock: things you do not own at the boundary (network, time, randomness, third-party SDKs, browser APIs like IntersectionObserver). Do not mock your own child components or hooks unless there is a strong reason.
  • Hooks: test via renderHook, or through a component. Prefer testing the visible effect of a hook in the component that uses it.
  • Context, routing and stores: wrap in a renderWithProviders helper that creates fresh providers (QueryClient with retries off, a router, a store) per test to avoid shared state.
  • What to test: rendering for key states (loading, empty, error, success), user interactions and resulting UI, form validation, permissions and conditional UI, accessibility (roles, labels, keyboard), and edge cases. Not: library internals, styling, implementation details, trivial getters.
  • Snapshots: small inline snapshots for stable output are fine; large snapshot files are brittle and get approved without reading. Visual regression tools (Chromatic, Playwright screenshots) are better for UI appearance.
  • Runners: Vitest (fast, Vite-native, Jest-compatible API) or Jest; Playwright for end-to-end (cross-browser, auto-waiting, tracing, parallel); Cypress is an alternative. Component testing in a real browser is available (Playwright/Cypress component mode, Vitest browser mode).
  • Server Components and Next.js: server components are hard to unit-test; test the pure data functions, use integration/e2e tests for pages, and Testing Library for client components. Mock next/navigation only when necessary verify current guidance.
  • Accessibility testing: jest-axe/vitest-axe and Playwright axe checks catch a subset of issues; manual keyboard and screen-reader checks are still needed.
  • Quality practices: keep tests independent and parallel-safe, avoid shared mutable fixtures, name tests as behaviours, run in CI on every PR, track flakiness, and treat a flaky test as a bug. Coverage is a signal, not a goal.
  • Test data: factories or builders; MSW handlers per scenario; Storybook stories as living fixtures with interaction tests (play functions).
  • TDD in UI: useful for logic-heavy parts (reducers, validation); for UI start from user stories and test through the DOM.

Traps

  • Testing implementation details: component state, instance methods, number of renders, CSS class names.
  • Defaulting to getByTestId everywhere instead of role and label queries.
  • Mocking every dependency, so the test passes while the real wiring is broken.
  • Sharing a QueryClient or store across tests so results leak between them.
  • Chasing 100% coverage with shallow tests and trusting it.

Likely follow-ups

Why getByRole first?
It matches how assistive technology and users find elements, and it fails if the markup is not accessible, so it tests accessibility for free.
How do you test a component that debounces?
Fake timers, advance by the delay, then assert; or assert on the final network request with MSW.
Unit versus integration versus end-to-end for a checkout flow?
Unit for price calculation, integration for the form with mocked API, and a small number of end-to-end tests for the full purchase on a staging environment.
How do you deal with flaky end-to-end tests?
Use auto-waiting locators, isolate test data, avoid fixed sleeps, trace failures, quarantine and fix quickly.
R13Added

Accessibility, security and i18n

“How do you make a React app accessible? How do you manage focus in SPAs and modals? What are React’s security considerations? How do you handle internationalisation?”

Say this first (30 seconds)

“Accessibility starts with semantic HTML: real buttons, links, headings, labels and landmarks, which already give keyboard and screen reader support. In React I add what single-page apps break: managing focus after route changes and in dialogs, announcing dynamic updates with live regions, keeping everything keyboard operable, and ARIA only where HTML has no native equivalent. I check with eslint-plugin-jsx-a11y, axe, keyboard-only testing and a screen reader. For security, React escapes interpolated text, so XSS risk comes from dangerouslySetInnerHTML, unsafe URLs, third-party code and server-rendered HTML. For internationalisation I use a library such as react-i18next or FormatJS with ICU messages and Intl APIs, avoid string concatenation, and design for right-to-left and text expansion.”

Details interviewers probe

  • Semantic HTML: <button> for actions, <a href> for navigation, <nav>, <main>, headings in order, lists, <label>, <fieldset>. A clickable <div> lacks keyboard, role and focus; fixing it with ARIA is more work than using a button.
  • ARIA: “no ARIA is better than bad ARIA”. Use roles and states (aria-expanded, aria-controls, aria-live, aria-invalid) to describe custom widgets, and follow the WAI-ARIA Authoring Practices patterns (tabs, combobox, menu, dialog).
  • Focus management in SPAs: client-side navigation does not reload the page, so screen readers receive no signal. Move focus to the main heading or container, update the title, and announce route changes (routers and Next.js provide a route announcer). In React use refs and focus() after render (effect). Never remove the focus outline without a replacement (:focus-visible).
  • Dialogs: focus trap (or inert on the background), aria-modal, Escape to close, scroll lock, return focus to the trigger. The native <dialog>.showModal() does most of this. Menus and comboboxes need arrow-key handling and aria-activedescendant or roving tabindex.
  • Live regions: role="status" or aria-live="polite" for toasts, search result counts and async status; role="alert" for errors. The region must exist in the DOM before its content changes.
  • Forms and images: visible labels, error association, required indicators not by colour alone; meaningful alt or empty alt="" for decorative images; captions for media.
  • Colour and motion: contrast ratios (WCAG AA 4.5:1 text), do not rely on colour alone, respect prefers-reduced-motion, support zoom and text resize without breaking layout.
  • Testing accessibility: lint (jsx-a11y), automated axe in tests and CI, Storybook a11y addon, keyboard-only walkthrough, screen reader smoke tests (NVDA, VoiceOver), and real user feedback. Automated tools find about a third of issues.
  • React-specific: htmlFor and useId for label association, fragments to avoid invalid markup, keys do not reach the DOM, ref for focus, and avoid tabIndex > 0.
  • Security in React: escaping covers interpolation; risk comes from dangerouslySetInnerHTML (sanitise with DOMPurify first), user-controlled href/src (validate scheme), target="_blank" without rel="noopener" (default in modern browsers), server rendering of unsanitised content, third-party widgets, dependency vulnerabilities, and storing tokens in localStorage. Environment variables with a public prefix are visible to everyone. Server Actions are public endpoints. Full details in J29 and the protocols guide.
  • Internationalisation (i18n): libraries: react-i18next, FormatJS (react-intl), LinguiJS, next-intl. Use message catalogues with ICU syntax for plurals, gender and variables; never concatenate sentences. Use Intl.DateTimeFormat, NumberFormat, RelativeTimeFormat (J31). Load locale bundles lazily. Keys: stable ids or source strings.
  • Layout concerns: right-to-left (dir="rtl", logical CSS properties like margin-inline-start), text expansion (German is about 30% longer), fonts for scripts, locale-aware sorting (Intl.Collator), time zones, currency, and pseudo-localisation in testing.
  • Routing and SEO: locale in the URL (/en/, /de/), lang attribute on <html>, hreflang alternates, server-side locale detection with user override.

Traps

  • Building custom widgets from divs with onClick and no keyboard support.
  • Adding ARIA that contradicts native semantics, such as role="button" on a link.
  • Forgetting focus after route changes and modal close.
  • Claiming “React prevents XSS” while using dangerouslySetInnerHTML on user content.
  • Hard-coding English strings, dates and number formats into components.

Likely follow-ups

How would you make a custom dropdown accessible?
Prefer a native <select> or a headless library; otherwise implement the combobox/listbox pattern with correct roles, keyboard navigation, aria-expanded and active-descendant management.
What is a skip link?
A first focusable link that jumps past navigation to the main content, important for keyboard users.
How do you support multiple languages without bloating the bundle?
Lazy-load locale files per route or language and share a message extraction workflow.
How do you audit a React app for accessibility?
Automated checks (axe, lint), keyboard walkthrough of core flows, screen reader pass, colour and zoom checks, and add checks to CI and design reviews.

Designing components and features

“Design a typeahead or autocomplete component. How would you design an infinite scroll feed, a data table, or a multi-step form? How do you structure a scalable React project?”

Say this first (30 seconds)

“For any frontend design question I follow the same frame: clarify requirements and constraints, define the component API and data model, sketch the component tree and where state lives, choose the data-fetching and caching strategy, then cover performance, accessibility, error and edge states, and testing. For a typeahead that means: a controlled input with debounced queries, request cancellation so stale responses are ignored, caching of recent queries, keyboard navigation and a proper combobox ARIA pattern, highlighted matches, loading and empty states, and a headless design so styling is replaceable. I state trade-offs aloud, for example client versus server filtering depending on data size, and what I would measure.”

Project structure and scalability

  • Organise by feature (domain), not by file type: features/checkout/{components,hooks,api,types} plus shared ui/, lib/. Colocate tests and stories. Keep clear public entry points (index.ts) and restrict cross-feature imports with lint rules (boundaries plugin) or Nx module boundaries.
  • Layers: UI components (presentational), feature components, hooks (logic and data), services and API clients, utilities. Dependencies point inward; the UI does not know transport details.
  • State placement: local state by default; server state in a data library (TanStack Query); global client state sparingly (Zustand, Redux Toolkit); URL for shareable state (filters, tabs, pagination); form state in a form library.
  • Code splitting and performance budget: route-level lazy loading, dynamic imports for heavy widgets, analysis with bundle visualisers, image and font optimisation, set budgets in CI.
  • Conventions and tooling: TypeScript strict, ESLint with hooks and a11y rules, Prettier, path aliases, consistent naming, PR templates, Storybook for shared components, CI running type check, lint, tests and build.
  • Anti-patterns: huge components with data fetching and markup mixed, prop drilling more than two levels, global state for everything, derived state stored in state, effects for event logic, copy-pasted components with slight variations, deep inheritance of styles, premature abstraction, giant context providers, barrel files that defeat tree shaking.
  • Migration and evolution: strangler approach for legacy (class to hooks, CRA to Vite or Next.js), codemods, feature flags, and adapters that let old and new code coexist.
  • Leading the team: define the component API guidelines, review checklists (accessibility, performance, tests), and decision records for choices such as state library or styling approach.

Traps

  • Starting to code or name libraries before clarifying requirements.
  • Designing only the happy path: ignore loading, empty, error, offline and accessibility states.
  • Over-engineering with global state and abstractions for a small feature.
  • Ignoring scale: no pagination or virtualisation for lists that can grow.
  • Not stating trade-offs or alternatives, or never saying how you would measure success.

Likely follow-ups

How would you handle race conditions in search?
Abort the previous request, or tag each request and ignore responses that are not the latest; data libraries do this with query keys.
How would you virtualise a list with variable row heights?
Use a library that measures rows (TanStack Virtual, react-window variable size), estimate heights initially, and cache measured sizes.
How do you decide between client-side and server-side filtering?
By data size, latency needs and privacy: small datasets filter locally for instant feedback; large ones need server queries with debounce and pagination.
How would you structure a design for a team of 20 developers?
Feature modules with enforced boundaries, shared design system, clear ownership, contract-first APIs, CI checks and documented conventions.

How to answer React questions at L4

  • Lead with the model (“UI is a function of state; render is pure; commit touches the DOM”), then the rule, then the trade-off. This shows understanding rather than recall.
  • Always give the reason behind a rule: hooks order because of the fiber list, keys because of identity, cleanup because of synchronisation.
  • For performance questions start with measuring and structure (colocation, composition), then memoisation, then rendering strategies.
  • For design questions use the frame in R14: requirements, API, data, state, fetching, quality, trade-offs, and say what you would measure.
  • Bring a real example for each theme: a re-render problem you profiled, a stale closure, a leak, a migration, a design-system decision.
  • Version-specific points (React 19, Compiler, Server Components) are fine with “I would confirm the exact version details in the release notes”.
  • The interview is theoretical: expect “explain”, “compare”, “how would you design” and “what are the trade-offs”, not live coding.
