Box model and margin collapsing

“Explain the CSS box model. What does box-sizing: border-box change, and why do most teams set it globally? What is margin collapsing, and when does it happen?”

Say this first (30 seconds)

“Every element is a box with four layers: content, padding, border, margin. By default, width sets the content box only, so padding and border are added on top and a width: 100% element with padding overflows. box-sizing: border-box makes width include padding and border, so the size I write is the size I get. That is why teams set it globally. Margin collapsing is a separate rule: vertical margins of adjacent blocks in normal flow merge into one, the larger of the two, instead of adding up. It also happens between a parent and its first or last child, and for an empty block. It does not happen in flex or grid containers, with floats, absolute positioning, or inside a new block formatting context.”

box-sizing

*, *::before, *::after { box-sizing: border-box; }
/* inheritable alternative: html { box-sizing: border-box } *, *::before, *::after { box-sizing: inherit } */
  • Why global: width: 50% plus padding and border in two columns no longer overflows; sizes are predictable; matches how designers think; matches how most CSS frameworks work.
  • Gotchas: min-width, max-width, height follow the same rule. Percentage padding and margin are relative to the containing block’s width (inline size), even for top and bottom. border-box cannot make the content box negative: if padding is bigger than width, the box grows.
  • Form controls: buttons and selects are typically border-box in the UA stylesheet, text inputs are content-box in some browsers check MDN; the global reset removes the difference.
  • outline and box-shadow are not part of the box and do not affect layout.

Margin collapsing in detail

CaseResult
Adjacent siblings, both positivelarger margin wins
One negativelargest positive + most negative (they add)
Both negativemost negative wins
Parent and first child, no border, padding, inline content or BFC betweenchild’s top margin “escapes” and becomes the parent’s margin: the parent moves down, not the child inside it
Empty block (no height, border, padding)its own top and bottom margins collapse into one, and can collapse with neighbours
Flex or grid items, floats, absolutely positioned, inline-blocknever collapse
Horizontal marginsnever collapse (in horizontal writing modes)

Ways to stop or avoid it: add padding or border to the parent; make the parent a new block formatting context with display: flow-root (cleanest) or overflow: auto; use a flex or grid container; or avoid the problem by spacing with gap or one-directional margins (margin-block-start only, the “owl” selector * + * { margin-block-start: 1rem }).

Traps

  • This was the unanswered half of the earlier session. Practise saying margin collapsing in two sentences: siblings, parent and child, empty block; not in flex or grid.
  • Saying margins “add up” vertically. In normal block flow they do not.
  • Over-claiming how form inputs default. Say “varies by control, which is why I reset globally”.
  • Forgetting that inline (non-replaced) elements ignore vertical margin and width/height.

Likely follow-ups

Margin or padding for spacing?
Padding is inside the box (background, click area); margin is outside and can collapse. Spacing between siblings is best done by the parent with gap in flex or grid, so components do not carry outer margins.
Why does my parent move down when the child has margin-top?
Parent-child margin collapse. Add padding, border or display: flow-root to the parent.
What is a margin on auto?
Horizontal: centres a block with a set width. In flex, auto margins absorb free space on that axis.
How do you apply border-box to a third-party widget?
The inherit pattern lets a component opt out locally without fighting the universal selector.

Cascade, specificity and layers

“What is the CSS cascade? When two rules target the same element and set the same property, how does the browser decide which one wins?”

Say this first (30 seconds)

“The cascade is the algorithm that picks one value for each property from all the competing declarations. It goes in order and stops at the first step that decides. One: origin and importance, so browser, user and author styles, with !important reversing the order. Two: cascade layers. Three: specificity, which is a comparison of ids, then classes, attributes and pseudo-classes, then element types, not a single number. Four: order of appearance, so the last rule wins. Inline styles sit above normal author selectors. Inheritance is a separate mechanism that only applies if the cascade finds no value.”

Things that are easy to get wrong

  • !important reverses the origin order. Important UA beats important user beats important author. Normal rules are the other way round: author beats user beats UA. That is how a user’s forced-colours or large-text setting can win.
  • Animations and transitions are in the ladder: a running animation overrides normal author declarations; a transition overrides even !important author declarations while it runs.
  • Layers sit before specificity: a low-specificity rule in a later layer beats a high-specificity rule in an earlier layer. Unlayered CSS beats all layers (for normal declarations). @layer reset, base, components, utilities; declares the order once.
  • Specificity is a tuple. Inline style is above it (1,0,0,0 in older notation); !important is a different step, not extra specificity.
  • Inheritance: some properties inherit (color, font-*, line-height, cursor, visibility), most do not (margin, padding, border, background, width). The cascade picks the winner for the element; if none, inheritance, then the initial value.
  • Keywords: inherit, initial, unset (inherit if inheritable, else initial), revert (back to the previous origin, usually the browser default), revert-layer, and all: unset.
@layer reset, base, components, utilities;

@layer components { .btn { padding: .5rem 1rem; } }
@layer utilities  { .p-0 { padding: 0; } }   /* wins over .btn without raising specificity or !important */

/* debugging: DevTools > Elements > Styles shows crossed-out losers; Computed shows the final value and its source */

Specificity strategy in real projects

  • Keep selectors flat (one class), avoid ids and deep nesting, avoid !important except for utilities or overriding third-party CSS.
  • Use :where() to write low-specificity defaults in a design system, so consumers can override easily.
  • Use @layer to order third-party, base and component CSS instead of fighting specificity.
  • A naming convention (BEM, see C13) or CSS Modules keeps selectors single-class.

Traps

  • Describing specificity as a number or “ranking”. It is a comparison of three buckets, left to right.
  • Saying “last rule wins” first. Order is the last tie-break, not the first step.
  • Forgetting origin and importance, or getting the !important reversal wrong.
  • Omitting @layer; it is the modern answer to specificity wars.

Likely follow-ups

Does :not(.a) add specificity?
Yes: the specificity of its most specific argument. :not() itself adds nothing.
Why does my inline style beat my class?
Element-attached styles sit above selector-based ones; only !important in a stylesheet beats it.
How do you override a third-party library’s CSS?
Load it into a lower layer (@import url(lib.css) layer(vendor)), then your unlayered or later-layer rules win without specificity hacks.
What does all: unset do?
Resets every property of the element (except direction and unicode-bidi) as unset; useful to isolate a component.
C3Asked · 22 Oct

Hiding elements

“What’s the difference between display: none, visibility: hidden, opacity: 0 and the hidden attribute? For each one, say what happens to layout, to events, and to screen readers. When would you pick each?”

Say this first (30 seconds)

“I compare them on four things: layout, pointer events, keyboard focus and screen readers. display: none removes the box: no space, no events, no focus, and not in the accessibility tree. visibility: hidden keeps the space, but also blocks events and focus and hides it from screen readers. opacity: 0 is the dangerous one: it keeps the space and the element is still clickable, focusable and read aloud, so it is only for animation. The hidden attribute is semantic display: none from the browser’s stylesheet, which author CSS can override.”

When to pick each

display: noneclosed modals, inactive tab panels, closed mobile navtoggling triggers layout; cannot be animated directly

visibility: hiddenkeep layout stable; fade-out end state; children may opt in with visibility: visibleremoved from accessibility tree and tab order

.fade.is-hidden { opacity: 0; visibility: hidden; transition: opacity .2s, visibility 0s .2s; } /* hide AFTER the fade */

           overflow: hidden; clip-path: inset(50%); white-space: nowrap; border: 0; }

/* display fade (verify support) */
.panel { transition: opacity .2s, display .2s allow-discrete; }
.panel[hidden] { opacity: 0; }
@starting-style { .panel:not([hidden]) { opacity: 0; } }

Traps (from the practice session)

  • Wrong fact: “visibility: hidden is available to screen readers.” It is not. It leaves the accessibility tree and the tab order, like display: none.
  • Describing only layout and events. Always add focus and screen reader behaviour for every option.
  • Using visibility: hidden for an error message and assuming it will be announced when it appears. Use a live region (role="alert" or aria-live) that exists before the text changes.
  • Believing pointer-events: none stops keyboard users. It does not.

Likely follow-ups

Which keep the element in the accessibility tree?
Only opacity: 0 (and the visually-hidden clip pattern).
Which causes layout recalculation when toggled?
display. visibility and opacity do not change layout.
How do you animate a dropdown out and then remove it?
Fade with opacity, flip visibility after the duration, or use allow-discrete for display verify.
Why is aria-hidden on a button a bug?
Hidden from screen readers but still focusable, so keyboard users land on a silent control.

Normal flow, display and formatting contexts

“What is normal flow? What is the difference between block, inline and inline-block? What is a block formatting context (BFC)?”

Say this first (30 seconds)

“Normal flow is how the browser lays things out before you change anything: block boxes stack vertically and fill the width; inline boxes flow in lines like text. block takes the full width and respects width, height and vertical margins; inline sits in the line, ignores width, height and vertical margin; inline-block sits in the line but behaves like a block inside, so width and height work. A block formatting context is an isolated layout region: floats and margins inside it do not leak out, and it contains its floats. I create one with display: flow-root.”

The three display values you must be able to compare

blockinlineinline-block
Starts a new lineyesnono
Widthfills the container (auto)shrinks to content; width ignoredshrink-to-fit; width works
Height, vertical marginworkignored (padding paints but does not push)work
Examplesdiv, p, sectionspan, a, strongbutton, input (often)
Gotchamargin collapse (C1)line-height and whitespacewhitespace gap between siblings (~4px)

Modern two-part display

display is really two things: outer (how the box sits among siblings: block or inline) and inner (how its children are laid out: flow, flex, grid). display: flex is shorthand for block flex; inline-flex is inline flex. display: contents removes the box but keeps its children in the layout (an accessibility history: it used to remove semantics from buttons and lists in some browsers check current state).

Other flow facts that come up

  • Replaced elements (img, video, iframe) have intrinsic size and are inline by default. A gap below an image comes from baseline alignment; fix with img { display: block } or vertical-align: middle.
  • Floats take an element out of flow so text wraps around it (images, drop caps). Do not use them for page layout anymore. Clear with clear or contain with flow-root.
  • Out of flow: floats, position: absolute and fixed. The parent does not size to them.
  • Line boxes: each line in an inline formatting context has its own height from the tallest inline box; line-height without a unit scales with font size and is the safest.
  • Writing modes: “block direction” and “inline direction” flip in vertical writing; this is why logical properties exist (C5).

Traps

  • Setting width on a span and wondering why nothing happens.
  • Using overflow: hidden to clear floats and then clipping a dropdown or shadow. Prefer flow-root.
  • Saying “flexbox replaced floats for everything”. Floats are still the right tool for wrapping text around an image.
  • Whitespace between inline-block items creating gaps; use flex or grid instead.

Likely follow-ups

What does display: contents do?
The element generates no box; its children participate in the parent’s layout as if the element were not there.
Why does an <img> have a gap under it?
It is inline, aligned to the text baseline, leaving room for descenders. Make it block.
What is contain?
A hint to isolate part of the tree for layout, paint or size; contain: layout creates a BFC and limits recalculation scope.

Units and sizing

“px, em, rem, %, vh, dvh, ch, fr: when do you use which? How does intrinsic sizing work?”

Say this first (30 seconds)

“I use rem for typography and spacing so everything scales with the user’s font-size preference, em when something should scale with its own font size, like button padding, and px for hairlines and borders. Percent is relative to the parent for that property; vw and vh are relative to the viewport, and on mobile I use dvh or svh because the browser toolbar changes the viewport height. ch is the width of a zero, good for line length around 60 to 75 characters. fr is a share of free space in grid. For fluid values I use clamp() with a rem part, so zoom still works.”

Intrinsic sizing: the browser sizes from content

Sizing functions

width: min(100% - 2rem, 70rem);                 /* container with gutters, no media query */
font-size: clamp(1rem, 0.9rem + 0.5vw, 1.5rem); /* fluid type: min, preferred, max; rem in the middle keeps zoom working */
aspect-ratio: 16 / 9;                           /* replaces padding-top hacks */
max-width: 65ch;                                /* readable line length */
margin-inline: auto; padding-block: 1rem;       /* logical properties: follow writing mode and RTL */
height: 100vh; height: 100dvh;                  /* fallback first, enhancement second */

Logical properties

margin-inline-start, padding-block, inset-inline, border-block-end, inline-size, block-size replace left/right/top/bottom/width/height so layouts work in RTL (Arabic, Hebrew) and vertical writing modes without a second stylesheet. In an i18n product this is the correct default.

Traps

  • Setting font sizes in px and saying the site is accessible. Users who raise the browser default font size get nothing. (Browser zoom works either way; the font-size preference only works with rem.)
  • width: 100vw with a vertical scrollbar: a horizontal scrollbar appears.
  • Using vh for a full-screen mobile section and having the bottom button hidden under the browser UI.
  • Percentage height with an auto parent: resolves to auto.
  • em for nested lists or components: sizes compound unexpectedly.

Likely follow-ups

What is a CSS pixel?
A reference unit (1/96 inch) that the browser maps to device pixels using the device pixel ratio; zoom changes that ratio.
How do you make fluid typography accessible?
clamp() with a rem component and sane min and max, then test at 200% zoom (WCAG 1.4.4 and 1.4.10).
Unitless line-height versus px?
Unitless is a multiplier of each element’s own font size and inherits as the number, avoiding overlap when child fonts differ.
min-height: 100dvh or height?
min-height, so content taller than the viewport can still grow.

Flexbox

“A flex container has three children. One has flex: 1, one has flex: 0 0 200px, one has no flex properties. What do the three values in the flex shorthand mean, and what does flex: 1 expand to? How is the free space shared out? Why does a flex child with long text or a wide image sometimes overflow its container, and how do you fix it?”

Say this first (30 seconds)

“flex is shorthand for grow, shrink and basis on the main axis. Basis is the starting size, grow is the share of leftover space, shrink is how an item gives up space when it does not fit. flex: 1 is 1 1 0%: it starts from zero and takes an equal share. With flex: 1, 0 0 200px and a default item, the 200px item is fixed, the default item keeps its content width, and the flex: 1 item takes all the rest. Overflow with long text happens because flex items have min-width: auto, which is the content’s minimum size, so they refuse to shrink below it. The fix is min-width: 0 on the item.”

The shorthand

ValueExpands toMeaning
flex: 11 1 0%grow equally from zero; items end up the same width regardless of content
flex: auto1 1 autostart from content size, then share the leftover; widths follow content
flex: none0 0 autorigid, content size
flex: 0 0 200pxfixed 200px, never grows or shrinks
default (initial)0 1 autocontent size, may shrink, never grows
  • flex-basis vs width: flex-basis wins on the main axis, unless it is auto, then width is used, then content size.
  • Shrinking is weighted: each item gives up space in proportion to flex-shrink × flex-basis, so larger items shrink more. Result is clamped by min-width/max-width; clamped items are frozen and the algorithm repeats.
  • gap is subtracted from free space; auto margins absorb free space before justify-content.

The overflow bug and every fix

For flex and grid items, min-width and min-height default to auto, which resolves to the content’s minimum size (longest unbreakable word, image width, or an item’s own width). For ordinary blocks auto computes to 0. So a long URL or a wide <img> stops the item from shrinking and the container bursts.

.row  { display: flex; gap: 1rem; }
.main { flex: 1; min-width: 0; }                   /* the fix: allow shrinking below content */
.side { flex: 0 0 200px; }
.title{ overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }  /* ellipsis needs min-width:0 on its flex parent */
.long { overflow-wrap: anywhere; }                 /* lets long strings break and lowers the min-content size */

.pane { display: flex; flex-direction: column; min-height: 0; }  /* column version: scroll areas need min-height:0 */
.cols { display: grid; grid-template-columns: minmax(0, 1fr) 300px; } /* grid version: 1fr = minmax(auto, 1fr) */
  • overflow: hidden (or auto) on the item also makes the automatic minimum 0.
  • In nested flex containers, every ancestor in the chain needs it.
  • Images: img { max-width: 100%; height: auto }, and min-width: 0 on the flex item that holds it.

Axes and alignment (quick reference)

flex-directionsets main axisrow (default), column, reverses
justify-contentmaindistributes leftover space: start, center, space-between, space-around, space-evenly
align-itemscrossone line: stretch (default), center, start, end, baseline

Traps (from the practice session)

  • Delivery: the answer was correct but written as a formatted document with LaTeX. Say it in about 60 seconds of short sentences.
  • Hedging: “some browsers evaluate flex: 1 to 0 or 0px”. State 1 1 0% flatly.
  • Saying “block elements have min-width: 0”. The initial value is auto for everyone; it only computes to 0 for non-flex, non-grid boxes.
  • Naming one fix only. Mention overflow, min-height: 0 for columns, and minmax(0, 1fr) for grid.

Likely follow-ups

Difference between flex: 1 and flex: auto?
1 1 0% gives equal widths; 1 1 auto starts from content so wider content stays wider.
Why does text-overflow: ellipsis not work in my flex child?
The item will not shrink (min-width auto), so it never overflows itself. Add min-width: 0 and overflow: hidden.
Why will my scroll area not scroll inside a column flex layout?
min-height: auto prevents shrinking. Add min-height: 0 and overflow: auto.
Does order change tab order?
No. Only the visual order changes; keyboard and screen readers follow the DOM, which is an accessibility risk.

Grid versus flexbox

“When do you choose grid and when flexbox? Write the grid CSS for a responsive card list with no media queries. What does repeat(auto-fit, minmax(240px, 1fr)) do, and how does it differ from auto-fill? What problem does subgrid solve?”

Say this first (30 seconds)

“Flexbox is one-dimensional: a row or a column, where the content decides the sizes. Grid is two-dimensional: I define rows and columns, and items are placed into them. I use grid for page and section layout and for card galleries, and flexbox for components: toolbars, nav bars, button groups, centring. They combine well: grid for the layout, flex inside the cells. For a responsive card list I use repeat(auto-fit, minmax(240px, 1fr)): as many columns as fit, each at least 240px, sharing the leftover. auto-fit collapses empty tracks so the cards stretch, auto-fill keeps the empty tracks. Subgrid lets a nested grid use its parent’s tracks, so content in different cards lines up.”

How to choose

FlexboxGrid
Dimension1D (row or column)2D (rows and columns together)
Approachcontent-out: items’ sizes shape the layoutlayout-in: you define tracks, items fill them
Best fornav bars, toolbars, button rows, centring, “space-between”, media objectpage layout, dashboards, card galleries, forms with label/input columns, overlapping items
Wrappingflex-wrap lines are independent: last row items do not align to columns aboveitems stay on the shared column lines
Gapsgapgap (row-gap, column-gap)
Rule of thumb“I do not know how many items, let them flow”“I know the shape of the layout”

Grid vocabulary and recipes

/* responsive cards, no media query. min(100%, 240px) avoids overflow on very narrow screens */
.cards { display: grid; gap: 1rem; grid-template-columns: repeat(auto-fit, minmax(min(100%, 240px), 1fr)); }

/* page layout with named areas */
.page { display: grid; min-height: 100dvh;
  grid-template: "head head" auto "nav main" 1fr "foot foot" auto / 14rem minmax(0, 1fr); }
.page > header { grid-area: head } .page > nav { grid-area: nav } .page > main { grid-area: main } .page > footer { grid-area: foot }

/* subgrid: card rows (title, body, footer) align across cards */
.card { display: grid; grid-row: span 3; grid-template-rows: subgrid; }
  • Tracks and lines: grid-template-columns defines explicit tracks; items go on lines (grid-column: 1 / 3 or span 2). grid-auto-rows sizes implicit rows; grid-auto-flow: dense back-fills holes (careful: it reorders visually).
  • Sizing: fr shares free space; minmax(0, 1fr) prevents content blow-out; auto fits content; fit-content() caps.
  • Alignment: justify-items / align-items for items inside cells, justify-content / align-content for tracks in the container, place-items: center for both.
  • Subgrid: a grid item that is also a grid can adopt the parent’s rows or columns. Solves aligned card sections and form rows. Supported in current evergreen browsers check Baseline.
  • Masonry: not standard yet; use columns, JS, or the emerging grid-lanes proposal verify status.
  • Overlap: place several items in the same cell (grid-area: 1 / 1) to stack a caption on an image without absolute positioning.

Traps

  • Saying “grid replaces flexbox”. They solve different problems and are used together.
  • Using auto-fit and auto-fill as synonyms. Explain the empty-track difference with a concrete case (fewer items than columns).
  • Writing minmax(240px, 1fr) without min(100%, 240px): horizontal overflow below 240px.
  • Putting long content in 1fr tracks and getting blow-out (needs minmax(0, 1fr)).
  • Re-ordering items visually with grid placement and breaking tab order.

Likely follow-ups

How do you centre one thing?
display: grid; place-items: center, or flex with justify-content and align-items centre. See C9.
Grid with a sticky header and independent scroll?
Rows auto 1fr, min-height: 0 on the scroll cell, overflow: auto.
Is grid slower than flexbox?
Not meaningfully for normal UIs; deep nested grids or huge item counts can cost layout time; measure.
What are grid line names and areas for?
Readable layouts and easy re-arrangement per breakpoint by redefining grid-template-areas.

Positioning, z-index and stacking contexts

“Explain position values. Why does my z-index: 9999 not work? What creates a stacking context?”

Say this first (30 seconds)

“static is normal flow. relative offsets from its own place and creates a reference for children. absolute is removed from flow and positioned against the nearest positioned ancestor. fixed is positioned against the viewport. sticky behaves as relative until it reaches a threshold, then sticks. z-index only orders elements inside the same stacking context. If my z-index: 9999 does nothing, an ancestor created a stacking context, such as opacity below 1, transform, or a positioned parent with a z-index, so the element can never get above elements outside that parent’s context.”

Position values

ValueIn flow?Positioned relative toNotes
staticyesn/adefault; top/left/z-index ignored
relativeyes (space kept)its normal positioncommon “anchor” for absolute children
absolutenonearest positioned ancestor (or the initial containing block)also: transformed ancestors become the containing block
fixednoviewportan ancestor with transform, filter or contain becomes its containing block (a common bug)
stickyyesnearest scrolling ancestor, within its parentneeds top etc.; fails if an ancestor has overflow: hidden/auto on the wrong element, or the parent is too short

inset: 0 is shorthand for top, right, bottom and left. z-index works on positioned elements and on flex and grid items.

What creates a stacking context

  • The root element.
  • position: absolute | relative with z-index other than auto; fixed and sticky always.
  • A flex or grid item with z-index other than auto.
  • opacity below 1; transform, filter, perspective, clip-path, mask, backdrop-filter not none.
  • mix-blend-mode not normal; isolation: isolate; will-change of those properties; contain: layout | paint; container-type verify.

Paint order inside one context (back to front): context’s own background, negative z-index, normal-flow blocks, floats, inline content, z-index: auto/0 positioned, positive z-index.

/* give a component its own context so its z-indexes cannot leak or lose */
.card { isolation: isolate; }

/* a z-index scale as tokens instead of 9999 */
:root { --z-dropdown: 10; --z-sticky: 20; --z-modal: 30; --z-toast: 40; }

/* modals and popovers: use the top layer, no z-index needed */
dialog::backdrop { background: rgb(0 0 0 / .5); }   /* <dialog> with showModal(), [popover] */

Debugging checklist for “my element is behind something”

  1. Is it positioned (or a flex/grid item) so that z-index applies?
  2. Walk up the ancestors in DevTools looking for opacity, transform, filter, position + z-index.
  3. Compare the z-index of the two contexts, not of the two elements.
  4. Use DevTools Layers or the “3D view” (Edge) to see stacking.
  5. Prefer the top layer (dialog, popover) or a portal to body for overlays.

Traps

  • Escalating z-index (999, 9999, 99999). Use a token scale and fix the context.
  • Thinking z-index is global.
  • Adding transform: translateZ(0) as a performance hack and breaking position: fixed children and stacking.
  • position: sticky inside an overflow: hidden ancestor: it will not stick.

Likely follow-ups

Why does position: fixed not stick to the viewport?
An ancestor with transform, filter, perspective or contain becomes its containing block.
How do you build a tooltip that is never clipped?
Render it in a portal or the top layer (popover), and position with the anchor API or Floating UI verify anchor support.
What is the top layer?
Browser-managed layer above all stacking contexts for dialog modals, popovers and fullscreen.
Sticky header over content: how?
position: sticky; top: 0; z-index from your scale, and scroll-padding-top so anchored targets are not hidden.

Responsive design, media and container queries

“How do you build a responsive layout? Media queries versus container queries? What do you do beyond breakpoints?”

Say this first (30 seconds)

“I start mobile-first with a fluid, intrinsic layout: grid with auto-fit and minmax, flex-wrap, clamp() for type and spacing, relative units. Media queries come in only where the design really needs to change, with breakpoints chosen by content and not by device names. For components that live in different places, like a card in a sidebar and in a main column, I use container queries, because the component’s own width is what matters, not the viewport. I also respond to user preferences: reduced motion, colour scheme, contrast, hover and pointer type. And I test at 320px and at 200% zoom.”

Building blocks

<meta name="viewport" content="width=device-width, initial-scale=1">

/* mobile-first: base styles are the small layout, enhance upward */
.layout { display: grid; gap: 1rem; }
@media (min-width: 48em) { .layout { grid-template-columns: 16rem minmax(0, 1fr); } }   /* em in queries scales with user font size */

/* container query */
.card-wrap { container: card / inline-size; }
@container card (min-width: 32rem) { .card { display: grid; grid-template-columns: 12rem 1fr; } }

/* user preferences */
@media (prefers-reduced-motion: reduce) { * { animation-duration: .01ms !important; transition-duration: .01ms !important; scroll-behavior: auto !important; } }
@media (prefers-color-scheme: dark) { :root { color-scheme: dark; } }
@media (hover: hover) and (pointer: fine) { .btn:hover { background: var(--hover); } }   /* no sticky hover on touch */
@media (prefers-contrast: more), (forced-colors: active) { .btn { border: 1px solid; } }

  • Naming breakpoints after devices (iPhone, iPad). Devices change; content does not.
  • Desktop-first max-width queries that you have to undo on mobile.
  • Hiding content on mobile with display: none instead of designing it (still downloaded).
  • Using viewport width for components inside a layout with a sidebar. That is the case for container queries.
  • Hover-only menus and tooltips that never open on touch.
  • Fixed px font sizes and user-scalable=no.

Likely follow-ups

Why em in media queries?
Browsers resolve em in queries from the user’s default font size, so layout adapts to larger text settings.
Does a container query make media queries obsolete?
No. Media queries still handle page-level layout and user preferences; container queries handle components.
How do you handle print?
@media print: hide navigation, expand links, avoid page breaks inside figures (break-inside: avoid).
How do you test reflow?
Set the viewport to 320px wide, zoom to 400%, and check no horizontal scroll apart from tables or code.

Custom properties, theming and dark mode

“What are CSS custom properties and how do they differ from Sass variables? How would you implement theming and dark mode?”

Say this first (30 seconds)

“Custom properties are real CSS values that live in the DOM: they cascade, inherit, and can change at runtime, for example per theme, per component or from JavaScript. Sass variables are replaced at build time and do not exist in the browser. For theming I define design tokens as custom properties on :root, override them under [data-theme="dark"] and under prefers-color-scheme, set color-scheme so form controls follow, and style components only through the tokens. I avoid a flash of the wrong theme by setting the attribute with a tiny inline script before first paint.”

Custom properties vs preprocessor variables

CSS custom propertiesSass/Less variables
Resolvedat runtime, in the browserat build time
Cascade, inheritanceyes (scoped to any element)no
Change from JS / media query / stateyes: el.style.setProperty('--x', v)no
Fallbackvar(--x, fallback)n/a
Works in mathinside calc(); no unit magic without @propertyyes
  • @property registers a typed custom property (syntax, initial value, inherits), which makes it animatable and gives validation check Baseline.
  • Invalid at computed-value time: a custom property with a wrong value makes the property that uses it fall back to inherited or initial, not to a previous declaration.
  • Performance: changing a custom property on :root forces style recalculation for the whole tree; update at the smallest scope you can.

Theming and dark mode implementation

:root { color-scheme: light dark; --bg: #f7f8fa; --fg: #17202b; --accent: #0a6a5e; }
@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { --bg: #0f1620; --fg: #e4eaf1; --accent: #58c8b3; } }
:root[data-theme="dark"] { --bg: #0f1620; --fg: #e4eaf1; --accent: #58c8b3; }   /* user override */
body { background: var(--bg); color: var(--fg); }

/* modern: one declaration per token (verify support) */
:root { --bg: light-dark(#f7f8fa, #0f1620); }

/* in the head, before CSS paints, to avoid a flash */
<script>try { const t = localStorage.theme; if (t) document.documentElement.dataset.theme = t } catch {}</script>
  • Three states: “system” (nothing set, follow prefers-color-scheme), explicit light, explicit dark. Persist the choice; wrap storage in try/catch.
  • color-scheme makes native controls, scrollbars and default canvas follow. Also add <meta name="color-scheme"> and theme-color for browser UI.
  • Dark mode is not inversion: reduce saturation, keep contrast at 4.5:1, elevate surfaces with lighter tints, check images and shadows.
  • SSR: store the theme in a cookie so the server can render the right attribute, avoiding a flash on first byte.
  • Also useful: color-mix() for tints and hover states, relative colour syntax, accent-color for native controls.

Traps

  • Defining a colour only inside the dark media block: with no definition on bare :root the light theme breaks.
  • Components referencing primitives (--blue-500) directly, so each theme change touches every component.
  • Saying custom properties are “just like Sass variables”.
  • Toggling the theme in an effect after hydration: users see a flash.

Likely follow-ups

Can custom properties be used in media queries?
No. var() does not work inside media or container query conditions.
How do you animate a custom property?
Register it with @property so the browser knows its type, then transition or animate it (for gradients).
How do you let consumers customise a component?
Expose a few documented custom properties as its public API (--card-radius); they also cross shadow DOM.
How would you build multi-brand theming?
Same semantic tokens, one token file per brand, loaded by attribute or build; components never change.

Modern selectors and features

“What modern CSS features do you use that older projects do not? What does :has() do? What is Baseline?”

Say this first (30 seconds)

“The big shifts are: :is() and :where() to group selectors with controlled specificity, :has() as a parent and relational selector, native nesting, cascade layers, container queries, subgrid, logical properties, clamp(), aspect-ratio, custom properties with @property, color-mix(), and :focus-visible.   • Colour: color-mix(in oklch, …), relative colour syntax, oklch(), light-dark(), accent-color.
  • Typography: text-wrap: balance (headings) and pretty, font-display, variable fonts, text-box-trim newer.

How you decide to use new features

  1. Check Baseline (“newly available” = in the latest versions of all core browsers; “widely available” = about 30 months) on MDN or web.dev.
  2. Compare with your browserslist and analytics.
  3. Prefer progressive enhancement: fallback first, enhancement inside @supports.
  4. Test in all three engines in CI (C15).

Traps

  • Assuming :has() is expensive and avoiding it. It is well optimised in browsers, but avoid unbounded forms like :has(*) in hot paths and measure if style recalculation is slow.
  • Believing nesting changes specificity rules. It desugars to :is(), so the parent’s highest specificity applies.
  • Using :focus for rings instead of :focus-visible.
  • Claiming “widely supported” without checking Baseline.

Likely follow-ups

Difference between :is() and :where()?
Same matching; :is() contributes its most specific argument’s specificity, :where() contributes zero.
What does & do in nesting?
Stands for the parent selector, needed for compound selectors like &:hover or &.active.
Why text-wrap: balance?
Balances line lengths in short blocks like headings, avoiding a single orphan word.
Container queries vs :has()?
Container queries respond to available space; :has() responds to content structure.

CSS architecture and methodologies

“How do you structure CSS in a large React project? BEM versus utility-first versus CSS Modules versus CSS-in-JS: trade-offs?”

Say this first (30 seconds)

“The problems at scale are global scope, specificity wars, dead code and unpredictable order. Every approach is a different answer to those. BEM solves it with a naming convention and flat selectors. CSS Modules solve it at build time by scoping class names per file. Utility-first, like Tailwind, avoids writing new CSS and keeps the bundle small, at the cost of verbose markup. Runtime CSS-in-JS gives co-location and dynamic styles but costs JavaScript at runtime and fits poorly with Server Components. For a React and Next.js app I would pick CSS Modules or Tailwind, with design tokens as custom properties and @layer to control order, and I would avoid runtime CSS-in-JS.”

A recommended setup for React and Next.js

  1. Tokens as custom properties (and a Tailwind or token config that reads them).
  2. CSS Modules per component for bespoke styling (or Tailwind utilities) with @layer reset, base, components, utilities.
  3. Variants through data-variant or class toggles (clsx, cva) and dynamic values through inline custom properties: style={{ '--progress': p }}.
  4. Linting: Stylelint (no-descending-specificity, property order, no unsupported features), formatting with Prettier, a CI check for unused CSS (PurgeCSS or Tailwind’s content scan).
  5. Design system or component library (headless primitives such as Radix, React Aria) for accessible behaviour; style them with your tokens.
  6. Documentation and visual tests in Storybook with Chromatic or Playwright screenshot tests.

Tech-debt angle (L4)

Expect “how would you clean up a legacy 10,000-line stylesheet?”. Traps

  • Declaring a winner without context. Name the constraints (team, SSR, dynamic styling, existing system).
  • Saying “CSS-in-JS is dead” or “Tailwind is bad”. Give trade-offs.
  • Deep selector nesting and #id selectors in a BEM codebase.
  • Ignoring ordering: the bundle order of CSS Modules or utilities can change specificity outcomes; use @layer.

Likely follow-ups

How do you avoid CSS regressions?
Component-level visual tests, a small set of tokens, lint rules, and ownership of the design system.
Is Tailwind bad for accessibility or maintainability?
Neither by itself. Accessibility comes from markup and behaviour; maintainability from extracting components and using the config as the token source.
Why is runtime CSS-in-JS awkward with React Server Components?
It relies on React context and runtime injection, which need client components; zero-runtime or CSS Modules work with server rendering directly.
Global CSS: when is it fine?
Reset, tokens, typography defaults, utilities. Not component styles.
C14Added

CSS performance and animation

“How can CSS affect performance? How do you make animations smooth? What is content-visibility?”

Say this first (30 seconds)

“CSS affects performance in three places: loading, because CSS is render-blocking; style and layout cost on the main thread; and animation smoothness. For loading I keep the critical CSS small and inline it, split the rest, and avoid @import chains. For runtime I keep the DOM small, avoid forced layout, and use contain and content-visibility: auto to skip offscreen work. For animation I only animate transform and opacity, which run on the compositor, I use will-change sparingly, and I respect prefers-reduced-motion. I check it in the DevTools Performance panel before optimising.”

Loading CSS

  • Render-blocking: a stylesheet in the head blocks first paint (and later synchronous scripts). Keep it small, compressed (Brotli), cached with hashed names.
  • Critical CSS: inline the above-the-fold rules, load the rest without blocking (<link rel="stylesheet" media="print" onload="this.media='all'"> or rel="preload" as="style"). Tools: Critters, Next.js, Astro.
  • Avoid @import in CSS: it serialises downloads. Use bundling or multiple <link>.
  • Remove unused CSS (DevTools Coverage, PurgeCSS, Tailwind’s content scan); split per route.
  • Fonts: font-display: swap or optional, preload the key WOFF2, subset, use size-adjust and related descriptors for the fallback to limit CLS.
  • Media queries on <link media> make non-matching stylesheets non-blocking (still downloaded at low priority).

Runtime cost

  • Selector cost is rarely the bottleneck in modern engines; very deep or universal selectors matter only with huge DOMs. DOM size, layout thrash and big repaints matter more.
  • Layout thrash: reading offsetHeight after writing styles in a loop forces synchronous layout each time. Batch reads, then writes; use requestAnimationFrame or ResizeObserver.
  • contain: layout paint style and content-visibility: auto with contain-intrinsic-size skip offscreen rendering (big wins on long feeds) check support.
  • Hit expensive properties less: large box-shadow, filter: blur(), backdrop-filter on big areas, gradients on huge surfaces.
  • Hardware layers: will-change or 3D transforms promote layers; too many cost GPU memory.

Animation checklist

.menu { transform: translateY(-8px); opacity: 0; transition: transform .2s ease, opacity .2s ease; }
.menu.open { transform: none; opacity: 1; }

@media (prefers-reduced-motion: reduce) { .menu { transition: none; } }

.feed-item { content-visibility: auto; contain-intrinsic-size: auto 240px; }
  • Use CSS transitions or Web Animations API for simple motion; avoid JS per-frame style writes.
  • INP is affected by style recalculation and layout caused by interactions; keep handlers short.
  • Scroll-linked effects: prefer CSS scroll-driven animations or passive listeners and IntersectionObserver support varies.
  • Accessibility: no flashing above 3 per second (WCAG 2.3.1); provide a pause for long motion (2.2.2); honour reduced motion.

How to measure

  • DevTools Performance: look at “Recalculate Style”, “Layout”, “Paint”, long tasks; Rendering panel: paint flashing, layout shift regions, layer borders.
  • Coverage tab for unused CSS; Lighthouse for render-blocking resources; WebPageTest filmstrip.
  • Field: CLS and INP from RUM (web-vitals).

Traps

  • Putting will-change: transform on everything “for performance”.
  • Animating height from 0 to auto with layout cost on long lists; use grid grid-template-rows: 0fr → 1fr or interpolate-size verify support.
  • Believing CSS selector optimisation is the first fix. Measure first.
  • Forgetting reduced motion and focus after animating content in.

Likely follow-ups

Why is transform cheaper than left?
It changes only the compositing of an existing layer, no layout or paint.
What is a layout shift and how does CSS cause it?
Visible elements moving unexpectedly: images without size, late fonts, injected banners, animations of layout properties. Fix with reserved space, aspect-ratio, font metrics, and transform.
What does contain-intrinsic-size do?
Gives skipped (content-visibility) elements a placeholder size so scrollbars and layout do not jump.
Critical CSS: risks?
Duplicated rules, stale inline CSS, flash of unstyled content below the fold if the async stylesheet is slow.

  3. Use features by Baseline status; polyfill only JS APIs, not CSS (CSS polyfills are usually not worth it, use fallbacks).
  4. Automated visual and functional tests in three engines, plus a manual pass on iOS Safari for touch, keyboard and scroll behaviour.
  5. Monitor in production; keep a record of known gaps and decisions.

Traps

  • “I test in Chrome and it works.” Chromium is not the web; iOS means WebKit for every browser.
  • User-agent sniffing for CSS fixes.
  • Adding prefixes by hand for everything.
  • Using a brand-new feature without a fallback and without checking analytics.
  • Forgetting accessibility differences across browser and screen reader pairs.

Likely follow-ups

What is the Interop project?
A yearly effort by browser vendors to align on a set of web-platform-tests, which is why behaviour differences shrink each year.
How do you test Safari without a Mac?

When do you drop a browser?
When traffic and revenue are low, support cost is high, or it no longer gets security updates; decide with product and document it.

A modern reset (box-sizing, margins, form font inherit, media display block) plus design-system defaults is enough; normalize.css is mostly historic.
