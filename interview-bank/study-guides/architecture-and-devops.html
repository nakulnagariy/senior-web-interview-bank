Frontend architecture and system design

“How do you architect a large frontend application? How do you structure layers and modules, manage dependencies, choose a rendering approach, and answer a frontend system design question such as ‘design a news feed’ or ‘design a dashboard’?”

Say this first (30 seconds)

“I architect a frontend around business domains, not technical file types: feature modules with clear public interfaces, layered so that UI components depend on hooks and domain logic, which depend on an API client, never the reverse. Shared design-system components and utilities sit below the features, and boundaries are enforced with lint rules so teams do not tangle. I choose the rendering model from the content: static or server rendering for SEO and first load, client rendering for rich interaction, usually a hybrid. For a system design question I clarify requirements and scale, define the API and data model, design the component tree and state, then cover rendering, caching, performance, accessibility, error handling, security and observability, and I state trade-offs and what I would measure.”

Details interviewers probe

  • Architecture goals: changeability (small blast radius), team autonomy, performance, reliability, accessibility, security, testability, and onboarding speed. Choose the simplest structure that meets today’s scale and leaves room to evolve; avoid over-engineering for hypothetical scale.
  • Modular monolith first: one deployable frontend with strong internal module boundaries is easier to build, test and deploy than micro-frontends, and can later be split along the same seams (A2). Boundaries matter more than deployment topology.
  • Layering and clean architecture for UI: presentation (components), application logic (hooks, state, use cases), domain (types and rules), infrastructure (API clients, storage). Keep business rules out of components so they are testable without rendering; adapters isolate vendors and APIs (J28).
  • Feature-sliced and domain-driven structure: organise by feature or bounded context (features/checkout) with internal layers; share only genuinely common code; apply the “rule of three” before abstracting; avoid a dumping-ground utils or common folder.
  • State architecture: server state in a query library, URL for shareable state, local state by default, a small global store for genuinely global client state (E1). Document where each kind lives.
  • Rendering architecture: SPA, MPA, SSR, SSG, ISR, islands, streaming, edge; pick per route (N1). Consider SEO, time to first byte, personalisation, caching and operational complexity.
  • Data layer: typed API client, schema validation at the boundary, error normalisation, auth handling, caching; optionally a backend-for-frontend to aggregate and shape APIs, hide tokens and tailor payloads to the UI (E9).
  • Cross-cutting concerns: authentication and authorisation, i18n, theming, feature flags, analytics, error reporting, logging, accessibility, performance budgets; provide them through well-defined providers and hooks rather than ad hoc imports.
  • Scalability of the codebase: build times (caching, incremental), test speed, ownership (CODEOWNERS), consistent conventions, code generation and templates, dependency governance, documentation (ADRs).
  • Example: design a news feed: requirements (infinite scroll, personalised, realtime updates, images); API with cursor pagination and ETags; client store keyed by feed id; virtualised list with stable keys; IntersectionObserver for loading; optimistic likes; image CDN with responsive images; skeletons; prefetch next page; offline cache; analytics for impressions; error and retry states; accessibility for feed pattern; metrics: LCP, INP, scroll jank.
  • Example: design a dashboard: widget grid with independent data sources and error boundaries; per-widget query caching and polling or WebSocket updates; virtualised tables; lazy-loaded chart libraries; layout persistence; role-based widgets; export; performance budgets; observability of widget load times.
  • Non-functional requirements: state targets (p75 LCP, availability, supported browsers, accessibility level WCAG 2.2 AA, i18n locales) so decisions are testable.
  • Evolutionary architecture: fitness functions (automated checks for bundle size, dependency rules, accessibility) keep architecture from eroding; strangler pattern to replace legacy pieces incrementally.
  • Communication: architecture diagrams (C4 model: context, containers, components), ADRs for decisions, RFCs for cross-team changes; keep them short and current.

Traps

  • Starting with technologies (“I would use React and Redux”) before requirements and constraints.
  • Over-engineering with micro-frontends or heavy abstractions for a small team.
  • Folders organised only by type (components, hooks, utils) so features are scattered and coupled.
  • Business logic buried in components, making it untestable.
  • Ignoring non-functional requirements such as accessibility, performance and observability in the design.

Likely follow-ups

How do you prevent a codebase from turning into a big ball of mud?
Enforced module boundaries, one-directional dependencies, ownership, architectural lint rules in CI, regular refactoring and ADRs.
How do you decide between SSR and CSR for a new product?
From SEO needs, first-load performance, personalisation, team skills and operational cost; often hybrid with static public pages and client-rendered authenticated areas.
Where does business logic live in a React app?
In plain TypeScript modules and hooks (domain and application layers), with components focusing on presentation.
What is a backend-for-frontend?
A server layer owned by the frontend team that aggregates and adapts backend APIs for a specific client, hiding complexity and credentials.
A2Added

Micro-frontends

“What are micro-frontends? When are they worth it? Compare composition approaches: iframes, Module Federation, web components, build-time packages, server-side composition. How do you handle routing, shared dependencies, state and styling?”

Say this first (30 seconds)

“Micro-frontends split a large web application into independently developed, tested and deployed pieces owned by different teams, usually along business domains, composed into one experience for the user. The benefit is team autonomy and independent releases for big organisations; the costs are complexity, duplicated dependencies, inconsistent UX, harder performance and harder cross-app communication. Composition can happen at build time through packages, at runtime in the browser with Module Federation, single-spa or web components, with iframes for strong isolation, or on the server or edge. I treat them as an organisational scaling tool and avoid them for small teams; a well-structured modular monolith usually delivers more value with less cost.”

Details interviewers probe

  • Why teams adopt them: many teams working on one product, long release trains, merge conflicts and fragile shared builds, desire for independent deployment and technology evolution, and acquisitions of separate products to unify. Typically 50+ engineers across several teams.
  • Split by business domain, not technical layer: vertical slices (search, checkout, account) owned end to end by a team including backend; horizontal splits (header, footer, buttons) produce coordination overhead.
  • Module Federation: webpack 5 (and Rspack, Vite plugins) lets an app expose and consume modules at runtime; configure shared singletons (React, router, design system) with version ranges to avoid duplicates; remotes loaded from URLs published by CI; fallback UI for failed loads; versioning via manifests verify tooling status.
  • Routing: the shell owns top-level routes and delegates subpaths to remotes; deep links must work; avoid two routers fighting over history; coordinate navigation through the shell or custom events.
  • Communication: prefer loose coupling: URL and query params, custom events (CustomEvent, BroadcastChannel), a small shared event bus or store contract with versioned payloads, and props from the shell. Avoid direct imports between remotes.
  • Shared dependencies and bundle size: duplicating React or UI libraries in each remote bloats pages; share singletons carefully but accept version coupling; measure total JavaScript per page and set budgets.
  • Design system and styling: a shared component library and tokens give a consistent look; isolate CSS (CSS Modules, scoped naming, shadow DOM) to prevent leakage; version the design system and plan upgrades across teams.
  • Authentication and state: shell handles auth and passes tokens or a session; avoid sharing mutable global state; each remote owns its data fetching and caching.
  • Independent deployment: each micro-frontend has its pipeline and can release without the others; contract tests and integration environments ensure compatibility; feature flags and canaries reduce risk; consider version pinning and rollbacks per remote (A6).
  • Testing: unit and component tests per remote; contract tests between shell and remotes; end-to-end tests of key journeys across remotes in an integration environment; visual regression of the composed page.
  • Performance: avoid waterfalls (load shell then remote manifests then bundles), preload remote entries, SSR or edge composition for first paint, shared caching, and monitor Core Web Vitals per route and per team.
  • Alternatives that often suffice: modular monolith in a monorepo with enforced boundaries, per-package ownership (CODEOWNERS), independent versioned packages released together, and path-based deployment of separate apps behind one domain (multi-zone in Next.js).
  • Organisational prerequisites: platform team providing templates and shared tooling, clear domain ownership, governance of shared contracts, observability, and willingness to accept duplication and inconsistency risks.
  • Migration use: micro-frontends are a strangler tool for replacing a legacy app piece by piece, running old and new frameworks side by side behind a shell.

Traps

  • Adopting micro-frontends for a three-team product because it sounds modern.
  • Splitting by UI component instead of business capability.
  • Letting each team choose a different framework and design, harming UX and performance.
  • Remotes importing each other, recreating a distributed monolith.
  • No strategy for shared dependency versions, error handling when a remote fails, or end-to-end testing.

Likely follow-ups

How do you share state between micro-frontends?
Minimise it: use URL, events and a small versioned contract; each remote owns its data; shared auth comes from the shell.
How do you keep the UI consistent?
A shared design system with tokens, versioned and governed, plus visual regression tests and design reviews.
What happens if a remote fails to load?
The shell shows a fallback and error boundary around the remote, reports the error, and remains usable.
What would you do instead for a mid-size team?
A modular monolith in a monorepo with enforced boundaries and CODEOWNERS.

Monorepos, shared code, ownership

“Monorepo or polyrepo? How do you structure shared libraries, versioning, ownership and tooling at scale? How do you prevent dependency hell and keep builds fast?”

Say this first (30 seconds)

“A monorepo keeps many projects in one repository, which makes cross-project changes atomic, shares tooling and dependencies, and simplifies refactoring; the costs are tooling for build speed, access control and discipline about boundaries. A polyrepo gives clear ownership and independent lifecycles but makes sharing code and coordinated changes harder, with version drift. For frontend platforms I usually prefer a monorepo with pnpm workspaces and Turborepo or Nx for task caching and affected-only builds, CODEOWNERS for review routing, module-boundary lint rules, and shared packages for the design system, utilities and configs, versioned with Changesets when published.”

Details interviewers probe

  • Tooling: pnpm or npm/yarn workspaces for linking; Turborepo (simple pipeline, remote cache), Nx (project graph, generators, boundaries, affected commands, plugins), Rush, Lerna (now Nx-backed), Bazel for very large polyglot repos. Choose by size and needs; start simple.
  • Task graph and caching: declare task dependencies (build depends on dependencies’ build); caches keyed by file hashes, env vars and dependency versions; remote cache shares outputs between developers and CI; run only affected projects on pull requests (B8, B10).
  • Dependency management: a single version of critical libraries (React, TypeScript) across the repo to avoid duplicates; tools such as syncpack enforce consistency; Renovate groups upgrades; use catalogues or overrides; avoid phantom dependencies by using pnpm.
  • Internal packages: “just-in-time” packages consumed as TypeScript source (fast iteration, bundler compiles them) or built packages (publishable); use TypeScript project references and path aliases consistently (T9); keep public APIs small with exports.
  • Versioning and publishing: internal-only packages can share one version via workspace protocol; published libraries use Changesets (version PRs, changelogs) or semantic-release with provenance; consider fixed versus independent versioning; keep a deprecation policy.
  • Ownership: CODEOWNERS routes reviews to the owning team; required reviewers for shared packages; labels and notifications; defined contribution process for platform packages; avoid “everyone owns it, so no one does”.
  • Boundaries and architecture rules: tags per project (type: app/feature/ui/util; scope: team) with allowed dependency matrices enforced by lint; ban deep imports; detect circular dependencies (madge, dependency-cruiser); keep apps thin and packages cohesive.
  • CI scaling: affected-only builds and tests, test sharding, caching, parallel jobs, per-project pipelines triggered by path filters, preview deployments per app, and flaky test management; track CI duration as a metric (B10).
  • Source control practices: trunk-based development with short-lived branches, feature flags, merge queues to keep the main branch green, sparse checkout or partial clones for large repos, and protected branches (A5).
  • Code sharing patterns: extract to a package after repeated use (rule of three); prefer composition and clear interfaces; avoid shared mutable singletons; document and test shared packages thoroughly because many apps depend on them.
  • Migration to a monorepo: import history (subtree/filter-repo), move one app at a time, unify tooling gradually, set up CI with caching first, and train teams; do not attempt a big bang.
  • Access and compliance: monorepos expose all code to everyone by default; use CODEOWNERS and, where required, separate repos for restricted code; audit trails and secrets scanning.
  • When a polyrepo is better: unrelated products, strict isolation requirements, different languages and toolchains, independent open-source projects, or teams that rarely change shared code.

Traps

  • Adopting a monorepo without caching or affected-only builds, so CI becomes slower for everyone.
  • Letting packages import apps or each other freely, creating cycles.
  • Multiple versions of React in one repo causing subtle bugs.
  • A giant shared package that every team edits without ownership.
  • No policy for breaking changes in shared packages.

Likely follow-ups

How do you keep CI fast in a monorepo?
Task caching, remote cache, affected-only commands, parallelism and test sharding, and path-based triggers.
How do you roll out a breaking change to a shared package?
Provide a codemod, migrate all consumers in the same PR (the monorepo advantage), or deprecate with a compatibility layer and a deadline.
What goes into CODEOWNERS?
Path patterns mapped to teams so reviews are automatically requested from the people responsible for that code.
Monorepo and micro-frontends: same thing?
No: repository structure and deployment topology are independent; you can have micro-frontends in a monorepo or a modular monolith in a monorepo.

Architecture decisions and trade-offs

“How do you make and document architectural decisions? What is an ADR? How do you evaluate technology choices, manage technical debt, handle legacy migration and communicate trade-offs to stakeholders?”

Say this first (30 seconds)

“I make architecture decisions explicit: define the problem and the constraints, list realistic options, evaluate them against criteria such as cost, risk, team skills, performance and reversibility, decide, and record it in a short Architecture Decision Record with the context, decision and consequences so future teams understand why. I separate reversible two-way-door decisions, which we make fast, from irreversible ones, which deserve more analysis and a proof of concept. I involve the people affected, prototype risky parts, and communicate in business terms. For legacy systems I prefer incremental migration with the strangler pattern over rewrites, and I manage technical debt by making it visible, prioritising by risk and cost, and allocating regular capacity.”

Details interviewers probe

  • ADRs: short markdown files (docs/adr/0014-…md) stored with the code, immutable once accepted (superseded by new ADRs rather than edited), covering status, context, decision, alternatives considered and consequences. They create institutional memory and speed onboarding.
  • RFCs: broader proposals for cross-team changes with a comment period, an owner, and a decision date; use for design systems, major dependencies, migrations and standards; keep them time-boxed to avoid endless debate.
  • Evaluating technology: define must-haves, run a time-boxed spike on the hardest use case, assess maintenance health and community, security posture, licence, hiring market, migration cost and exit strategy; involve a sceptic; avoid résumé-driven development and hype.
  • Build versus buy versus adopt open source: buy or adopt commodity capabilities (auth, payments, analytics, UI primitives); build what differentiates the product; weigh total cost of ownership including maintenance and integration.
  • Technical debt: deliberate (conscious shortcut with a plan) versus accidental; inventory in a debt register with impact, interest (how much it slows work) and fix cost; prioritise by risk to users and delivery speed; allocate capacity (for example 15 to 20% per sprint), attach cleanup to feature work (boy-scout rule), and use metrics (change failure rate, lead time, defect hotspots) to justify investment.
  • Legacy modernisation: assess value and risk, establish tests around existing behaviour (characterisation tests), apply the strangler pattern, migrate by vertical slice, keep both systems running, use feature flags and parallel runs, and communicate progress and benefits; rewrites only for small or truly broken systems.
  • Reversibility and lock-in: isolate vendors behind interfaces; prefer open standards; estimate exit cost; avoid irreversible commitments without a trial; keep data portable.
  • Trade-off articulation: state what you gain and give up, for whom and over what time frame; use concrete numbers (build time, bundle size, cost) and scenarios; acknowledge uncertainty; propose experiments to reduce it.
  • Stakeholder communication: translate technical concerns into business impact (risk, cost, time to market, customer experience); present options with a recommendation; show a roadmap with milestones and value at each step; keep an honest view of risks and dependencies.
  • Governance without bureaucracy: lightweight architecture reviews for impactful decisions, a guild or community of practice, golden paths (paved roads) that make the recommended choice easiest, and autonomy within guardrails.
  • Fitness functions: automated checks encoding architectural goals (bundle budgets, dependency rules, accessibility, security scans) so architecture is verified continuously.
  • Cognitive load and team topology: design architecture and boundaries around team ownership (Conway’s law); reduce cross-team dependencies; platform teams provide self-service capabilities.
  • Learning from decisions: review outcomes after a period, record lessons, and update ADRs; celebrate reversed decisions as learning, not failure.

Traps

  • Decisions made in meetings or chat with no record, then forgotten or contested.
  • Analysis paralysis on reversible choices, or snap decisions on irreversible ones.
  • Choosing technology for novelty rather than fit and team capability.
  • Proposing a full rewrite without evidence or a migration path.
  • Presenting technical debt as technical purity instead of business risk and cost.

Likely follow-ups

How do you justify paying down technical debt?
Quantify its interest: slower delivery, incidents, onboarding cost, and show a plan with measurable outcomes and incremental steps.
How do you handle disagreement on an architecture choice?
Clarify criteria, run a time-boxed spike, document the options, decide with the accountable owner, and commit while recording the dissent and a review date.
When is a rewrite justified?
When the system is small, the technology is end-of-life with no migration path, or the cost of change is truly unsustainable; even then, migrate in slices.
What is Conway’s law and why does it matter?
Systems mirror the communication structure of the organisations that build them; align team boundaries with desired architecture.

CI/CD pipelines and branching

“Explain continuous integration, continuous delivery and continuous deployment. How do you design a pipeline? Trunk-based development versus Git Flow? What quality gates and environments do you use? Which CI tools have you used?”

Say this first (30 seconds)

“Continuous integration means developers merge small changes into the main branch frequently, and every change is automatically built and tested. Continuous delivery means every passing change is releasable and can be deployed at any time with a click; continuous deployment goes further and releases every passing change automatically. A good pipeline is fast and staged: install with caching, static checks, unit and integration tests, build once, publish an immutable artifact, deploy to a preview or staging environment, run end-to-end and smoke tests, then promote the same artifact to production with a progressive rollout and automatic rollback. I favour trunk-based development with short-lived branches and feature flags, because long-lived branches create painful merges and delay feedback.”

Details interviewers probe

  • Definitions: CI = integrate and verify frequently. Continuous delivery = always releasable with a manual release decision. Continuous deployment = automatic release to production after passing gates. Choose by risk appetite, regulation and test confidence; many teams deploy continuously to production for web apps behind flags.
  • Pipeline design principles: fast feedback (target under 10 minutes for the PR check), deterministic, idempotent, parallel where possible, cached dependencies and build outputs, fail early, clear logs, ownership by the team, pipeline as code (versioned YAML), and reusable templates for consistency.
  • Build once, promote: the artifact built in CI is what runs in every environment; configuration is injected per environment; no rebuilds between staging and production (B10).
  • Environments: ephemeral preview per pull request, shared development/integration, staging mirroring production, and production; manage data, secrets and access per environment; keep staging representative; consider testing in production safely with flags and canaries.
  • Testing in the pipeline: unit and component tests on every PR; integration tests with service containers; e2e against the preview; smoke tests after deploy; synthetic checks in production; flaky test policy (quarantine and fix) (R12, E10).
  • Trunk-based development details: small PRs, branch by abstraction, feature flags, pair/mob to reduce review delay, merge queues to avoid broken main, rebase or squash merges, protected main with required checks, and code review within hours (G1).
  • Release versioning and tags: semantic versions for libraries; for apps use build ids or commit SHAs plus release tags; generate changelogs from Conventional Commits; keep release notes for stakeholders.
  • Pipeline security: least-privilege tokens, short-lived credentials via OIDC to the cloud instead of stored keys, pinned third-party actions by commit SHA, secret masking, protected environments with approvals, dependency and image scanning, signed artifacts (A12).
  • Tools: GitHub Actions, GitLab CI, Azure DevOps Pipelines, Jenkins (self-hosted, plugin-heavy), CircleCI, Bitbucket Pipelines, Buildkite, Argo CD/Flux for GitOps deployment; choose by existing platform, scale and compliance. Concepts transfer: stages, jobs, runners/agents, caches, artifacts, secrets, environments, approvals.
  • GitOps: desired state of environments stored in Git; a controller (Argo CD, Flux) reconciles clusters to match; deployments are pull requests to config repos; gives auditability and easy rollback.
  • Metrics (DORA): deployment frequency, lead time for changes, change failure rate, time to restore service; track and improve them, avoid using them to rank individuals (G4, G11).
  • Handling failures: automatic rollback on failed health checks or SLO burn, fix-forward versus rollback policy, post-deploy verification, notifications to the right channel, and blameless review of failed deployments.
  • Monorepo pipelines: affected-only builds, remote caching, path filters, per-app deployments (A3).
  • Database and dependency changes: backward-compatible migrations (expand, migrate, contract) so application and schema versions can differ during rollout (A6).

Traps

  • Confusing continuous delivery with continuous deployment.
  • Slow pipelines that developers bypass or batch changes around.
  • Rebuilding for production, so what is tested differs from what ships.
  • Long-lived feature branches with big-bang merges.
  • Long-lived cloud credentials stored as CI secrets, or unpinned third-party actions.

Likely follow-ups

How do you merge unfinished work to main?
Behind a feature flag, or by branch by abstraction, so main stays releasable.
How do you keep a pipeline under ten minutes?
Cache, parallelise, run affected-only, shard tests and push slow tests to later stages or nightly runs.
Where do manual approvals belong?
Only where policy requires them, typically before production; automate everything else and make approvals fast.
What is a merge queue?
A system that tests the combination of queued PRs against the latest main before merging, preventing a broken main.
A6Added

Deployment strategies

“Compare rolling, blue-green and canary deployments. What about recreate, A/B testing, shadow traffic and dark launches? How do you roll back? How do you handle database migrations and deployment skew for frontends?”

Say this first (30 seconds)

“Deployment strategies trade speed, risk and cost. Recreate stops the old version and starts the new, simple but with downtime. Rolling replaces instances gradually, so capacity stays up but two versions coexist briefly. Blue-green runs two full environments: I deploy to the idle one, test it, then switch traffic instantly, with instant rollback by switching back, at the price of double capacity. Canary sends a small percentage of real traffic to the new version, watches metrics, and increases gradually or rolls back automatically, which limits the blast radius and is my default for risky changes. Feature flags separate deploying code from releasing features, and database migrations must be backward-compatible so both versions can run at once.”

Details interviewers probe

  • Rolling updates: Kubernetes default: maxSurge and maxUnavailable control pace; readiness probes gate traffic; rollback with kubectl rollout undo. Both versions serve concurrently, so APIs and schemas must be compatible.
  • Blue-green: two production-identical environments; deploy and smoke test the idle one with real configuration; switch the load balancer, DNS or CDN origin; keep the old environment for fast rollback, then tear down or reuse. Challenges: state (databases, sessions, caches), cost, and long-lived connections.
  • Canary: start with internal users or 1 to 5% of traffic by percentage, region, cookie or header; compare canary and baseline on error rate, latency, business metrics and web vitals; automate promotion and rollback with analysis (Argo Rollouts, Flagger, Spinnaker, cloud deployment services). Sticky routing ensures users see one version during a session.
  • Frontend specifics: static assets are immutable and versioned; the HTML entry point decides which version loads; canary by routing a percentage of HTML requests (edge worker, CDN rule, cookie) to the new build; keep old assets available for open tabs (deployment skew) (B10).
  • A/B testing versus canary: A/B tests compare variants for product metrics with statistical rigour; canaries check safety of a new build; both route subsets of users but have different goals and analysis.
  • Dark launches and shadow traffic: run new code paths invisibly (mirror requests to the new service, compare results) to validate behaviour at real load before exposing users; ensure shadowed calls do not cause side effects.
  • Feature flags with deployment: deploy dark, enable for staff, then percentage rollout, then everyone; kill switches for instant disable without redeploy (A7).
  • Rollback versus roll forward: rollback is fast when the change is reversible; data migrations and external side effects make it harder, so prefer expand/contract and forward-fixable designs; practise rollbacks; keep previous artifacts and configuration versions.
  • Database migrations in deployments: expand (additive, nullable), deploy code that handles both, migrate data in the background in batches, switch reads and writes, then contract (remove old) in a later release; avoid renaming columns in one step; test migrations on production-size data; use online schema change tools for large tables (D6).
  • API and contract compatibility: tolerate unknown fields, add rather than change, version when breaking, and support old clients through a deprecation window; frontends and backends deploy independently so assume skew.
  • Health and verification: readiness/liveness probes, automated smoke tests after deploy, SLO-based gates, real user monitoring by version, and alerts tied to the release; progressive delivery pauses automatically when metrics degrade.
  • Zero-downtime requirements: graceful shutdown and connection draining, backward-compatible changes, sufficient capacity during rollout, warm caches, and avoiding long migrations holding locks.
  • Release windows and change management: in regulated settings, combine progressive delivery with change records, approvals and freeze periods; automate evidence collection.

Traps

  • Blue-green with a database change that breaks the old version, so rollback is impossible.
  • Canary without meaningful metrics or automatic rollback, so “canary” is just a slow release.
  • Rolling out incompatible API changes while both versions are live.
  • Deleting old static assets immediately and breaking open tabs.
  • Equating deployment with release, instead of separating them with flags.

Likely follow-ups

Canary versus blue-green: when each?
Canary for gradual risk reduction with real traffic and good metrics; blue-green for fast, all-or-nothing switches and easy rollback when you can afford duplicate capacity.
How do you roll back a bad frontend release?
Point the entry HTML back to the previous build (or redeploy the previous artifact), keep both asset sets, and flip flags off.
How do you ship a database column rename safely?
Add the new column, write to both, backfill, switch reads, then drop the old column in a later release.
What metrics gate a canary?
Error rate, latency percentiles, saturation, key business events and Core Web Vitals compared with the baseline.
A7Added

Feature flags and configuration

“What are feature flags and how do you use them? Types of flags, rollout strategies, kill switches, evaluating flags on client versus server, flag debt, testing with flags, and tools such as LaunchDarkly or Unleash.”

Say this first (30 seconds)

“A feature flag is a runtime switch that turns behaviour on or off without redeploying, which decouples deployment from release. I use flags for trunk-based development of unfinished work, gradual percentage rollouts, targeting specific users or segments, A/B experiments, and kill switches that disable a risky feature instantly. Flags have different lifetimes: release flags are temporary and must be removed after rollout, ops flags and permission flags can be long-lived. They need discipline: naming and ownership, defaults that are safe if the flag service is unavailable, evaluating on the server for security-sensitive features, tests for both states, and a cleanup process, because stale flags become hidden complexity and bugs.”

Details interviewers probe

  • Use cases: trunk-based development, progressive delivery (1%, 10%, 50%, 100%), targeted betas (internal staff, region, plan), A/B and multivariate experiments, operational controls (rate limits, degrade modes), and entitlement management. Flags let you release on a business schedule while deploying continuously.
  • Rollout strategies: percentage by user id hash (sticky), ring-based (staff, beta, everyone), geography or tenant-based, time-based schedules, and automatic rollout with guardrail metrics that pause or revert on regression.
  • Kill switches: pre-built toggles around risky dependencies and heavy features that can be disabled in seconds during an incident without a deploy (A11); include in runbooks and test them.
  • Implementation approaches: simple config or environment variables (static, need redeploy), database-backed flags, open-source services (Unleash, Flagsmith, GrowthBook, OpenFeature standard), and SaaS (LaunchDarkly, Statsig, Split, Optimizely). OpenFeature provides a vendor-neutral API to avoid lock-in verify adoption.
  • Server versus client evaluation: server evaluation keeps rules private and is secure; client SDKs receive evaluated values for the user (not the rules) and are visible in the browser, so never hide sensitive functionality behind them. For SSR, evaluate on the server and hydrate values to avoid flicker; for static pages use edge evaluation or client-side after load with a placeholder.
  • React integration: a provider with a hook (useFlag('checkout.newPayment')); keep flag checks at the boundary (route or component), not scattered; use dependency injection so tests can set flag values; avoid conditional hooks driven by flags in unsafe ways (hooks rules apply).
  • Testing: unit tests for both flag states; integration tests for combinations that matter; avoid the combinatorial explosion by limiting the number of simultaneous flags and removing old ones; use flag overrides in e2e tests; test the “flag service down” default.
  • Flag debt: stale flags cause dead code, confusing behaviour and risk (a famous trading firm lost hundreds of millions through a repurposed flag). Mitigate: expiry dates, ownership, automatic cleanup tickets, lint rules or code scanners (Piranha), regular flag reviews, and deleting both the flag and the losing code path.
  • Configuration management beyond flags: typed configuration per environment, remote config for non-code settings, secrets in a vault, runtime configuration for SPAs (A6, B10), and validation at startup. Distinguish configuration (operational parameters) from flags (behaviour switches).
  • Data and analytics: record flag exposure with user and variant for experiments; ensure consent and privacy; use statistical methods (sample size, significance, guardrail metrics) to interpret results; avoid peeking early.
  • Operational concerns: latency and availability of the flag service (local evaluation, streaming with fallbacks), audit logs of changes, access control and approvals for production changes, environment parity, and rate of changes.
  • Performance: keep rule evaluation local and fast; avoid synchronous network calls on the critical path; bootstrap initial values in HTML.
  • Ethical and product aspects: do not use flags to degrade experience unfairly; communicate changes to support teams; keep documentation of what is live for whom.

Traps

  • Leaving release flags in the code for years until nobody knows what they do.
  • Protecting a paid feature only with a client-side flag.
  • No default when the flag service is unreachable, so the app breaks or flips unpredictably.
  • Nesting many flags and creating untested combinations.
  • Reusing an old flag key for a different feature.

Likely follow-ups

How do you ensure a user sees the same variant every time?
Deterministic bucketing: hash the stable user or device id with the flag key to a percentage bucket.
How do you avoid UI flicker with client flags?
Evaluate on the server or edge and send resolved values with the HTML, or hold rendering of the flagged region until values are ready.
Flag versus configuration?
Flags switch behaviour and are usually temporary; configuration tunes parameters and is long-lived; both need ownership and validation.
How do you clean up flags?
Track expiry and owner, create removal tickets automatically at 100% rollout, and delete code, flag and tests together.

Docker and containers

“What is Docker and how do containers differ from virtual machines? Explain images, layers, Dockerfile best practices, multi-stage builds, volumes, networking, Docker Compose, registries and securing containers. How do you containerise a Node or Next.js app?”

Say this first (30 seconds)

“A container packages an application with its dependencies into an isolated process that shares the host operating system kernel, using namespaces and cgroups, so it is lightweight and starts in seconds compared with a virtual machine that includes a whole guest OS. An image is a layered, immutable template built from a Dockerfile; a container is a running instance of it. For a Node app I use a multi-stage Dockerfile: one stage installs dependencies and builds, and a small final stage copies only the production output and runs as a non-root user, with a .dockerignore, pinned base image, health check and graceful shutdown. I tag images by commit SHA, store them in a registry, scan them for vulnerabilities, and run them through an orchestrator such as Kubernetes or ECS.”

Details interviewers probe

  • Core concepts: image (layers + metadata), container (running process with its own filesystem, network and PID namespaces), registry (Docker Hub, GHCR, ECR, ACR), tag versus digest (image@sha256:… is immutable), Dockerfile instructions (FROM, RUN, COPY, ENV, EXPOSE, USER, CMD versus ENTRYPOINT, HEALTHCHECK), build context and .dockerignore, BuildKit caching.
  • Dockerfile best practices: small pinned base images; multi-stage builds; order instructions from least to most frequently changing; combine related RUN commands and clean caches; npm ci --omit=dev in the runtime stage; avoid latest; use exec-form CMD so signals reach the process (graceful shutdown with SIGTERM); run as non-root; do not bake secrets into layers; one process per container; add a health check.
  • Node and Next.js in containers: output: 'standalone' in Next.js produces a minimal server; copy .next/static and public; set NODE_ENV=production; configure memory limits and --max-old-space-size; use a process manager like tini or Node’s signal handling; serve static assets from a CDN (N12).
  • Volumes and persistence: containers are ephemeral; use volumes for persistent data (databases in development), bind mounts for local source in dev, and external managed services or object storage in production; never rely on container filesystem state.
  • Networking: bridge networks, port mapping (-p 3000:3000), container DNS by service name in Compose, host networking (rare), overlay networks across hosts; expose only needed ports.
  • Docker Compose: declarative multi-container setups for local development and testing (app, database, cache, mocks); depends_on with health conditions; profiles; override files; not the production orchestrator for large systems.
  • Security: minimal base images, non-root user, drop capabilities, read-only root filesystem, no secrets in images (use runtime secrets), scan images (Trivy, Grype, Snyk), sign images (Cosign), keep base images patched, avoid privileged containers and the Docker socket mount, limit resources, and use trusted registries (A12).
  • Build optimisation: BuildKit cache mounts for package managers, layer ordering, remote cache in CI (--cache-from), multi-platform builds (buildx for amd64 and arm64), and smaller contexts.
  • Resource management: CPU and memory limits and requests (cgroups); a Node process in a limited container needs memory-aware heap settings; OOM kills show as exit code 137.
  • Dev containers: reproducible development environments defined in devcontainer.json for consistent onboarding (B9).
  • Alternatives and standards: OCI image and runtime standards; Podman (daemonless), containerd, BuildKit, Buildpacks (build images without Dockerfiles), serverless containers (Cloud Run, Fargate, Azure Container Apps).
  • Frontend relevance: containerise SSR servers, BFFs and build/test environments (Playwright images), run consistent CI environments, and serve static builds with nginx or Caddy in a small image with correct cache headers and SPA fallback.
  • Common issues: large images from copying node_modules or build tools, slow builds due to poor layer order, wrong signals (container not stopping), zombie processes, timezone and locale differences, file permission problems with bind mounts, and architecture mismatches (arm Mac versus amd64 servers).

Traps

  • Saying containers are “lightweight VMs”; they share the host kernel and isolate processes.
  • Copying the whole project before installing dependencies, invalidating the cache on every change.
  • Using the latest tag in production, so builds are not reproducible.
  • Running as root and baking secrets or .env files into the image.
  • Using shell-form CMD so SIGTERM never reaches Node and shutdown is not graceful.

Likely follow-ups

What is the difference between an image and a container?
An image is the immutable layered template; a container is a running instance with a writable layer on top.
CMD versus ENTRYPOINT?
ENTRYPOINT defines the executable; CMD provides default arguments that can be overridden.
How do you pass configuration and secrets to a container?
Environment variables or mounted files injected at runtime by the orchestrator or secret manager, never baked into the image.
Why is my image huge?
Probably includes build tools and dev dependencies; use multi-stage builds, slim bases and a .dockerignore.

Kubernetes, cloud and infrastructure as code

“Explain Kubernetes at a working level: pods, deployments, services, ingress, config, autoscaling. What cloud services does a frontend platform use (AWS S3, CloudFront, Lambda, ECS/EKS, Route 53)? What is infrastructure as code and when is serverless the right choice?”

Say this first (30 seconds)

“Kubernetes is a container orchestrator: I declare the desired state, such as three replicas of this image with these resources, and controllers continuously reconcile the cluster to match. The key objects are pods, the smallest unit running containers; deployments, which manage replicas and rolling updates; services, which give pods a stable address and load balance; ingress, which routes external HTTP traffic; ConfigMaps and Secrets for configuration; and the horizontal pod autoscaler. In the cloud, a typical frontend stack is object storage plus a CDN for static sites, containers on ECS, EKS or Cloud Run for server rendering and APIs, serverless functions for event-driven work, a managed database, DNS and a load balancer. I define all of it as code with Terraform or similar so environments are reproducible and reviewed.”

Details interviewers probe

  • Pods and containers: a pod holds one or more tightly coupled containers sharing network and storage; pods are ephemeral and replaced, never patched. Sidecars (proxy, log shipper) extend behaviour. Resource requests (scheduling) and limits (enforcement) prevent noisy neighbours; exceeding memory limits leads to OOM kills.
  • Deployments and updates: declarative rollouts with maxSurge/maxUnavailable; readiness probes remove pods from service until ready; liveness probes restart stuck containers; preStop hooks and terminationGracePeriodSeconds enable graceful shutdown; rollback with rollout undo; progressive delivery tools add canaries (A6).
  • Services and networking: ClusterIP, NodePort, LoadBalancer; DNS names inside the cluster; ingress controllers (nginx, Traefik, cloud ALB) and the Gateway API; service meshes (Istio, Linkerd) for mTLS and traffic policies in large systems.
  • Configuration and secrets: ConfigMaps for non-sensitive config, Secrets (base64, not encrypted by default; enable encryption at rest, use external secret operators with cloud vaults), environment variables or mounted files, immutable config versions with rolling restarts.
  • Autoscaling: HPA scales replicas on CPU, memory or custom metrics (requests per second, queue length); Vertical Pod Autoscaler tunes requests; cluster autoscaler adds nodes; KEDA scales on events; set sensible min/max and cooldowns.
  • Helm, Kustomize, GitOps: package manifests (Helm charts), overlay per environment (Kustomize), deploy through Argo CD or Flux from Git (A5); avoid manual kubectl apply in production.
  • When Kubernetes is overkill: small teams and simple apps are often better on managed platforms (Vercel, Netlify, Cloud Run, Fargate, App Service) where the platform handles scaling and patching; Kubernetes pays off with many services, custom networking, multi-tenant platforms and portability needs, but demands operational skill.
  • Cloud building blocks for a frontend platform: object storage + CDN for static assets; edge functions for redirects and personalisation; container services for SSR/BFF; serverless functions (Lambda, Cloud Functions) for event handlers and glue; managed databases and caches; queues and event buses; secrets manager; IAM; VPC and security groups; observability services.
  • Serverless trade-offs: pay per use, automatic scaling, no server management; cold starts, execution time limits, connection limits to databases (use proxies), vendor-specific tooling, harder local testing, and costs that rise at steady high load. Good for spiky, event-driven or low-traffic workloads; containers suit steady load and long-running processes.
  • Infrastructure as code: Terraform/OpenTofu (declarative, multi-cloud, state file), Pulumi (general-purpose languages), AWS CDK/CloudFormation, Bicep (Azure). Practices: modules, remote state with locking, environments via workspaces or separate stacks, plan reviewed in pull requests, drift detection, policy as code (OPA, Sentinel), no manual console changes.
  • Environments and accounts: separate accounts or projects per environment, least-privilege IAM roles, network segmentation, tagging for cost allocation, and landing zones for governance.
  • Reliability on cloud: multiple availability zones, health checks, autoscaling groups, managed database failover, backups, infrastructure redundancy in more than one region for critical systems (cost and complexity trade-off), and tested disaster recovery with RPO/RTO targets.
  • Costs awareness: right-size, use autoscaling and spot instances where safe, cache at the CDN, set budgets and alerts, tag resources, and review idle resources (A12).
  • Frontend-specific hosting patterns: static SPA on S3 + CloudFront with SPA fallback and immutable caching; SSR on containers or serverless with CDN in front; image optimisation service; edge middleware; separate asset domain optional.

Traps

  • Reaching for Kubernetes for a small app that a managed platform would run with far less effort.
  • Treating pods as pets: storing state locally or patching running containers.
  • Missing resource requests and limits, so pods are evicted or starve others.
  • Manual console changes that drift from the Terraform state.
  • Serverless functions opening a new database connection per invocation and exhausting the database.

Likely follow-ups

Pod versus deployment versus service?
A pod runs containers; a deployment manages replicas and updates of pods; a service gives them a stable network identity and load balancing.
Liveness versus readiness probes?
Liveness restarts a container that is stuck; readiness controls whether it receives traffic.
How would you host a React SPA and an API on AWS?
SPA on S3 behind CloudFront with immutable asset caching and SPA fallback; API on ECS Fargate or Lambda behind an ALB or API Gateway with RDS; Route 53 and ACM for DNS and TLS; WAF; all defined in Terraform.
Why infrastructure as code?
Reproducible environments, review and audit through Git, fast recovery, and drift detection.

Observability, SLOs and alerting

“What is observability and how does it differ from monitoring? Logs, metrics and traces. What are SLIs, SLOs and error budgets? How do you set up alerting and dashboards? How do you monitor a frontend in production?”

Say this first (30 seconds)

“Monitoring tells you whether known things are broken; observability lets you ask new questions about system behaviour from the data it emits: logs for events, metrics for trends and alerts, and traces for the path of a request across services, tied together by correlation ids. I define service level indicators, measurable signals like the proportion of requests under 300 ms or pages with good LCP, set service level objectives such as 99.9% over 30 days, and use the remaining error budget to balance reliability and feature velocity. Alerts fire on symptoms users feel, not every cause, and link to runbooks. For the frontend I add real-user monitoring, error tracking with source maps and release tags, and synthetic checks of key journeys.”

Details interviewers probe

  • Logs: structured, leveled, with correlation ids; centralised (ELK, Loki, CloudWatch, Datadog); retention and cost management; sampling noisy logs; no secrets or personal data (D11).
  • Metrics: counters, gauges, histograms; golden signals: latency, traffic, errors, saturation (Google SRE) and RED/USE methods; label cardinality must stay bounded; percentiles (p50, p95, p99) rather than averages.
  • Traces: spans form a tree per request; context propagation (W3C traceparent) through HTTP and messaging; sampling (head-based, tail-based) to control cost; link front-end RUM sessions to backend traces.
  • OpenTelemetry: vendor-neutral APIs, SDKs and collector for traces, metrics and logs; auto-instrumentation for common frameworks; export to many backends, avoiding lock-in.
  • SLIs and SLOs: choose SLIs close to user experience (availability, latency, correctness, freshness; frontend: LCP, INP, error-free sessions, successful checkouts); SLOs set a target for a rolling window; error budgets quantify allowed unreliability; burn-rate alerts (fast and slow windows) catch problems early without paging on blips.
  • Alerting quality: avoid alert fatigue: page only for user-impacting urgent conditions, route others to tickets or dashboards, tune thresholds, deduplicate, add context (graphs, recent deploys, runbook links), and review alert volume and false-positive rate regularly.
  • Dashboards: a service overview (golden signals), dependency health, release comparison, business KPIs (orders per minute) and per-team views; avoid wall-of-graphs; design for the on-call engineer at 3 a.m.
  • Frontend observability: error tracking (Sentry, Datadog RUM) with source maps and release versions; web vitals by route and device; session replay with privacy masking; JS error rate and failed API calls from the client; resource timing; feature-flag state attached to events; synthetic checks for login, search and checkout; correlate with backend traces (B4, F6).
  • Release observability: mark deployments on graphs, compare versions side by side, auto-rollback on regression, and track change failure rate and time to restore (DORA).
  • Business and product metrics: conversion funnels, drop-off, feature usage; link technical health to business outcomes so incidents are prioritised by impact.
  • Cost and governance: telemetry volume is expensive; set retention tiers, sampling, and data ownership; protect privacy (GDPR) in logs and replay.
  • On-call and ownership: teams own the services they run; rotation with support, runbooks, escalation policies, and postmortems (A11).
  • Debugging with observability: start from an alert or user report, narrow with metrics by dimension (route, version, region), follow a trace to the slow span or failing dependency, read logs for the specific request, form a hypothesis, test, and fix.

Traps

  • Alerting on infrastructure metrics that do not correlate with user pain.
  • SLOs of 100%, which are impossible and block all change.
  • Averages for latency, hiding tail pain.
  • High-cardinality labels (user ids) in metrics, exploding cost.
  • No frontend visibility, so the backend looks healthy while users see errors.

Likely follow-ups

Monitoring versus observability?
Monitoring checks known conditions with predefined dashboards and alerts; observability provides rich, correlated telemetry so you can investigate unknown failure modes.
What is a burn-rate alert?
An alert on how fast the error budget is being consumed relative to the SLO window, catching fast severe outages and slow leaks.
What are the golden signals?
Latency, traffic, errors and saturation.
How do you know the frontend is healthy in production?
RUM vitals and error rates by release, synthetic journeys, API failure rates seen from the client, and business funnel metrics.

Incident management and resilience

“How do you handle a production incident? Severity levels, roles, communication, mitigation versus root cause, postmortems. What resilience patterns do you build in: timeouts, retries, circuit breakers, graceful degradation, disaster recovery?”

Say this first (30 seconds)

“During an incident the priority is to restore service, not to find the root cause. I assess severity, assign an incident commander, open a channel, communicate status to stakeholders at a regular cadence, and apply the fastest safe mitigation: roll back, disable a feature flag, scale up or fail over. Once service is restored we investigate and hold a blameless postmortem that records the timeline, root and contributing causes, impact, what went well and badly, and concrete action items with owners. Prevention comes from resilience patterns, timeouts, retries with backoff, circuit breakers, bulkheads and graceful degradation, plus backups, disaster recovery plans with defined recovery objectives, and practising failure through game days.”

Details interviewers probe

  • First response: acknowledge the alert, confirm impact (who and how many are affected), declare severity, start an incident channel and bridge, name an incident commander, and avoid parallel uncoordinated changes. Check recent changes first: deployments, flag changes, infrastructure or dependency changes cause most incidents.
  • Mitigation options: rollback the last deploy, disable a feature flag, scale capacity, fail over to a replica or region, block abusive traffic, serve a static fallback page, degrade non-critical features, restore from backup. Prefer reversible, low-risk actions; communicate what you are doing and why.
  • Communication: regular updates to stakeholders and customers (status page) with what is known, impact, actions and next update time; no speculation; internal and external messages aligned; support teams briefed. Over-communicate during major incidents.
  • Diagnosis approach: dashboards and traces to localise (which service, region, version), compare with baseline, review logs for specific requests, form and test hypotheses one at a time, keep a timeline, and escalate to experts early.
  • Blameless postmortems: focus on systems and conditions, not people; record summary, impact, detection, timeline, root cause and contributing factors (five whys, fault trees), what went well and poorly, and action items prioritised, owned and tracked to completion. Share widely to spread learning. Distinguish mitigation actions from prevention actions and from detection improvements.
  • Frontend incidents: a broken release (rollback by repointing HTML, keep old assets), a third-party script outage (feature-flagged kill switch, timeouts, async loading), CDN or DNS problems, expired certificates, API outages (graceful error UI, cached data), build/dependency compromise, and widespread JavaScript errors after a deploy (error tracking by release).
  • Resilient frontend design: error boundaries, retries with backoff for idempotent calls, timeouts and abort, offline support and cached data, skeletons and partial rendering, feature degradation when a service fails, static fallbacks for critical pages (status, maintenance, checkout alternatives), and clear user messaging (F10).
  • Backend patterns: circuit breakers, bulkheads, queues to absorb spikes, idempotency, rate limiting and load shedding, health checks, autoscaling, multi-AZ deployment, and dependency isolation (D12).
  • Disaster recovery: define RPO and RTO per system; strategies from backup and restore to pilot light, warm standby and active-active across regions; automate and test failover; protect backups from deletion and ransomware; rehearse restores regularly.
  • Chaos engineering and game days: deliberately inject failures (kill instances, add latency, block dependencies) in controlled conditions to verify resilience and train responders; start in staging, then production with blast-radius limits.
  • Runbooks and on-call: concise runbooks per alert (what it means, how to check, how to mitigate), escalation paths, fair rotations with handover, compensation and rest policies, and training with simulated incidents; reduce toil through automation.
  • Metrics: MTTD (detect), MTTA (acknowledge), MTTR (restore), incident count and severity, change failure rate, repeat incidents, postmortem action completion rate.
  • Leadership behaviours: stay calm, delegate, make decisions with incomplete information, protect the team from blame, and follow through on learning.

Traps

  • Hunting for the root cause while customers remain down, instead of mitigating first.
  • Making several uncoordinated changes at once, so nobody knows what fixed or worsened it.
  • Blame-focused postmortems that make people hide mistakes.
  • Action items with no owner or deadline, so the same incident repeats.
  • Untested backups and failover plans that fail when needed.

Likely follow-ups

What do you do in the first 10 minutes of a SEV1?
Declare it, assign roles, check what changed recently, mitigate (usually rollback or flag off), communicate impact and next update, and keep a timeline.
RPO versus RTO?
RPO is the maximum acceptable data loss measured in time; RTO is the maximum acceptable time to restore service.
How do you make postmortems effective?
Blameless, evidence-based, with prioritised, owned action items and visible follow-up.
How would you handle a failing third-party script that breaks checkout?
Disable it with a kill switch or tag-manager rule, ensure scripts load async with timeouts, and add monitoring plus a fallback.

DevSecOps, cost and platform thinking

“How do you build security into the delivery pipeline? SAST, DAST, dependency and secrets scanning, SBOM, image signing. How do you manage cloud cost? What is platform engineering and a golden path?”

Say this first (30 seconds)

“DevSecOps moves security earlier and automates it: the pipeline scans code for vulnerabilities, dependencies for known CVEs and licences, and commits for leaked secrets; container images are scanned and signed; infrastructure as code is checked against policies; and deployments use least-privilege, short-lived credentials. Findings are triaged by severity and exploitability with agreed fix times. Alongside security, I keep an eye on cost, tagging resources, setting budgets and alerts, right-sizing and caching, because cost is an engineering constraint too. At organisation scale, platform engineering provides self-service golden paths, templated pipelines, infrastructure and observability, so product teams ship safely without each rebuilding the same tooling.”

Details interviewers probe

  • Static analysis (SAST) and code scanning: CodeQL, Semgrep, SonarQube, ESLint security rules; run on pull requests with developer-friendly results; tune to reduce false positives; block merges on critical findings only to maintain trust.
  • Dependency and supply-chain security: software composition analysis (Dependabot, Renovate, Snyk, Socket, npm audit); licence compliance; lockfiles; pin and verify; restrict install scripts; SBOM generation (CycloneDX, SPDX) for inventory and incident response; provenance attestations (SLSA levels, npm provenance); private registries and mirrors (B8, J29).
  • Secrets management: never commit secrets; pre-commit and server-side scanning (gitleaks, GitHub secret scanning); central vaults (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault); injected at runtime; rotation; short-lived credentials via OIDC federation from CI to cloud; revoke on leak and review exposure.
  • Container and infrastructure security: image scanning (Trivy, Grype), minimal bases, signed images (Cosign) and admission policies that only run signed images, IaC scanning (Checkov, tfsec), policy as code (OPA, Kyverno), least-privilege IAM, network segmentation, encryption at rest and in transit, audit logs.
  • DAST and runtime: dynamic scanning (OWASP ZAP) against staging, penetration tests before major releases, bug bounty programmes, WAF rules, runtime detection (Falco), and continuous monitoring of misconfigurations (cloud security posture management).
  • Pipeline security: protect branches and require reviews, pin third-party actions by SHA, restrict who can trigger deployments, separate build and deploy permissions, isolate runners, avoid executing untrusted PR code with secrets, sign and verify artifacts, and audit pipeline changes.
  • Compliance as code: automate evidence for SOC 2, ISO 27001, GDPR, PCI-DSS controls through pipeline logs, policy checks and access reviews; keep approvals and change records traceable.
  • Culture: security champions in teams, threat modelling in design reviews, training with real examples, blameless handling of vulnerabilities, and metrics (time to fix, open criticals) that drive improvement rather than blame.
  • Cost management (FinOps): visibility first (tagging, cost dashboards per team and environment), then optimisation (right-sizing, autoscaling, spot instances, storage tiers, log retention, CDN offload), then governance (budgets, anomaly alerts, reviews). Include egress and observability costs; compare serverless versus containers at steady load; build cost awareness into design reviews.
  • Platform engineering: internal developer platform offering self-service environments, CI/CD templates, observability, secrets and deployment through a portal or CLI (Backstage), with documentation and support; measure adoption, lead time and developer satisfaction; avoid mandating rigid platforms that slow teams.
  • Developer experience: fast pipelines, reliable preview environments, clear errors, good documentation, and automation of toil; DX investment pays back in throughput and retention (B9).
  • Sustainability: efficient builds, less data transferred, right-sized infrastructure, and scheduling non-urgent jobs reduce energy use and cost.
  • Balancing speed and safety: guardrails over gates: automate checks and use progressive delivery rather than heavy manual approvals; reserve human review for high-risk changes.

Traps

  • Flooding developers with scanner noise until they ignore all findings.
  • Long-lived credentials in CI, or secrets baked into images and repos.
  • Security as a late-stage gate by a separate team instead of a shared, automated practice.
  • Optimising cloud cost without visibility or ownership, or sacrificing reliability for savings.
  • Building a platform nobody asked for, with no product thinking or adoption metrics.

Likely follow-ups

What is an SBOM and why?
A software bill of materials listing components and versions, enabling fast impact analysis when a vulnerability is announced and supporting compliance.
How do you avoid long-lived cloud keys in CI?
Use OIDC federation so the pipeline obtains short-lived, scoped credentials per run.
How do you reduce a high cloud bill?
Allocate costs by tag, find the top spenders, right-size, cache and compress, tune retention, use committed or spot capacity, and add budgets and alerts.
What is a golden path?
A supported, opinionated route (templates and tooling) that makes the secure, observable, compliant way the easiest way to ship.

How to answer architecture and DevOps questions at L4

  • Lead with the problem and constraints, offer two or three options, recommend one and name what would change your mind. This is the pattern interviewers look for.
  • Show you have operated systems: mention how you detect, mitigate, roll back and learn, with a real example of an incident, a migration or a pipeline you improved.
  • Quantify outcomes: build time, deploy frequency, change failure rate, error budget, cost saved.
  • Keep reversibility and blast radius in every answer: flags, canaries, expand/contract migrations, rollbacks.
  • Be honest about operational weight: Kubernetes, micro-frontends and multi-region designs are costly, so justify them by need.
  • The interview is theoretical: expect “how would you design”, “compare”, “what would you do first” and “what are the trade-offs”, not live coding.
