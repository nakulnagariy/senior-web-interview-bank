The critical rendering path

“What happens when you type a URL and press Enter? Explain how the browser turns HTML, CSS and JavaScript into pixels. What blocks rendering? What do async and defer do?”

Say this first (30 seconds)

“The browser resolves DNS, opens a TCP and TLS connection, sends an HTTP request and receives HTML. It parses the HTML incrementally into the DOM. When it meets stylesheets it builds the CSSOM; CSS is render-blocking because the browser needs it to know what elements look like. The DOM and CSSOM combine into a render tree of visible boxes, then the browser calculates layout, paints, and composites layers on the GPU. Scripts are parser-blocking by default: the parser stops to download and run them, and they wait for pending CSS because they may query styles. defer downloads in parallel and runs after parsing in order; async runs as soon as it arrives, in any order. The first paint can only happen after the critical CSS is ready, so I keep the critical path short.”

Details interviewers probe

  • URL to page, step by step: URL parsing and HSTS check; service worker and cache lookup; DNS resolution (browser, OS, resolver caches); TCP handshake (or QUIC for HTTP/3); TLS handshake; HTTP request; server work; response streamed to the parser; subresource requests discovered by the preload scanner; render and paint; JavaScript execution and hydration; further requests. Each step has optimisations (DNS prefetch, preconnect, keep-alive, CDN, caching).
  • HTML parsing: incremental, error-tolerant tokeniser and tree builder. A preload scanner looks ahead to start downloading images, scripts and styles while the main parser is blocked. DOM is built progressively and can be rendered before the document ends (streaming HTML).
  • CSSOM and render blocking: external stylesheets block rendering (to avoid a flash of unstyled content) and block script execution that follows them. Reduce by inlining critical CSS, splitting by media (media="print" is not blocking), and loading the rest asynchronously (preload then swap). Avoid @import chains (serial requests).
  • Render tree: includes visible nodes only: display: none is excluded; visibility: hidden is included (takes space); pseudo-elements are included.
  • Events: DOMContentLoaded fires when HTML is parsed and deferred scripts have run; load after all resources; readystatechange for document states. First Contentful Paint and LCP are separate timing marks.
  • Resource hints: preload (fetch a needed resource early), preconnect (open connection), dns-prefetch, prefetch (next navigation), modulepreload, and fetchpriority to tune; use sparingly because over-preloading steals bandwidth (performance guide).
  • Fonts: text is hidden or swapped while fonts load; font-display: swap or optional, preload key fonts, subset and use WOFF2 to limit layout shift and delay.
  • Images: discovered by the preload scanner; set dimensions to avoid layout shift; the LCP image should not be lazy-loaded or hidden behind JavaScript.
  • Single-page app rendering: the HTML is nearly empty, so FCP waits for JavaScript to download, parse, execute and fetch data; this is why SSR/SSG or streaming improves first paint (Next.js guide).
  • Main thread: parsing, style, layout, paint recording and JavaScript share the main thread; long scripts delay everything, including input handling (J18).
  • Measuring: DevTools Performance panel (parse, style, layout, paint), Lighthouse, the Network waterfall (critical chain), PerformanceObserver for paint timing entries.
  • Streaming and early flush: servers should send the head early (with links to critical CSS and preloads) before slow work finishes; 103 Early Hints lets the browser start fetching before the final response verify support.

Traps

  • Saying scripts are always blocking. Modern attributes and modules change that.
  • Believing async preserves execution order. Only defer does.
  • Forgetting that CSS delays script execution, so a slow stylesheet delays interactivity too.
  • Lazy-loading or JS-injecting the LCP image, so the preload scanner cannot find it.
  • Describing only network steps and ignoring parse, style, layout and paint.

Likely follow-ups

How do you reduce time to first paint?
Smaller critical CSS and HTML, deferred scripts, fewer round trips (CDN, preconnect, HTTP/2 or 3), server rendering, compressed responses, and preloading the LCP resource.
defer versus async versus module scripts?
Defer: ordered, after parsing. Async: unordered, as soon as ready. Modules: deferred by default and support imports.
What is the preload scanner?
A lightweight secondary parser that finds resources ahead of the main parser so downloads start early even when the main parser is blocked.
What triggers DOMContentLoaded versus load?
The first after parsing and deferred scripts; the second after all subresources such as images have finished.

Layout, paint and compositing

“What are reflow and repaint? What is layout thrashing? Why are transform and opacity cheap to animate? What are compositor layers and will-change?”

Say this first (30 seconds)

“After style calculation, the browser runs layout, also called reflow, to compute the size and position of every box; then paint to draw them into layers; then composite to assemble layers on the GPU. Changing a property that affects geometry, such as width, top or font size, triggers layout and everything after it. Changing only appearance, such as colour, triggers paint. Changing transform or opacity can often be handled by the compositor alone, with no layout or paint, which is why those are the right properties to animate. Layout thrashing happens when code alternates reading layout values, such as offsetHeight, with writing styles, forcing the browser to recalculate synchronously on every read. I batch reads before writes and animate on the compositor.”

Details interviewers probe

  • Style recalculation: matching selectors to elements and computing styles. Cost grows with the number of elements affected and selector complexity; keep DOM size moderate (under about 1,500 nodes is a common guideline) and avoid expensive selectors in hot paths.
  • Layout (reflow): computing geometry; changes can cascade to children, siblings and ancestors. Global layout is costly on large DOMs. Flexbox and grid are efficient but deep nesting adds cost.
  • Paint: recording drawing instructions for each layer, then rasterising tiles (on raster threads/GPU). Large box shadows, filters, gradients and big layers cost more.
  • Compositing: layers (promoted by transform, opacity animations, will-change, video, canvas, fixed positioning in some cases) are drawn and combined by the compositor thread, which can scroll and animate without the main thread. This is why compositor animations stay smooth even when JavaScript is busy.
  • will-change and layers: a hint to promote an element ahead of animation. Overuse creates many layers, consuming GPU memory and slowing compositing; apply just before animation and remove after. transform: translateZ(0) hacks are outdated.
  • Containment: contain: layout paint style and content-visibility: auto let the browser skip rendering off-screen content, big wins on long pages; provide contain-intrinsic-size to avoid scroll jumps (CSS guide).
  • Smoothness target: 60 frames per second means about 16.7 ms per frame for all work; modern devices run at 90 to 120 Hz. Janky frames come from long JavaScript, forced layout and heavy paints. requestAnimationFrame aligns visual updates with the frame (J22).
  • Scrolling performance: passive event listeners, avoid heavy scroll handlers, use position: sticky, IntersectionObserver, and virtualisation of long lists.
  • Layout shift: late-loading content moving things around (CLS); reserve space with dimensions, aspect-ratio and skeletons, avoid inserting content above existing content, and prefer transforms for movement.
  • Diagnosing: DevTools Performance (purple layout, green paint), the Rendering panel (paint flashing, layout shift regions, layer borders), Layers panel, and long animation frame (LoAF) attribution verify.
  • Fonts and text: text layout is expensive; avoid changing fonts after load; use font-display and size-adjust fallbacks.
  • Animation libraries: prefer CSS transitions and the Web Animations API for compositor-friendly properties; JavaScript-driven animation of layout properties should be a last resort.

Traps

  • Animating top, left or width instead of transform.
  • Putting will-change on dozens of elements permanently.
  • Reading layout properties inside loops that also write styles.
  • Saying “repaint and reflow are the same”. Reflow recomputes geometry; repaint redraws pixels.
  • Assuming opacity is always free; it needs its own layer and memory.

Likely follow-ups

Why is transform smoother than left?
transform changes how an existing layer is composited without recomputing layout or repainting; left triggers layout and paint every frame.
How do you find layout thrashing?
The Performance panel shows repeated forced reflow warnings with the stack that triggered them.
What does content-visibility: auto do?
It skips layout and paint for off-screen sections until they approach the viewport, reducing initial render cost.
Is layout the same on every browser?
The model is standardised, but engines optimise differently; test on real devices and across engines.

Browser architecture and cross-browser strategy

“How is a modern browser built? What is site isolation? How do you handle cross-browser compatibility, polyfills and progressive enhancement? How do you decide which browsers to support?”

Say this first (30 seconds)

“Modern browsers are multi-process: a browser process manages UI and coordination, renderer processes run each site’s pages with the JavaScript engine and layout, a GPU process handles compositing, and a network process handles requests. Site isolation puts different sites in different processes to contain security bugs. There are three engine families: Blink in Chrome and Edge, WebKit in Safari, and Gecko in Firefox, and on iOS all browsers use WebKit. For compatibility I define a support matrix from analytics, write standards-based code, feature-detect instead of sniffing user agents, use progressive enhancement so the core works everywhere, add polyfills only for what my targets lack, set browserslist to drive transpilation and prefixing, and test on real devices and services like BrowserStack.”

Details interviewers probe

  • Processes and threads: each renderer has a main thread (JavaScript, DOM, style, layout), compositor thread, and raster workers. Web Workers run in the renderer on separate threads (J23). Out-of-process iframes isolate cross-site frames.
  • Same-origin policy and sandboxing: origins (scheme, host, port) isolate data; renderers are sandboxed and cannot access files directly; IPC goes through the browser process. This underpins CORS, cookies and CSP (protocols guide).
  • Engines and JS engines: Blink+V8, WebKit+JavaScriptCore, Gecko+SpiderMonkey (J26). They differ in feature timing, bugs and performance characteristics; Safari historically lags on some features and has stricter storage and autoplay policies. On iOS all browsers use WebKit (some regions differ verify).
  • Support matrix: decide from real traffic (analytics) and business needs (corporate IE-like constraints, older Android WebViews, smart TVs). Use “defaults” or a percentage target in browserslist (> 0.5%, last 2 versions, not dead) and document unsupported browsers with a graceful message.
  • Feature detection: 'IntersectionObserver' in window, CSS.supports('display','grid'), @supports in CSS, Modernizr (legacy). Avoid user-agent sniffing: fragile and wrong. For bugs that detection cannot catch, use targeted workarounds documented with the browser version.
  • Progressive enhancement versus graceful degradation: start from a working baseline (semantic HTML, basic CSS) and layer enhancements; degradation starts from the full experience and tries to fall back. Progressive enhancement is more robust.
  • Polyfills and transpilation: transpile syntax with Babel/SWC for your targets; polyfill missing APIs with core-js (selective useBuiltIns: 'usage'), or load polyfills conditionally with a script that detects need (differential loading with type=module/nomodule is largely obsolete). Polyfills cannot emulate everything (layout features, CSS). See B7.
  • CSS compatibility: Autoprefixer adds vendor prefixes based on browserslist; use @supports and fallbacks; check caniuse and MDN compatibility data; PostCSS plugins down-level modern syntax (nesting, custom media) when needed.
  • Common cross-browser issues: date and time input differences, scroll behaviour and 100vh on mobile (use dvh), form control styling, flexbox/grid gaps in old versions, :has() and container query support, storage eviction in Safari, autoplay and permissions policies, webfont rendering, and touch versus pointer events.
  • Testing: automated cross-browser runs with Playwright (Chromium, Firefox, WebKit) and cloud grids (BrowserStack, Sauce Labs, LambdaTest); real device labs for key phones; visual regression per browser; manual smoke tests on Safari/iOS before releases.
  • Interop and standards: the Interop project aligns engines on test suites; web-platform-tests define conformance; features reach “Baseline widely available” after about 30 months of cross-browser support verify the definition.
  • Mobile and WebViews: embedded browsers (Android WebView, iOS WKWebView, in-app browsers like social apps) lag behind and have quirks; test inside them if users arrive from apps.
  • Accessibility and assistive tech: screen reader and browser combinations behave differently (VoiceOver with Safari, NVDA with Firefox/Chrome); include them in test plans (R13).

Traps

  • Detecting browsers by user agent string.
  • Targeting “the latest Chrome” without checking the actual audience (Safari on iOS is often large).
  • Shipping all polyfills to all users instead of conditionally.
  • Assuming a feature works everywhere because it works in Chrome DevTools.
  • Believing polyfills fix CSS or layout differences.

Likely follow-ups

How do you decide when to drop a browser?
When usage falls below an agreed threshold and the maintenance cost or blocked features outweigh the audience, communicated in advance with a graceful fallback.
What does Autoprefixer need?
A browserslist configuration; it reads it and adds only the prefixes those browsers require.
What is site isolation?
Putting each site in its own renderer process so a compromised page cannot read other sites’ memory.
Why test on real iOS devices?
All iOS browsers use WebKit with its own storage, viewport and media quirks that desktop emulation does not reproduce.

DevTools and debugging workflows

“How do you debug performance, layout, network and memory problems in the browser? Which DevTools panels do you use and what do you look for? How do you debug production issues?”

Say this first (30 seconds)

“I pick the panel by symptom. For slow loads I use the Network panel with throttling to read the waterfall and critical chain, and Lighthouse for a first diagnosis. For jank or slow interactions I record in the Performance panel and read the flame chart for long tasks, forced layouts and expensive scripts. For layout bugs I use Elements, the computed styles and box model, and the Rendering tab’s layout shift and paint flashing. For leaks I use Memory heap snapshots. For storage and service workers, the Application panel. In production I rely on error tracking with source maps, real-user monitoring and logs, because I cannot attach a debugger there.”

Details interviewers probe

  • Network panel: filter by type, disable cache, throttle (Fast 3G, Slow 3G, offline), view timing breakdown (queueing, DNS, connect, TLS, TTFB, download), initiator chains, request priority, response headers (cache, compression, CORS), copy as cURL/fetch, HAR export for sharing.
  • Performance panel: record page load or an interaction; read the main thread flame chart (yellow scripting, purple layout and style, green paint); identify long tasks (over 50 ms), what called them, and forced synchronous layouts; use the Interactions track for INP; CPU throttling and network throttling reflect mobile reality; the Insights panel summarises issues verify.
  • Lighthouse and the Performance Insights: lab audits for performance, accessibility, SEO and best practices with prioritised suggestions; lab data is a starting point, not user reality (performance guide).
  • Elements, Computed, Layout: inspect applied and overridden rules; toggle classes and states; grid and flex overlays; animations panel; accessibility tree and contrast checks.
  • Sources: breakpoints (line, conditional, logpoint, DOM change, XHR, event listener, exception), watch expressions, call stack with async frames, blackboxing libraries, workspaces and local overrides (try fixes against production assets), snippets.
  • Console: console.table, console.time, console.trace, console.assert, $0 (selected element), monitorEvents, copy(); the live expression feature; do not leave debug logs in production.
  • Application: storage inspection and clearing, service worker lifecycle controls (update on reload, bypass for network), Cache Storage, background services, back/forward cache test, Manifest and installability checks.
  • Source maps in production: upload to error trackers (Sentry) rather than publishing them publicly; use hidden-source-map style options; match maps to releases; map minified stack traces for readable errors (J21).
  • Framework tools: React DevTools (component tree, props and hooks, Profiler with “why did this render”), Redux DevTools (actions, time travel), TanStack Query devtools, Angular DevTools, Vue DevTools.
  • Remote debugging: Chrome chrome://inspect for Android, Safari Web Inspector for iOS devices, WebView debugging; essential for mobile-only bugs.
  • Debugging workflow: reproduce reliably, gather environment (browser, device, network, feature flags), bisect (git bisect, toggle flags), check console and network first, isolate in a minimal case, fix, add a regression test, and describe the root cause.
  • Production debugging: session replay (with privacy controls), breadcrumbs of user actions, release tagging, feature flag state in error context, structured logs, trace ids correlating frontend and backend, and sampled RUM traces (DevOps guide).
  • Performance profiling in Node: --inspect with DevTools, CPU profiles and flame graphs (clinic.js, 0x), heap snapshots (Node guide).

Traps

  • Judging performance on a fast laptop with cache enabled and no throttling.
  • Trusting a single Lighthouse score as the truth for users.
  • Shipping unminified source maps publicly, exposing source code.
  • Debugging production by guessing instead of adding observability.
  • Leaving the Network panel on “Disable cache” and missing cache-related bugs.

Likely follow-ups

How do you find what is making the main thread busy?
Record a profile, inspect the longest tasks and their call trees, and look for scripting, forced layout or style recalculation.
How do you debug an issue only on iPhone?
Safari remote inspector with a connected device, or a cloud device lab, plus logging and error tracking with device context.
What is a logpoint?
A breakpoint that logs an expression without pausing or editing code, useful in production-like scenarios.
How do you test slow networks?
DevTools network and CPU throttling, plus real devices on throttled networks and WebPageTest profiles.

What bundlers do: webpack, Vite, esbuild, Rollup

“What does a bundler do and why do we need one? Compare webpack, Vite, Rollup, esbuild, Parcel and Turbopack. How does Vite’s dev server differ from webpack’s? What is HMR?”

Say this first (30 seconds)

“A bundler starts from entry points, resolves the module graph of imports, transforms files such as TypeScript, JSX, CSS and images, and emits optimised static assets: bundled, minified, tree-shaken, code-split and content-hashed for caching. We need it because source is split into many modules and uses syntax and formats that browsers or npm packages do not consume directly. Webpack is the long-standing, highly configurable bundler with a huge plugin ecosystem, bundling during development too. Vite takes a different approach: in development it serves source as native ES modules on demand and pre-bundles dependencies with esbuild, so startup is near instant and hot module replacement is fast, and for production it bundles with Rollup. esbuild and SWC are very fast compilers written in Go and Rust, and Turbopack and Rspack are Rust-based bundlers.”

Details interviewers probe

  • Why bundle at all? Fewer requests (less relevant with HTTP/2 and 3), resolve node_modules bare imports, transform non-standard syntax and file types, tree shake, minify, split code, add content hashes for long-term caching, inline small assets, and produce consistent output for many browsers.
  • Core concepts: entry points; module resolution (resolve.alias, extensions, exports field); loaders or plugins (transform files: babel-loader, css-loader, asset modules in webpack; plugins in Vite and Rollup); chunks (units of output); output naming with content hashes; source maps; mode (development or production).
  • Webpack: configuration-heavy, loaders and plugins, Module Federation for micro-frontends (architecture guide), persistent caching in v5, asset modules, splitChunks optimisation, DefinePlugin for env constants. Strengths: flexibility, maturity. Weaknesses: complexity, slower builds, config sprawl.
  • Vite: uses native ESM in dev, esbuild for dependency pre-bundling and TypeScript transforms, Rollup for production. Config is small (vite.config.ts), strong defaults for CSS modules, PostCSS, assets, env variables (import.meta.env.VITE_*), SSR support, library mode, and a plugin API compatible with Rollup plugins. Caveat: differences between dev (unbundled) and prod (bundled) can surface edge cases; test the production build. Rolldown aims to unify the two verify status.
  • Rollup: ES module-focused, excellent tree shaking and clean library output (ESM, CJS, UMD); the base of Vite’s production build and many libraries.
  • esbuild and SWC: compilers and minifiers that are 10 to 100 times faster than JavaScript tools; esbuild has limited type-checking (none) and plugin ability; SWC powers Next.js and many toolchains. Neither type-checks TypeScript (T1).
  • Turbopack and Rspack: Rust-based; Turbopack is the Next.js bundler with incremental computation; Rspack is webpack-API compatible for easier migration. Maturity varies verify.
  • Hot Module Replacement (HMR): after an edit, the dev server sends the changed module to the browser, which swaps it without a full reload and preserves state where possible. React Fast Refresh preserves component state when only components change. HMR boundaries accept updates; if none, a full reload occurs.
  • Dev proxy and server features: proxying API calls to avoid CORS in development, HTTPS, middleware, history API fallback, and mock servers.
  • Assets and CSS: imports of images and fonts become URLs or inlined data URIs under a size threshold; CSS is extracted to files in production, minified with Lightning CSS or cssnano; CSS Modules scope class names.
  • Environment variables and defines: replaced at build time; only prefixed variables are exposed to client code; never put secrets in them; the same artifact for all environments requires runtime config (B10).
  • Choosing: new apps: Vite (or a framework’s default: Next.js with Turbopack/webpack). Libraries: Rollup/tsup. Large webpack apps: stay, or migrate to Rspack for speed. Evaluate on build time, ecosystem, plugin needs, SSR, and team familiarity.
  • Legacy: Create React App is deprecated; Gulp/Grunt are task runners, not module bundlers; Browserify predates ES modules.
  • Native ESM and import maps: browsers can load modules without bundling; import maps map bare specifiers to URLs; for production, bundling still wins for request count, tree shaking and compatibility.

Traps

  • “Vite does not bundle.” It does in production (Rollup); only the dev server is unbundled.
  • Assuming esbuild or SWC type-check TypeScript.
  • Exposing secrets via client-prefixed environment variables.
  • Testing only the dev server and shipping a production build that behaves differently.
  • Migrating bundlers without measuring the build-time benefit.

Likely follow-ups

Why is Vite’s dev server fast to start?
It does not bundle the app; it serves modules on demand and pre-bundles only dependencies with a fast compiler.
What is a loader versus a plugin in webpack?
Loaders transform individual files by type; plugins hook into the whole build lifecycle (emit assets, optimise, define constants).
How does HMR keep state?
It replaces only the changed module and re-runs it; framework integrations (React Fast Refresh) re-render components without remounting when possible.
Why content hashes in file names?
They enable immutable, long-lived caching; a changed file gets a new URL, unchanged files stay cached.

Tree shaking, code splitting, bundle optimisation

“What is tree shaking and what makes code tree-shakable? How does code splitting work? How do you analyse and reduce bundle size and improve caching?”

Say this first (30 seconds)

“Tree shaking removes unused exports from the final bundle. It relies on ES modules having static import and export statements, so the bundler can analyse which exports are used without running code; CommonJS is dynamic and cannot be shaken reliably. Code must also be side-effect free, which packages declare with sideEffects: false. Code splitting breaks the bundle into chunks loaded on demand with dynamic import(), typically per route and for heavy widgets, so users download only what they need. To optimise I analyse the bundle with a visualiser, remove or replace heavy dependencies, split vendor and shared code sensibly, compress with Brotli, use content hashes for long-term caching, and set performance budgets in CI.”

Details interviewers probe

  • Tree shaking mechanics: the bundler marks exports as used or unused across the module graph (“mark and sweep”); the minifier drops the unused code. It needs ESM; libraries must publish ESM builds (module/exports fields) and declare sideEffects accurately, otherwise the bundler must keep modules that might have side effects (CSS imports need to be listed as side effects).
  • Barrel files: index.ts re-exporting everything can pull in whole directories during development and defeat shaking in some setups; import from specific paths or enable library-specific optimisations (optimizePackageImports).
  • Splitting strategies: entry-based (multiple entries), dynamic import (on demand), and vendor/common chunking by splitChunks (webpack) or manualChunks (Rollup/Vite). Group stable libraries (React) into a vendor chunk that changes rarely and caches well; avoid over-splitting.
  • Route-based splitting in frameworks: Next.js splits per route automatically; React Router uses lazy; Angular uses lazy-loaded routes. Component-level splitting uses React.lazy/next/dynamic with Suspense (R9).
  • Analysis: rollup-plugin-visualizer, webpack-bundle-analyzer, source-map-explorer, Next.js bundle analyser, Bundlephobia for packages. Look for duplicate packages (two versions of lodash), moment locales, large JSON, polyfills, and unexpected libraries pulled into the main chunk.
  • Reduction tactics: replace heavy libraries (moment → date-fns/Intl, lodash → native or per-function imports), remove unused dependencies, lazy-load below-the-fold or admin features, use smaller UI libraries or headless, avoid shipping both ESM and CJS, set precise browserslist to avoid unnecessary transpilation and polyfills, compress images (separate from JS), and move work to the server (Server Components).
  • Compression: Brotli (better than gzip, precompressed at build or by CDN) for text assets; measure transfer size and parse/execute time, because bytes are only part of the cost on slow CPUs.
  • Long-term caching: content hashes in filenames, Cache-Control: public, max-age=31536000, immutable, stable chunk ids (so unchanged chunks keep their hash), a small runtime or manifest that changes often, and HTML with short or no caching referencing the hashed assets.
  • Preloading and prefetching: <link rel="modulepreload"> for critical chunks, prefetch for likely next routes (framework Link does this), and magic comments (/* webpackPrefetch: true */) verify syntax per bundler.
  • Source maps: separate files generated in production, not served publicly, uploaded to error tracking.
  • Performance budgets: set limits per route (for example 170 KB gzip of JavaScript for key pages) enforced by size-limit or bundle analysers in CI; fail PRs that exceed.
  • Runtime cost beyond bytes: parse and compile time, hydration, and main-thread execution; a 300 KB bundle can cost seconds on low-end phones; measure with CPU throttling.
  • Library authors: publish ESM with exports, mark sideEffects, avoid top-level side effects, ship types separately, and keep dependencies minimal (T9).

Traps

  • Expecting tree shaking to work on CommonJS packages or modules with side effects.
  • Splitting into too many chunks and creating request waterfalls.
  • Importing a whole utility library for one function.
  • Changing vendor chunk contents on every release, destroying caching.
  • Measuring only gzip size and ignoring execution time on slow devices.

Likely follow-ups

Why does import _ from 'lodash' bloat the bundle?
The CommonJS build is not tree-shakable, so the whole library is included; use lodash-es or per-function imports.
How do you find the biggest contributors?
Generate a bundle visualisation of the production build, sort by size, and check duplicates and unintended inclusions.
What does sideEffects: false promise?
That importing the package’s modules does nothing except define exports, so unused modules can be dropped safely.
How do you decide what to lazy-load?
Not needed for first render or interaction: routes, modals, admin tools, editors, charts; measure impact on LCP and INP.
B7Added

Transpilation: Babel, SWC, polyfills, PostCSS

“What is the difference between transpiling and polyfilling? What do Babel and SWC do? How does browserslist influence the output? What is PostCSS?”

Say this first (30 seconds)

“Transpiling rewrites newer syntax into older syntax that target browsers understand, such as arrow functions or optional chaining; polyfilling adds missing runtime APIs, such as Promise.allSettled or Array.prototype.at, by implementing them in JavaScript. Syntax cannot be polyfilled and APIs cannot be transpiled, so both are needed depending on targets. Babel is the established JavaScript compiler with a huge plugin ecosystem; SWC is a much faster Rust equivalent used by Next.js; esbuild also transforms but with fewer features. browserslist declares the target browsers and drives which transforms and polyfills are applied. PostCSS does the same for CSS: it parses CSS into an AST that plugins transform, for example Autoprefixer for vendor prefixes. The goal is to ship the least code that supports the real audience.”

Details interviewers probe

  • Babel: parses code to an AST, plugins transform it, a generator emits code. @babel/preset-env picks transforms by target; @babel/preset-react, @babel/preset-typescript (strips types, does not check). Plugins for decorators, class properties, and custom macros. Slower than SWC but the most extensible; used by many Jest, Storybook and legacy setups.
  • SWC: Rust-based, compatible with many Babel transforms, built into Next.js and used in Vite plugins (plugin-react-swc), Jest transforms and Rspack. Also minifies. Custom plugins are written in Rust or WASM, so extension is harder than Babel.
  • Polyfill strategies: core-js with useBuiltIns: 'usage' (Babel includes only what the code uses and targets need) or 'entry'; a polyfill service served by user agent (polyfill.io-style; note the 2024 supply-chain compromise of a popular domain, so self-host or use trusted providers verify); feature-detect and load conditionally. Avoid polyfills for features your support matrix already covers.
  • Runtime helpers and size: repeated helper code per file inflates bundles; @babel/plugin-transform-runtime and importHelpers (tsc, with tslib) share helpers. Loose mode trades spec compliance for size.
  • JSX transform: the automatic runtime (react/jsx-runtime) removes the need to import React; compile-time transforms replace createElement calls.
  • TypeScript compilation: Babel/SWC/esbuild strip types per file (so isolatedModules constraints apply); enums and const enum need care; decorators and metadata need specific plugins (T8, T9).
  • Targets and modern output: modern evergreen targets (ES2020+) avoid most transforms; the old “modern/legacy double bundle” (module/nomodule) is rarely worth it now. Libraries should ship modern ESM and let applications transpile for their own targets.
  • PostCSS and CSS tooling: PostCSS parses CSS into an AST and runs plugins; Autoprefixer reads browserslist; postcss-preset-env converts modern CSS features; cssnano minifies; Sass/Less preprocessors compile before PostCSS; Lightning CSS is a faster alternative integrated in Vite and Parcel. CSS Modules and Tailwind run as PostCSS plugins.
  • Source maps: each transform chain must preserve mappings so errors and debugging point to original files (B4).
  • Sass (SCSS) in brief: variables, nesting, mixins and modules compile to CSS; modern CSS has custom properties and nesting, so reassess whether you need it (CSS Part 5).
  • Verification: test the production bundle in the lowest supported browser; check that no untranspiled syntax slips from node_modules (some packages ship ES2020+ and must be included in the transform).
  • Compiler plugins in React: the React Compiler is a Babel/SWC-integrated transform (R5).
  • Build-time constants: process.env.NODE_ENV replacement enables dead-code elimination of development-only branches in libraries.

Traps

  • Believing polyfills can add new syntax such as optional chaining.
  • Transpiling to ES5 for everyone out of habit, inflating bundles and slowing parse.
  • Loading a polyfill from a third-party CDN without integrity or trust.
  • Forgetting that Babel and SWC strip TypeScript types without checking them.
  • Not transpiling a dependency that ships modern syntax to a target that cannot run it.

Likely follow-ups

Transpiler versus polyfill?
A transpiler rewrites syntax at build time; a polyfill implements missing APIs at run time. Different problems, often both needed.
How does browserslist reach Autoprefixer and Babel?
Both read the same configuration (package.json or .browserslistrc) and compute the needed transforms and prefixes.
Why move from Babel to SWC?
Much faster builds and tests with a similar feature set; give up some plugin extensibility.
How do you reduce polyfill size?
Tighten targets, use usage-based inclusion, and rely on native features, loading extra polyfills only when detection fails.

Package managers, semver, monorepos

“Compare npm, Yarn and pnpm. How does semantic versioning work? What are peer dependencies and lockfiles? How do you manage a monorepo with workspaces, Turborepo or Nx? How do you publish packages?”

Say this first (30 seconds)

“A package manager installs dependencies from a registry into node_modules and records exact versions in a lockfile so installs are reproducible. npm is the default, Yarn added workspaces and Plug’n’Play, and pnpm uses a content-addressable store with symlinks, which saves disk space, installs faster and prevents accessing undeclared dependencies. Semantic versioning, major.minor.patch, signals compatibility: patch for fixes, minor for backward-compatible features, major for breaking changes; ranges like ^1.2.3 allow minor and patch updates. In a monorepo, workspaces link local packages, and tools like Turborepo and Nx cache and orchestrate tasks across them using the dependency graph. For publishing I use Changesets or semantic-release to version and generate changelogs, with provenance and lockfile discipline for supply-chain safety.”

Details interviewers probe

  • npm, Yarn, pnpm, Bun: npm (bundled with Node; workspaces since v7), Yarn Classic (v1) and Yarn Berry (v2+ with Plug’n’Play, zero-installs, constraints), pnpm (strict, fast, disk-efficient, great for monorepos), Bun (runtime and package manager, very fast). Choose by team convention and monorepo needs; do not mix managers in one repo.
  • Dependency types: dependencies (needed at runtime), devDependencies (build and test), peerDependencies (the host app must provide, for plugins and UI libs such as React), optionalDependencies. For apps the split matters less; for libraries it defines what consumers install.
  • Semver in practice: ^ and ~ ranges allow automatic updates, so the lockfile is what pins reality. Pre-release tags (1.0.0-beta.2). 0.x versions treat minor bumps as breaking by convention. Breaking changes should be signalled by a major version and migration notes; types are part of the API (T13).
  • Lockfile discipline: commit it; install with npm ci/--frozen-lockfile in CI; review lockfile diffs in PRs for suspicious changes; run npm audit and automated update bots (Dependabot, Renovate); use overrides/resolutions for forced versions of transitive dependencies.
  • Peer dependency conflicts: “ERESOLVE” errors arise when versions do not satisfy each other; fix by aligning versions, using overrides, or upgrading; avoid blanket --force/--legacy-peer-deps without understanding.
  • Scripts and lifecycle: scripts in package.json, npx/pnpm dlx for one-off tools, pre/post hooks, postinstall scripts (a supply-chain risk; consider --ignore-scripts with allowlists).
  • Monorepo benefits: atomic cross-package changes, shared tooling and configuration, easier refactoring, single dependency policy, simpler code sharing. Costs: tooling complexity, longer CI without caching, access control, large repo size. Alternatives: polyrepo with published packages (clear ownership, version overhead).
  • Workspaces: workspaces field links packages; internal dependencies referenced with workspace:*; hoisting rules; TypeScript project references (T9) and path aliases need to match.
  • Turborepo and Nx: compute a task graph from package dependencies; cache outputs keyed by hash of inputs (source, env, dependencies); run in parallel; “affected” commands for CI; remote caching shares results across developers and CI. Nx adds generators, module boundary lint rules, and plugin-based project detection.
  • Publishing libraries: build ESM (and CJS if needed) with exports and types; files allowlist; sideEffects; peer dependencies for frameworks; verify with publint and arethetypeswrong; version with Changesets; publish with CI using provenance (--provenance) and trusted publishing; private registries (Verdaccio, GitHub Packages, Artifactory) for internal packages.
  • Security: typosquatting, dependency confusion (scope internal packages and configure registries), malicious maintainers and compromised accounts, install scripts; mitigations: lockfiles, integrity checks, 2FA, scoped registries, review of new dependencies, SBOMs (J29).
  • Node version management: .nvmrc/engines, Volta or fnm, Corepack to pin the package manager version; same Node version locally, in CI and in production.
  • Dedupe and size: npm dedupe, check duplicates in the bundle, remove unused packages (Knip), prefer fewer dependencies.

Traps

  • Not committing the lockfile, or running npm install instead of npm ci in CI.
  • Forcing past peer-dependency errors without understanding the conflict.
  • Putting build tools in dependencies of a library (consumers install them) or React there instead of peerDependencies.
  • Assuming minor and patch updates never break things.
  • Choosing a monorepo without caching, so CI time grows with every package.

Likely follow-ups

What are phantom dependencies?
Packages your code imports without declaring them, working only because a flat node_modules hoisted them; pnpm’s strict layout exposes these bugs.
What does ^1.2.3 mean?
Any version at least 1.2.3 and below 2.0.0 (minor and patch updates).
Monorepo or polyrepo?
Monorepo for tightly related packages with shared tooling and frequent cross-cutting changes; polyrepo when teams and release cycles are independent.
How does remote caching speed up CI?
Task outputs are keyed by input hash and stored remotely, so an unchanged package’s build or test is restored instead of re-run.

Code quality tooling and developer environment

“Which tools do you use to keep a codebase consistent and healthy? ESLint, Prettier, Husky, lint-staged, commit conventions. How do you set up environment variables, local development and a good developer experience?”

Say this first (30 seconds)

“I automate consistency so reviews focus on design. Prettier formats code with no debate; ESLint finds bugs and enforces rules, with plugins for React hooks, accessibility, imports and type-aware TypeScript checks; Stylelint does the same for CSS. Git hooks via Husky and lint-staged run fast checks on staged files, while CI runs the full set as the authoritative gate. Conventional Commits give structured messages that drive changelogs and releases. For developer experience, a single command sets up and starts the project, environment variables follow a typed, documented schema with .env.example, Node and package manager versions are pinned, and fast feedback comes from HMR and tests that run in seconds. The aim is that a new developer is productive on day one.”

Details interviewers probe

  • ESLint: pluggable linter with rules for errors and style; modern “flat config” (eslint.config.js); plugins: react, react-hooks (rules of hooks and exhaustive-deps), jsx-a11y, @typescript-eslint (type-aware: no-floating-promises, no-misused-promises), import, unicorn, testing-library, framework configs (next/core-web-vitals). Use shared configs across repos; treat warnings as errors in CI.
  • Prettier: opinionated formatter; stops style debates; integrate in the editor and CI (prettier --check); avoid ESLint stylistic rules that conflict (eslint-config-prettier). Biome and oxlint are faster Rust alternatives that combine formatting and linting verify feature parity.
  • Stylelint and other linters: Stylelint for CSS/SCSS (property order, no duplicate selectors, token usage), markdownlint, actionlint for GitHub Actions, commitlint for messages, secret scanners (gitleaks) in pre-commit and CI.
  • Git hooks: Husky manages hooks in the repo; lint-staged runs commands only on staged files; keep them under a few seconds; run type checks and tests in pre-push or CI, not pre-commit.
  • Conventional Commits: feat:, fix:, chore:, BREAKING CHANGE: in messages; enable automated version bumps and changelogs (semantic-release, Changesets via PR files); also improves history readability. Squash merges with a good title are an alternative.
  • EditorConfig and editor setup: .editorconfig for indentation and line endings; recommended extensions and settings committed in .vscode; format on save.
  • Static analysis beyond lint: TypeScript strict mode, dead code and unused dependency detection (Knip), circular dependency checks (madge, dependency-cruiser), architectural boundary rules (ESLint boundaries, Nx), bundle size limits, SonarQube for code smells and duplication, accessibility linting.
  • Environment variables: configuration separate from code (twelve-factor); .env files loaded by tools (Vite, Next.js, dotenv); never commit secrets; provide .env.example; validate with a schema; different values per environment; understand build-time inlining versus runtime reads.
  • Developer experience (DX): fast install and start, HMR, helpful error overlays, consistent scripts (dev, build, test, lint), a README with prerequisites and troubleshooting, dev containers or Docker Compose for dependencies (databases), mock APIs, seed data, and shared VS Code tasks. Track DX with surveys and CI/install times.
  • Local HTTPS and proxies: dev proxy for API calls to avoid CORS (server.proxy), local certificates (mkcert) for features needing secure contexts (service workers, clipboard, geolocation).
  • Path aliases: @/components configured in tsconfig and the bundler/test runner consistently (T9).
  • Documentation and templates: project templates or generators (plop, Nx generators, create-* scripts), PR and issue templates, CODEOWNERS, contribution guide.
  • Standardising across teams: shared config packages (@company/eslint-config, tsconfig bases), a platform or tooling team, and versioned updates via Renovate.

Traps

  • Slow pre-commit hooks that run the entire test suite, so people bypass them.
  • Relying only on hooks; they can be skipped, so CI must enforce.
  • Conflicting ESLint style rules and Prettier causing endless auto-fix loops.
  • Reading process.env everywhere without validation, discovering missing variables in production.
  • Putting secrets in client-exposed variables or committing .env files.

Likely follow-ups

ESLint versus Prettier?
Prettier formats layout; ESLint analyses code for bugs and patterns. Use both, with the Prettier config disabling conflicting ESLint rules.
How do you introduce lint rules to a legacy codebase?
Start with warnings, auto-fix what is safe, enforce on changed files (lint-staged or diff-only), and ratchet to errors over time.
Where do you keep secrets for local development?
Git-ignored .env.local files, or a secrets manager with a developer CLI; never in the repository.
How do you onboard a new developer quickly?
One-command setup, pinned toolchain versions, seeded mocks, clear README, and a first-day “hello world” PR with CI feedback.

The production build pipeline

“Walk through how you take a frontend app from source to production. How do you handle environment config, caching, source maps, build speed and reproducible builds? How do you serve and invalidate static assets?”

Say this first (30 seconds)

“The pipeline installs dependencies from the lockfile, runs static checks and tests, builds once into immutable artifacts, and promotes the same artifact through environments instead of rebuilding for each. The build outputs content-hashed assets served from a CDN with long immutable caching, while the HTML entry point is cached briefly or revalidated so new releases are picked up. Source maps are generated but uploaded to the error tracker rather than served publicly. Environment-specific values are injected at deploy or run time rather than baked into the artifact, or built per environment if they must be inlined. I speed up builds with dependency and build caches, incremental builds and affected-only tasks, and I keep builds reproducible with pinned Node and package versions.”

Details interviewers probe

  • Build once, deploy many: rebuilding per environment risks differences (different dependency resolution, timestamps). Produce one immutable artifact (a folder, tarball or container image) tagged with the commit SHA, and promote it dev → staging → production, injecting configuration at deploy time.
  • Environment configuration: server-side variables read at run time; for static SPAs, inject a config.js or fetch /config.json at startup so the same bundle serves all environments; VITE_*/NEXT_PUBLIC_* values are inlined at build time and require a rebuild per environment. Feature flags decouple release from deploy (DevOps guide).
  • Reproducible builds: pinned Node and package manager versions (.nvmrc, Corepack), lockfile installs, deterministic build tools, no network fetches at build time beyond the registry, container builds with fixed base images (by digest), and build provenance.
  • Build caching and speed: cache the package manager store and build caches (.next/cache, Vite/webpack persistent cache), use Turborepo/Nx remote caching, incremental TypeScript (tsc -b), parallel jobs (lint, test, typecheck) and sharded tests, and faster tools (SWC, esbuild, Rspack). Measure and track build time as a team metric.
  • Asset hashing and CDN: content hashes ([contenthash]) in file names; CDN in front with Brotli; versioned asset paths; separate asset domain optional (cookieless; but adds a connection); invalidate only HTML or the manifest on release; purge mistakes with cache-busting rather than relying on invalidation.
  • Deployment skew and chunk errors: when a new release deletes old chunks, users with an open tab fail to load lazy routes (“ChunkLoadError”, “Failed to fetch dynamically imported module”). Mitigate by retaining previous assets for days, retry then force a reload on chunk errors, versioned deployments (skew protection), and service worker update strategies (performance guide).
  • Source maps: generate in the build (hidden-source-map), upload to Sentry/Datadog with the release id, and do not publish them to the public CDN; restrict access if you must host them.
  • Quality gates in the pipeline: type check, lint, unit and integration tests, bundle size budgets, accessibility checks, Lighthouse CI for key pages, dependency audit and licence checks, secret scanning, container scanning if applicable.
  • Environments and previews: ephemeral preview deployments per pull request with unique URLs for review and e2e; staging mirrors production; production-like data safe for testing; protect with auth where needed.
  • Release strategy: progressive delivery with canary or blue-green, feature flags for dark launches, automatic rollback on error-rate or latency regression, and fast manual rollback (redeploy the previous artifact) (DevOps guide).
  • Static hosting setups: S3 + CloudFront, Netlify, Vercel, Cloudflare Pages, nginx in a container. Configure SPA fallback to index.html, security headers, compression, HTTP/2 or 3, and correct MIME types.
  • Monorepo builds: build only affected projects; share packages built once; consistent versions; publish internal packages before apps.
  • Observability of releases: tag errors and RUM with the release id; dashboards compare versions; alert on regressions after deploy; keep a changelog and release notes.
  • Failure handling: pipeline retries for flaky infrastructure only, clear logs, artifacts and traces from failed e2e, notifications, and ownership of the pipeline.

Traps

  • Rebuilding for each environment and shipping something different from what was tested.
  • Caching index.html for a year, so users never receive new releases.
  • Deleting old assets at deploy time and breaking users with open tabs.
  • Publishing source maps publicly with sensitive comments or logic.
  • Letting build time grow unchecked until developers avoid running the pipeline.

Likely follow-ups

How do you handle different API URLs per environment in a static SPA?
Runtime configuration loaded at startup (a config file or endpoint) so one artifact works everywhere, or a per-environment build if values must be inlined.
How do you invalidate a CDN safely on release?
Hashed assets never need invalidation; only HTML or a manifest is revalidated or purged.
What causes ChunkLoadError and how do you fix it?
Old HTML referencing deleted chunks; keep previous assets, handle the error by reloading, and use skew protection.
How do you speed up a 20-minute pipeline?
Profile stages, cache dependencies and builds, parallelise and shard tests, run only affected packages, and move slow tests to later stages.

How to answer browser and tooling questions at L4

  • For “what happens when…” questions, walk the pipeline in order and say where each optimisation applies (DNS, connection, parse, render, hydrate).
