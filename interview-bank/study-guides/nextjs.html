Rendering strategies: CSR, SSR, SSG, ISR, PPR

“Explain client-side rendering, server-side rendering, static generation and incremental static regeneration. How do you choose a rendering strategy per page? What is partial prerendering?”

Say this first (30 seconds)

“The strategies differ in when and where HTML is produced. Client-side rendering ships a nearly empty shell and builds the page in the browser: simple and cheap to host, but slow first content and weak for SEO. Server-side rendering generates HTML on every request, so it is always fresh and personalised, at the cost of server work and a slower time to first byte. Static site generation builds HTML once at build time and serves it from a CDN, which is fastest, but content is only as fresh as the last build. Incremental static regeneration keeps static speed and refreshes pages in the background after a time interval or on demand. Partial prerendering serves a static shell instantly and streams in the dynamic parts. I choose per page from how often the content changes, whether it is personalised, and SEO needs.”

Details interviewers probe

  • CSR: the browser downloads JavaScript, runs it, fetches data, then renders. Pros: simple deployment (static files), rich interactivity, cheap. Cons: blank screen until JS runs, poor LCP, SEO and social previews depend on crawler JavaScript support, performance varies with device. Good for authenticated dashboards and tools where SEO is irrelevant.
  • SSR: the server runs the React tree per request and returns HTML; the browser shows it quickly, then hydrates (attaches event handlers). Pros: good first paint and SEO, access to request data (cookies, headers). Cons: TTFB depends on server and data latency, scaling cost, hydration cost, an “uncanny valley” where the page looks ready but is not interactive.
  • SSG: pages are built at build time (generateStaticParams for dynamic routes) and served from a CDN. Pros: best TTFB, resilience, low cost. Cons: build time grows with page count; content updates need a rebuild; cannot personalise per request (use client fetching for user parts).
  • ISR: serves the cached static page and, after the revalidate window, regenerates it in the background (stale-while-revalidate); on-demand revalidation (revalidatePath, revalidateTag) updates exactly when content changes (CMS webhook). Pages not pre-built are generated on first request and cached.
  • Streaming SSR: the server sends HTML in chunks as Suspense boundaries resolve, so slow data does not block the whole page (N8).
  • Partial prerendering (PPR) and cache components: a route has a static shell prerendered at build and dynamic parts (inside Suspense) rendered per request and streamed; one HTTP response, one CDN-friendly shell. It evolved from an experimental flag into the Cache Components model in newer versions verify the status in your Next.js version.
  • Metrics lens: TTFB (server and network), FCP and LCP (what is shown early), INP (interactivity after hydration), CLS (stability). SSG and PPR favour TTFB and LCP; CSR hurts LCP; SSR depends on data latency.
  • Hydration costs: all client components hydrate; large trees delay interactivity. Server Components reduce what hydrates. Islands architectures (Astro) and resumability (Qwik) are alternatives that avoid hydrating everything.
  • Example choices: marketing and docs: SSG/ISR. Blog or catalogue with frequent edits: ISR with on-demand revalidation. Product page: static shell, cached product data, dynamic price and stock via PPR or client fetching. Search results: SSR or client fetching. Account dashboard: dynamic server rendering or CSR. News ticker: client polling or streaming.
  • In Next.js a route is static by default if it uses no dynamic APIs or uncached data; using cookies(), headers(), searchParams or connection() makes it dynamic (N4). Pages Router used explicit functions (getStaticProps, getServerSideProps).
  • Edge rendering: rendering close to users on edge runtimes lowers latency but limits Node APIs and database proximity; data location often dominates (N12).
  • Hybrid personalisation: render shared content statically and personalise with client fetching, edge middleware rewrites (A/B tests), or dynamic holes.

Traps

  • “SSR is always better for SEO and performance.” It adds server latency; static is faster whenever content allows it.
  • Confusing hydration with rendering: the server produces the HTML, the client hydrates to make it interactive.
  • Saying ISR re-renders on every request. It serves the cache and regenerates at most once per window in the background.
  • Choosing one mode for the entire site instead of per route.
  • Forgetting that personalised data in a static page leaks to everyone or forces dynamic rendering.

Likely follow-ups

What does stale-while-revalidate mean in ISR?
The first request after expiry still gets the old page instantly, and a background render produces the fresh page for later requests.
How do you show a logged-in user’s name on a static page?
Keep the page static and fetch user data on the client, or use PPR with a dynamic hole inside Suspense.
How does SEO differ between CSR and SSR?
Crawlers can run JavaScript, but later and less reliably; server-rendered HTML is indexed immediately and gives correct social previews.
What is the downside of SSG for a site with a million pages?
Very long builds; use on-demand ISR (generate on first request) and pre-build only the most important pages.

The App Router and file conventions

“How does the App Router work? Explain layouts, pages, loading and error files, route groups, dynamic routes, parallel and intercepting routes. How does it differ from the Pages Router?”

Say this first (30 seconds)

“The App Router, in the app directory, maps folders to URL segments and uses special files in each folder: page.tsx makes the route public, layout.tsx wraps the segment and its children and persists across navigation, loading.tsx is an automatic Suspense fallback, error.tsx is an error boundary, not-found.tsx handles 404s, and route.ts defines an API endpoint. Components are Server Components by default, and layouts nest, so shared UI and data are not re-rendered when moving between child routes. Compared with the Pages Router, which uses pages/ with getServerSideProps and getStaticProps, the App Router gives nested layouts, streaming, Server Components, and colocated data fetching.”

Details interviewers probe

  • Colocation: only page and route files are public; other files in the folder (components, tests, styles) are safe. Prefix a folder with _ to make intent explicit.
  • Layouts: defined by layout.tsx, receive children, preserve state and do not re-render when navigating between children (good for navigation shells). The root layout is required and renders <html> and <body>. Layouts cannot read searchParams or the pathname (they do not re-render on navigation); use a client component with hooks for the active link. template.tsx is like a layout that remounts on every navigation (animations, per-page effects).
  • loading.tsx and error.tsx: shorthand for wrapping the segment in Suspense and an error boundary. error.tsx must be a client component, receives error and reset; global-error.tsx catches root layout errors. not-found.tsx renders with notFound().
  • Dynamic routes: [id], catch-all [...slug], optional catch-all [[...slug]]. In recent versions params and searchParams are promises that you await verify (Next 15+). Use generateStaticParams to pre-render known values.
  • Route groups (name): organise routes or apply different layouts to sibling sections without affecting the URL (marketing versus app shell).
  • Parallel routes (@slot): render several pages in the same layout simultaneously (dashboards with independent loading and error states); default.tsx is the fallback for unmatched slots. Intercepting routes (.), (..), (...): show another route in the current context (a photo as a modal) while the URL is shareable and a hard refresh shows the full page.
  • Route handlers (route.ts): export HTTP method functions using the Web Request/Response APIs (N6).
  • Special metadata files: favicon, opengraph-image, sitemap.ts, robots.ts, manifest (N10).
  • Pages Router comparison: pages/ directory, one layout via _app, data via getStaticProps, getServerSideProps, getStaticPaths, getInitialProps; all components are client components that hydrate. It remains supported; both routers can coexist and migration is incremental (route by route). The App Router adds nested layouts, streaming, Server Components, Server Actions and simpler colocated data fetching, with a steeper learning curve and more caching to understand.
  • Navigation: <Link> for client-side transitions with prefetching, useRouter (client) and redirect() (server) (N7).
  • Project organisation: src/ optional, feature folders colocated inside route segments or in a shared features/ folder; keep route files thin and push logic into modules.
  • Static assets: public/ served from root; imported images get automatic dimensions and optimisation.
  • Turbopack and build: the bundler is Turbopack (default in recent versions) or webpack verify; it only affects tooling, not the file conventions.

Traps

  • Expecting a layout to re-render (or read searchParams) when navigating between child routes. It does not.
  • Adding 'use client' to a layout to use one hook, turning the subtree into client code. Extract a small client component instead.
  • Forgetting that error.tsx does not catch errors in the layout of the same segment (use the parent’s or global-error).
  • Putting a route.ts and a page.tsx in the same segment; they conflict.
  • Assuming files like utils.ts next to a page are routed. Only special files are.

Likely follow-ups

Layout versus template?
A layout persists and keeps state across navigations; a template creates a new instance each time, resetting state and re-running effects.
How would you build a modal that has its own URL?
An intercepting route plus a parallel @modal slot: soft navigation shows the modal over the page, direct loads show the full page.
How do you migrate from Pages to App Router?
Incrementally: move routes one by one into app/, replace data functions with server components, keep shared code in components, and run both routers meanwhile.
Where do you fetch data for a layout?
In the layout itself if it is shared (it is deduped), or in nested pages; remember layouts do not re-run when children change.

Server and Client Components in Next.js

“When do you use a Server Component and when a Client Component in Next.js? How do you compose them? How do you use context providers and third-party libraries that need the browser?”

Say this first (30 seconds)

“In the App Router everything is a Server Component unless a file starts with 'use client'. I keep as much as possible on the server: data fetching, secrets, heavy libraries and static markup, because none of that ships to the browser. I use client components for interactivity: state, effects, event handlers, browser APIs and context consumers, and I push the 'use client' boundary down to small leaves, such as a button or a form, instead of marking a whole page. A client component cannot import a server component, but it can receive one as children, so a provider component can wrap server-rendered content. Props crossing the boundary must be serialisable, and secrets must stay in server-only modules.”

Details interviewers probe

  • Directive scope: 'use client' marks a module boundary: that file and everything it imports are client code. You do not need it in files imported by an already client file. 'use server' marks Server Actions, not server components.
  • Server component capabilities and limits: can be async, read environment secrets, query databases, call internal services, and use fs. Cannot use state, effects, browser APIs or event handlers, nor consume context (useContext only in client components).
  • Importing rules: a server component can import client components. A client component cannot import a server component, but may render one passed as children or a prop. This allows “donut” layouts.
  • Context and global state: providers must be client components; create a Providers client file and use it in the root layout. Avoid per-request data in module-level variables on the server (shared across requests). Theme, i18n, query client and auth state typically live here.
  • Third-party components: libraries that use hooks or browser APIs may lack a 'use client' directive; re-export them from your own client file. Prefer libraries that ship server-compatible builds.
  • Server-only code: import 'server-only' in modules that must never reach the client (database access, secrets). Build fails if a client component imports it. 'client-only' is the opposite. Environment variables without the NEXT_PUBLIC_ prefix are not exposed to the browser.
  • Data passing: pass the minimum data. Do not send entire database rows with sensitive fields; map to a DTO. Tainting APIs exist to mark objects that must not cross verify (experimental).
  • Sharing code: pure utilities can be shared by both sides; code touching window, DOM or Node-only APIs must be isolated.
  • Dynamic imports: next/dynamic or React.lazy for heavy client components; ssr: false is only allowed in client components to render something browser-only verify (restricted in server components since 15).
  • Performance effect: fewer client components mean less JavaScript to download and hydrate, improving INP and LCP on low-end devices. Track the “First Load JS” in the build output.
  • Common refactors: split a page into a server shell that fetches data and small client children for interaction; move data fetching from useEffect in client components to the server component and pass as props; replace global client state for server data with server components plus revalidation.
  • Testing: test client components with Testing Library; test server logic as plain functions; use end-to-end tests for pages (R12).
  • Streaming boundaries: wrap slow server components in Suspense to stream them (N8).

Traps

  • Putting 'use client' at the top of every file “to make errors go away”, losing the benefits of server rendering.
  • Importing a server-only module into a client component and leaking secrets or breaking the build.
  • Passing a function or class instance as a prop from server to client.
  • Reading window or localStorage during render in a component that also renders on the server.
  • Creating shared mutable state in a module on the server and leaking data between users.

Likely follow-ups

Does a client component render on the server?
Yes: client components are still pre-rendered to HTML on the server and then hydrated. The directive only means their code is also shipped to the browser.
How do you use a context provider in the root layout?
Create a client Providers component and render it around children; children remain server-rendered.
Where should data fetching live?
In server components close to where the data is used, with requests started in parallel; client fetching only for interactive or user-driven data.
How do you prevent leaking secrets?
server-only imports, no NEXT_PUBLIC_ prefix for secrets, DTOs for props, and review what crosses the boundary.

Data fetching, static versus dynamic rendering

“How do you fetch data in the App Router? How does Next.js decide whether a route is static or dynamic? What are generateStaticParams and the segment config options? How do you avoid waterfalls?”

Say this first (30 seconds)

“In the App Router I fetch data directly in async Server Components with fetch, an ORM or any server library, so no getServerSideProps is needed. Next.js decides at build time whether a route can be static: it is dynamic if it uses request-time APIs such as cookies(), headers() or searchParams, uses uncached data under the version’s default rules, or sets a dynamic segment option. Static routes are prerendered and cached; generateStaticParams lists the dynamic parameter values to prerender. To avoid request waterfalls, I start independent requests in parallel with Promise.all or separate components under Suspense, preload data, and dedupe repeated calls with React cache or Next’s request memoisation.”

Details interviewers probe

  • Fetching in server components: async function Page() { const data = await fetch(...).then(r => r.json()); … }. You can also query databases directly, call internal services and read files. Colocate the fetch with the component that needs the data; Next.js dedupes identical fetch GETs within a render pass (request memoisation), and React cache() memoises non-fetch calls (ORM queries).
  • Fetch options: fetch(url, { next: { revalidate: 60, tags: ['posts'] } }), cache: 'force-cache' | 'no-store'. In Next.js 15 fetch requests and GET route handlers are not cached by default; in 14 they were verify the default for your version. Newer versions introduce a use cache directive for explicit caching (N5).
  • Dynamic APIs: reading cookies(), headers(), draftMode(), searchParams, or calling connection() opts the route (or the Suspense hole, with PPR) into request-time rendering. These APIs are async in recent versions verify (15+).
  • Static params: generateStaticParams returns the parameter sets to prerender (for example all product slugs or the top 1,000), and dynamicParams controls whether others are rendered on demand and cached. This is how SSG and ISR combine for large catalogues.
  • Revalidation: time-based (revalidate seconds), on-demand by path or tag (revalidatePath, revalidateTag) from Server Actions or route handlers (webhooks from a CMS).
  • Waterfalls: sequential awaits in the same component, or nested components that each fetch only after the parent finishes. Fix with Promise.all, hoisting fetches, preloading patterns (call the fetch early without awaiting), or splitting into sibling components under Suspense.
  • Client-side fetching still has a place: interactive search, polling, infinite scroll, optimistic updates, user-specific data after load; use TanStack Query or SWR in client components, optionally seeded with server data (hydration/initialData).
  • Error and loading states: loading.tsx, Suspense boundaries, error.tsx, and notFound() for missing data. Return meaningful status codes: a page that renders “not found” UI but responds 200 is a soft 404 (hurts SEO), so call notFound().
  • Data access layer: keep database and API calls in a server-only module with authorisation checks and DTO mapping, used by server components and actions (N11).
  • Search params and dynamic UI: reading searchParams in a page makes it dynamic; for client-side filtering use useSearchParams inside a Suspense boundary so the rest of the page can stay static.
  • Pages Router equivalents: getStaticProps (SSG, with revalidate for ISR), getServerSideProps (SSR), getStaticPaths (+fallback), client fetching. Mapping is conceptual, not one-to-one.
  • Build output: next build prints routes with symbols for static, SSG with params, dynamic and partially prerendered, and “First Load JS”. Read it to catch accidental dynamic routes.

Traps

  • Reading cookies() or searchParams in a shared layout and accidentally making the whole subtree dynamic.
  • Assuming fetch is cached by default without checking the Next.js version.
  • Awaiting several independent requests one after another.
  • Rendering a “not found” message with a 200 status.
  • Prerendering with generateStaticParams but forgetting what happens to unknown params.

Likely follow-ups

How do you statically render a page that also shows the user’s name?
Keep the page static and render the name in a client component or a dynamic Suspense hole; do not read cookies in the static shell.
What is request memoisation?
Identical fetch GET calls (same URL and options) during one server render pass are executed once, so components can fetch independently without prop drilling.
How do you pre-render a million product pages?
Pre-build the top ones with generateStaticParams, leave dynamicParams on so the rest generate on first request and are cached, and revalidate via tags.
How do you force a page to be dynamic?
Use a dynamic API, export const dynamic = 'force-dynamic', or uncached data per the version’s rules.

The caching layers

“Explain Next.js caching. What are request memoisation, the Data Cache, the Full Route Cache and the Router Cache? How do you revalidate? What changed in newer versions?”

Say this first (30 seconds)

“Next.js caches at several layers, and the key skill is knowing which one is serving a stale result. On the server, request memoisation dedupes identical fetches within one render pass. The Data Cache stores fetch results persistently across requests and deployments. The Full Route Cache stores the rendered HTML and RSC payload of static routes. On the client, the Router Cache keeps visited and prefetched route segments in memory for instant navigation. I control freshness with time-based revalidation, on-demand revalidatePath and revalidateTag, and opting out with dynamic rendering or no-store. Defaults changed in version 15, where fetch and route handlers are no longer cached by default, and newer versions add an explicit use cache directive, so I always verify the behaviour for the version in use.”

Details interviewers probe

  • Request memoisation: automatic for fetch GET with identical URL and options during a single server render. Scope is one request; it lets components fetch independently without lifting data. For ORM or other calls use React.cache().
  • Data Cache: server-side persistent cache for fetch responses (and unstable_cache/use cache results). Controlled by cache and next.revalidate options and tags. It persists across deployments unless purged; on self-hosting it needs a shared cache handler for multiple instances (N12).
  • Full Route Cache: rendered output (HTML and RSC payload) for static routes, generated at build or on revalidation. Dynamic routes bypass it. Invalidating the Data Cache invalidates the routes that depend on it.
  • Router Cache: client-side, per user session, in memory. Stores prefetched (<Link> in viewport) and visited segments. Defaults changed: in Next.js 15 page segments are no longer cached by default (staleTimes are 0), while layouts and shared segments can still be reused verify defaults per version. router.refresh() and Server Actions that revalidate clear it.
  • Time-based versus on-demand revalidation: time-based accepts bounded staleness with no integration; on-demand gives immediate freshness when content changes (CMS webhook calls a route handler that runs revalidateTag). Tags group data across routes (a product tag across list and detail pages).
  • Opting out: fetch(url, { cache: 'no-store' }), export const dynamic = 'force-dynamic', revalidate = 0, or using dynamic APIs. Route handlers and unstable_noStore() variants exist.
  • Version differences: 13 and 14 cached fetch and GET route handlers by default (confusing results); 15 changed the default to uncached and made caching opt-in; 16 emphasises explicit caching with use cache and cache components, cacheLife/cacheTag and updated revalidation helpers verify names and semantics. Interviewers like candidates who know that defaults moved.
  • use cache model: a directive on a function, component or file that caches its result keyed by arguments and closed-over values, with a lifetime profile; the cache boundary decides what becomes part of the static shell and what stays dynamic verify.
  • CDN and HTTP caching: beyond Next’s caches, Cache-Control headers control CDN and browser caching of HTML, API responses and assets; static assets under _next/static are immutable with hashed names. Understand that a CDN can hold a stale page after you revalidate unless the platform purges it.
  • Personalisation risk: never cache user-specific responses in shared caches; do not read cookies in a cached function, or the result may be shared incorrectly (the framework guards against this by requiring dynamic APIs outside cache scopes).
  • Practical approach: choose a freshness requirement per data type (static content: long or on-demand; prices: short; account data: no cache), tag it, and revalidate on write operations from your own Server Actions.
  • Observability: response headers (x-nextjs-cache: HIT, MISS, STALE on supported setups), logging of fetch cache status in development, and tests that mutate then read.

Traps

  • Describing caching without noting it differs by Next.js version.
  • Calling revalidateTag and expecting an already-open browser tab to update; the Router Cache and open pages need refresh or navigation.
  • Mixing user-specific data into a cached fetch.
  • Believing the Data Cache is cleared on every deploy. It persists unless configured otherwise.
  • Testing in development and assuming production caching behaves the same (development disables most caching).

Likely follow-ups

How do you update a product page right after an admin edits it?
The admin Server Action writes to the database then calls revalidateTag('product-123') (or revalidatePath); the next request regenerates the page.
Why might a user see old data after navigating back?
The client Router Cache served a stored segment; call router.refresh() or revalidate in the action that mutated.
What is the difference between the Data Cache and the Full Route Cache?
The Data Cache stores individual fetch results; the Full Route Cache stores the final rendered route output built from them.
How do multiple instances share the cache when self-hosting?
A custom cache handler backed by Redis or object storage, otherwise each instance has its own cache and ISR becomes inconsistent.

Mutations: Server Actions and route handlers

“How do you handle mutations in the App Router? What are Server Actions and how do they differ from API routes? How do you secure them and update the UI afterwards?”

Say this first (30 seconds)

“A Server Action is an async function marked 'use server' that I can call from a form or a client component as if it were local; Next.js turns it into a POST endpoint, runs the code on the server, and can revalidate caches and redirect afterwards. It removes the boilerplate of writing an API route and fetch call for UI-driven mutations, and works with forms before JavaScript loads. Route handlers (route.ts) remain the right tool for public APIs, webhooks, third-party consumers and non-UI clients. Server Actions are public endpoints, so I validate input with a schema, authenticate and authorise inside every action, and rate-limit. After the mutation I call revalidatePath or revalidateTag so the UI shows fresh data, and use useActionState and useOptimistic for pending and optimistic states.”

Details interviewers probe

  • Defining actions: a function with 'use server' at the top of the function or a file of exports. Import them into client components, pass them as props, or use them as <form action>. Arguments and return values must be serialisable. Bound arguments created by closures are encrypted by Next.js, but still treat everything client-sent as untrusted.
  • Security model: an action is an HTTP endpoint with a generated id, reachable by anyone who can craft a POST. Always authenticate and authorise inside the action (do not rely on hiding the button or middleware alone), validate and sanitise all inputs (Zod), check resource ownership, rate-limit sensitive actions, and avoid returning sensitive data. Next.js adds built-in protections: POST-only, origin and host comparison against CSRF, unguessable ids for unused actions removed from the bundle verify details. Add idempotency keys for payments.
  • Forms and progressive enhancement: with <form action={serverAction}> the form works before hydration, then enhances with client-side pending state (R8). useActionState returns result state and a pending flag, useFormStatus exposes pending to nested buttons, useOptimistic shows instant feedback.
  • After mutation: call revalidatePath / revalidateTag to refresh data; redirect() to navigate (it throws, so call it outside try/catch); cookies().set() to store sessions. The response includes the updated RSC payload so the UI refreshes in one round trip.
  • Error handling: return structured results for expected failures (validation errors per field) instead of throwing; let unexpected errors reach error.tsx; map errors to user-friendly messages; log with context.
  • Concurrency: actions invoked from the client run sequentially per client, so they are not suited to high-parallelism data fetching; use them for mutations, not reads.
  • Route handlers: export GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS functions receiving a NextRequest (extends Request) and returning a Response/NextResponse. Use for webhooks (verify signatures with the raw body), OAuth callbacks, file upload endpoints, public JSON APIs, image or PDF generation. CORS headers must be added manually.
  • Upload handling: large files should go directly to object storage with presigned URLs rather than through the Next.js server, which has body size limits and cost.
  • Client-side mutations with libraries: TanStack Query mutations calling a route handler suit complex client flows, offline queues, and cache management when you want fine-grained control.
  • Testing: unit-test the action logic as functions with mocked dependencies; end-to-end tests for form flows; contract tests for route handlers.
  • Anti-patterns: fetching data through Server Actions (use server components), mutating without revalidating, putting business logic directly in the action instead of a service layer, trusting client-provided user ids.
  • Middleware versus action auth: middleware can pre-filter, but the action itself must check permissions because middleware may be bypassed or misconfigured (N11).

Traps

  • Treating Server Actions as private internal functions. They are public endpoints.
  • Forgetting to revalidate, then seeing stale UI after a successful write.
  • Wrapping redirect() in try/catch, which swallows its control-flow exception.
  • Using Server Actions as a general-purpose API for mobile apps or third parties.
  • Skipping server-side validation because the form has client validation.

Likely follow-ups

How do you prevent double submission?
Disable the button while pending, make the action idempotent with a key, and handle unique constraints on the server.
Server Action versus API route performance?
Similar, both are server round trips; actions save boilerplate and return fresh UI in one trip, but queue calls and are less suited to parallel work.
How do you handle file uploads?
Presigned URL to object storage from the client, then a small action or handler records the metadata; avoid streaming large files through the app server.
How do you protect an admin-only action?
Check the session and role inside the action, verify the target resource belongs to the user, and log the operation.

Routing, navigation and middleware

“How does client-side navigation work in Next.js? What does <Link> prefetch? What is middleware and what is it good and bad for? How do you handle redirects, rewrites and internationalised routing?”

Say this first (30 seconds)

“<Link> performs client-side navigation: it prefetches the route when the link enters the viewport (static parts in production), and navigation fetches only the RSC payload of the segments that changed, keeping shared layouts mounted. Programmatic navigation uses useRouter in client components and redirect() on the server. Middleware is code that runs before a request is completed, close to the user, and can rewrite, redirect, set headers or cookies. It is good for lightweight, cross-cutting concerns: locale detection, optimistic auth redirects, A/B bucketing, bot filtering and security headers. It is the wrong place for heavy computation, database calls or as the only authorisation check. In recent versions the file convention was renamed to a proxy file, so I check the current naming.”

Details interviewers probe

  • <Link>: renders an anchor (good for SEO and accessibility), prefetches in production when visible, supports replace, scroll, prefetch={false}. Prefetching dynamic routes loads only up to the nearest loading.tsx. Heavy prefetch on long lists can cost bandwidth; disable per link where needed.
  • Programmatic navigation: useRouter().push/replace/back/refresh/prefetch in client components; redirect()/permanentRedirect() in server components and actions; notFound(). router.refresh() refetches server data for the current route without losing client state.
  • Reading the URL: usePathname, useSearchParams (needs a Suspense boundary for static routes), useParams; server components receive params and searchParams props.
  • Config-based rules: redirects() (permanent or temporary), rewrites() (proxying to another origin or clean URLs), and headers() in next.config are evaluated before middleware and are cheaper for static rules.
  • Middleware: a middleware.ts at the project root exporting a function and a config.matcher. It runs for every matching request before the route; historically on the Edge runtime with limited Node APIs, with Node runtime support added later; recent versions rename it to proxy.ts verify naming and runtime for your version. Keep it fast: it sits on the critical path of every request.
  • Authentication with middleware: checking for the presence or validity of a session cookie to redirect anonymous users is a common optimisation. It is not a security boundary alone: a vulnerability in early 2025 allowed bypassing middleware with a crafted header, and middleware matchers can miss routes. Always re-check authorisation in the data layer and actions verify advisory and patched versions.
  • Internationalised routing: the App Router has no built-in i18n routing config (the Pages Router did). Common pattern: a [locale] dynamic segment, middleware that negotiates the locale from Accept-Language and cookies and redirects, a library such as next-intl, generateStaticParams for locales, hreflang alternates in metadata.
  • Feature flags and A/B tests: middleware assigns a bucket cookie and rewrites to a variant route; keep variants static where possible so the CDN can cache per variant.
  • Redirect semantics: 307/308 preserve the method, 301/302 may change it; use permanent redirects for SEO moves; avoid chains and loops; do not redirect on every request for something that could be a static config.
  • Route protection design: layered: middleware for fast redirect, server layout or page check for rendering, data access layer for the real authorisation, and UI hiding for UX only (N11).
  • Scroll and focus: Next.js manages scroll to top on navigation and focuses the new page; custom behaviour needs care for accessibility (R13).
  • Parallel and intercepting routes enable modal navigation with shareable URLs (N2).

Traps

  • Doing database queries or heavy logic in middleware, adding latency to every request.
  • Using middleware as the only authorisation layer.
  • Matching every path including static assets, which wastes execution.
  • Prefetching hundreds of links on a long page and flooding the network.
  • Assuming useSearchParams is free; without Suspense it forces client rendering of the whole page at build.

Likely follow-ups

Redirects in config versus middleware?
Config is declarative, cheap and evaluated first; middleware is for dynamic decisions based on cookies, headers or geography.
How do you protect a route?
Middleware redirect for UX, plus a server-side session check in the layout/page, plus authorisation in the data layer and actions.
Rewrite versus redirect?
A rewrite serves other content while the URL stays the same; a redirect changes the URL in the browser.
How would you implement locale-based routing?
[locale] segment, middleware negotiation with a persisted preference, static params per locale, localised metadata and alternates.

Streaming, Suspense and hydration

“How does streaming work in Next.js? What is hydration and what causes hydration errors? How do loading.tsx and Suspense improve perceived performance?”

Say this first (30 seconds)

“With streaming, the server does not wait for the slowest data before sending anything. It sends the HTML shell first, with Suspense fallbacks, and streams each boundary’s content as its data resolves, so the user sees useful content early and TTFB is not tied to the slowest query. loading.tsx is a convenient Suspense boundary for a segment. Hydration is the step where React attaches event handlers and state to the server-rendered HTML in the browser; React 18 hydrates selectively, starting with the parts the user interacts with. A hydration error means the first client render did not match the server HTML, typically because of dates, random values, browser-only checks, invalid HTML nesting, or browser extensions. I fix those by making the render deterministic or deferring client-only values to an effect.”

Details interviewers probe

  • How streaming works: HTTP chunked transfer. The response begins with the shell and Suspense fallbacks; as each boundary resolves, the server sends extra HTML and a tiny inline script that moves it into place. The status code and headers are sent with the first chunk, so errors found later cannot change the status (redirects and notFound() after streaming begins use client-side handling and metadata caveats).
  • loading.tsx: automatic Suspense around the segment’s page, giving an instant loading state on navigation and enabling prefetching of a dynamic route up to this boundary. For finer control, place explicit <Suspense> around slow components with matching skeletons.
  • Designing boundaries: fast, important content outside Suspense (title, price); slow, secondary content inside (reviews, recommendations); skeletons sized to avoid layout shift; avoid nesting so deep that content pops in chaotically. Independent boundaries fetch in parallel.
  • SEO and streaming: crawlers receive the full streamed document; metadata is handled so that it lands in <head> (streamed metadata behaviour has details for bots) verify.
  • Hydration: the browser downloads the JavaScript for client components, React walks the server HTML and attaches handlers, reusing existing DOM. Until hydration completes, interactions may be ignored or queued (React replays some events). Hydration cost scales with client component tree size, so Server Components reduce it.
  • Causes of hydration errors: non-deterministic output (Date.now(), Math.random(), locale and time-zone formatting), reading window, localStorage or matchMedia during render, invalid HTML nesting (<div> inside <p>, <a> inside <a>), mismatched conditional rendering based on user agent, browser extensions modifying the DOM, and CDN or middleware transforming HTML.
  • Fixes: deterministic rendering (pass the timestamp from the server and format with a fixed locale/zone), useEffect or useSyncExternalStore for client-only values with a server snapshot, suppressHydrationWarning for a single known text mismatch, next/dynamic with ssr: false inside a client component for purely browser widgets, and fix invalid markup.
  • Progressive enhancement: server-rendered HTML with forms and links works before hydration; Server Actions forms submit natively.
  • Partial prerendering: the static shell and streamed dynamic holes are delivered together (N1).
  • Metrics: streaming improves TTFB-to-first-content and LCP when the LCP element is in the shell, but late-streamed layout can hurt CLS; reserve space.
  • Operational notes: proxies and CDNs must not buffer streamed responses (disable buffering on nginx, check platform support); compression settings can delay chunks; edge runtimes stream well.
  • Alternatives to hydration cost: islands architecture (Astro), resumability (Qwik); in React, Server Components and lazy-loaded client islands.

Traps

  • Using one huge Suspense boundary or none, so streaming brings no benefit.
  • Skeletons that differ in size from content, causing layout shift.
  • Fixing a hydration warning by suppressing it everywhere instead of making the output deterministic.
  • Believing a streamed page cannot return a 404 or redirect status; the decision must be made before the first chunk is sent.
  • Behind a buffering proxy, streaming silently degrades to a blocking response.

Likely follow-ups

Why do we see a flash of different content on load?
A hydration mismatch or a client-only value (theme, user) applied after hydration. Set it on the server via cookies, or use a blocking script for theme before paint.
What is selective hydration?
React hydrates Suspense boundaries independently and in priority order, so an interacted-with part becomes interactive first.
How do you show a loading state for navigation?
loading.tsx for the segment, plus useLinkStatus or useTransition for inline pending indicators verify API names.
How does streaming interact with caching?
The static shell can be cached on a CDN; streamed dynamic parts are generated per request and not cached unless you cache them explicitly (N5).

Performance: images, fonts, scripts, bundles

“How does Next.js help with performance? Explain next/image, next/font, next/script, code splitting and bundle analysis. How would you improve a slow Next.js page?”

Say this first (30 seconds)

“Next.js bakes in many optimisations. next/image serves responsive, lazily loaded images in modern formats like AVIF and WebP, reserves space to avoid layout shift, and has a priority option for the LCP image. next/font self-hosts fonts at build time with no external request and adjusts fallbacks to reduce layout shift. next/script controls when third-party scripts load. The framework code-splits per route and supports dynamic imports, and Server Components keep libraries out of the client bundle. To fix a slow page I measure first with Lighthouse and field data for Core Web Vitals, then work on the biggest cost: usually the LCP image, too much JavaScript, third-party scripts, slow server data, or layout shift.”

Details interviewers probe

  • next/image: required width/height (or fill with a sized parent) prevent CLS. sizes tells the browser which width it will render so it picks the right srcset candidate; omitting sizes on responsive layouts downloads oversized images. Mark the LCP image priority (or preload/fetchPriority="high" in recent versions) and leave the rest lazy. Remote images need remotePatterns. Optimisation runs on the Next.js server or a custom loader (Cloudinary, Imgix); self-hosting needs sharp and a cache. Quality, formats and cache TTL are configurable verify option names.
  • next/font: next/font/google and /local download at build time and serve with the app; automatic font-display and fallback metrics reduce layout shift; load only needed subsets and weights; use variable fonts.
  • next/script: third-party scripts (analytics, chat, ads) are a top cause of slow INP. Prefer afterInteractive or lazyOnload; load on interaction or via a tag manager with governance; consider moving off the main thread (Partytown) or server-side tagging.
  • Bundle size: build output shows “First Load JS” per route. Reduce with Server Components, avoiding heavy client libraries, next/dynamic for below-the-fold or modal components, optimizePackageImports for icon libraries, replacing moment with date-fns or Intl, and checking duplicates. Analyse with @next/bundle-analyzer or the built-in analyser verify tool.
  • Prefetching and navigation speed: <Link> prefetch, static shells with PPR, loading.tsx for instant feedback; avoid fetching waterfalls (N4).
  • Rendering mode for speed: static or ISR over SSR wherever allowed; cache expensive data; stream slow parts; put compute near the database; use CDN caching headers.
  • CSS: prefer CSS Modules, Tailwind or zero-runtime CSS; runtime CSS-in-JS (styled-components, Emotion) has server-component limitations and runtime cost. Inline critical CSS is handled by the framework; avoid huge global stylesheets.
  • Hydration and long tasks: keep client trees small; split interactive widgets; defer non-critical work with requestIdleCallback or transitions (J18, R9).
  • Compiler and build speed: SWC/Turbopack for compile speed; React Compiler option for fewer re-renders verify; output: 'standalone' reduces deploy size.
  • Measuring: Lighthouse for lab data, Chrome UX Report and Vercel/Next analytics (useReportWebVitals) for field data, WebPageTest, the Performance panel. Set budgets and fail CI when exceeded (PWA/performance guide covers methods).
  • Edge versus region: serving HTML from the edge helps only if its data is also nearby; otherwise a single region close to the database is faster for dynamic pages.
  • Data over-fetching: select only needed fields, paginate, stream the long tail, and avoid sending big JSON as props to client components (it is serialised into the HTML).

Traps

  • Using <img> for the hero, or a Next Image without sizes and priority, then wondering why LCP is slow.
  • Marking every image priority, which defeats lazy loading and competes for bandwidth.
  • Optimising micro-details while a third-party script blocks the main thread.
  • Passing huge objects as props to client components, bloating HTML and hydration.
  • Assuming “edge” automatically means faster even when the database is in one distant region.

Likely follow-ups

How does next/image avoid layout shift?
You supply dimensions (or an aspect ratio via fill), so the browser reserves space before the image loads.
How would you reduce JavaScript on a page?
Move components to the server, split heavy client widgets with dynamic imports, remove or defer third parties, tree-shake libraries and check the analyser.
How do you track Core Web Vitals in production?
useReportWebVitals or a RUM tool sending field data, segmented by route, device and country.
Why is Server Component data safer for performance?
It runs near the data, avoids client waterfalls, and ships HTML not code; only interactive parts cost JavaScript.

SEO and metadata

“How do you handle SEO in Next.js? What is the Metadata API? How do you do canonical URLs, Open Graph, sitemaps and structured data? How does rendering mode affect SEO?”

Say this first (30 seconds)

“SEO in Next.js starts with rendering the content on the server or at build time so crawlers get full HTML, then adding correct metadata. The Metadata API lets me export a metadata object or an async generateMetadata function per layout or page for title, description, canonical URL, Open Graph, Twitter cards and robots directives. Files like sitemap.ts, robots.ts and opengraph-image are generated by convention. I add structured data as JSON-LD, use semantic HTML, return real status codes (404 for missing, 301/308 for moves), localise with hreflang, and keep Core Web Vitals healthy because they affect ranking. Client-only rendering is risky for important content.”

Details interviewers probe

  • Static metadata and generateMetadata: export an object for fixed pages; an async function for dynamic ones (fetch the product by params). Metadata merges from parent to child; child fields override. title.template and metadataBase (to resolve relative URLs) go in the root layout. Metadata is server-only (cannot be exported from client components).
  • Open Graph and social cards: openGraph and twitter fields, or generate dynamic images with opengraph-image.tsx using ImageResponse. Social crawlers do not run JavaScript, which is a key reason CSR-only fails for shareable pages.
  • Canonical and duplicates: alternates: { canonical } for filtered, paginated or parameterised URLs that duplicate content; avoid indexing faceted-search combinations; use robots: { index: false } for thin pages.
  • Sitemap and robots: app/sitemap.ts returns URL entries (for large sites generate multiple sitemaps from a database), app/robots.ts sets allow/disallow and the sitemap location. Do not block resources crawlers need.
  • Structured data: embed JSON-LD in a <script type="application/ld+json"> in the page; escape the JSON to avoid script injection (replace <). Validate with Google’s Rich Results test.
  • Status codes and soft 404s: a missing resource must return 404 (notFound()); redirects for moved content must be permanent (308). With streaming, decide before the first chunk. A “not found” UI served with 200 is a soft 404.
  • Internationalisation: locale in the path, alternates.languages for hreflang, translated metadata per locale, and <html lang>.
  • Rendering mode and crawling: Google can render JavaScript but queues it; other search engines and social bots may not. SSR/SSG/ISR give immediate content. Content hidden behind interaction or fetched only after login is not indexed.
  • Links and navigation: use real anchors (<Link> renders <a href>); meaningful link text; clean, stable URLs; breadcrumbs; internal linking structure.
  • Images and accessibility: descriptive alt, correct headings, semantic HTML, and fast loading images; accessibility and SEO overlap strongly.
  • Performance as ranking factor: Core Web Vitals are part of page experience; monitor field data (N9).
  • Preview and draft modes: draftMode() lets editors preview unpublished CMS content without affecting the cached public pages, and should be protected by a secret.
  • Monitoring: Search Console for indexing and coverage errors, log crawler visits, and track rendered HTML with a “fetch as Google” style test after deploys.

Traps

  • Client-only rendering for content that should be indexed and shared.
  • Duplicate content from query parameters or trailing slashes without canonicals.
  • Forgetting metadataBase, producing wrong absolute Open Graph URLs.
  • Returning 200 for missing pages (soft 404) or using temporary redirects for permanent moves.
  • Injecting unescaped user content into JSON-LD.

Likely follow-ups

How do you set a per-product title and image?
generateMetadata reading the product by slug, with an opengraph-image route generating a card.
Is SSR required for SEO?
Not strictly, but server or static HTML is the reliable path; Google can render JS, but delays and other crawlers make it risky.
How do you manage SEO for a huge catalogue?
Paginated sitemaps, canonical rules for facets, ISR for pages, internal linking and monitoring indexed counts.
What is a soft 404?
A page that says “not found” but returns HTTP 200, which search engines may index or distrust.

Authentication and security

“How do you implement authentication in Next.js? Sessions versus JWT? Where do you check authorisation? How do you protect secrets, set security headers and defend against common attacks?”

Say this first (30 seconds)

“I implement auth with a library such as Auth.js (NextAuth), Clerk or Supabase Auth, or my own session layer, storing the session in an HttpOnly, Secure, SameSite cookie. Authentication proves who the user is; authorisation decides what they can do, and it must be enforced on the server at the data access layer and in every Server Action and route handler, not only in middleware or the UI. Middleware is useful for an optimistic redirect but must not be the sole check. I keep secrets in server-only modules and environment variables without the public prefix, return DTOs rather than raw rows, validate all inputs, set security headers including a nonce-based Content Security Policy, and keep the framework patched.”

Details interviewers probe

  • Options: Auth.js (formerly NextAuth) for OAuth/credentials with adapters; hosted providers (Clerk, Auth0, Okta, Supabase Auth, Firebase Auth); custom sessions with a library such as jose for signed or encrypted cookies. Choose by compliance, cost, MFA, SSO and team capacity. Do not write your own crypto.
  • Flows: OAuth/OIDC authorisation code flow with PKCE for social and SSO login (protocols guide), credentials with strong password hashing (argon2/bcrypt) and rate limiting, magic links, passkeys (WebAuthn). Callback handled by a route handler.
  • Session storage and reading: read the cookie with cookies() in server code; wrap session retrieval in a cached function (React.cache) so it is verified once per request; refresh tokens rotate; sign out clears the cookie and server record.
  • Data Access Layer pattern: all data access goes through server-only functions that check the session and permissions and return minimal DTOs. Pages and actions call the DAL; never pass full user records to client components.
  • Authorisation models: RBAC (roles), ABAC (attributes), ownership checks, tenant isolation for multi-tenant apps. Enforce in code and, where possible, in the database (Postgres row-level security with Supabase).
  • Middleware caveats: useful to redirect unauthenticated users quickly. It must not be the only protection: matchers can miss routes (including data endpoints and Server Actions), and a 2025 vulnerability allowed bypass through a spoofed internal header on affected versions verify the advisory and fixed versions. Re-check in server code.
  • Server Actions security: public endpoints; authenticate, authorise, validate (Zod), rate-limit, check ownership; do not trust IDs from the client (N6).
  • CSRF: SameSite cookies plus Next.js origin checks for actions; custom route handlers using cookie auth need their own CSRF defence (token or origin check). APIs using bearer tokens in headers are not CSRF-prone.
  • Security headers and CSP: set via headers() in next.config or middleware: Content-Security-Policy (nonce-based with strict-dynamic; Next supports nonces in dynamic rendering), Strict-Transport-Security, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, frame-ancestors. Nonces force dynamic rendering of affected pages, a trade-off versus static caching.
  • Environment variables: only NEXT_PUBLIC_* are exposed to the browser and inlined at build time; others stay on the server. Never commit .env files with secrets; use platform secret stores. Rotating a public value requires a rebuild.
  • Other risks: XSS via dangerouslySetInnerHTML and unsanitised markdown (J29), SSRF in server-side fetches of user-provided URLs (allowlist), open redirects in ?next= parameters, path traversal in file serving, dependency and supply-chain vulnerabilities, leaking data through props or logs, image optimiser abuse (restrict remotePatterns).
  • Operational security: keep Next.js and React patched (several critical advisories in 2025 affected middleware and Server Components) verify, subscribe to advisories, enable dependency scanning, use least-privilege cloud credentials, audit logs.
  • Rate limiting and abuse: at the edge or gateway (Upstash, platform WAF), per IP and per account, with stricter limits on login, password reset and expensive actions.

Traps

  • Protecting only with middleware or with hidden UI.
  • Putting access tokens in localStorage and calling it done.
  • Trusting a user id or role sent from the client.
  • Exposing secrets through NEXT_PUBLIC_ variables or returning raw database rows to client components.
  • Implementing a homemade JWT or password scheme instead of a vetted library.

Likely follow-ups

Where do you verify the session in the App Router?
In a server-only helper called by layouts, pages, actions and the DAL, memoised per request; middleware only does a light pre-check.
How do you implement role-based UI?
Send the role (or permissions) from the server as part of the session DTO to render the UI, but enforce permissions again in every server operation.
How do you set a nonce-based CSP?
Generate a nonce per request in middleware, set the CSP header and pass the nonce to scripts; pages become dynamic, so apply it where the security benefit justifies it.
JWT or database session?
Database/server sessions for easy revocation and smaller exposure; short-lived JWTs with rotation when you need stateless verification across services.

Deployment, runtimes and operations

“How do you deploy a Next.js app? Vercel versus self-hosting? What are the Node and Edge runtimes? How do ISR and caching work when self-hosted? When would you not use Next.js?”

Say this first (30 seconds)

“Next.js can be deployed on Vercel, which understands every feature natively, or self-hosted as a Node server (next start), in a Docker container with output: 'standalone', on a serverless or container platform through an adapter such as OpenNext, or as a fully static export when there are no server features. Pages can run on the Node.js runtime, with full API access, or the Edge runtime, with lower latency but a limited API surface. Self-hosting means I own the operational concerns: a shared cache handler so ISR and the Data Cache work across instances, an image optimiser, CDN and cache headers, health checks, scaling, observability and secrets. I choose Next.js when I need hybrid rendering, SEO and a rich React app; I avoid it for purely static sites, where a lighter tool is simpler, or for heavy back-office SPAs with no SEO needs.”

Details interviewers probe

  • Build and run: next build produces .next output; next start runs the production server. output: 'standalone' traces dependencies into a minimal folder for small Docker images (copy public and .next/static too); serve static assets from a CDN with long-lived immutable caching (hashed names).
  • Docker and orchestration: multi-stage Dockerfile, non-root user, health endpoint, graceful shutdown on SIGTERM, resource limits, horizontal scaling behind a load balancer. Stateless instances only if the cache is shared.
  • ISR and Data Cache in multiple instances: the default cache lives on the instance’s disk and memory; with several instances each has its own copy, causing inconsistent revalidation. Configure a custom cacheHandler backed by Redis or object storage, and propagate revalidateTag across instances verify the supported mechanism for your version. Managed platforms solve this for you.
  • Image optimisation self-hosted: needs sharp and CPU; consider an external image service or CDN-based optimiser to offload.
  • Static export: good for marketing sites and docs; remember that features needing a server (middleware, Server Actions, dynamic routes without params, ISR, redirects config) are unavailable.
  • Environment configuration: NEXT_PUBLIC_* values are baked at build time, so one image cannot serve several environments unless you inject runtime config via an endpoint or server-side props. Server variables are read at run time. Keep secrets in a secrets manager, not in the image.
  • CI/CD: install with a lockfile, lint, type-check, test, build with caching (.next/cache), run end-to-end tests against a preview deployment, deploy with progressive rollout (canary or blue-green; DevOps guide), keep rollbacks one command away. Preview environments per pull request are a major productivity gain.
  • Observability: OpenTelemetry instrumentation (instrumentation.ts), structured logs, error tracking (Sentry), real-user monitoring of web vitals, alerts on error rate, latency and cache hit ratio; track slow server components and data calls.
  • Scaling and cost: most traffic should hit CDN-cached static output; dynamic rendering costs CPU per request. Reduce cost by caching, ISR, avoiding unnecessary dynamic APIs, and sizing instances by measured load.
  • Runtime selection per route: export const runtime = 'edge' | 'nodejs'. Edge helps middleware and lightweight personalisation, but a global edge function that queries a single-region database can be slower than a regional Node function.
  • Upgrading and migration: follow upgrade guides and codemods (npx @next/codemod), update React and Next together, test caching behaviour after upgrades, and migrate Pages to App routes incrementally.
  • When not to use Next.js: purely static content sites (Astro, Eleventy), authenticated SPAs with no SEO need where Vite and React Router are simpler, apps needing a non-Node backend ecosystem, or when the team cannot operate the server and caching complexity. Alternatives with different trade-offs: Remix/React Router framework mode, Astro, SvelteKit, Nuxt, TanStack Start.
  • Vendor lock-in view: Next.js is open source, but some features are shaped around Vercel’s infrastructure; reduce lock-in by following standard APIs, abstracting storage and cache, and testing a self-hosted build.

Traps

  • Scaling a self-hosted app to several instances without a shared cache, then seeing inconsistent ISR.
  • Expecting NEXT_PUBLIC_ variables to change at run time without a rebuild.
  • Choosing the Edge runtime by default and hitting unsupported Node APIs or distant database latency.
  • Using static export and then adding features that need a server.
  • Choosing Next.js for every project without weighing simpler options.

Likely follow-ups

How do you containerise a Next.js app?
Multi-stage Docker build with output: 'standalone', copy static assets and public files, run as non-root, add a health check, and serve _next/static via CDN.
How do you do zero-downtime deployments?
Rolling or blue-green deploys with health checks, versioned static asset paths (or a deployment id) so old clients can still fetch their chunks during rollout.
What is skew protection?
Keeping old assets and server actions available to clients still running the previous build, preventing errors during deploys verify feature names.
How do you monitor a Next.js app in production?
OpenTelemetry traces, logs, RUM for web vitals, error tracking with source maps, and alerts on SLOs.

How to answer Next.js questions at L4

  • Frame rendering questions around data: how often it changes, whether it is personalised, and who needs it first (users and crawlers). Then pick static, ISR, dynamic or a streamed mix.
  • For caching questions name the layer and the version. Say plainly that defaults changed in Next.js 15 and that you check the docs for the version in use.
  • Separate security layers: middleware for UX, server for rendering, data access layer for authorisation, database rules as the last line.
  • Give a performance story with numbers: the metric, the cause you found, the change, the measured result.
  • Be balanced about trade-offs and lock-in: when you would pick Next.js and when something simpler is better.
  • The interview is theoretical: expect “explain”, “compare”, “how would you design” and “what are the trade-offs”, not live coding.
