Sass and SCSS

“What is Sass/SCSS and why use it? Explain variables, nesting, mixins, functions, partials, @use and @forward, maps, control directives and placeholders. What does Sass give you that native CSS now provides, and what does it still add?”

Say this first (30 seconds)

“Sass is a CSS preprocessor: I write SCSS, a superset of CSS syntax, and a compiler turns it into plain CSS at build time. It adds variables, nesting, mixins for reusable blocks, functions, partial files organised with the module system (@use and @forward), maps and loops for generating styles, and placeholder selectors for sharing rules. Because the output is static CSS, Sass values do not exist at run time, unlike native custom properties. Modern CSS now has custom properties, nesting and color-mix(), so I use Sass mainly for build-time logic such as generating utility classes or scales, mixins with arguments, math, and existing codebases such as Bootstrap, while preferring custom properties for anything that must change at run time, such as themes.”

Details interviewers probe

  • SCSS versus indented Sass: SCSS uses braces and semicolons and is a strict superset of CSS (any valid CSS is valid SCSS); the older indented syntax omits braces. SCSS is the standard. Compilers: Dart Sass (current, reference), LibSass and node-sass are deprecated.
  • Variables and scope: $brand: #2563eb;, !default to make configurable, !global to assign globally; lexical block scope. Use maps for scales: $space: (1: .25rem, 2: .5rem) with map.get($space, 2).
  • Nesting: mirror structure with & for parent references (&:hover, &__element, .theme-dark &); limit depth to two or three levels to avoid specificity bloat and unreadable output. Native CSS nesting now exists, so Sass nesting is less crucial (C20).
  • Mixins and includes: reusable blocks with arguments and defaults (@mixin breakpoint($bp)), content blocks (@content) for wrapping media queries; each include duplicates declarations in output, so avoid large mixins used many times.
  • Extend and placeholders: %placeholder with @extend groups selectors to share one rule block, producing smaller CSS than mixins, but it can create surprising selector ordering and cross-file coupling; many teams prefer mixins or utility classes.
  • Functions and math: @function returning values (rem(24px)), math.div (the / division operator is deprecated), colour functions (color.adjust, color.scale), responsive helpers; native calc(), clamp() and color-mix() cover many cases at run time.
  • Control directives: @if/@else, @each, @for, @while generate repetitive CSS (utility classes, grid columns, spacing scales) from data; this is where Sass still shines.
  • Architecture with Sass: a 7-1 or ITCSS-style folder structure (abstracts/tokens, base, layout, components, pages, themes, vendors) with an index using @forward; keep tokens in one module; compile per entry; avoid global leakage by using @use (C17).
  • Source maps and tooling: compile via Vite, webpack (sass-loader), Next.js (built-in), or the CLI; source maps map output to SCSS in DevTools; combine with PostCSS (Autoprefixer) and minifiers; watch build times with large Sass trees.
  • CSS Modules with Sass: *.module.scss scopes class names and still allows Sass features; common in React/Next.js apps.
  • Sass versus alternatives: Less and Stylus (older), PostCSS-based approaches (postcss-preset-env, nesting), Lightning CSS, and plain modern CSS; Sass remains popular because of Bootstrap, existing codebases and its maturity.
  • When to avoid heavy Sass: deep nesting, giant mixin libraries, and heavy @extend chains make CSS hard to debug; prefer simple structure plus custom properties.
  • Performance and output size: mixin repetition and over-nesting bloat output; analyse compiled CSS size; split critical CSS; remove unused styles (PurgeCSS, Tailwind-like tree shaking for utilities).

Traps

  • Expecting Sass variables to change at run time or per theme.
  • Deep nesting that produces long, high-specificity selectors.
  • Still using @import and the / division operator, both deprecated.
  • Using @extend across unrelated files and creating fragile output.
  • Describing Sass as “more powerful than CSS” without saying it compiles away before the browser runs.

Likely follow-ups

Mixin versus @extend?
A mixin copies declarations into each include and accepts arguments; @extend merges selectors into one rule and cannot take arguments but can reorder output unexpectedly.
Why @use instead of @import?
@use namespaces members and loads each module once, avoiding global scope collisions and duplicated CSS.
Can you theme with Sass variables?
Only by compiling separate bundles; for run-time theming use custom properties, optionally generated from Sass maps.
Do you still need Sass today?
Often not for new projects, but it helps with build-time generation, shared mixins and existing frameworks.

CSS architecture and naming methodologies

“How do you structure CSS in a large codebase? Compare BEM, OOCSS, SMACSS, ITCSS, utility-first and CUBE CSS. How do you manage specificity, the cascade and style leakage? What do cascade layers and @scope add?”

Say this first (30 seconds)

“CSS is global by default, so at scale you need conventions that keep specificity low and predictable and styles scoped. BEM names classes by block, element and modifier, such as card__title--large, which makes ownership explicit and keeps selectors flat. ITCSS organises the stylesheet in layers from generic to specific, so the cascade and specificity grow in a controlled direction. Utility-first, as in Tailwind, composes small single-purpose classes in markup. CSS Modules or component styles scope class names automatically. Modern CSS gives structural tools: cascade layers to control precedence regardless of specificity, and @scope and nesting for local rules. I choose by team and tooling, and the common rules are low specificity, no styling by structure or IDs, and one place to define each thing.”

Details interviewers probe

  • Why architecture matters: global scope, specificity wars, source-order dependence, dead CSS that nobody dares delete, and inconsistent patterns. The aim is predictability: a new developer can add styles without breaking others.
  • BEM: block (standalone component), element (part of a block, __), modifier (variant or state, --). Pros: flat specificity, clear ownership, works without tooling. Cons: verbose names, discipline needed, nested elements (card__body__title is discouraged: flatten to card__title). Pair with Sass &__element for brevity (C16).
  • ITCSS (Inverted Triangle): layers ordered from low specificity and wide reach to high specificity and narrow reach: settings, tools, generic, elements, objects, components, trumps. It structures the stylesheet so cascade conflicts are rare; combine with BEM for naming.
  • SMACSS and OOCSS: categorise rules (base, layout, module, state, theme) and separate structure from skin and container from content; they inspired later methods; know the vocabulary.
  • CUBE CSS: Composition (layout primitives), Utilities, Blocks, Exceptions: embrace the cascade, use a small number of global rules and lightweight utilities, and data attributes for exceptions.
  • Specificity management: specificity order (inline, IDs, classes/attributes/pseudo-classes, elements); avoid IDs and overly qualified selectors (div.card ul li a); keep selector depth low; use :where() to zero out specificity for defaults and :is()/:not() with care; avoid !important outside utilities; prefer reordering or layers to escalating specificity (CSS guide C3).
  • Cascade layers (@layer): explicit precedence between groups of rules independent of specificity; order declared once at the top; ideal for resets, third-party libraries, design systems and utilities; supported in all modern browsers verify the support level for your audience. Tailwind v4 and many design systems use layers.
  • @scope: limits rules to a subtree with optional lower boundary (donut scope) and proximity-based precedence, offering native scoping without class conventions; newer feature verify browser support.
  • Native nesting and :has(): reduce the need for preprocessors and extra classes but can recreate deep selectors if abused; keep nesting shallow.
  • Component-scoped solutions: CSS Modules (hashed class names per file), CSS-in-JS (scoped by generation), framework-scoped styles (Vue, Svelte, Angular emulated encapsulation), Shadow DOM (true encapsulation) (S9, E7).
  • File organisation: colocate component styles with components, global base/tokens in a shared package, one stylesheet per feature or route for loading performance, naming files after components; avoid giant catch-all stylesheets.
  • Dead code and growth control: coverage tools (DevTools Coverage), PurgeCSS/Tailwind content scanning, Stylelint rules for max specificity and no duplicate selectors, review practices, and periodic audits with CSS Stats.
  • Migrating legacy CSS: introduce layers to contain old CSS, scope new components with Modules or BEM, replace utilities gradually, and avoid wholesale rewrites; measure with visual regression tests (A4).
  • Naming and API consistency: predictable state classes or data attributes (is-open or [data-state="open"]), consistent modifiers, avoid names tied to appearance (.red-button) in favour of meaning or role.

Traps

  • Styling by deep structure (.sidebar ul li a), which breaks when markup changes.
  • Fighting specificity with !important and more nested selectors instead of structure.
  • Over-long BEM names from nested elements.
  • Treating methodologies as dogma instead of tools; consistency within the codebase matters most.
  • Putting third-party CSS after your own without layers, so it overrides your styles.

Likely follow-ups

How do you override a library’s styles cleanly?
Load the library inside a low-priority @layer (or lower specificity), then write your styles in a later layer, avoiding !important.
BEM or CSS Modules?
BEM uses naming discipline and works anywhere; CSS Modules scope classes automatically at build time; both give low specificity, and they can be combined.
What does :where() do?
It matches like :is() but contributes zero specificity, ideal for easily overridable base styles.
How would you tame a 10-year-old stylesheet?
Contain it in a low layer, measure unused CSS, add scoped components gradually, and use visual regression tests to refactor safely.

Tailwind CSS and utility-first design

“What is utility-first CSS and how does Tailwind work? Explain the config and theme, variants, JIT scanning, @apply, component extraction, dark mode and Tailwind 4. What are the trade-offs versus BEM or CSS-in-JS?”

Say this first (30 seconds)

“Utility-first CSS styles elements by composing many small single-purpose classes directly in the markup, such as flex items-center gap-4 p-4 rounded-lg. Tailwind generates those utilities from a design-token configuration and scans my source files to emit only the classes I use, so the CSS stays small. Variants such as hover:, md: and dark: apply a utility conditionally. Benefits are speed, consistency from a constrained token scale, no naming and no dead CSS. Costs are long class lists, a learning curve, and the need to extract repeated patterns into components rather than CSS classes. Dynamic class names must be written in full so the scanner can see them, and accessibility and semantics are still my job.”

Details interviewers probe

  • Core idea and rationale: avoids naming and context-switching between HTML and CSS files, keeps styles local to the element (changing one component cannot break another), and limits CSS growth because utilities are reused. Criticisms: markup noise and “inline styles with extras”; the counter is constraints (a scale), variants (states and breakpoints) and pseudo-selectors that inline styles lack.
  • Configuration and tokens: theme values for colours, spacing, type, radii, breakpoints; extend rather than replace the defaults; map to your design tokens (S2); in v4, tokens are CSS variables defined with @theme and available at run time for theming; v3 used JavaScript config and plugins verify the version in use.
  • Content scanning (JIT): Tailwind scans files for class-like strings and generates matching utilities on demand; arbitrary values (top-[117px]) generate one-off classes; safelisting is for classes that cannot be detected statically.
  • Variants: state (hover, focus-visible, disabled), responsive (mobile-first md:), dark mode (dark: via media or a class/attribute strategy), group/peer for parent and sibling state, has-[], container queries, motion preferences, aria-* and data-* variants.
  • Reuse and extraction: extract components (React/Vue/Angular components) or partials, not CSS classes; @apply exists but is discouraged for general use because it recreates naming and ordering problems; helpers: clsx, cva (class-variance-authority) for variants, tailwind-merge to resolve conflicting classes.
  • Plugins and ecosystem: typography, forms, container queries (built in for v4), animate plugins; component kits built on Tailwind: shadcn/ui, Headless UI, daisyUI, Flowbite; Prettier plugin sorts class names consistently (E8).
  • Accessibility and semantics: utilities do not make markup accessible; use semantic elements, focus styles (focus-visible:), sufficient contrast, motion preferences, and screen-reader utilities (sr-only).
  • Performance: small CSS output, no runtime; scanning cost at build; large arbitrary-value usage reduces reuse; critical CSS is small enough to inline; works with Server Components (E7, N9).
  • Dark mode and theming: pair dark: variants with semantic tokens (CSS variables) to avoid doubling every class; theme switching via a class or data attribute set before first paint (S2).
  • Versus alternatives: BEM/Sass separates concerns but requires naming and growth control; CSS-in-JS offers dynamic styles at runtime cost; CSS Modules scope styles. Tailwind trades markup length for consistency and speed; large design systems may layer semantic components on top.
  • Team adoption: agree on conventions (ordering, extraction rules, limits on arbitrary values), lint with eslint-plugin-tailwindcss verify tool, document patterns, and review class lists for duplication; onboarding includes learning the scale and variants.
  • Tailwind 4 highlights: new engine for faster builds, CSS-first configuration, automatic content detection, built-in container queries, cascade layers and native CSS features such as color-mix and @property verify the final feature list.
  • Migration and coexistence: adopt in new components while legacy CSS remains in a lower layer; prefix utilities (tw-) to avoid collisions; remove the old CSS gradually.

Traps

  • Building class names with string concatenation so the scanner cannot find them.
  • Reaching for @apply everywhere and recreating a naming problem.
  • Copy-pasting long class lists instead of extracting components.
  • Assuming Tailwind handles accessibility and responsive behaviour automatically.
  • Unlimited arbitrary values that bypass the design scale.

Likely follow-ups

Why does Tailwind output small CSS?
It generates only the utilities found in your source files, rather than shipping a full framework.
How do you handle component variants?
With cva or a lookup map of complete class strings, merged with tailwind-merge.
Is Tailwind just inline styles?
No: utilities support pseudo-classes, media and container queries, a shared scale, and are deduplicated in a stylesheet with consistent specificity.
When would you avoid Tailwind?
When the team strongly prefers separated styles, when a mature BEM/Sass system already works, or when runtime theming needs dominate; also for very small static pages.

Bootstrap and other CSS frameworks

“What are Bootstrap and similar frameworks, how does the Bootstrap grid and utility system work, how do you customise it with Sass, and when do you choose a CSS framework, a component library or custom CSS? What are Bulma, Foundation and Material?”

Say this first (30 seconds)

“Bootstrap is a widely used CSS and JavaScript framework providing a responsive 12-column flexbox grid, ready-made components such as navbars, modals and forms, and utility classes for spacing, display and flex. Version 5 dropped jQuery and added utilities and CSS variables. You customise it by overriding Sass variables before importing its source, or with CSS custom properties, rather than overriding compiled CSS. Frameworks give speed and consistency for prototypes, admin tools and teams without design resources; the costs are a recognisable look, extra CSS weight if not trimmed, and fighting the framework when the design diverges. Modern projects often prefer utility frameworks like Tailwind or headless component libraries for more control, but Bootstrap remains common in enterprise codebases.”

Details interviewers probe

  • Grid system: .container (fixed or fluid), .row (flex wrapper with negative gutters), .col-* (flex items spanning 12 columns), breakpoint prefixes, auto-sizing columns (.col), offsets, ordering utilities, gutters (g-*); newer versions offer an optional CSS Grid engine; compare with writing your own CSS grid and flexbox layouts, which is often simpler and more flexible today (CSS guide C-layout topics).
  • Utilities and components: spacing scale (m-3, px-4), display and flex helpers, colours, borders, shadows, visibility; component markup follows documented structures with classes; JS components (modal, dropdown, collapse, tooltip) rely on data attributes or an instance API and work with ARIA patterns; in React, use React-Bootstrap to avoid manipulating the DOM directly with Bootstrap’s JavaScript.
  • Customisation strategies: override Sass variables and maps ($theme-colors, $spacers, $grid-breakpoints) before importing; import only needed parts (@import "bootstrap/scss/functions"…) to reduce size; use the CSS variables for run-time theming (--bs-primary) and data-bs-theme="dark" for dark mode; avoid overriding with heavy specificity in a separate stylesheet.
  • Performance and size: compiled Bootstrap CSS is around 150 KB unminified (about 25 KB gzipped, check current) and the JS bundle adds weight; trim unused components via Sass imports, PurgeCSS, or tree-shaken JS; consider CSS-only usage.
  • Accessibility: components implement many ARIA patterns (modal focus management, dropdown keyboard), but custom compositions still need testing; ensure colour contrast of default palette meets requirements when customised.
  • Other frameworks: Bulma (CSS-only, Flexbox, easy to read, modifiers like is-primary), Foundation (powerful grid and accessibility, decreasing popularity), Semantic UI (largely replaced by Fomantic), Material Design Lite (retired), Primer (GitHub), Carbon (IBM), Fluent (Microsoft); component libraries such as MUI, Ant Design, Chakra, Mantine blend styling with React components (E8).
  • Choosing between approaches: prototype, internal tools and admin dashboards: Bootstrap or a component library; branded marketing and product UI with a design system: custom tokens plus Tailwind, CSS Modules or headless components; long-lived apps with legacy Bootstrap: encapsulate and migrate gradually.
  • Common problems: sites that look generic, fighting defaults, specificity conflicts when overriding, loading both Bootstrap and another framework, version upgrade pain (Bootstrap 4 to 5 changed many classes and removed jQuery), and bundle bloat.
  • Migration paths: replace Bootstrap components behind your own wrappers, move layout to native grid/flex, introduce tokens as CSS variables, then drop the framework CSS (A4, S1).
  • CSS frameworks in the Angular and React worlds: ng-bootstrap, ngx-bootstrap, React-Bootstrap provide component bindings without jQuery; Angular Material and CDK implement Material Design with accessibility.
  • Licensing and governance: MIT for Bootstrap, Tailwind and Bulma; check licences for commercial component kits and UI templates.

Traps

  • Overriding Bootstrap’s compiled CSS with more specific selectors instead of customising Sass variables.
  • Importing the entire framework for a few components.
  • Mixing Bootstrap JavaScript with a React or Angular rendered DOM and getting stale state.
  • Assuming components are fully accessible regardless of how you compose them.
  • Choosing a framework because it is familiar when the product needs a distinct brand.

Likely follow-ups

Bootstrap versus Tailwind?
Bootstrap provides ready-made components and a grid; Tailwind provides low-level utilities and requires building components, giving more design freedom.
How do you customise the Bootstrap theme?
Set Sass variables before importing Bootstrap’s source (or override CSS variables), and import only the needed modules.
How does the 12-column grid work?
Rows are flex containers; columns take a fraction of 12 per breakpoint, wrapping to new lines when the total exceeds 12.
Would you still use a 12-column grid today?
For legacy or quick layouts yes; for new work CSS Grid and flexbox give more precise and simpler layouts.

The CSS toolchain and modern CSS versus preprocessors

“Which tools process CSS: PostCSS, Autoprefixer, Lightning CSS, Stylelint, CSS Modules, PurgeCSS? Which preprocessor features does native CSS now cover (variables, nesting, color-mix, layers, container queries)? How would you set up CSS for a new project in 2026?”

Say this first (30 seconds)

“The CSS toolchain transforms, lints and optimises stylesheets. PostCSS parses CSS into an AST so plugins can add vendor prefixes with Autoprefixer, compile future syntax with preset-env and minify; Lightning CSS is a very fast Rust alternative that does parsing, prefixing, nesting and minification, and is built into Vite and Parcel. Stylelint enforces conventions, and CSS Modules scope class names. Native CSS now covers many preprocessor features: custom properties, nesting, calc(), clamp(), color-mix(), cascade layers, container queries and :has(). For a new project I would start with plain modern CSS or CSS Modules plus custom properties for tokens, add PostCSS or Lightning CSS for prefixing driven by browserslist, use Stylelint, and reach for Sass or Tailwind only when their specific benefits are needed.”

Details interviewers probe

  • PostCSS: a tool for transforming CSS with JavaScript plugins; plugins: Autoprefixer (adds prefixes from browserslist and caniuse data), postcss-preset-env (polyfills future CSS by target), postcss-nesting, cssnano (minify), postcss-import, Tailwind (as a plugin in v3); configured via postcss.config.js; widely integrated into Vite, Next.js and webpack (B7).
  • Lightning CSS: parses, transforms, prefixes and minifies CSS, supports nesting, modern colour syntax, CSS Modules and custom media; used by Vite (optional), Parcel and Tailwind v4’s toolchain; much faster than JS-based pipelines verify integration details.
  • Stylelint: configurable linter with rules for errors and conventions: no duplicate selectors, max specificity, property order, forbid hard-coded colours (use tokens), enforce naming patterns; integrates with editors and CI (B9).
  • CSS Modules: file-local class names via hashing (styles.button), composes, :global; works with CSS, Sass and PostCSS; typed class names via generators; default in Next.js and Vite setups (E7).
  • Removing unused CSS: Tailwind scans content; PurgeCSS and Lightning CSS can drop unused selectors but need safelists for dynamic classes and third-party markup; DevTools Coverage identifies dead code; keep component-scoped CSS so removing a component removes its styles.
  • Critical CSS and loading: inline above-the-fold CSS, load the rest asynchronously, split CSS by route, avoid @import chains in production CSS, compress with Brotli, and use content-visibility to defer rendering costs (F2, B1).
  • Native replacements in detail: custom properties for tokens and theming (runtime), CSS nesting (with relaxed syntax in newer versions), @layer for precedence, container queries and units for component-level responsiveness, :has() for parent selection, color-mix() and relative colour syntax for palettes, @property for typed variables and animation of custom properties, @scope, @starting-style, view transitions verify support per feature on caniuse and Baseline.
  • Fallbacks and progressive enhancement: use @supports to gate new features, provide baseline styles, and let PostCSS/Lightning CSS down-level syntax per browserslist when required (B3).
  • Setting up CSS for a new project: choose scoping (CSS Modules or Tailwind or framework-scoped), define tokens as custom properties, set up @layer order, add PostCSS/Lightning CSS with browserslist, Stylelint, and a visual regression or Storybook pipeline; document conventions; add Sass only if build-time logic is needed.
  • CSS-in-JS comparison: runtime CSS-in-JS gives dynamic styling and co-location but adds runtime cost and RSC friction; zero-runtime variants extract static CSS; for most apps CSS Modules or utilities plus custom properties for dynamic values give the best performance (E7).
  • Maintainability practices: keep specificity low, avoid duplication through tokens and components, review for dead CSS regularly, restrict global styles to resets and tokens, and use visual tests during refactors.
  • Debugging CSS toolchain issues: inspect source maps from compiled CSS back to SCSS or Modules, check the computed output in DevTools, verify prefixes in the built file, and confirm browserslist resolution with npx browserslist.

Traps

  • Adding Sass, PostCSS, CSS-in-JS and a framework to a small project without need.
  • PurgeCSS removing dynamically generated classes because they were not safelisted.
  • Using new CSS features without feature checks or fallbacks for the support matrix.
  • Maintaining duplicated tokens in Sass variables and custom properties.
  • Believing native nesting and Sass nesting behave identically in every detail.

Likely follow-ups

What does Autoprefixer need to work?
A browserslist target list; it then adds only the vendor prefixes those browsers require.
Do you still need Sass?
Rarely for new projects; it remains useful for build-time loops and maps, shared mixins and legacy frameworks.
How do you find and remove unused CSS?
DevTools Coverage and static analysis to find candidates, then component-scoped styles or content scanning with safelists to remove them safely.
Why did Lightning CSS appear?
To replace multiple JavaScript tools with one fast native pipeline for parsing, transforming and minifying modern CSS.

How to answer CSS tooling questions at L4

  • Lead with the problem each tool solves: global scope, specificity, dead CSS, browser support, consistency.
  • Give a recommendation and its trade-off, not a tool list: “tokens as custom properties, scoped styles, Sass only if build-time logic is needed”.
  • Separate build-time from run-time: Sass variables versus custom properties is the classic probe.
  • Talk about team and migration: conventions, linting, visual regression tests, gradual replacement of legacy CSS.
  • The interview is theoretical: expect “when would you choose” and “what are the trade-offs”, not writing stylesheets.
