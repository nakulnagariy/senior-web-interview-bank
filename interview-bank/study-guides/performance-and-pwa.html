Core Web Vitals and performance metrics

“What are the Core Web Vitals? Explain LCP, INP and CLS, their thresholds, how each is measured, and what typically makes them bad. What other metrics matter (TTFB, FCP, TBT)? Why do they matter for the business?”

Say this first (30 seconds)

“Core Web Vitals are Google’s user-centred metrics for loading, interactivity and visual stability. Largest Contentful Paint measures when the main content appears, good is 2.5 seconds or less. Interaction to Next Paint measures responsiveness across all interactions on the page, good is 200 milliseconds or less; it replaced First Input Delay in 2024. Cumulative Layout Shift measures unexpected movement of content, good is 0.1 or less. They are assessed at the 75th percentile of real users, split by mobile and desktop. Supporting diagnostics include Time to First Byte, First Contentful Paint and Total Blocking Time, which is a lab proxy for responsiveness. They matter because speed affects conversion, engagement and search ranking, but I treat them as a user-experience tool, not a score to game.”

Details interviewers probe

  • LCP: render time of the largest image, video poster or block-level text in the viewport. Breakdown: TTFB, resource load delay, resource load duration, element render delay. Improve by faster server and CDN, preloading the LCP resource with fetchpriority="high", not lazy-loading it, optimising its size and format, removing render-blocking resources, and server rendering the element so it does not wait for JavaScript.
  • INP: considers all clicks, taps and key presses; reports a high percentile of interaction latencies (roughly the worst). Components: input delay (main thread busy), processing time (event handlers), presentation delay (rendering the next frame). Improve by breaking up long tasks, doing less work in handlers, deferring non-urgent updates (transitions), avoiding layout thrash, reducing DOM size and hydration cost, and moving heavy work to workers (J18, J23, R9).
  • CLS: sum of layout-shift scores (impact fraction × distance fraction) in the worst session window, ignoring shifts within 500 ms of user input. Fix by reserving space (width/height or aspect-ratio), font-display with size-adjust fallback, skeletons of the right size, avoiding insertion above content, and composited animations (transform).
  • Other metrics: TTFB (server and network), FCP (first text or image), Speed Index and Total Blocking Time (lab), Time to Interactive (deprecated), First Input Delay (replaced by INP). Custom metrics with the User Timing API (performance.mark/measure) capture business milestones (search results visible, checkout ready).
  • Lab versus field: lab (Lighthouse, WebPageTest) is repeatable and good for debugging; field (Chrome User Experience Report, RUM) reflects real devices, networks and behaviour and is what Google ranks on. Lab can pass while field fails because users have slower phones and different content.
  • Percentiles: use p75 for Core Web Vitals; look at p90/p95 for tail pain; averages hide problems. Segment by device, connection, country, page type and logged-in state.
  • Business impact: case studies link speed to conversion, bounce and revenue; Core Web Vitals are a ranking signal (modest). Tie performance work to measurable outcomes (conversion funnel, engagement) when asking for time.
  • Metrics evolve: INP replaced FID (March 2024); thresholds and new metrics (such as Long Animation Frames) change, so check web.dev verify current thresholds.
  • SPA nuance: metrics were designed for page loads; soft navigations in single-page apps may not be fully measured by CWV (experimental soft navigation support) so add custom route-change metrics.
  • Where Core Web Vitals show up: Search Console report, PageSpeed Insights (field data from CrUX plus lab), Chrome DevTools Performance and Insights, the web-vitals JavaScript library, and RUM vendors.
  • Trade-offs: optimising one metric can hurt another (preloading everything improves LCP but wastes bandwidth; aggressive lazy-loading delays LCP). Focus on the user journey that matters most.

Traps

  • Still quoting First Input Delay as a Core Web Vital.
  • Reporting a single Lighthouse score as the performance state of the site.
  • Using averages instead of the 75th percentile.
  • Lazy-loading the LCP image or hiding it behind client-side rendering.
  • Ignoring CLS on pages that load fine on a fast desktop.

Likely follow-ups

How is INP different from FID?
FID measured only the delay before the first interaction’s handler; INP measures the full latency (to the next paint) of all interactions and reports a high percentile.
What is the LCP element on a typical page?
Usually the hero image or a heading block; find it in DevTools Performance or PageSpeed Insights and optimise that specific resource.
Why might field data be worse than lab data?
Real users have slower CPUs and networks, cold caches, extensions, and interact in ways the lab script does not.
How do you improve CLS caused by web fonts?
Preload the key font, use font-display: swap or optional with fallback metrics adjusted via size-adjust and ascent-override.

Loading performance and resource hints

“How do you make a page load faster? Explain preload, preconnect, prefetch, fetchpriority, critical CSS, defer/async, compression, CDNs and the effect of third-party scripts.”

Say this first (30 seconds)

“Loading performance is about shortening the critical path: get the first bytes quickly, discover important resources early, and avoid blocking rendering. I reduce server and network latency with a CDN, caching, compression and HTTP/2 or 3. I inline or prioritise critical CSS and defer the rest, load JavaScript with defer or modules and ship less of it. I help the browser with hints: preload for resources needed soon, preconnect for important third-party origins, fetchpriority to raise the LCP image, and prefetch for likely next navigations. I control third-party scripts, which are a major cause of slow pages, and I measure the waterfall to confirm the critical chain actually got shorter.”

Details interviewers probe

  • Server and network: reduce TTFB with caching (full-page, CDN, edge), fast data access, streaming HTML, HTTP/2 or 3, Brotli compression, keep-alive, and servers near users. Static and ISR pages served from a CDN beat dynamic rendering for TTFB (N1).
  • Render-blocking resources: CSS blocks rendering, synchronous scripts block parsing. Inline critical CSS (small, above-the-fold), load the rest with media tricks or preload-and-swap, split CSS per route, and use defer/type="module" for scripts (B1).
  • Preloading correctly: <link rel="preload" as="image" href imagesrcset> for the LCP image when it is not discoverable in HTML (CSS background, JS-injected); as="font" crossorigin for fonts (crossorigin is required even for same-origin). Unused preloads trigger warnings and waste bandwidth.
  • Priority hints: fetchpriority="high" on the LCP image, low on carousels’ off-screen images and non-critical scripts; browsers have defaults that you refine.
  • Preconnect limits: use for the two to four origins you need soon (API, font host, image CDN); each connection consumes resources. Consider self-hosting third-party assets to avoid new connections.
  • Prefetch and speculation: <link rel="prefetch"> for likely next resources; framework Link prefetching; the Speculation Rules API for prefetch/prerender of likely next pages with instant navigations verify browser support.
  • Reduce what you load: remove unused JavaScript and CSS (Coverage panel), lazy-load below-the-fold images and iframes, split bundles, avoid large fonts and icon libraries, and trim third-party tags (B6).
  • Third-party scripts: analytics, ads, chat, tag managers and A/B tools often dominate blocking time and CLS. Audit with the Network/Performance panels or Lighthouse’s third-party summary; load with async/defer, after interaction or idle; use facades (click-to-load YouTube or chat); self-host critical ones; use server-side tagging; set budgets and review owners.
  • Compression and formats: Brotli for text (pre-compress static assets), gzip fallback; minify JS and CSS; WebP/AVIF for images; WOFF2 for fonts; avoid huge JSON, and compress API responses.
  • Fonts in the critical path: preload the one or two fonts used above the fold, subset, font-display, self-host to avoid extra origins (F3).
  • Client-side rendering costs: JavaScript must download, parse, execute and fetch data before content appears; SSR/SSG, streaming and Server Components avoid that chain (N1, R11).
  • Measuring the result: DevTools waterfall (critical request chains), WebPageTest filmstrip and connection view, Lighthouse “Reduce unused” and “Render-blocking” audits; compare before and after on throttled mobile profiles.
  • Anti-patterns: CSS @import chains, JS-injected stylesheets, giant above-the-fold carousels, loading all fonts and weights, synchronous third-party tags in <head>, redirect chains (each costs a round trip), and no cache headers.

Traps

  • Preloading many resources and starving the truly critical ones.
  • Forgetting crossorigin on font preloads, so they are fetched twice.
  • Inlining so much CSS that HTML grows and cannot be cached.
  • Optimising the lab waterfall on a fast connection but not throttled mobile.
  • Adding a tag manager with no governance and then wondering why the page is slow.

Likely follow-ups

Preload versus prefetch?
Preload is high-priority for the current page; prefetch is low-priority for a future navigation.
How do you find render-blocking resources?
Lighthouse audit, DevTools Network “Priority” and the Performance panel; check stylesheets and synchronous scripts in the head.
How do you handle a tag manager that owns many scripts?
Governance (approval process), load after consent and idle, limit tags, monitor their cost, and consider server-side tagging.
Why do redirects hurt?
Each hop costs a full round trip plus potential connection setup; avoid chains and use direct canonical URLs.

Images, fonts and media

“How do you optimise images, web fonts, video and icons? Explain responsive images (srcset, sizes, <picture>), lazy loading, AVIF/WebP, font loading and layout shift.”

Say this first (30 seconds)

“Images are usually the largest bytes on a page, so I serve the right size and format: responsive srcset and sizes so the browser picks an appropriate width, modern formats such as AVIF or WebP with fallbacks, compression tuned by content, and dimensions on every image to avoid layout shift. Below-the-fold images use loading="lazy", but the LCP image is eager with high priority. A CDN with an image transformation service can resize and convert on demand. For fonts I use WOFF2, subset, self-host, preload only the critical ones, and use font-display with adjusted fallbacks to limit shift. Video gets proper encoding, poster images and lazy loading, and SVG or CSS replace raster icons where possible.”

Details interviewers probe

  • Choosing widths: generate a ladder of widths (for example 320, 640, 960, 1280, 1920) and let srcset with w descriptors and an accurate sizes do the selection; use x descriptors only for fixed-size images (1x, 2x). Do not serve a desktop 2000 px image to a phone.
  • Dimensions and aspect ratio: always set width and height attributes (modern browsers compute aspect-ratio from them) or use CSS aspect-ratio, so the layout reserves space (CLS).
  • Lazy loading: native loading="lazy" for images and iframes below the fold; never on the LCP image; decoding="async" to avoid blocking; for carousels and tabs, lazy-load hidden slides. IntersectionObserver for custom behaviour (J27).
  • Compression strategy: pick quality per content type (photography around quality 60 to 80 in AVIF/WebP), strip metadata, consider perceptual metrics (SSIM, Butteraugli), and automate in the build or at the CDN (Cloudinary, Imgix, Cloudflare Images, next/image) (N9).
  • Placeholders: dominant-colour or blurred low-quality placeholders (LQIP, BlurHash, ThumbHash) improve perceived performance; keep placeholder data tiny and avoid shifts.
  • Background images in CSS: not discovered by the preload scanner; for LCP use an <img> or preload; image-set() provides resolution switching.
  • Video: encode to H.264/H.265/AV1 and VP9, serve adaptive streaming (HLS/DASH) for long content, use preload="none" or metadata, poster images, playsinline muted loop for animation replacements, lazy-load below the fold, and facade embeds for YouTube to avoid loading heavy players upfront.
  • Icons: inline SVG or an SVG sprite with <use>; tree-shaken icon components; avoid whole-icon-font downloads; optimise SVG with SVGO; ensure accessible names.
  • Fonts, deeper: each additional weight or style is another file; subset by Unicode range (unicode-range) to load scripts only when needed; font-display: optional removes shift but may skip the custom font on first visit; preload with crossorigin; avoid blocking third-party font CSS (self-host Google Fonts or use next/font).
  • Layout shift from fonts: fallback font metrics differ; tune with size-adjust, ascent-override, descent-override, line-gap-override, or use frameworks that compute them automatically.
  • Caching and CDNs: immutable caching for fingerprinted images; Vary: Accept when negotiating format on the server; CDN image resizing with signed URLs to prevent abuse; set sensible limits and allowlists.
  • Accessibility: meaningful alt, empty alt for decorative images, captions for video, avoid text in images, prefers-reduced-motion for autoplaying animation.
  • Auditing: Lighthouse “Properly size images”, “Serve images in next-gen formats”, “Efficiently encode”, Network panel sizes and priorities, Squoosh for experiments, WebPageTest image analysis.

Traps

  • srcset without sizes on responsive layouts, so browsers assume full width.
  • Lazy-loading the hero image, delaying LCP.
  • Missing width and height, causing layout shift as images load.
  • Serving animated GIFs instead of video.
  • Loading six font weights for a design that uses two.

Likely follow-ups

How does the browser choose from srcset?
It calculates the needed pixel width from sizes and the device pixel ratio and picks the best candidate, also considering network conditions and cache.
AVIF or WebP?
AVIF compresses better but encodes slower; serve AVIF with WebP and JPEG fallbacks via <picture> or content negotiation.
How do you prevent font-related layout shift?
Preload critical fonts, adjust fallback metrics, subset, and choose swap or optional by tolerance.
Is lazy loading always good?
No: only for off-screen content. Above-the-fold and LCP images must load immediately.

JavaScript and main-thread performance

“How do you reduce JavaScript cost? What are long tasks and Total Blocking Time? How do you break up work, defer third-party code and reduce hydration cost? How do web workers help?”

Say this first (30 seconds)

“JavaScript is the most expensive resource byte for byte because it must be downloaded, parsed, compiled and executed on the main thread, which also handles input and rendering. So I ship less: code splitting, tree shaking, lighter dependencies, and moving work to the server with SSR and Server Components. I break long tasks, anything over 50 ms, into smaller chunks that yield to the browser using scheduler.yield or timeouts, defer non-critical and third-party code until after interaction or idle, reduce hydration with partial hydration and fewer client components, and move heavy computation to Web Workers. I confirm in the Performance panel using CPU throttling that long tasks are gone and Interaction to Next Paint improved.”

Details interviewers probe

  • Long tasks and TBT: a long task is any main-thread task over 50 ms; Total Blocking Time sums the portion beyond 50 ms between FCP and interactive in lab runs and correlates with INP. Find them in the Performance panel (red corner markers) and the Long Tasks / Long Animation Frames API verify LoAF support.
  • Yielding strategies: scheduler.yield() (continue with higher priority than other tasks), scheduler.postTask() with priorities, setTimeout or MessageChannel fallbacks, requestIdleCallback for low-priority work, and isInputPending() in specialised cases. Chunk loops, batch DOM updates, and avoid doing large work inside event handlers (J22).
  • Hydration costs: every client component must hydrate, executing component code and attaching handlers; large trees delay interactivity (INP). Reduce with Server Components, smaller client islands, lazy hydration on visibility or interaction, route-level code splitting, and avoiding rendering huge lists on first load (R11, N8).
  • Execution cost reduction: avoid expensive work at module load, memoise results, debounce and throttle handlers, use passive listeners, and avoid synchronous layout reads (B2). Prefer CSS to JavaScript for layout and animation.
  • Dependency hygiene: audit what is large (bundle analyser), replace moment/lodash/heavy UI kits, avoid duplicate libraries, check sideEffects, and lazy-load heavy features such as editors, charts and maps (B6, E11).
  • Third-party management: inventory and cost per tag; defer until after load or consent; use async; facade pattern; resource budgets; Partytown for web-worker execution (experimental); review contracts and remove unused tags regularly.
  • Code caching: browsers cache compiled code for scripts with stable URLs after repeat visits; avoid changing filenames unnecessarily and keep vendor chunks stable.
  • Modern syntax output: targeting modern browsers avoids transpilation overhead and polyfills, shrinking and speeding up code (B7).
  • Web Workers and Comlink: move non-UI work off thread; mind the message cost; reuse a pool; transfer large buffers (J23).
  • React-specific: avoid unnecessary re-renders (R5), use transitions and deferred values for expensive updates, virtualise lists, split routes, keep client state small, and measure with the Profiler.
  • Memory and GC pressure: allocations in hot paths trigger garbage collection pauses; leaks degrade performance over time (J24, J25).
  • Mobile reality: test on mid-range Android devices or use 4x to 6x CPU throttling; desktop machines hide problems; use field data segmented by device class.
  • Server alternatives: shifting work to the server (data shaping, rendering) reduces client execution; edge caching and streaming improve perceived speed.

Traps

  • Focusing on download size alone and ignoring parse and execution cost.
  • Testing only on a fast development machine.
  • Wrapping everything in useMemo instead of removing work or splitting code.
  • Treating third-party tags as outside engineering’s responsibility.
  • Moving work to a Web Worker without accounting for message-passing overhead.

Likely follow-ups

How do you find which script causes a long task?
Record a Performance profile; the flame chart attributes the task to functions and scripts, and the Bottom-Up tab ranks self time by source.
What is TBT and how does it relate to INP?
TBT is a lab measure of main-thread blocking during load; it correlates with INP, which measures real interaction latency in the field.
Defer, async or dynamic import for a non-critical script?
Dynamic import or idle loading for features; async/defer for independent scripts; choose by whether it is needed for first interaction.
How do you reduce hydration time?
Send less client code, use server rendering for static parts, lazy-hydrate below-the-fold components, and avoid large initial state payloads.

Interaction and rendering performance

“How do you make interactions feel instant? How do you keep scrolling and animation at 60 fps, optimise long lists, and use content-visibility, virtualisation and optimistic UI?”

Say this first (30 seconds)

“Interactions feel instant when feedback appears within about 100 milliseconds and the page stays responsive. I keep event handlers light, show immediate visual feedback, and defer expensive work. For rendering, I avoid layout thrashing, animate only transform and opacity so animations run on the compositor, use CSS containment and content-visibility to skip off-screen work, and keep the DOM small. Long lists are virtualised so only visible rows render. In React I use transitions, memoisation where it helps and optimistic UI so the interface reacts before the server answers. I verify smoothness with the Performance panel and INP.”

Details interviewers probe

  • Instant feedback patterns: pressed states and spinners within 100 ms, skeletons instead of blank areas, optimistic updates, preserving previous content while loading (stale-while-revalidate UI), prefetching on hover or viewport entry, and instant client-side navigation with prefetched data.
  • Handlers: keep them short; do heavy logic after the visual update with startTransition, requestAnimationFrame or idle callbacks; avoid synchronous storage or heavy JSON work; split rendering of large results; debounce search (J22).
  • Scrolling: use passive listeners, avoid layout reads in scroll handlers, prefer CSS (scroll-snap, position: sticky) and IntersectionObserver, avoid large fixed or blurred layers that repaint each scroll, and test with “paint flashing”.
  • Animation: compositor-friendly properties (transform, opacity), the Web Animations API or CSS, will-change sparingly, no layout-property animation, reduce motion via prefers-reduced-motion; FLIP technique for layout-change animation (B2).
  • Rendering containment: content-visibility: auto with contain-intrinsic-size skips rendering for off-screen sections; contain: layout paint isolates components; keeps style and layout recalculation local.
  • DOM size: large DOMs slow style, layout, memory and interaction; aim for fewer nodes, avoid deep nesting, virtualise lists and tables, paginate or “load more”, and avoid hidden but mounted heavy components.
  • Virtualisation caveats: variable heights need measurement, scroll position restoration, accessibility semantics, sticky headers, keyboard navigation and browser find-in-page limitations; sometimes pagination or server-side filtering is a better fix.
  • React interaction patterns: transitions for filtering large lists, useDeferredValue, memoised rows with stable props, avoiding context churn, keys that preserve DOM, Suspense boundaries for loading regions (R5, R9).
  • Forms and typing: keep controlled inputs fast (colocate state, uncontrolled libraries), avoid re-rendering the whole page per keystroke, debounce validation and search, and do not block typing on network.
  • Image decode and layout during interaction: avoid layout shifts after clicks (expanding sections smoothly with grid-template-rows transitions or measured heights).
  • Measure: Performance panel interactions, the Rendering tab (FPS meter, paint flashing, layer borders), INP attribution with the web-vitals library (which element and which phase), and Long Animation Frames data in RUM.
  • Perceived performance tricks: progressive loading, content placeholders, preloading next steps, animations that mask latency, and avoiding spinners for very short waits (flash of loading) with a small delay threshold.

Traps

  • Virtualising without handling accessibility and scroll restoration.
  • Animating height, top or box-shadow and blaming the device.
  • Optimistic UI without rollback and error messaging.
  • Putting expensive work inside scroll and input handlers.
  • Ignoring DOM size and then adding memoisation to compensate.

Likely follow-ups

How do you keep typing responsive while filtering a big list?
Keep input state urgent and defer the filtering render with a transition or deferred value, memoise rows, and virtualise the list.
What is the FLIP technique?
First, Last, Invert, Play: measure start and end positions, then animate the difference with transform to avoid layout-property animation.
When is content-visibility: auto risky?
It can shift scroll size when sections render (set contain-intrinsic-size) and hides content from find-in-page until rendered in some cases.
How do you diagnose a janky scroll?
Record while scrolling, look for long main-thread tasks, forced layouts and heavy paints, and check for non-passive handlers and large layers.

Measurement, monitoring and budgets

“How do you measure and monitor web performance? Lab versus field data, Lighthouse, WebPageTest, RUM, the web-vitals library, performance budgets and CI gating. How do you build a performance culture?”

Say this first (30 seconds)

“I combine lab and field data. Lab tools such as Lighthouse and WebPageTest run controlled tests, which are reproducible and good for diagnosing; field data from real users, through the Chrome User Experience Report or my own real-user monitoring with the web-vitals library, shows what customers actually experience and is what I report on, at the 75th percentile and segmented by device, network and page type. I set performance budgets for bundle size and metrics and enforce them in CI with Lighthouse CI or size limits, alert on regressions in production, and attribute problems to releases. Performance is a team habit: budgets in definition of done, dashboards everyone can see, and regular reviews, not a one-off project.”

Details interviewers probe

  • Lighthouse: lab audits on a throttled simulated device for performance, accessibility, best practices, SEO. Scores vary run to run; use medians of several runs, run in CI (Lighthouse CI) and compare against a baseline rather than chasing 100. It reports metrics plus opportunities and diagnostics.
  • WebPageTest: real browsers, locations and devices, filmstrip and waterfall, connection throttling profiles, repeat view, scripting, comparison tests, and Core Web Vitals metrics; excellent for diagnosing the critical path and third parties.
  • CrUX and PageSpeed Insights: Chrome User Experience Report provides 28-day field data at origin and URL level for Chrome users; PSI combines CrUX with a Lighthouse run. Limited to sufficient traffic and Chrome; useful for competitor benchmarks.
  • web-vitals library: onLCP, onINP, onCLS, onTTFB, onFCP report values with attribution builds that tell you which element or event caused the problem; send to analytics or a RUM backend using navigator.sendBeacon when the page becomes hidden (J31).
  • Browser APIs: PerformanceObserver (paint, LCP, layout-shift, event, longtask, long-animation-frame, resource entries), Navigation Timing and Resource Timing for network breakdown, User Timing marks and measures, Server-Timing headers to expose backend durations in the browser.
  • Budgets: choose targets from user need and competitors: for example JavaScript under 170 KB gzipped on critical routes, LCP under 2.5 s at p75 on mobile, no long task over 200 ms on key flows. Types: quantity (bytes, requests), timing (metrics), and rule-based (Lighthouse score). Enforce with size-limit, bundlewatch, Lighthouse CI assertions, and webpack/Vite performance hints.
  • Segmenting RUM data: by device memory and CPU class, connection type, country, browser, logged-in state, page template, A/B variant and release; the worst segments reveal problems averages hide. Compare before and after deploys with release tags.
  • Alerting: thresholds on p75 or p90 regression percentages, not individual spikes; link alerts to deploys; keep SLOs (for example 75% of mobile sessions with good LCP) and use error budgets to prioritise work.
  • Investigation workflow: start from RUM to find the worst page and segment; reproduce in the lab with matching throttling; profile; fix; verify in CI; release; confirm in field data after enough traffic (CrUX lags by weeks).
  • Synthetic monitoring: scheduled tests of critical journeys from several regions (Checkly, Datadog Synthetics, SpeedCurve) detect outages and regressions even with low real traffic.
  • Culture and process: include performance in design reviews and PR templates, share a dashboard, celebrate wins, assign owners per metric, run periodic audits of third-party tags and bundle growth, and educate with examples. Present business impact (conversion, SEO) to prioritise.
  • Pitfalls in measurement: cold versus warm cache, test device differences, extensions, A/B tests altering pages, bot traffic, ignoring soft navigations in SPAs, and sampling bias.
  • Privacy: RUM must avoid personal data, honour consent policies and keep retention limits.

Traps

  • Reporting a Lighthouse score from one run as truth.
  • Optimising for lab metrics while field p75 stays poor.
  • Budgets that nobody enforces automatically.
  • Collecting RUM without segmentation or release tags.
  • Declaring victory before field data has had time to update.

Likely follow-ups

How do you set a performance budget?
Derive from user goals and competitor data, split by route and device class, express in bytes and metrics, and enforce in CI with alerts in production.
How do you find the cause of a poor INP in the field?
Use the web-vitals attribution build to log the interaction target and phase breakdown, then reproduce with CPU throttling.
Why can PSI show different numbers from DevTools?
PSI mixes field data (CrUX) with a simulated lab run; DevTools runs on your machine and network.
What is Server-Timing?
A response header that exposes backend phase durations to the browser’s Performance API for end-to-end analysis.

Caching and delivery strategies

“Which caching layers can improve frontend performance? How do HTTP caching, CDN caching, service worker caching and application caching work together? How do you cache an SPA, an API, and HTML?”

Say this first (30 seconds)

“Caching works in layers, and each request should be answered by the nearest layer that is still correct. The browser HTTP cache and the service worker cache serve repeat visits instantly; the CDN serves users from the edge without reaching the origin; the server or reverse proxy caches rendered pages and API results; and in the application, libraries like TanStack Query and memoisation avoid recomputing. Immutable, content-hashed assets get year-long caching; HTML and APIs get short lifetimes with revalidation or stale-while-revalidate; personal data is never cached in shared layers. The hardest part is invalidation, so I design URLs and tags so that changes are visible quickly without purging everything.”

Details interviewers probe

  • HTTP cache directives and CDN behaviour: covered in P3: max-age, s-maxage, immutable, stale-while-revalidate, ETag, Vary. Know the standard recipes by heart.
  • CDN features: edge caching, cache keys and normalisation, tiered caching and origin shield, stale-if-error for resilience, purge by URL/tag/prefix, edge compute (Workers, Lambda@Edge) for rewrites, A/B tests and auth, image optimisation, DDoS protection. Choose TTLs per content type; confirm cache hit ratio in analytics.
  • Caching HTML for SPAs and SSR: an SPA shell can be CDN-cached with short TTL or revalidation; SSR pages can be cached at the edge with s-maxage and tags when not personalised (N5); never cache pages containing user data without keys.
  • API caching: GET with ETag and conditional requests; Cache-Control: public, max-age for public data; CDN caching for read-heavy endpoints; separate personalised endpoints; GraphQL needs persisted queries and GET to cache at the edge.
  • Client data caches: TanStack Query/SWR/RTK Query as the layer above HTTP: dedupe in-flight requests, staleTime, background refetch, invalidation after mutations, persistence to IndexedDB for offline (E4).
  • Service worker cache: pre-cache the app shell at install; runtime caching strategies for assets and API responses; versioned cache names; cleanup in activate; remember both service worker and HTTP caches may apply (F9).
  • Back/forward cache: whole-page restoration for instant back navigation; avoid unload handlers and open connections that block it (J31).
  • Memoisation and computation caches: useMemo, selectors, server-side memoisation, React.cache; cache keys must include all inputs; bound the size (LRU) to avoid leaks (J25).
  • Cache invalidation strategies: versioned URLs (cheapest), time-based expiry, event-based purge (webhook on content change), tag-based invalidation, write-through updating, and “stale but fresh enough” with SWR. Be explicit about acceptable staleness per data type.
  • Cache stampede and resilience: when a hot item expires, many requests hit the origin; mitigate with request coalescing at the CDN, jittered TTLs, stale-while-revalidate and locks in application caches.
  • Security of caching: avoid caching personalised content in shared caches, beware cache poisoning via unkeyed headers and cache deception (caching a private page under a static-looking URL), use Vary and private correctly (P3).
  • Observability: track cache hit ratio, TTFB by hit/miss, origin load, error rates; headers like Age, X-Cache; compare pre- and post-change performance.
  • Edge and regionality: caching improves latency only if the content can be shared; for dynamic data put compute near the database or replicate data; know the speed-of-light limits.

Traps

  • Caching personalised responses at the CDN and leaking them to other users.
  • Long cache lifetimes on mutable, non-versioned URLs.
  • Adding caches without measuring hit ratio, so they add complexity but little benefit.
  • Forgetting that a service worker adds another layer that can serve stale content.
  • Believing a purge fixes browsers that already cached the resource for a year.

Likely follow-ups

How do you roll out new frontend code safely with caching?
Hashed assets are immutable; revalidated HTML points to them; keep previous assets for skew; deploy progressively.
How do you cache a personalised page?
Cache the static shell and fetch or stream the personalised parts separately, or vary the cache key per user segment, never the whole page keyed on cookies.
What is a cache stampede?
Many simultaneous requests for an expired hot key overload the origin; coalescing and SWR prevent it.
How do you measure whether caching helps?
Hit ratio, origin request reduction, TTFB distribution for hits versus misses, and user-facing metrics.

PWA fundamentals

“What is a Progressive Web App? What makes it installable? Explain the web app manifest, service workers, HTTPS, offline support, push notifications, and PWA versus native apps. What are the platform limitations?”

Say this first (30 seconds)

“A Progressive Web App is a web app enhanced to behave like an installed app: it is reliable through a service worker that handles offline and flaky networks, fast through caching, and installable, with its own icon and standalone window. The core pieces are HTTPS, a web app manifest describing name, icons, start URL and display mode, and a service worker. Optional capabilities include push notifications, background sync and file handling. PWAs give one codebase across platforms with web distribution and no store review, but have limits: less access to device APIs than native, and iOS historically lagged in push and storage. I adopt PWA features progressively where they add value, such as offline reading or fast repeat visits.”

Details interviewers probe

  • Characteristics: reliable (loads instantly, works offline or on poor networks), fast, engaging (installable, notifications), progressive (works for all browsers), responsive, secure (HTTPS), linkable. Think enhancement, not a separate product.
  • Web app manifest: JSON linked by <link rel="manifest">: name, short_name, icons (including maskable), start_url, scope, display (standalone, minimal-ui, fullscreen, browser), orientation, theme_color, background_color, shortcuts, screenshots (richer install UI), id, display_override, share_target, file_handlers.
  • Install experience: browsers show an install affordance when criteria are met; the beforeinstallprompt event (Chromium) lets you offer a custom install button; appinstalled event; detect standalone with display-mode media query; iOS Safari requires manual “Add to Home Screen” (and has its own meta tags).
  • Offline and caching: service worker pre-caches an app shell and serves cached or fallback pages; combine with IndexedDB for data; show offline state clearly (F9, F10).
  • Push notifications: Push API with a push service (FCM, APNs through browsers), VAPID keys, service worker push and notificationclick events, permission prompt design (ask in context). Support: broad on Android/desktop; iOS and iPadOS 16.4+ for installed PWAs only verify current.
  • Background capabilities: Background Sync (retry sends when online), Periodic Background Sync, Background Fetch (large downloads), badges (navigator.setAppBadge), file handling, share target, protocol handlers; many are Chromium-only; always feature-detect (J31).
  • Storage: quotas per origin, eviction under pressure unless persisted (navigator.storage.persist()); Safari clears script-writable storage after a period without use for non-installed sites; design for data loss with server sync.
  • PWA versus native trade-offs: one codebase and instant updates versus limited hardware APIs, store presence and background processing; wrappers (Capacitor, TWA for Play Store, PWABuilder for Microsoft Store) allow store distribution of PWAs.
  • Business cases: faster repeat visits, higher engagement and conversion (many published case studies), offline access for field workers, lower acquisition friction than installs.
  • Testing and auditing: Lighthouse no longer has a PWA category in recent versions (installability checks moved to DevTools Application panel); test on real devices, offline mode, throttling, and install flows verify tooling.
  • Frameworks and tooling: Workbox (service worker libraries), vite-plugin-pwa, next-pwa/Serwist, Angular service worker (ng add @angular/pwa), PWABuilder.
  • Security and privacy: service workers need HTTPS and are powerful (intercept requests), so prevent XSS and supply-chain compromises; scope narrowly; handle user data in caches carefully (do not cache authenticated responses unsafely); clear caches on logout.

Traps

  • Equating PWA with “offline only” or assuming it needs a framework.
  • Prompting for notification permission on first load.
  • Assuming iOS behaves like Android for push, storage and install.
  • Caching authenticated or personalised responses in the service worker without cleanup on logout.
  • Promising native-level capabilities that the web platform cannot deliver.

Likely follow-ups

What makes a site installable?
HTTPS, a valid manifest with name, icons and start URL, and a display mode of standalone or similar; browsers may add engagement heuristics.
When would you choose a PWA over a native app?
When web reach, fast iteration and one codebase matter more than deep device integration or store-only requirements.
How do you ask for push permission well?
After the user takes a related action, explain the value, and respect denial; never at page load.
How do users update a PWA?
The browser checks for a new service worker on navigation; you control activation and can prompt to reload (F9).

Service workers in depth

“Explain the service worker lifecycle: install, waiting, activate. What are caching strategies? How do you handle updates and avoid stale content? What is Workbox? What are the pitfalls?”

Say this first (30 seconds)

“A service worker is a script that runs separately from the page and acts as a programmable network proxy for the pages it controls. Its lifecycle has distinct phases: it is registered, then installs, where I pre-cache the app shell; then a new version waits until old versions’ pages close, unless I skip waiting; then it activates, where I clean old caches and may claim open pages. Once active it intercepts fetch events, and I choose strategies per request type: cache-first for versioned assets, network-first for HTML and fresh data, stale-while-revalidate for content that can be slightly old. Workbox provides tested implementations. The main pitfalls are serving stale code, caching errors, and not planning the update flow, so I version caches, prompt users to reload, and test updates carefully.”

Details interviewers probe

  • Registration and scope: navigator.serviceWorker.register('/sw.js', { scope: '/' }) after page load (load event) to avoid competing with startup; the worker controls pages under its scope (path of the script by default); one registration per scope; HTTPS required (localhost allowed).
  • Install event: event.waitUntil(caches.open('v3').then(c => c.addAll([…]))) pre-caches the shell; failure of any request fails installation (use only essential files). Build tools generate the precache manifest with content hashes (Workbox injectManifest/generateSW).
  • Waiting and activation: a new worker waits while pages use the old one. self.skipWaiting() activates immediately; clients.claim() takes control of open pages. Doing both without coordination can mix new worker logic with old page code and break pages: reload the page after activation or version messages. Provide a UI prompt using the waiting state and postMessage.
  • Activate event: delete caches not in the current allowlist, migrate IndexedDB data, enable navigation preload (registration.navigationPreload.enable()) so network requests start while the worker boots.
  • Fetch event: event.respondWith(...) with a strategy; match by URL, request destination and mode; clone responses before caching (response.clone()); only cache OK responses; avoid caching POST; handle range requests for media carefully.
  • Update flow design: detect updates with registration.onupdatefound; show a toast; on accept send SKIP_WAITING; on controllerchange reload; ensure sw.js itself is served with Cache-Control: no-cache; periodically call registration.update() in long-lived tabs.
  • HTML and app shell: caching HTML cache-first can trap users on old versions; use network-first or revalidate with a version check; precache hashed assets matched with the current HTML.
  • Offline fallback: precache /offline.html and return it for navigation requests that fail; for data, serve last-known data with an “offline” indicator and queue writes.
  • Background Sync and queues: Workbox Background Sync plugin retries failed POSTs when connectivity returns; handle duplicates with idempotency keys; limited browser support, so provide a fallback queue in IndexedDB.
  • Communication: postMessage between page and worker, MessageChannel, BroadcastChannel, clients.matchAll() to notify all tabs (e.g., update ready).
  • Lifecycle limits: the worker is terminated when idle and restarted on events, so keep no state in global variables; use IndexedDB or caches for persistence; keep startup fast.
  • Debugging: DevTools → Application → Service Workers (status, update on reload, bypass for network, unregister), Cache Storage inspector, offline checkbox; chrome://serviceworker-internals; test update flows with two versions, and test first-visit and repeat-visit separately.
  • Workbox and tooling: strategies (CacheFirst, NetworkFirst, StaleWhileRevalidate), plugins (expiration, cacheable response, broadcast update), precaching with revisioning, build integrations (Vite PWA, webpack plugin, Next.js via Serwist). Kill-switch service worker: ship a worker that unregisters itself if something goes wrong.
  • Security: a compromised or buggy service worker affects all visits; protect deployment, avoid importing third-party scripts into the worker, and never cache sensitive responses unsafely; clear caches and unregister on logout where appropriate.
  • When not to use one: simple marketing pages with good HTTP caching may not need a service worker; its complexity and update risk must be justified by offline or push needs.

Traps

  • Caching sw.js or index.html aggressively, so users cannot receive updates.
  • Calling skipWaiting and clients.claim blindly and breaking open pages mid-session.
  • Forgetting to clone responses before caching them.
  • Caching error responses or opaque cross-origin responses.
  • Shipping without a kill switch or update plan.

Likely follow-ups

Why does a new service worker “wait”?
To avoid replacing the worker controlling open pages mid-session; it activates when old clients close or when you skip waiting.
Which strategy for an API call?
Network-first with a short timeout for fresh data, or stale-while-revalidate for tolerable staleness, with offline fallback.
How do you roll back a broken service worker?
Deploy a fixed or no-op worker that deletes caches and unregisters, served with no-cache headers.
Service worker versus HTTP cache?
HTTP cache follows server headers; the service worker is programmable and can serve offline, apply custom strategies and intercept all requests.
F10Added

Resilience: slow networks, low-end devices, offline UX

“How do you design for slow networks, low-end devices and offline use? What are adaptive loading and Save-Data? How do you handle offline data sync and conflicts? How do you balance performance work against business priorities?”

Say this first (30 seconds)

“Many users have slow, flaky networks and low-end phones, so I design for the median real user, not my laptop. I set budgets for bytes and CPU, test with throttled network and CPU and real devices, and adapt: serve lighter assets under Save-Data or slow connections, avoid heavy JavaScript and animation on weak devices, and keep the core experience working without JavaScript where feasible. For offline I use a service worker for the shell and cached content, store data locally, queue writes with idempotency keys, show clear connectivity state, and sync with conflict handling when back online. I prioritise performance work by impact on key journeys and business metrics, and I communicate trade-offs rather than treating speed as an absolute.”

Details interviewers probe

  • Who your users are: global audiences on mid-range Android phones with 3G/4G, high latency, data caps and throttled CPUs; the performance of “the 75th percentile device” defines success. Use field data segmented by device class (device memory, CPU cores) and connection type.
  • Network resilience: retries with backoff and timeouts, request deduplication, small payloads (pagination, field selection), compression, caching (F7), progressive loading, optimistic UI, avoiding waterfalls, and handling partial failures gracefully with inline error and retry.
  • Adaptive loading: use Save-Data header and navigator.connection.saveData/effectiveType (Chromium) and deviceMemory as hints, serve lower image quality or fewer features, skip autoplay and prefetch, and allow users to choose “lite mode”. Respect prefers-reduced-motion. Treat signals as hints; never block features entirely based on them.
  • Low-end device strategy: less JavaScript, avoid large DOMs and heavy animations, reduce hydration, virtualise lists, use CSS for effects, avoid memory spikes, and test thermal and memory-constrained behaviour; consider server rendering and static content for core flows.
  • Progressive enhancement: core content and actions work with HTML and links/forms; JavaScript enhances. Server rendering plus progressive enhancement gives resilience when scripts fail to load on poor networks (N8).
  • Offline UX: offline page and cached last-seen data; indicators for connectivity and sync; disable actions that cannot work offline with explanation; queue allowed actions; avoid error toasts for expected offline states; test airplane mode and “lie-fi” (connected but unusable), which is the hardest case.
  • Local persistence: IndexedDB for structured data (libraries: Dexie, idb, RxDB, PouchDB), Cache Storage for responses, OPFS for large files; manage quotas and eviction, encrypt sensitive data where needed, and clear on logout (J30).
  • Sync and conflict resolution: choose per data type: last-write-wins (simple, loses edits), field-level merges, operational transforms or CRDTs for collaborative text, server-authoritative with user resolution UI. Use version numbers or ETags for optimistic concurrency and idempotency keys to avoid duplicates.
  • Background sync limits: Background Sync is Chromium-only; provide a manual retry and sync when the app opens; keep queues bounded.
  • Performance versus business trade-offs: quantify impact (conversion by LCP bucket, bounce rates), map to revenue; propose staged improvements with measurable outcomes; negotiate budgets for third-party tags and marketing assets; protect critical journeys (checkout, login) first; document decisions.
  • Sustainability angle: less data and CPU means lower energy use and cost; mention as a secondary benefit.
  • Accessibility intersection: slow and low-end users overlap with assistive tech users; keep interfaces simple, stable and keyboard operable; avoid motion and layout shift.
  • Emerging markets and constraints: data cost sensitivity, intermittent power, shared devices; lite apps, image-light modes and clear data-use controls matter.

Traps

  • Trusting navigator.onLine as the truth about connectivity.
  • Offline-first without a conflict strategy, silently overwriting user data.
  • Testing performance only on a fast network and a developer laptop.
  • Gating features on connection hints that are unavailable in many browsers.
  • Treating performance as purely technical and not linking it to user and business outcomes.

Likely follow-ups

How do you test “lie-fi”?
Throttle or drop packets with network conditioning tools or DevTools custom profiles, set request timeouts, and verify the UI shows retryable errors rather than hanging spinners.
How do you resolve edit conflicts offline?
Choose by data type: last-write-wins for preferences, field-level merge for forms, CRDTs for collaborative text, and user-mediated resolution for critical conflicts.
How do you justify performance work to product owners?
Show the link between metric buckets and conversion or retention, estimate effort, and propose a measurable target on key journeys.
What do you do for a user on Save-Data?
Serve lighter images and fewer third-party scripts, avoid autoplay and prefetch, and keep core functionality intact.

How to answer performance questions at L4
