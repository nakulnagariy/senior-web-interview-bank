HTTP/1.1, HTTP/2 and HTTP/3

“What are the differences between HTTP/1.1, HTTP/2 and HTTP/3? What is multiplexing and head-of-line blocking? Explain methods, status codes, idempotency and important headers.”

Say this first (30 seconds)

“HTTP/1.1 sends one request at a time per connection, so browsers open several connections and still suffer head-of-line blocking at the application level. HTTP/2 keeps one TCP connection and multiplexes many streams over it as binary frames, compresses headers with HPACK, and lets the server prioritise streams, which removes the need for tricks like domain sharding and sprite sheets. But because it runs on TCP, one lost packet stalls all streams. HTTP/3 runs over QUIC on UDP, with streams that are independent at the transport level, built-in TLS 1.3, faster connection setup with 0-RTT and connection migration when the network changes. Semantics stay the same across versions: methods, status codes and headers.”

Details interviewers probe

  • HTTP/1.1: persistent connections (keep-alive), chunked transfer encoding, Host header (virtual hosting), pipelining (rarely used because of head-of-line blocking). Optimisations: domain sharding, concatenation, sprites, inlining.
  • HTTP/2: binary framing, multiplexed streams, HPACK header compression, prioritisation (weaker in practice, replaced by Extensible Priorities), flow control, server push (deprecated and removed from Chrome; use preload and 103 Early Hints verify). Concerns: TCP-level head-of-line blocking, one connection per origin (so coalescing across hostnames can help).
  • HTTP/3 and QUIC: transport on UDP implemented in user space; per-stream loss recovery; 1-RTT handshake (0-RTT for resumed connections, with replay caveats); connection IDs allow migration; congestion control per connection. Deployment requires server and CDN support; enterprise firewalls sometimes block UDP, hence fallback.
  • Methods and idempotency: safe methods do not change state (GET, HEAD, OPTIONS); idempotent methods give the same result when repeated (GET, PUT, DELETE); POST is not idempotent, so retries need idempotency keys. This matters for retry logic and caching (E9).
  • Status codes to know cold: 200 OK, 201 Created (with Location), 204 No Content, 301/308 permanent redirects, 302/307 temporary, 304 Not Modified (conditional request), 400 Bad Request, 401 Unauthorized (unauthenticated), 403 Forbidden (authenticated but not allowed), 404, 409 Conflict, 422 Unprocessable, 429 Too Many Requests (Retry-After), 500, 502, 503, 504.
  • Redirect semantics: 301 and 302 may change POST to GET in clients; 307 and 308 preserve the method and body. Prefer 308/307 for APIs; 301 for SEO moves of pages.
  • Important request headers: Accept, Accept-Encoding, Accept-Language, Authorization, Cookie, Origin, Referer, User-Agent, Content-Type, If-None-Match. Response: Content-Type, Content-Encoding, Cache-Control, ETag, Set-Cookie, Location, Vary, CORS and security headers.
  • Content negotiation and compression: Accept-Encoding: br, gzip and Content-Encoding; Brotli for text; Vary: Accept-Encoding so caches store per encoding. Media types and charset in Content-Type.
  • Range requests and streaming: Range/206 Partial Content for video seeking and resumable downloads; chunked/streamed responses for server-rendered HTML and large data.
  • Connection performance: keep-alive, connection reuse, preconnect, CDNs terminating TLS near users, fewer round trips; HTTP/2 or 3 mostly helps when many parallel requests exist.
  • Debugging: DevTools Network “Protocol” column, curl -v --http2/--http3, WebPageTest, Wireshark with key log for deep dives.

Traps

  • Saying HTTP/2 solves head-of-line blocking entirely. It removes it at the HTTP layer but TCP still blocks.
  • Continuing HTTP/1.1-era hacks (sharding, giant bundles) as if they still help.
  • Mixing up 401 and 403, or using 200 with an error body.
  • Believing HTTP/3 is “faster” for all cases; gains are largest on lossy or high-latency networks.
  • Retrying non-idempotent POST requests blindly.

Likely follow-ups

Why was HTTP/3 built on UDP?
TCP is implemented in operating systems and middleboxes and is hard to change; QUIC on UDP evolves in user space and gives independent streams.
401 versus 403?
401: not authenticated (missing or invalid credentials). 403: authenticated but not permitted.
How does a browser learn a site supports HTTP/3?
Through the Alt-Svc header (or DNS HTTPS records) after a first HTTP/2 connection, then it tries QUIC.
PUT versus PATCH?
PUT replaces the whole resource and is idempotent; PATCH applies a partial change, idempotency depends on the patch semantics.
P2Added

DNS, TCP, TLS: the network path

“What happens at the network level when a browser loads an HTTPS page? How do DNS, the TCP handshake and the TLS handshake work? What do HSTS, CDNs and preconnect do?”

Say this first (30 seconds)

“First the browser resolves the hostname to an IP address through DNS, checking its own cache, the operating system and a recursive resolver. Then it opens a TCP connection with a three-way handshake, and on top of it a TLS handshake: the client and server agree on a cipher, the server proves its identity with a certificate chained to a trusted authority, and they derive session keys, so everything after is encrypted and tamper-evident. TLS 1.3 needs one round trip, and QUIC combines transport and TLS. Only then is the HTTP request sent. Each step costs round trips, so we reduce latency with CDNs close to users, connection reuse, preconnect, HTTP/2 or 3, and HSTS ensures browsers use HTTPS from the first request.”

Details interviewers probe

  • DNS: hierarchical (root, TLD, authoritative). Records: A/AAAA (IP), CNAME (alias), MX, TXT, NS, HTTPS/SVCB. Caching by TTL at browser, OS, resolver. Lowering TTL before a migration enables faster cutover. DNS can be a performance and availability dependency; use a reliable provider and consider DNS over HTTPS for privacy.
  • TCP: reliable ordered byte stream; three-way handshake; slow start and congestion control mean new connections start slowly; connection reuse avoids repeated handshakes. TCP Fast Open and QUIC reduce setup costs.
  • TLS handshake: negotiation of protocol version and cipher suite, key exchange (ephemeral Diffie-Hellman gives forward secrecy), certificate verification (chain to a trusted CA, hostname match, validity, revocation via OCSP stapling or CRLite), then symmetric encryption (AES-GCM, ChaCha20). TLS 1.3 removes legacy ciphers, reduces the handshake to one round trip, and supports 0-RTT resumption (replayable, so only for idempotent requests).
  • Certificates: issued by CAs (Let’s Encrypt automates free certificates); SANs list hostnames; wildcard certificates; expiry causes outages, so automate renewal and monitor. Certificate Transparency logs help detect mis-issuance.
  • HTTPS benefits: confidentiality, integrity, authentication of the server; required for HTTP/2 and 3, service workers, geolocation, clipboard, and secure cookies; also ranking and trust signals.
  • HSTS: Strict-Transport-Security: max-age=31536000; includeSubDomains; preload tells browsers to use HTTPS only, preventing downgrade and cookie hijacking on first visits when preloaded. Misconfiguration with includeSubDomains can break HTTP-only subdomains.
  • Mixed content: loading HTTP subresources on an HTTPS page is blocked or upgraded; fix URLs and use upgrade-insecure-requests in CSP as a safety net.
  • Latency reduction: CDNs and edge termination; <link rel="preconnect"> and dns-prefetch for critical third-party origins; fewer origins; keep-alive; HTTP/2 or 3; TLS session resumption; OCSP stapling; compressing responses; place servers near users and near data.
  • CDN role: caches static content at the edge, terminates TLS close to users, absorbs traffic spikes and DDoS, optimises routes to the origin, and can run edge logic. Cache keys, purging and headers determine behaviour (P3).
  • Proxies and load balancers: reverse proxies (nginx, Envoy), TLS termination, sticky sessions, health checks, X-Forwarded-For and Forwarded headers; WebSockets need upgrade support.
  • Debugging the path: dig/nslookup, curl -v with timing (-w), openssl s_client, DevTools timing breakdown (DNS, Initial connection, SSL, TTFB), SSL Labs for configuration review.
  • Security threats at this level: man-in-the-middle (stopped by valid TLS), DNS spoofing (DNSSEC, DoH), certificate misuse, downgrade attacks (HSTS), and expired certificates causing outages.

Traps

  • Saying TLS “encrypts the URL”: the host name is visible (SNI) though paths and bodies are encrypted; Encrypted Client Hello is emerging.
  • Letting certificates expire because renewal is manual.
  • Setting HSTS preload or includeSubDomains without checking all subdomains.
  • Over-using preconnect to many origins; each connection costs CPU and battery.
  • Ignoring DNS TTL when planning a cutover.

Likely follow-ups

How does the browser know to trust a certificate?
It validates the chain up to a root CA in its trust store, checks hostname, validity period and revocation status.
What is forward secrecy?
Ephemeral session keys mean a later compromise of the server’s private key cannot decrypt past recorded traffic.
What does a CDN do for dynamic content?
It terminates connections near users and reuses optimised connections to the origin, and can cache short-lived or personalised-by-key responses.
How would you speed up a slow first request?
Examine DNS, connect and TLS timings; use a CDN, HTTP/3, preconnect, and a faster server response with caching.
P3Added

HTTP caching

“How does HTTP caching work? Explain Cache-Control, ETag, conditional requests, Vary, stale-while-revalidate and how you cache an SPA and an API. How do you bust caches?”

Say this first (30 seconds)

“HTTP caching lets browsers and intermediaries reuse responses. The server controls it with Cache-Control: max-age says how long a response is fresh; within that time the browser uses it without contacting the server. When it expires, the browser revalidates with a conditional request using If-None-Match and the ETag, and the server answers 304 Not Modified with no body if unchanged. no-store forbids storing, no-cache means store but always revalidate, private restricts to the browser, public allows shared caches such as CDNs. For static assets I use content-hashed filenames with a year-long immutable lifetime; for HTML I revalidate. Vary tells caches which request headers change the response.”

Details interviewers probe

  • Cache layers: browser memory and disk cache, service worker cache, CDN edge, reverse proxy, application cache. A response may be served from any of them; know which you control with headers.
  • Cache-Control directives: max-age (browser freshness), s-maxage (shared caches), no-store (do not store), no-cache (store, but validate before use), must-revalidate (do not serve stale after expiry), public/private, immutable (will not change during freshness; skip revalidation on reload), stale-while-revalidate (serve stale while refreshing in the background), stale-if-error. The older Expires header and Pragma are superseded.
  • Validation: ETag (strong or weak W/"…") with If-None-Match; Last-Modified with If-Modified-Since. A 304 saves bandwidth but still costs a round trip, so long freshness plus fingerprinting beats frequent revalidation.
  • Heuristic caching: without explicit directives, caches may guess freshness from Last-Modified (a fraction of its age), causing surprising stale content; always set Cache-Control explicitly.
  • Cache busting: change the URL when content changes: content hashes in filenames (best), version query strings (less reliable with some CDNs), and revalidating HTML so it points to new asset names (B10). Purging a CDN is for emergencies, not routine releases.
  • Vary and cache keys: shared caches key on URL plus the headers named in Vary. Excessive variation (User-Agent, Cookie) fragments the cache; normalise at the CDN (device class, language).
  • CDN caching: CDNs honour s-maxage; cache key rules (ignore tracking query params), cache tags and surrogate keys for targeted purges, tiered caching, and origin shield; dynamic pages can use short TTL with stale-while-revalidate. Do not cache responses with Set-Cookie accidentally.
  • API caching: GET only; ETags for conditional requests; consistent query-string ordering; short TTLs for volatile data; use client-side caches (TanStack Query) on top; mutations must invalidate or version (E4).
  • Reload behaviour: normal navigation uses fresh entries; reload revalidates the main resource; hard reload bypasses cache; immutable prevents revalidation of subresources on reload in supporting browsers.
  • Back/forward cache: separate from the HTTP cache; no-store historically blocked it (P7, J31).
  • Service worker caching: programmatic strategies (cache-first, network-first, stale-while-revalidate) layered above the HTTP cache; remember both layers apply (performance guide).
  • Security and privacy: do not cache personalised or sensitive responses in shared caches (private or no-store); cache poisoning through unkeyed headers is an attack class; avoid reflecting unkeyed headers in cacheable responses.
  • Debugging: DevTools “Size” column (from memory cache, disk cache, service worker), Age and X-Cache/CF-Cache-Status headers, curl -I twice, and testing with cache disabled and enabled.

Traps

  • Believing no-cache means “do not cache”. It means “validate before reuse”; no-store forbids storing.
  • Long max-age on a non-hashed filename, trapping users on old code.
  • Caching HTML for a long time while hashed assets change, or the opposite.
  • Adding Vary: Cookie or User-Agent to a cacheable page and killing the hit ratio.
  • Sending cache headers on personalised responses through a shared CDN.

Likely follow-ups

How do you roll out a new JavaScript bundle?
Content-hashed filename with a year-long immutable lifetime, and revalidated HTML referencing it.
What is the point of stale-while-revalidate?
Users get an instant (slightly stale) response while the cache refreshes in the background, hiding latency.
ETag versus Last-Modified?
ETag is a content validator (more precise, works for dynamic content); Last-Modified is time-based with one-second resolution.
How do you cache an API without serving stale personal data?
Use private or no CDN caching for user-specific responses, vary or key by user where appropriate, and short TTL for shared data.

Real-time protocols and API styles

“How do WebSockets work? Compare WebSockets, Server-Sent Events, long polling, WebRTC and webhooks. How do REST, GraphQL and gRPC differ at the protocol level? How do you scale real-time connections?”

Say this first (30 seconds)

“A WebSocket starts as an HTTP request with an Upgrade header; if the server agrees, the connection becomes a persistent full-duplex channel where either side can send messages, framed over TCP, with no per-message HTTP overhead. Server-Sent Events are simpler: a long-lived HTTP response for one-way server-to-client text events with automatic reconnect. Long polling and plain polling use ordinary requests. WebRTC provides peer-to-peer audio, video and data with signalling through a server and NAT traversal. Webhooks are server-to-server callbacks. For scale, real-time connections are stateful, so I use sticky or connection-aware load balancing, a pub/sub backbone like Redis or a managed service so any node can broadcast, heartbeats, and backpressure handling.”

Details interviewers probe

  • WebSocket protocol: handshake via HTTP/1.1 Upgrade; after 101 it is a framed message protocol over the same TCP connection; subprotocols (Sec-WebSocket-Protocol); no built-in reconnect, ordering across reconnects, or authentication beyond what you add. Over HTTP/2 and 3 there are extended CONNECT variants.
  • Security of WebSockets: validate the Origin header server-side (cross-site WebSocket hijacking), authenticate and authorise on connect and per message, use wss://, limit message size and rate, sanitise payloads, avoid tokens in URLs (they are logged).
  • Server-Sent Events: EventSource, text/event-stream, automatic reconnect with Last-Event-ID; limited to GET (use fetch streams for POST bodies) and a per-domain connection cap on HTTP/1.1; excellent for notifications, progress and LLM token streaming (J30).
  • Long polling and polling: long polling holds a request until data is available and then repeats; polling asks on a schedule. Simple through any proxy, but wasteful at scale.
  • WebRTC: peer-to-peer using ICE, STUN (discover public address) and TURN (relay when direct fails), DTLS-SRTP for media, SDP for session description, signalling via your own channel (often WebSocket); used for video calls and low-latency data channels.
  • Webhooks: event delivery to your endpoint: verify the signature (HMAC) on the raw body, respond fast with 2xx and process asynchronously, make handlers idempotent, handle retries and duplicates, and allow replay; protect against SSRF when you send webhooks.
  • gRPC and gRPC-web: Protocol Buffers over HTTP/2 with strong typing, streaming and code generation; browsers cannot speak native gRPC, so gRPC-web or Connect protocol via a proxy is used; common between backend services.
  • REST, GraphQL, gRPC at a glance: REST (resources, HTTP semantics, cacheable), GraphQL (single endpoint, client-shaped queries, subscriptions over WebSocket/SSE), gRPC (binary contracts, streaming, internal services) (E9).
  • Scaling considerations: memory per connection, file descriptor limits, load balancer idle timeouts (send heartbeats), sticky sessions or connection-agnostic design through pub/sub, graceful draining on deploy so clients reconnect smoothly, and horizontal scaling with managed services (Ably, Pusher, AWS API Gateway WebSocket) when operating your own is not worthwhile.
  • Client behaviour: exponential backoff with jitter, resubscribe after reconnect, sequence numbers or last-seen ids to fetch missed messages, offline queue for outgoing messages, mobile background limits and battery use, merge messages into client caches (E4).
  • Fallbacks and compatibility: corporate proxies may block WebSockets; libraries like Socket.IO provide fallbacks, rooms and acknowledgements at the cost of a custom protocol.
  • Choosing: notifications and feeds: SSE or push. Chat, presence and collaborative editing: WebSocket (with CRDT/OT for merging). Video and voice: WebRTC. Third-party integrations: webhooks. Infrequent updates: polling.

Traps

  • Using WebSockets for everything when SSE or polling suffices and is easier to operate.
  • Not validating Origin or authenticating the socket.
  • Ignoring load-balancer idle timeouts, so connections drop silently without heartbeats.
  • Assuming messages are never lost or duplicated across reconnects.
  • Webhook handlers that do heavy work before responding, causing timeouts and retries.

Likely follow-ups

How does the WebSocket handshake work?
An HTTP GET with Upgrade: websocket and a key; the server answers 101 with an accept hash, after which the connection carries WebSocket frames.
How do you broadcast to all users across several servers?
Publish to a pub/sub channel; every node subscribes and forwards to its connected clients.
How do you secure a webhook receiver?
Verify HMAC signatures with a shared secret, check timestamps against replay, use HTTPS and idempotent processing.
SSE or WebSocket for streaming LLM responses?
SSE (or fetch streaming) is typically enough: one-way, simple, works over standard HTTP infrastructure.

Same-origin policy and CORS

“What is the same-origin policy? What is CORS, a preflight request, and what do the CORS headers do? Why do CORS errors happen and how do you fix them properly? Is CORS a security feature?”

Say this first (30 seconds)

“The same-origin policy is the browser’s core isolation rule: a page can freely load resources from other origins, but scripts can only read responses from their own origin, where an origin is scheme plus host plus port. CORS, cross-origin resource sharing, is the controlled relaxation of that rule: the server tells the browser, through headers like Access-Control-Allow-Origin, which other origins may read its responses. For requests that could have side effects, such as a JSON POST or any with custom headers, the browser first sends an OPTIONS preflight asking permission. CORS protects users’ browsers, not the server: it is enforced by the browser only, and it does not stop curl or another server. The fix for a CORS error is to configure the server correctly, an allowlist of origins, not to disable it or use a wildcard with credentials.”

Details interviewers probe

  • Same-origin policy scope: restricts reading cross-origin responses from fetch/XHR, accessing another origin’s DOM (iframes), and storage (each origin has its own localStorage, IndexedDB and cookies rules). Cookies use site-based rules (P6). postMessage is the safe channel between origins.
  • Simple requests (no preflight): GET, HEAD or POST with only safe headers and content types application/x-www-form-urlencoded, multipart/form-data, text/plain. The request is sent and the browser then checks the response headers before exposing it. Note the request still reaches the server, which is why CSRF defences are needed regardless (P6).
  • Preflight triggers: methods like PUT, PATCH, DELETE; headers such as Authorization or custom ones; Content-Type: application/json. Preflight responses can be cached with Access-Control-Max-Age to reduce extra round trips.
  • Key response headers: Access-Control-Allow-Origin (one origin or *), -Allow-Methods, -Allow-Headers, -Allow-Credentials, -Expose-Headers (which response headers JS may read), -Max-Age. Add Vary: Origin when the allowed origin is dynamic so caches do not mix responses.
  • Credentials rules: with cookies or HTTP auth, the wildcard is disallowed; you must echo an exact, validated origin from an allowlist. Never reflect arbitrary Origin values or allow null; use exact matching, not “ends with” checks.
  • Common causes of CORS errors: missing headers on the API, headers present on success but not on error responses or redirects, preflight blocked by authentication middleware or a 404/405 on OPTIONS, wildcard with credentials, proxies stripping headers, mixed http/https or port mismatches, and misunderstanding that the error appears in the browser while the request actually succeeded server-side.
  • Proper fixes: configure the API (a CORS middleware with an allowlist), handle OPTIONS before auth, return CORS headers on errors, or avoid cross-origin by serving the API under the same origin through a reverse proxy or the framework’s dev proxy. Do not “fix” it with browser extensions or no-cors (which only yields an unreadable opaque response).
  • CORS versus CSRF: CORS controls reading responses; CSRF is about unwanted state-changing requests, which CORS does not prevent for simple requests. Defend with SameSite cookies, CSRF tokens and checking Origin (P6).
  • Related policies: Cross-Origin-Resource-Policy (who may embed my resource), Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy (isolation, needed for SharedArrayBuffer), crossorigin attribute on <script>/<img> to request CORS (needed for SRI and detailed error reporting), Private Network Access for local networks.
  • Fonts and canvas: web fonts from other origins need CORS; images drawn on canvas taint it unless served with CORS and loaded with crossorigin.
  • Cross-origin communication options: postMessage with explicit targetOrigin and origin checks on receipt, JSONP (legacy and unsafe), proxying through your server, BroadcastChannel within an origin.
  • Subdomains and document.domain: relaxing same-origin for subdomains with document.domain is deprecated; use postMessage or a shared parent-domain strategy.
  • Testing: inspect OPTIONS and the actual request in DevTools; use curl with an Origin header to verify server responses; automated tests for allowlist behaviour.

Traps

  • Saying CORS protects the API. It protects other sites’ scripts from reading data in a user’s browser; the API itself is unaffected.
  • Using Access-Control-Allow-Origin: * with credentials, or reflecting any origin.
  • Forgetting that the request is still sent for simple cross-origin POSTs.
  • Applying CORS headers only to successful responses.
  • Using mode: 'no-cors' to “fix” errors and getting an opaque response.

Likely follow-ups

Why does the browser send a preflight?
To ask the server whether a potentially side-effecting cross-origin request is allowed before sending it, protecting older servers that never expected such requests.
How do you avoid CORS in development?
Use the dev server’s proxy so the browser sees one origin, and configure real CORS on the API for production if cross-origin is intended.
Can CORS be used to block malicious sites from calling my API?
Not for non-browser clients, and not for simple requests; use authentication, CSRF protection and server-side authorisation.
What is an opaque response?
The result of a no-cors fetch: status and body are hidden from JavaScript.
P6Added

Cookies, sessions and CSRF

“How do cookies work? Explain HttpOnly, Secure, SameSite, Domain and Path. How do sessions work? What is CSRF and how do you defend against it? What is changing with third-party cookies?”

Say this first (30 seconds)

“A cookie is a small piece of data the server sets with Set-Cookie and the browser sends back automatically on matching requests. That automatic sending is both the convenience and the danger. HttpOnly hides the cookie from JavaScript, limiting theft by XSS; Secure restricts it to HTTPS; SameSite controls whether it is sent on cross-site requests, with Lax the modern default and Strict the most protective; Domain and Path scope where it is sent, and Max-Age or Expires sets lifetime. A session stores state on the server and gives the browser only an opaque id in a cookie. CSRF tricks a logged-in user’s browser into sending an unwanted request with their cookies; defences are SameSite cookies, anti-CSRF tokens and checking the Origin header.”

Details interviewers probe

  • Attributes in detail: HttpOnly (not in document.cookie, still sent), Secure (HTTPS only), SameSite (Strict: never cross-site; Lax: sent on top-level GET navigations but not on cross-site subrequests or POSTs; None: always, needs Secure), Domain (if set, includes all subdomains; omit for host-only), Path, Max-Age/Expires, Priority, Partitioned. Cookie prefixes __Host- and __Secure- enforce safe attributes.
  • Site versus origin: “same-site” means same registrable domain (eTLD+1), so app.example.com and api.example.com are same-site but cross-origin. SameSite concerns sites, CORS concerns origins.
  • Size and limits: about 4 KB per cookie and a limited count per domain; cookies are sent on every matching request, so keep them small and avoid putting them on static asset domains.
  • Sessions versus tokens: server sessions (cookie with id) are simple and revocable; stateless tokens (JWT) scale across services but are hard to revoke and bigger. A session cookie remains the most robust choice for browser apps, often via a backend-for-frontend (P8).
  • Session security: long random ids from a CSPRNG, rotate after authentication (prevents fixation), idle and absolute timeouts, bind to context carefully (IP binding is fragile), invalidate on logout, store server-side, and protect with HTTPS everywhere.
  • XSS and cookies: HttpOnly stops scripts reading the cookie but an XSS can still perform actions as the user through the browser; so it reduces but does not remove the impact (J29).
  • CSRF tokens: synchroniser token (server stores it) or double-submit cookie (token in cookie and header, compared, preferably signed); send in a custom header for AJAX, hidden field for forms. Frameworks provide middleware. Tokens must not be leaked in URLs.
  • Sec-Fetch-* headers: Sec-Fetch-Site, -Mode, -Dest let servers reject unexpected cross-site requests (resource isolation policy), a strong modern defence layer.
  • Login CSRF and clickjacking: login forms need CSRF protection too; clickjacking (framing the site) is prevented with frame-ancestors or X-Frame-Options (P7).
  • Third-party cookies: used for cross-site tracking, embedded widgets, SSO and payments. Browsers block or restrict them (Safari and Firefox by default; Chrome’s plan changed several times verify current status). Alternatives: first-party contexts, Partitioned cookies (CHIPS), Storage Access API, redirects and tokens, server-side tracking.
  • Cookie consent and privacy: non-essential cookies (analytics, ads) need consent under GDPR and ePrivacy; strictly necessary cookies (session, security) do not; document cookies in a policy (P11).
  • Alternatives to cookies in browsers: localStorage (readable by any script), tokens in memory with refresh via HttpOnly cookie, IndexedDB; none send automatically, avoiding CSRF but exposing tokens to XSS (J29, J30).
  • Debugging: DevTools Application → Cookies, the “Issues” panel for SameSite warnings, and checking Set-Cookie headers in Network.

Traps

  • Saying HttpOnly prevents XSS. It prevents cookie theft by script, not XSS itself.
  • Confusing same-site with same-origin.
  • Setting SameSite=None without Secure (rejected by browsers).
  • Putting Domain=.example.com and exposing the session to every subdomain, including vulnerable ones.
  • Relying only on SameSite and skipping CSRF tokens for sensitive flows or older browsers.

Likely follow-ups

What does SameSite=Lax block?
Sending the cookie on cross-site subrequests and non-GET requests such as a forged POST, while still allowing it on normal top-level link navigations.
Why do APIs using bearer tokens avoid CSRF?
The browser does not attach the Authorization header automatically; JavaScript from your origin must add it.
How do you log a user out everywhere?
Invalidate the server-side sessions (or token family) and clear cookies; stateless JWTs need a deny list or short expiry.
How do you share sessions across subdomains?
Set Domain to the parent only when necessary, understand the wider exposure, or use SSO with token exchange.

Security headers and Content Security Policy

“Which security headers do you set and why? How does Content Security Policy work and how do you roll one out? What are Trusted Types, SRI, COOP and COEP?”

Say this first (30 seconds)

“Security headers instruct the browser to enforce protections. The essentials are Strict-Transport-Security to force HTTPS, X-Content-Type-Options: nosniff to stop MIME sniffing, Referrer-Policy to limit leaking URLs, Permissions-Policy to restrict powerful features, and clickjacking protection with CSP frame-ancestors. The most powerful is Content Security Policy: a header listing which sources may supply scripts, styles, images, frames and connections, so even if an attacker injects markup, the browser refuses to run script from disallowed places. A strict CSP uses per-request nonces or hashes with strict-dynamic and no unsafe-inline. I roll it out in report-only mode first, collect violations, fix them, then enforce. Subresource Integrity pins third-party files by hash, and COOP/COEP enable cross-origin isolation.”

Details interviewers probe

  • CSP directives: default-src (fallback), script-src, style-src, img-src, connect-src (fetch, XHR, WebSocket), font-src, frame-src, frame-ancestors, form-action, base-uri, object-src, worker-src, report-to/report-uri. Sources: 'self', hosts, https:, 'nonce-…', 'sha256-…', 'strict-dynamic', and unsafe keywords ('unsafe-inline', 'unsafe-eval') that weaken protection.
  • Allowlist CSPs fail: long host allowlists are often bypassable through JSONP endpoints or script gadgets on allowed hosts. Nonce- or hash-based policies with strict-dynamic (trust scripts loaded by trusted scripts) are the recommended approach.
  • Nonces: unpredictable per-response value added to the header and to each allowed <script nonce>; requires dynamic HTML generation (SSR, middleware), which conflicts with fully static caching; hashes work for static inline scripts.
  • Frameworks: Next.js supports nonces via middleware (dynamic pages), Angular and others have CSP guidance; inline styles from CSS-in-JS often need nonces or hashes; third-party tags (analytics, chat) complicate policies, so govern them.
  • Report-only and monitoring: Content-Security-Policy-Report-Only logs violations without blocking; collect reports with a service (report-uri, Sentry), triage noise from browser extensions, then enforce. Keep monitoring after enforcement.
  • Trusted Types: the browser requires dangerous DOM sinks (innerHTML, eval) to receive typed objects created by named policies, eliminating most DOM XSS if every sink goes through sanitising policies; support is strongest in Chromium verify.
  • Subresource Integrity: integrity hash on <script>/<link> from a CDN ensures the file is unchanged; needs crossorigin; protects against CDN compromise but breaks if the file legitimately changes, so pin versions.
  • HSTS details: max-age, includeSubDomains, preload; start with a short max-age, increase after validation, preload only when all subdomains are HTTPS.
  • Referrer-Policy: strict-origin-when-cross-origin (default in modern browsers) sends full URL same-origin and only the origin cross-site; use no-referrer for sensitive pages, and never put secrets in URLs.
  • Permissions-Policy: turn off features you do not use (camera=(), geolocation=()) and restrict embeds with the allow attribute on iframes.
  • Clickjacking: UI redress through invisible iframes; stop with frame-ancestors 'none' (or specific origins) and legacy X-Frame-Options: DENY; sensitive actions can also require re-auth or user gesture checks.
  • COOP, COEP, CORP: COOP: same-origin and COEP: require-corp together achieve cross-origin isolation, enabling SharedArrayBuffer and high-resolution timers; they break third-party embeds that do not send CORP/CORS, so adopt deliberately (J23).
  • Other headers: Cache-Control: no-store on sensitive responses, Clear-Site-Data on logout, Content-Disposition for downloads, X-XSS-Protection is obsolete (remove or set 0), Server/X-Powered-By version leaks should be minimised.
  • Testing and tooling: securityheaders.com, Mozilla Observatory, CSP Evaluator, browser DevTools Issues and Security panels; add header checks to CI or smoke tests; helmet middleware for Node apps.
  • Where to set headers: at the CDN or reverse proxy for consistency across apps, or in the framework (Next.js headers(), Express helmet); ensure error pages and static assets also receive them.

Traps

  • A CSP with 'unsafe-inline' in script-src and calling it protection; inline XSS still runs.
  • Long domain allowlists that include JSONP or user-content hosts.
  • Enabling a CSP straight in enforce mode on a complex site and breaking production.
  • Reusing a nonce across responses or caching a nonce-bearing HTML page.
  • Applying COOP/COEP casually and breaking embedded third-party content.

Likely follow-ups

What does strict-dynamic do?
It lets scripts that carry a valid nonce or hash load further scripts dynamically, ignoring host allowlists, which simplifies policies for modern bundled apps.
How do you handle CSP with third-party tags?
Load them through a nonce-trusted loader or tag manager under governance, restrict their connect-src, and monitor violations.
CSP or input sanitisation?
Both: sanitise and encode to prevent injection, CSP to limit damage if something slips through.
What is a nonce?
A random, single-use token generated per response that marks allowed inline scripts and styles.

Authentication: OAuth 2.0, OIDC, JWT

“Explain OAuth 2.0 and OpenID Connect. Walk through the authorisation code flow with PKCE. What is a JWT and what are its pitfalls? Where should a single-page app keep tokens?”

Say this first (30 seconds)

“OAuth 2.0 is a delegation framework: it lets a user grant an application limited access to their resources without sharing a password, through tokens. OpenID Connect, OIDC, is a thin identity layer on top that adds an ID token proving who the user is. For browser and mobile apps, the recommended flow is the authorisation code flow with PKCE: the app redirects to the identity provider, the user authenticates and consents, the provider redirects back with a short-lived code, and the app exchanges that code, together with the PKCE verifier, for tokens. A JWT is a signed, base64url-encoded JSON token with header, claims and signature; the receiver verifies the signature and claims such as issuer, audience and expiry. Pitfalls include not validating, long lifetimes and hard revocation. For SPAs I prefer a backend-for-frontend keeping tokens server-side behind an HttpOnly cookie.”

Details interviewers probe

  • Roles in OAuth 2.0: resource owner (user), client (your app), authorisation server (issues tokens), resource server (API). Scopes limit what a token can do. Public clients (SPAs, mobile) cannot keep a secret; confidential clients (servers) can.
  • Flows today: authorisation code + PKCE for all clients (OAuth 2.1 direction); client credentials for machine-to-machine; device code for TVs and CLIs; refresh token flow. Avoid implicit flow (tokens in URL fragments) and resource owner password credentials.
  • OIDC: adds openid scope, ID token (a JWT with identity claims), the UserInfo endpoint, discovery document (/.well-known/openid-configuration) and standard claims (email, name). Use it for “Sign in with Google/Microsoft” and enterprise SSO.
  • JWT versus opaque tokens: JWTs are self-contained (resources validate locally with a public key from JWKS) but cannot be revoked before expiry without extra infrastructure; opaque tokens need introspection calls to the auth server but are easily revoked. Choose by scale and revocation needs.
  • Signature algorithms: asymmetric (RS256, ES256) lets APIs verify without holding the signing key; symmetric HS256 shares one secret. Pin allowed algorithms server-side; ignore the header’s claim. Rotate keys with kid and JWKS.
  • Refresh tokens: long-lived; use rotation (each use returns a new one and invalidates the old, with reuse detection), limit lifetime, bind to the client, and store only where it is safe (HttpOnly cookie or server). In SPAs, silent refresh via iframe is broken by third-party cookie rules; use refresh tokens with rotation or BFF.
  • Where to store tokens in a SPA: options: memory (safe from persistence, lost on refresh, still reachable by XSS), localStorage (any script can read it: XSS steals tokens), HttpOnly cookies (not readable by JS, need CSRF protection). The current best practice for high-security apps is a BFF: the server performs the OAuth flow, keeps tokens server-side, and gives the browser only a session cookie; the browser app calls the BFF (N11, J29).
  • State, nonce and redirect URIs: state prevents CSRF on the callback; nonce binds the ID token to the session; register exact redirect URIs (no wildcards) to avoid open-redirect token theft.
  • Authorisation models: RBAC (roles), ABAC (attributes), scopes for delegation, per-resource ownership checks; claims in tokens can go stale, so for sensitive decisions check current data.
  • SAML and enterprise SSO: XML-based SSO for corporate identity providers (Okta, Azure AD/Entra); OIDC is the modern equivalent; many enterprise clients require SAML or OIDC federation.
  • Libraries and hosted services: Auth0, Okta, Azure AD B2C/Entra, Cognito, Keycloak (self-hosted), Clerk, Firebase/Supabase Auth, Auth.js; prefer certified libraries; never implement token validation or cryptography by hand.
  • Logout and session termination: clear the app session, optionally call the IdP end-session endpoint (single logout), revoke refresh tokens, handle back-channel logout in enterprise setups.
  • Common attacks: authorisation code interception (PKCE), token theft via XSS, CSRF on callback (state), open redirects, mix-up attacks, replay of tokens, phishing consent screens, and misconfigured audiences letting tokens for one API work on another.
  • API side: validate the bearer token on every request (signature, exp, aud, scopes), return 401 for invalid tokens and 403 for insufficient scope, and never trust client-provided identity claims.

Traps

  • Saying OAuth is an authentication protocol. It is authorisation; OIDC adds authentication.
  • Treating JWT payloads as secret or encrypted. They are only signed.
  • Skipping audience and issuer checks because the signature verifies.
  • Keeping long-lived access tokens in localStorage in a SPA without considering XSS.
  • Using the implicit flow or wildcard redirect URIs.

Likely follow-ups

What problem does PKCE solve?
It binds the authorisation code to the client that started the flow, so an intercepted code cannot be redeemed by an attacker; essential for public clients.
How do you revoke a JWT?
Short expiry plus refresh tokens that can be revoked, a deny list of token ids, or switch to opaque tokens with introspection.
ID token versus access token?
The ID token is for the client to learn who authenticated; the access token is for calling APIs. Do not send ID tokens to APIs.
What is a backend-for-frontend?
A server component that handles OAuth, holds tokens, and proxies API calls, exposing only a session cookie to the browser.

Passkeys, MFA and session management

“What are passkeys and WebAuthn? How do MFA methods compare? How do you store passwords safely? How do you design login, reset and session flows securely?”

Say this first (30 seconds)

“Passwords are the weakest link, so modern authentication moves towards phishing-resistant credentials. WebAuthn, the standard behind passkeys, uses public-key cryptography: the device creates a key pair per site, the private key never leaves the authenticator and is unlocked by biometrics or a PIN, and the server stores only the public key and verifies signed challenges. Because the credential is bound to the origin, it cannot be phished and there is no shared secret to leak. Where passwords still exist, I store them with a slow salted hash such as Argon2id or bcrypt, enforce rate limiting and breached-password checks, add MFA, prefer authenticator apps or security keys to SMS, and make reset flows time-limited, single-use and non-enumerating.”

Details interviewers probe

  • WebAuthn mechanics: navigator.credentials.create() for registration (server provides challenge, relying-party id, user info; gets public key and attestation) and .get() for authentication (server challenge; signed assertion). The relying-party id ties credentials to the domain, so look-alike domains fail. Libraries: SimpleWebAuthn; platforms: Apple, Google, Microsoft, 1Password.
  • Passkeys: discoverable WebAuthn credentials, often synced across a user’s devices, with cross-device sign-in via QR/Bluetooth. Trade-offs: sync provider trust and account recovery; adoption requires UX for enrolment (“create a passkey”) and fallback. Conditional UI (autofill) shows passkeys in the username field.
  • MFA types: something you know, have, are. TOTP (RFC 6238) apps, hardware keys (FIDO2), push notifications with number matching, SMS/voice (weakest), recovery codes. Prefer step-up MFA for sensitive actions and risk-based prompts (new device, location).
  • Password handling: length over complexity (minimum 8 to 12, allow long passphrases and paste), check against breached lists (Have I Been Pwned k-anonymity API), no composition rules that encourage patterns, no periodic forced rotation without cause, use Argon2id or bcrypt with a work factor, and constant-time comparison. Salt prevents rainbow tables; pepper adds a secret outside the database.
  • Brute force and credential stuffing: rate limit by account and IP, progressive delays or CAPTCHAs, lockouts that do not enable denial of service, device fingerprints and risk scoring, bot detection, and alerts. Return identical messages for unknown users and wrong passwords.
  • Account recovery and reset: single-use, short-lived, unguessable tokens sent to a verified channel; invalidate on use and on password change; do not reveal whether an email exists; require re-authentication for changing email or MFA; notify on security changes. Recovery is often the weakest link, so it must not bypass MFA.
  • Session management: new session id after login, idle and absolute timeouts, “remember me” as a separate long-lived token with rotation, device list with revoke, logout everywhere, bind sensitive actions to recent authentication, and secure cookie attributes (P6).
  • Signup and verification: verify emails, protect against enumeration, handle disposable emails per policy, and apply bot protection on registration.
  • Authorisation basics: deny by default, check on the server per resource, avoid insecure direct object references (IDOR) by verifying ownership, log access to sensitive data, and separate admin interfaces.
  • Frontend responsibilities: correct input types and autocomplete attributes (username, current-password, new-password, one-time-code) so password managers and OTP autofill work; accessible error handling; not storing credentials client-side; clearing sensitive state on logout; masking and avoiding logging secrets.
  • Compliance and privacy: handle credentials and identifiers under GDPR; minimise retained data; follow standards such as OWASP ASVS and NIST 800-63B for authentication guidance.
  • Build or buy: most teams should use an identity provider rather than building login, because secure storage, recovery, MFA, bot defence and compliance are costly to get right.

Traps

  • Offering SMS as the strongest MFA, or letting account recovery bypass MFA.
  • Storing passwords with a fast hash such as SHA-256, or encrypting them reversibly.
  • Revealing whether an account exists through different error messages or timing.
  • Locking accounts after a few failures so attackers can lock out real users.
  • Blocking paste or autofill in password fields.

Likely follow-ups

Why are passkeys phishing-resistant?
The credential is bound to the real site’s origin, so a fake site cannot request a valid signature, and there is no secret to type or intercept.
Why a slow hash for passwords?
To make offline brute force after a database leak expensive; fast hashes let attackers test billions of guesses per second.
How do you detect credential stuffing?
Spikes of failed logins across many accounts from distributed IPs, breached-credential checks, rate limits, device and behavioural signals.
What is step-up authentication?
Requiring an additional or stronger factor for sensitive operations such as changing payment details.

OWASP Top 10 for frontend engineers

“Which OWASP Top 10 risks matter most to frontend developers? Explain broken access control, injection, XSS, insecure design, vulnerable components, SSRF and security misconfiguration with practical frontend mitigations.”

Say this first (30 seconds)

“The OWASP Top 10 lists the most critical web application risks. For a frontend lead the ones I act on most are broken access control, since hiding a button is not authorisation and every action must be enforced on the server; injection, including XSS, where untrusted data is interpreted as code in a browser context; vulnerable and outdated components, which for frontends means npm dependencies; security misconfiguration such as missing headers, permissive CORS and exposed source maps or secrets; identification and authentication failures; insecure design, meaning threat modelling before building; and logging and monitoring failures. My practice is secure defaults in frameworks, validation and encoding at boundaries, least privilege, dependency hygiene, security headers, and automated scanning in CI.”

Details interviewers probe

  • Broken access control (A01): missing server checks, IDOR (changing an id in a URL returns someone else’s data), privilege escalation, forced browsing to admin routes, missing function-level checks, CORS misconfig, JWT claim tampering. Mitigate: deny by default, check ownership and role on every request, centralise authorisation, test with multiple user roles, and never trust client-side checks.
  • Injection and XSS (A03): SQL, NoSQL, command and template injection on the server; XSS in the browser (stored, reflected, DOM-based). Frontend: output encoding via framework defaults, avoid innerHTML and dangerouslySetInnerHTML, sanitise with DOMPurify, validate URL schemes, strict CSP and Trusted Types (J29, P7).
  • Cryptographic failures (A02): sensitive data over HTTP, weak ciphers, secrets in code or bundles, tokens in URLs or logs, caching of sensitive responses. Mitigate: TLS everywhere, Cache-Control: no-store for sensitive pages, never expose API keys with privileges in the client, rotate leaked secrets.
  • Insecure design (A04): flaws at the design level (no rate limiting on password reset, business logic abuse such as coupon stacking). Mitigate with threat modelling, abuse-case tests, and security requirements in user stories (P11).
  • Security misconfiguration (A05): missing security headers, verbose error pages and stack traces, directory listing, public cloud buckets, debug mode in production, default accounts, exposed .env or .git, source maps and admin tools public. Mitigate: hardened templates, automated config scans, environment parity, least privilege.
  • Vulnerable and outdated components (A06): npm dependency CVEs and abandoned packages; mitigate with automated updates, npm audit, Dependabot/Renovate, software composition analysis (Snyk, Socket, GitHub advisories), minimal dependencies, and a policy for patch timelines (B8, J29).
  • Identification and authentication failures (A07): weak passwords, credential stuffing, session fixation, missing MFA, tokens that never expire (P8, P9).
  • Software and data integrity failures (A08): unsigned updates, insecure CI/CD, untrusted CDNs, deserialisation of untrusted data, dependency confusion. Mitigate: pinned and verified dependencies, signed builds and provenance, SRI, protected pipelines and branches.
  • Logging and monitoring failures (A09): no visibility into attacks. Log authentication events, access control failures and input validation failures; ship to a central system; alert on anomalies; avoid logging PII, tokens and passwords; frontend error and abuse telemetry with privacy in mind.
  • SSRF (A10): server fetches an attacker-supplied URL (link previews, import by URL, webhooks, image optimisers), reaching internal services or cloud metadata. Mitigate: allowlists, resolve and validate IPs, block private ranges and metadata endpoints, disable unnecessary redirects, run in a network-restricted sandbox. Relevant for Next.js image optimisation and server-side fetching.
  • Other frontend topics: open redirects (?next= validation), clickjacking, postMessage with wildcard origins, DOM clobbering, prototype pollution, ReDoS, target="_blank" tabnabbing (rel="noopener"), unsafe file uploads (type and size checks, store outside web root, scan), and client-side feature flags that expose hidden features.
  • Testing and tooling: SAST (ESLint security plugins, CodeQL, Semgrep), DAST (OWASP ZAP), dependency scanning, secret scanning (gitleaks), penetration tests, bug bounty, and security unit tests for authz rules. Include security checks as CI gates.
  • Culture: security champions, threat-modelling sessions at design time, secure code review checklists, training with real examples, incident drills, and responsible disclosure policy.

Traps

  • Reciting the list without tying items to concrete frontend actions or examples.
  • Treating security as the backend team’s job.
  • Believing client-side validation or hidden routes provide protection.
  • Running scanners but ignoring findings and patch deadlines.
  • Shipping source maps, debug tools or verbose errors to production.

Likely follow-ups

What is IDOR and how do you prevent it?
Accessing another user’s object by changing an identifier; prevent with server-side ownership checks on every request, not by hiding ids.
How do you secure a file upload?
Validate type and size on the server, rename and store outside the web root or in object storage, scan for malware, serve with safe headers, and avoid executing uploaded content.
What would you do in the first week after discovering a vulnerable dependency?
Assess exposure and exploitability, patch or mitigate, deploy with tests, check logs for exploitation, and add automation to prevent recurrence.
How do you bring security into agile delivery?
Threat model new features, add security acceptance criteria, automate scans in CI, review high-risk changes, and track findings like bugs.

Threat modelling, privacy and secure delivery

“How do you threat-model a feature? How do you handle privacy requirements such as GDPR in a frontend? How do you secure the delivery pipeline and respond to a security incident?”

Say this first (30 seconds)

“Threat modelling asks four questions: what are we building, what can go wrong, what are we going to do about it, and did we do a good job. I draw the data flows and trust boundaries, then walk through STRIDE categories such as spoofing, tampering and information disclosure to list threats and rank them by impact and likelihood, then assign mitigations and tests. For privacy I practise data minimisation, collect consent for non-essential tracking, support access and deletion requests, and keep personal data out of logs and URLs. For delivery security I protect branches and pipelines, scan code and dependencies, manage secrets in a vault, sign and verify artifacts, and apply least privilege. When an incident happens I contain, eradicate, recover, communicate and write a blameless post-incident review.”

Details interviewers probe

  • Threat modelling process: scope the system and assets; draw data flow diagrams with trust boundaries; enumerate threats with STRIDE (or attack trees, PASTA, LINDDUN for privacy); rate risk (impact × likelihood, DREAD is outdated); decide mitigations; track as backlog items with owners; revisit on change. Keep it lightweight and collaborative.
  • Frontend assets and threats: session tokens, personal data, payment forms, admin features, feature flags, source code (public), third-party scripts (skimming, Magecart), supply chain, and user-generated content. Typical mitigations: CSP, SRI, sandboxed iframes for payments (hosted fields), segregated admin apps, rate limiting.
  • Privacy by design and GDPR basics: lawful basis, data minimisation, purpose limitation, consent for non-essential cookies and tracking, transparency (privacy notice), data subject rights (access, rectification, erasure, portability), data retention limits, DPA with processors, breach notification (72 hours). CCPA/CPRA and other laws have similar themes.
  • Frontend privacy practices: consent management platforms that truly block scripts until consent; load analytics conditionally; do not put PII in URLs, local storage or analytics events; mask data in session replay; anonymise IPs; respect Do Not Track/Global Privacy Control where required; cookie banner with equal-weight options; document third parties.
  • Data classification: public, internal, confidential, restricted; handle PII, financial and health data with stricter controls (encryption, access logging, retention). Never log secrets or full personal records.
  • Secure SDLC practices: security requirements and acceptance criteria, secure coding guidelines, peer review for sensitive code, SAST and DAST, dependency management, penetration testing before major releases, bug bounty, and security champions embedded in teams.
  • Supply-chain security: pin and verify dependencies, restrict install scripts, use provenance and signed packages, protect CI secrets (short-lived OIDC credentials rather than long-lived keys), isolate build environments, review third-party GitHub Actions (pin by commit SHA), and monitor for typosquats and compromised packages.
  • Secrets management: never in code or images; use vaults (HashiCorp Vault, AWS Secrets Manager), environment injection at deploy, rotation, scoped credentials, and secret scanning with pre-commit and server-side checks; if leaked, revoke immediately.
  • Least privilege and zero trust: minimal IAM roles, per-service credentials, network segmentation, short-lived tokens, verify every request regardless of network location.
  • Incident response lifecycle: preparation (runbooks, contacts, logging), detection and triage (severity), containment (disable accounts, revoke tokens, isolate), eradication and recovery (patch, redeploy, restore), communication (internal, customers, regulators), and post-incident review with actions. Frontend incidents: compromised third-party script (remove tag, rotate, CSP report), leaked key in bundle (revoke, scrub), XSS (patch, invalidate sessions).
  • Resilience and abuse controls: rate limiting, bot management, CAPTCHAs and proof-of-work only where needed, WAF rules, DDoS protection at the CDN, graceful degradation.
  • Accessibility and security overlap: clear error messages without leaking details; accessible MFA and recovery; avoid security measures that exclude users (CAPTCHA alternatives).
  • Communicating risk: explain impact in business terms, offer options with cost and mitigation, document accepted risks with owner and review date.

Traps

  • Doing threat modelling once, as a document, instead of continuously with the design.
  • Loading analytics and ad scripts before consent and calling it compliant.
  • Long-lived cloud keys in CI secrets instead of short-lived federated credentials.
  • Third-party GitHub Actions referenced by mutable tags.
  • Blaming individuals in incident reviews instead of fixing the system.

Likely follow-ups

How would you threat-model a checkout page?
Diagram the flow with the payment provider; consider tampering with prices, card skimming through third-party scripts, replay, and session theft; mitigate with server-side pricing, hosted payment fields, CSP and SRI, and idempotency.
What are the obligations after a data breach?
Contain it, assess the data affected, and notify the regulator within 72 hours and affected users where required, while documenting the response.
How do you reduce third-party script risk?
Fewer scripts, tag governance, CSP and SRI, sandboxed iframes, performance and security review before adding, and monitoring for changes.
What is least privilege?
Granting each user, service and pipeline only the access needed for its task, limiting damage from compromise.
