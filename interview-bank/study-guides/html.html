Clickable div: semantics and the accessibility tree

“How do you make a clickable <div> accessible, and why prefer a native element?”

Say this first (30 seconds)

“I wouldn’t make it accessible, I’d replace it with a <button>. A native button gives me four things for free: a role, an accessible name from its content, keyboard focus, and Enter and Space activation. A div gives me none of them. To fake it I need role="button", tabindex="0", a keydown handler for Enter and a keyup handler for Space, visible focus styles, and ARIA state like aria-pressed or aria-disabled. That is five things to get right and test, so the first rule of ARIA is: use the native element if one exists.”

What the browser builds from your markup

The browser builds two trees from the HTML. The DOM tree is for scripts and CSS. The accessibility tree is for assistive technology (screen readers, voice control, switch devices). Each node in the accessibility tree has four things: role (what it is), name (what it is called), state/value (checked, expanded, disabled) and relationships (described by, controls). A <div> maps to a generic node with no role and no name, so a screen reader user does not know it is clickable. Tab skips it, because a div is not focusable.

What a native <button> gives you

NeedNative <button>Div you have to build
Roleimplicit buttonrole="button"
Namefrom text content, or aria-labelsame, but you must check it is computed
Focusin the tab ordertabindex="0"
Activationclick on Enter (keydown) and Space (keyup)both key handlers; preventDefault() on Space or the page scrolls
Disableddisabled removes it from tab order and blocks clicksaria-disabled + ignore events + tabindex="-1"
Form behavioursubmits its form (default type="submit")none
Focus ringUA default, :focus-visibleyou write it
Forced colors (Windows high contrast)themed automaticallyoften invisible

If you truly cannot change the element

<div role="button" tabindex="0" class="btn" aria-pressed="false">Mute</div>

el.addEventListener('click', toggle);
el.addEventListener('keydown', e => { if (e.key === 'Enter') { e.preventDefault(); toggle(); } });
el.addEventListener('keyup',   e => { if (e.key === ' ')     { e.preventDefault(); toggle(); } });
/* plus: .btn:focus-visible { outline: 2px solid } and aria-pressed updated in toggle() */

Real cases: a third-party library renders the div, a legacy component cannot be changed yet, or you are building a widget with no native equivalent (tabs, combobox, tree). Even then, follow the ARIA Authoring Practices pattern for that widget.

Related: why tabindex alone is not enough

tabindex="0" makes the div focusable. It does not give it a role, so a screen reader says “Save, group” or just “Save”, with no hint that it is a control. Keyboard users can focus it but pressing Enter does nothing unless you wrote the handler. This was the gap in the first answer.

Traps

  • Claiming Lighthouse will catch a click handler on a div. It will not; it cannot know the div is interactive. Use manual keyboard testing, eslint-plugin-jsx-a11y (click-events-have-key-events, no-static-element-interactions) and axe in CI.
  • Putting role="button" on a <div> and thinking you are done. The role is only a promise; you still owe the behaviour.
  • Nesting interactive elements, for example a button inside <a>. It is invalid HTML and screen readers announce it badly.

Likely follow-ups

What is the first rule of ARIA?
Do not use ARIA if a native HTML element or attribute already has the semantics and behaviour you need.
Does Space or Enter activate a button on keydown?
Enter fires click on keydown; Space fires click on keyup. That is why the div needs two handlers.
Can a button contain a heading or a div?
No. Button content must be phrasing content, and the button’s children are presentational for assistive technology.
How would you test this?
Unplug the mouse: Tab to it, activate with Enter and Space, check focus ring, then run NVDA or VoiceOver and listen for “button”.
Q2Asked · 29 Sep

<a> versus <button>

“When do you use <a> and when do you use <button>?”

Say this first (30 seconds)

“A link goes somewhere: it has a URL, so it works with middle click, open in new tab, copy link, bookmarks, history and crawlers. A button does something on the current page: submit, toggle, open a menu. I decide by asking: does this change the URL? If yes, it is an <a href>, even in a single-page app. If no, it is a <button type="button">. Inside a form, a button defaults to type="submit", so I always set the type explicitly.”

Differences that show up in practice

<a href><button>
Role announcedlinkbutton
Activates withEnterEnter and Space
Browser featuresopen in new tab, copy link, preview URL on hover, historynone
Crawlableyes, crawlers follow hrefno
In a formnot involveddefaults to submit
Screen reader shortcutlinks list (K, Insert+F7)buttons list (B)
Disabledno such concept; hide or removedisabled attribute

Single-page apps

Client-side routing still needs real anchors. Use the router’s <Link to="/x"> (it renders <a href="/x"> and intercepts the click). Do not write <button onClick={() => navigate('/x')}>: the user loses open-in-new-tab and crawlers lose the link.

Opening in a new tab: target="_blank" with rel="noopener". Modern browsers treat _blank as noopener by default verify, but writing it is harmless. Warn users (visually and in the name) when a link opens a new window.

Download: <a href="/file.pdf" download> is still a link. Name it with file type and size.

Traps

  • <a href="#" onclick="..."> or <a role="button">: a link used as a button. The URL changes to #, Space scrolls the page, and the screen reader says “link”. Use a button.
  • <button> inside a form without type="button": it submits the form when clicked, a very common bug in a “Cancel” or “Add row” button.
  • A “skip to content” control must be an anchor (href="#main"), because it navigates to a place in the page.
  • Wrapping a button in an anchor, or an anchor in a button. Invalid; one interactive element per control.

Likely follow-ups

A “Learn more” card is fully clickable. How do you build it?
One real link on the heading, stretched over the card with a ::after pseudo-element (position absolute, inset 0). Do not wrap the whole card in an anchor with nested links.
Why does a link not activate on Space?
By design: Space scrolls the page for a link. A link is for navigation; Space is reserved for the button role.
Menu that opens on click: link or button?
Button with aria-expanded and aria-controls. Items inside are links if they navigate.
Is <a> without href a link?
No, it is a placeholder with no role and no focus. Always give it an href or use a different element.
Q3Asked · 29 Sep

Landmarks, headings and <article>

“Landmarks and heading structure; what does <article> mean?”

Say this first (30 seconds)

“Landmarks and headings are how screen reader users scan a page the way sighted users scan visually. Landmarks are the big regions: header, nav, main, aside, footer. Headings give the outline: one h1, then h2 sections, without skipping levels, chosen by structure and not by font size. <article> is a self-contained piece of content that makes sense on its own and could be syndicated: a blog post, a comment, a news item. It is not a generic layout wrapper; that is a div.”

Landmark roles and their elements

ElementLandmark roleRule
<header>banneronly when it is a direct child of body. Inside article or section it is just a header.
<nav>navigationlabel each one if there are several: aria-label="Breadcrumb".
<main>mainexactly one visible per page. The target of the skip link.
<aside>complementarytangential content, related links, sidebars.
<footer>contentinfoonly when a direct child of body.
<section>regiononly if it has an accessible name; otherwise no landmark.
<form>formonly if it has an accessible name.
<search>searchnewer element; or role="search" on a form verify support.

Headings

  • Screen reader users navigate by heading (H key, or a headings list) more than by any other method, so headings are the table of contents.
  • One h1 per page is the safe convention. HTML allows more, but the “outline algorithm” was never implemented in browsers or assistive tech, so do not rely on nested sectioning to reset levels.
  • Do not skip levels. Do not pick a level for its size; style with CSS.
  • In a component library the heading level must be a prop (as="h3") because the correct level depends on where the component is placed.

What <article> and <section> mean

  • <article>: independently distributable or reusable content. Test: “would this still make sense in an RSS reader?” Blog post, forum post, comment (nested articles are allowed), product card in a listing, widget.
  • <section>: a thematic grouping that normally has a heading. Without a name it is not a landmark.
  • <div>: no meaning. When you only need a style or layout hook, use this.

Traps

  • Saying article is for “a block of text”. It is about self-containment, not text.
  • Wrapping every block in a <section> with no heading: no benefit, noisy markup.
  • Two <nav> elements both announced as “navigation” with no labels. Label them.
  • Using headings for visual emphasis (a bold “Note:” as h4), or using bold text for real headings.
  • Content outside any landmark. Screen reader users jumping by landmark miss it.

Likely follow-ups

Which landmarks must every page have?
main at minimum; banner, navigation and contentinfo in most layouts.
How do you let keyboard users bypass the header?
A skip link as the first focusable element: <a href="#main">Skip to content</a>, visible on focus, with main having id="main" and tabindex="-1" so focus really moves.
Is a heading inside <button> okay?
No. The reverse is the accordion pattern: the heading contains the button.
How do you check the outline?
Browser accessibility tree in DevTools, the axe or WAVE extension, or a screen reader headings list.

ARIA essentials and accessible names

“What is ARIA, when would you use it, and how does a control get its accessible name?”

Say this first (30 seconds)

“ARIA is a set of attributes that adds roles, states and properties to the accessibility tree where HTML cannot express them. It changes what assistive technology hears and nothing else: no behaviour, no focus, no styling. So the first rule is to prefer native HTML. I use ARIA for what HTML cannot say: aria-expanded on a disclosure, aria-live for status messages, aria-current in navigation, labels on icon-only buttons, and roles for widgets with no native element, like tabs or combobox. Bad ARIA is worse than none.”

The five rules of ARIA

  1. Do not use ARIA if a native element can do it.
  2. Do not change native semantics (<h2 role="tab"> is wrong; put a button inside).
  3. All interactive ARIA controls must be keyboard operable.
  4. Do not use role="presentation" or aria-hidden="true" on a focusable element.
  5. Every interactive element needs an accessible name.

Three kinds of attributes

KindExamplesChanges?
Rolesdialog, tablist, tab, combobox, alert, statusstatic
Statesaria-expanded, aria-checked, aria-pressed, aria-selected, aria-disabled, aria-invalidchanges with interaction: you must update from JS
Propertiesaria-label, aria-labelledby, aria-describedby, aria-controls, aria-live, aria-currentmostly static relationships

How the accessible name is computed

aria-label vs aria-labelledby vs aria-describedby

  • aria-labelledby: points to visible text by id. Preferred, because the name stays in sync with the UI and is translated with it.
  • aria-label: a string. For things with no visible text (icon buttons, a second nav). Not auto-translated by page translation tools in every browser; keep it short. Include the visible text when there is any, so voice control (“click Search”) matches WCAG 2.5.3 Label in Name.
  • aria-describedby: extra description read after the name: hints, errors, password rules.

Live regions: announcing changes without moving focus

<div id="status" role="status" aria-live="polite"></div>   <!-- present at page load -->
status.textContent = '3 results found';          <!-- inject text later -->
  • polite (role status): waits for the user to be idle. For search results, saved, cart updated.
  • assertive (role alert): interrupts. Only for errors and critical warnings.
  • The container must exist in the DOM before the text changes. Inserting a new role="alert" element with text is unreliable across screen readers test.

Other attributes you should know

  • aria-expanded on the control that toggles; aria-controls has weak real support, do not rely on it alone.
  • aria-current="page" on the active nav link; aria-current="step" in a wizard.
  • aria-hidden="true": removes from the accessibility tree only, the element stays focusable. Never put it on or around focusable content. Use inert to remove both.
  • aria-invalid, aria-required (prefer native required), aria-busy.

Traps

  • aria-label on a div or span with no role: ignored by most screen readers.
  • Redundant ARIA: <button role="button">, <nav role="navigation">.
  • Putting aria-label on everything “to be safe”. It overrides real visible text and breaks voice control.
  • Role without keyboard support: role="tab" needs arrow-key handling and roving tabindex.
  • Forgetting that states are only attributes: aria-expanded="true" does not open anything.

Likely follow-ups

Where do you find the correct pattern for a custom widget?
The W3C ARIA Authoring Practices Guide (APG): roles, states and keyboard model per widget.
What is the difference between alert and status?
Alert is assertive and interrupts; status is polite and waits.
An icon button has an SVG inside. What do you do?
aria-label on the button (or visually hidden text), and aria-hidden="true" and focusable="false" on the SVG.
What does role="presentation" do?
Strips the native semantics of an element (for example layout tables); children still exposed.
Q5Added

Keyboard and focus management

“How do you make a custom component keyboard accessible? How do you manage focus in a single-page app?”

Say this first (30 seconds)

“Everything a mouse can do must work with a keyboard, in a logical order, with a visible focus indicator. Native controls already do this. For custom widgets I follow the ARIA Authoring Practices keyboard model: one tab stop for the whole widget, arrow keys inside it (roving tabindex), Escape to close, and focus returned to the trigger afterwards. In a single-page app, route changes do not reload the page, so I move focus myself to the new page’s heading or main container and announce the change.”

Tabindex

ValueMeaningUse
not setnative controls only (a[href], button, input, select, textarea, summary)default
0focusable, in DOM ordercustom widget that should be a tab stop
-1focusable by script (el.focus()), not by Tabroving items, focus targets like headings and main
positive (1, 2…)jumps the orderAvoid. Breaks the natural order and is unmaintainable.

Roving tabindex: one tab stop, arrows inside

Focus indicators

  • Never outline: none without a replacement. Use :focus-visible so the ring shows for keyboard and not on mouse click.
  • WCAG 2.2: focus must be visible (2.4.7), not hidden behind sticky headers or cookie banners (2.4.11 Focus Not Obscured, AA), and the indicator needs enough contrast and size (2.4.13, AAA) verify numbers. Use scroll-padding-top so a sticky header does not cover the focused item.
  • Windows forced-colors mode: use outline (it is kept) and not only box-shadow (it is removed).

Focus in a single-page app

  1. Route change: move focus to the page h1 (give it tabindex="-1") or the main, and update document.title. Without it keyboard users stay on the old link and screen reader users hear nothing. Many routers have this built in or as an option check yours.
  2. Open a modal: focus first meaningful element inside; on close, return focus to the trigger (see Q8).
  3. Delete an item: the focused element vanishes, so focus drops to body. Move it to the next item or the list heading.
  4. Async content (toasts, results): use a live region instead of stealing focus.
  5. Skip link to #main at the top.

The keyboard map you should know

KeyStandard behaviour
Tab / Shift+Tabmove between tab stops
Enteractivate links, buttons; submit forms
Spaceactivate buttons, toggle checkbox, scroll page
Escapeclose dialog, menu, popover; cancel
Arrow keysmove inside radio group, tabs, menu, listbox, slider
Home / Endfirst or last item in composite widgets

Traps

  • tabindex="0" on everything. Only on interactive custom widgets, otherwise the tab order fills with noise.
  • Keyboard trap: focus enters a widget and cannot leave (WCAG 2.1.2). Only a modal may contain focus, and Escape must close it.
  • CSS order, grid placement or position that makes the visual order differ from the DOM order. Tab follows the DOM.
  • display:none or visibility:hidden content is not focusable; opacity:0 content still is (a ghost tab stop).
  • Calling focus() on page load without a reason. It scrolls and surprises users.

Likely follow-ups

How do you make a tab list accessible?
role="tablist", tab and tabpanel, aria-selected, roving tabindex, arrow keys switch tabs, panel linked via aria-controls / aria-labelledby.
What is inert?
HTML attribute that makes a subtree non-interactive: not focusable, not clickable, hidden from assistive tech. The right tool for the background of a custom modal.
How do you test keyboard accessibility?
Unplug the mouse and do the main flows. Look for: reachability, order, visible focus, traps, Escape behaviour.
Why avoid positive tabindex?
It forces those elements to the front of the order, ahead of the rest of the page; every new element then needs a number.
Q6Asked · 29 Sep

Form labels and touch targets

“How do you label inputs properly? What about touch target size?”

Say this first (30 seconds)

“Every input gets a visible, programmatically associated <label>: either for matching the input’s id, or the input wrapped inside the label. A placeholder is not a label: it disappears when you type, usually has low contrast, and is not reliably exposed as a name. The label also enlarges the click target. For touch, WCAG 2.2 sets a minimum of 24 by 24 CSS pixels at AA, and 44 by 44 is the recommended target; Apple uses 44 points and Material uses 48 dp. I add padding or a larger hit area instead of making the visual bigger.”

Ways to label a control

<!-- 1. explicit: best default -->
<label for="email">Email</label>
<input id="email" name="email" type="email" autocomplete="email">

<!-- 2. implicit: wrapping (works, but some AT combos are weaker than explicit) -->
<label>Email <input name="email" type="email"></label>

<!-- 3. no visible text possible (search icon): name it, but a visible label is still better -->
<input type="search" aria-label="Search the docs">

<!-- 4. group: radios and checkboxes need a group name -->
<fieldset><legend>Delivery speed</legend> ... radios ... </fieldset>

Why placeholder is not a label

  • It vanishes on input, so users with memory or cognitive difficulties lose the prompt, and cannot review a filled form.
  • Default placeholder colour often fails the 4.5:1 text contrast ratio.
  • Not a reliable accessible name in all browser and screen reader combinations. Use it only for an example format (“name@company.com”), together with a label.
  • Floating labels are acceptable only if the label stays visible and legible after the float.

Target size

.icon-btn { min-inline-size: 44px; min-block-size: 44px; display: inline-grid; place-items: center; }
/* small visual, large hit area */
.chip::after { content: ""; position: absolute; inset: -8px; }

Related form accessibility checklist

  • Hints and errors linked with aria-describedby; invalid fields get aria-invalid="true"; error text states what to do, not just “invalid”.
  • Required: native required, and say it in text (“required”), not only with a red asterisk.
  • Autocomplete tokens (email, given-name, new-password) satisfy WCAG 1.3.5 and help password managers.
  • Mobile keyboards: correct type, inputmode, enterkeyhint.
  • Do not disable paste on password or confirm fields.

Traps

  • for that points to an id which does not exist (or duplicate ids), silently no label.
  • Using the same aria-label text for all repeated controls: “Delete”, “Delete”, “Delete”. Say what: “Delete invoice 1042”.
  • Reporting 44 px as the WCAG AA requirement. AA is 24 px (2.2); 44 is AAA and platform guidance.
  • Making tiny icon-only controls with 4 px gaps: fails target spacing.

Likely follow-ups

Label above, beside or inside the field?
Above is the most scannable and works at narrow widths and with zoom; side-by-side wastes space on mobile; inside only as floating label with care.
How do you name a group of radios?
fieldset + legend, or role="radiogroup" with aria-labelledby.
Can you hide a label?
Yes, visually, with the visually-hidden pattern, when the context is obvious (search box with a button). Never display:none.
What is the accessible name of an <input> with both label and placeholder?
The label. Placeholder is the last source in the name computation.
Q7Asked · 29 Sep

Semantic HTML and SEO

“Does semantic HTML improve SEO?”

Say this first (30 seconds)

“Not directly. Search engines do not rank a page higher because it uses <nav> instead of <div>. But semantics help in indirect ways: crawlers understand the structure and the main content, real <a href> links are followed, headings and a correct title give the topic, and image alt text feeds image search. The same markup also gives better accessibility and often better user experience signals. The bigger SEO levers are rendering strategy (SSR or SSG so content is in the HTML), page speed and Core Web Vitals, unique titles and meta descriptions, canonical URLs, and structured data.”

What really helps crawlers

Checklist you can recite

AreaDo
Documentunique <title> and meta description per page; lang; canonical URL; robots meta only when needed
Structureone h1, logical headings, main, nav; keep important content out of tabs that load on demand
Linksreal <a href>; descriptive link text (not “click here”); rel="nofollow"/ugc/sponsored where right
Imagesmeaningful alt, real file names, width/height, modern formats; image sitemap if needed
Structured dataJSON-LD (Article, Product, BreadcrumbList); validate in Google’s Rich Results Test
RenderingSSR, SSG or ISR for content pages (Next.js); avoid content only after hydration
PerformanceCore Web Vitals (LCP, INP, CLS) are a page experience signal, minor tie-breaker
Internationalisationhreflang alternates

How to phrase it carefully

Say “no direct ranking boost” and “indirect benefits”. Avoid absolute claims like “semantic HTML improves rankings”. Google has said it does not use semantic elements as a ranking factor, and that wording is safer in an interview Google Search Central docs.

Traps

  • Saying “yes, big boost” without evidence, or the opposite: “no effect at all”. The right answer is “indirect”.
  • Router links built with onClick and window.location: invisible to crawlers.
  • Hiding text with display:none for keyword stuffing; treated as a spam signal.
  • Multiple h1 stuffed with keywords.

Likely follow-ups

Does Google run JavaScript?
Yes, with an evergreen Chromium renderer, but rendering is queued and can be delayed, so critical content should be in the initial HTML.
Which Next.js strategy for a blog? A dashboard?
Blog: SSG or ISR. Dashboard behind login: client rendering or SSR; SEO is irrelevant.
What is canonical for?
Tells search engines which URL is the main version when several URLs serve the same content (tracking params, filters).
What is a sitemap?
An XML list of URLs that helps discovery; it does not guarantee indexing.
Q8Asked · 29 Sep

Native <dialog> versus a custom modal

“Native <dialog> versus a custom modal; how do you build and test an accessible one?”

Say this first (30 seconds)

“I prefer the native <dialog> with showModal(). The browser puts it in the top layer, makes everything else inert (so no clicking or tabbing behind it), moves focus into it, closes on Escape, and returns focus to the trigger when it closes. A custom modal needs all of that by hand: role="dialog" and aria-modal, a label, focus management, inert background, Escape handling, scroll lock, and a portal. The native element does not do everything: scroll lock, backdrop click to close, and animations are still my job. I test with the keyboard, axe, and a screen reader.”

Native dialog: what it gives

  • Top layer: renders above everything, no z-index war, no portal needed.
  • Inert background: page behind cannot be clicked, focused or read. This is not a classic focus trap; the browser UI (address bar) stays reachable, which is the intended behaviour.
  • Focus: moves to the first focusable element, or the one with autofocus. When the dialog closes, the spec restores focus to the previously focused element. State this confidently.
  • Escape fires a cancel event (preventDefault() to stop it) then close.
  • Forms: <form method="dialog"> closes the dialog on submit and sets dialog.returnValue to the clicked button’s value.
  • role="dialog" is implicit. You must still give it a name: aria-labelledby pointing at its heading. Use role="alertdialog" for confirmations that need an answer.
  • aria-modal on a custom dialog is only a hint to assistive tech; it does not block interaction in the DOM.
<button id="open">Edit profile</button>
<dialog id="dlg" aria-labelledby="dlg-title">
  <form method="dialog">
    <h2 id="dlg-title">Edit profile</h2>
    <label>Name <input name="n" autofocus></label>
    <button value="cancel">Cancel</button>
    <button value="save">Save</button>
  </form>
</dialog>
<script>
  open.onclick = () => dlg.showModal();
  dlg.addEventListener('click', e => { if (e.target === dlg) dlg.close('backdrop'); }); // backdrop click
  dlg.addEventListener('close', () => console.log(dlg.returnValue));
</script>
<style> body:has(dialog[open]) { overflow: hidden } </style>   /* scroll lock (verify :has support target) */

What a custom modal must implement

RequirementHow
Role and namerole="dialog" (or alertdialog), aria-modal="true", aria-labelledby
Block the backgroundinert on siblings of the portal root (best), or aria-hidden + a focus trap
Focus infocus first control or heading with tabindex="-1" on open
Contain focustrap Tab / Shift+Tab, or rely on inert
Escapeclose handler; ensure it does not close a nested popover wrongly
Restore focusremember document.activeElement before opening; refocus after closing (if it still exists)
Scroll lockoverflow:hidden on body; handle scrollbar width shift on desktop
Stackingrender in a portal at the end of body

In React, libraries such as Radix UI, React Aria or Headless UI implement this; pick one instead of rewriting it, unless you are building the design system.

When custom ARIA is right

Native elements cover dialog, popover (popover attribute), details, select. There is no native element for combobox with async filtering, tabs, tree, or menu bar, so the ARIA pattern from the Authoring Practices Guide applies. Consider the native popover attribute for non-modal overlays (tooltips, menus) check Baseline support.

How to test

ToolWhat it proves
Keyboard onlyopen with Enter, focus inside, Tab cycles, Escape closes, focus returns
axe / Lighthouserole, name and ARIA attribute validity, contrast. Cannot judge focus behaviour.
Playwright / Testing Libraryautomated focus assertions: expect(trigger).toBeFocused() after close; background has inert

Traps

  • Calling dialog.show() (non-modal) and expecting inert background and backdrop. Use showModal().
  • Setting the open attribute manually: skips the top layer and the focus behaviour.
  • Believing aria-modal="true" blocks the background. It is a hint; use inert.
  • Hedging on facts you know (“I think it restores focus”). It does, per spec.
  • Animating display directly; use @starting-style and transition-behavior: allow-discrete verify support.

Likely follow-ups

How do you close on backdrop click with native dialog?
Listen for click on the dialog and check e.target === dialog (padding on an inner wrapper so content clicks do not match). Newer closedby attribute may do it declaratively verify.
Dialog vs popover?
Dialog modal blocks the page; popover is light-dismiss, non-modal, for menus and tooltips.
Where do you put the trigger label for confirmations?

What automated accessibility tools can catch

“Which accessibility problems can automated tools catch?” (follow-up)

Say this first (30 seconds)

“Automated tools catch a minority of problems, roughly a third to a half depending on how you count verify the source, and mostly the mechanical ones: missing alt attributes, missing form labels, insufficient colour contrast, invalid ARIA, duplicate ids, missing lang. They cannot judge meaning: whether alt text is good, whether focus order makes sense, whether a custom widget works with a keyboard, or whether a screen reader announces the right thing. Details worth knowing

  • Lighthouse runs a subset of axe-core rules and gives a score. A 100 does not mean accessible. It will not flag a div with a click handler.
  • axe-core is the engine behind most tools (browser extension, jest-axe, @axe-core/playwright, Storybook). Its rule set reports “violations”, “incomplete” (needs human review) and “passes”. Read the incomplete list.
  • Contrast checkers fail on gradients, images, hover states, and text over video.
  • Static lint (eslint-plugin-jsx-a11y) catches patterns such as click-without-key handler, alt missing, invalid roles.
  • WCAG basics: 4 principles (POUR: perceivable, operable, understandable, robust), levels A / AA / AAA; target AA, current version 2.2. Legal context: European Accessibility Act (applies from June 2025 verify), ADA and Section 508 in the US.

A realistic team process

  1. Design: contrast, focus states, target size and error states in the design system.
  2. Build: use native elements and an accessible primitive library.
  3. PR: lint + component axe tests; a keyboard walkthrough noted in the PR description.
  4. CI: axe on key pages, fail the build on new serious violations only (baseline the old ones).
  5. Release: screen reader pass on the top journeys; track issues in the backlog with severity.

Traps

  • Quoting a precise percentage with confidence. Say “roughly a third to a half”.
  • Treating a Lighthouse score as a compliance certificate.
  • Saying screen reader testing is optional. Different screen reader and browser pairs behave differently.
  • Testing only in Chrome with no assistive technology.

NVDA + Firefox or Chrome and JAWS + Chrome on Windows; VoiceOver + Safari on macOS and iOS; TalkBack + Chrome on Android.

AA: 4.5:1 for normal text, 3:1 for large text (18pt, or 14pt bold) and UI components.
How do you introduce accessibility into an existing product?
Audit key flows, baseline automated violations, fix design system components first (biggest leverage), add CI gating for new issues, train the team.
What is the difference between WCAG A, AA and AAA?
Increasing strictness. AA is the usual legal and contractual target; AAA is not required in full.

Web Components: when and when not

“Web Components: when would you use them and when not?”

Say this first (30 seconds)

“Web Components are the browser’s native component model: custom elements, shadow DOM for encapsulation, and templates with slots. They are framework-agnostic, so they fit a design system shared by React, Angular and plain pages, micro-frontends, and widgets embedded in third-party sites. I would not use them for an app that lives in one framework, where the framework’s components are simpler; or where SSR and SEO matter and I cannot use declarative shadow DOM; or for form-heavy components without extra work, because shadow DOM breaks label and ARIA id references and needs ElementInternals for forms.”

The four building blocks

  • Custom elements: customElements.define('my-card', class extends HTMLElement {…}). Name must contain a hyphen.
  • Shadow DOM: this.attachShadow({mode:'open'}) encapsulates markup and CSS.
  • HTML templates and slots: <template> clones markup; <slot> projects light DOM children (named slots too).
  • ES modules to ship and import them.

When to choose Web Components

  • One design system, many frameworks (React, Angular, legacy jQuery pages). Examples: Salesforce Lightning, Adobe Spectrum Web Components, Shoelace/Web Awesome, Material Web.
  • Micro-frontends and widgets embedded in sites you do not control (chat widgets, payment forms), where style isolation matters.
  • Long-lived UI primitives that should survive framework rewrites.
  • Progressive enhancement of server-rendered pages with small interactive pieces.

When not

  • The whole app is React/Angular with one team: framework components are simpler, have better tooling, and avoid shadow DOM friction.
  • SEO or first paint depends on server HTML: needs declarative shadow DOM (<template shadowrootmode="open">) or a framework such as Lit with SSR support verify tooling.
  • Rich forms and accessibility-heavy widgets: labels (for/id) and ARIA id references do not cross shadow boundaries; need ElementInternals and careful design cross-root ARIA is still evolving.
  • Global styling or CSS-in-JS expected to reach inside (utility CSS like Tailwind does not).
  • No one owns it long-term, or the team is small.

Notes you should know

  • No polyfill needed in modern browsers. jQuery and other libraries work with custom elements directly.
  • Lit (small library, reactive properties, templating) is the usual way to write them without boilerplate.
  • React: React 19 improved custom element support (props set as properties when defined, custom events). Earlier versions needed refs and manual event wiring check React docs.
  • Prefer native: <select>, <details>, <dialog>, popover before inventing a custom element. Customized built-ins (is="…") are not supported in Safari.
  • Theming strategy: expose CSS custom properties (design tokens), and ::part() for deliberate hooks. Do not leave users with only a closed shadow root.

Traps

  • “Web Components replace React.” They are a lower-level standard; there is no reactive rendering or state management built in.
  • Forgetting composed: true so the event never leaves the shadow root.
  • Reading attributes or children in the constructor (not available yet).
  • Using closed shadow roots for “security”. It is not a security boundary and blocks tools and testing.
  • Saying “needs a polyfill”. It does not in current evergreen browsers.

Likely follow-ups

How do you style a component from outside?
CSS custom properties (inherit through shadow), ::part() for exposed parts, and slotted content is styled by the page.
How do you make it work in a form?
static formAssociated = true and attachInternals() to set value, validity and participate in FormData.
Light DOM vs shadow DOM?
Light DOM component (no shadow root) gets page styles and accessibility refs but no encapsulation; choose per component.
How do you test them?
Playwright or Web Test Runner in a real browser; query through shadow roots with locators that pierce open roots.

Document head and resource hints

“What goes in the <head>, and in what order? What is the difference between preload, preconnect, prefetch and dns-prefetch?”

Say this first (30 seconds)

“The head is the page’s metadata and its resource plan. First <meta charset> within the first 1024 bytes, then the viewport meta, title, and the critical CSS and preload hints, then scripts with defer. Resource hints tell the browser what to do early: preconnect opens the connection to another origin now, preload fetches a resource I know the current page needs with high priority, prefetch fetches something for a likely next navigation at low priority, and dns-prefetch only resolves the DNS. I use them sparingly and measure, because too many hints compete for bandwidth.”

Essentials

  <meta name="color-scheme" content="light dark">
  <link rel="preconnect" href="https://cdn.acme.com" crossorigin>
  <link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin>
  <link rel="stylesheet" href="/app.css">

  <meta property="og:title" content="...">       <!-- social previews -->

Resource hints compared

  • preload requires as (and type, crossorigin for fonts). A preload that is not used within a few seconds gives a console warning. Preloading things already discoverable in markup is usually redundant.
  • preload is for things the preload scanner cannot find: fonts referenced from CSS, background images in CSS, resources injected by JS, the LCP image in CSS.

  • Preloading everything: priority inflation means the real critical resources compete with the rest.
  • Forgetting crossorigin on font preload: browser downloads it twice.
  • Mixing up preload (this page) with prefetch (next page).
  • Putting <meta charset> after a long title or scripts.

async, defer and module scripts

“async versus defer versus module scripts, and what each does to DOMContentLoaded.”

Say this first (30 seconds)

“A normal script blocks the HTML parser while it downloads and runs. async downloads in parallel and runs as soon as it arrives, interrupting the parser, in no guaranteed order, and DOMContentLoaded does not wait for it: right for independent scripts like analytics. defer downloads in parallel, runs after parsing finishes, in document order, before DOMContentLoaded: right for application code. A type="module" script is deferred by default, plus it is strict mode, has its own scope, runs once per URL, needs CORS, and supports import. Put them in the <head> so the browser finds them early.”

Rules to remember

  • async is for scripts that do not depend on anything else (analytics, ads), not for “dependent” ones.
  • defer and async only work on scripts with a src. async on a module overrides deferral: it runs when ready.
  • nomodule marks a fallback for browsers that do not understand modules (largely historic now).
  • Dynamically inserted scripts (document.createElement('script')) behave as async by default; set script.async = false to keep order.
  • CSS and scripts: a classic script cannot execute until earlier stylesheets have loaded, because it might read styles. A slow CSS therefore delays scripts as well as rendering.
  • Putting scripts at the end of <body> is outdated: the preload scanner finds them late. Use <script defer> in the head.
  • DOMContentLoaded: HTML parsed and deferred/module scripts done; stylesheets and images may still load. load: everything including images and sub-resources.

Which should I use? A quick guide

  • Your application bundle: type="module" (or defer).
  • Analytics, tag managers, ads: async, or inject after load / idle.
  • Script that must run before first paint (theme flag to prevent flash): a tiny inline classic script in the head.
  • Heavy third party: load on interaction or via a facade; Partytown/Worker for long-running ones.

Traps

  • Calling async “for scripts that depend on each other”. It is for independent scripts.
  • Expecting defer on an inline script to do anything.
  • Believing DOMContentLoaded waits for async. It does not.
  • Forgetting that modules need CORS headers when served from a CDN.

Does defer help LCP?
It stops scripts blocking HTML parsing, so content and the LCP element are discovered and painted earlier; execution cost still counts toward INP and TBT.
Why do modules need CORS?
They are fetched in CORS mode (credentials omitted by default) for same-origin and cross-origin loads alike.
What does import() do?
Dynamic import: loads a module on demand, returns a promise; the basis of code splitting.
Where does the bundler fit?
Bundlers (Vite, webpack) emit module scripts plus preload tags for chunks; configure code splitting and modulepreload.

Serving and preloading images for performance

“How do you serve and preload images for performance?”

From HTML to pixels: the rendering pipeline

“What does the browser do between receiving HTML and showing pixels; how do you speed it up?”

Say this first (30 seconds)

“The browser parses bytes into tokens and builds the DOM, parses CSS into the CSSOM, combines them into a render tree (anything with display:none is excluded), runs layout to compute geometry, paints the layers, and the compositor combines them on the GPU. CSS blocks rendering and later synchronous scripts; scripts block the parser. So I speed it up by sending less and sending it earlier: inline critical CSS, defer JS, preload what the scanner cannot see, preconnect to key origins, compress and cache, and keep the DOM small. I measure first with DevTools Performance, Lighthouse and WebPageTest, then verify with field data.”

Step by step

  1. Network: DNS, TCP, TLS (QUIC for HTTP/3), request, TTFB. The server may stream HTML so the browser starts early.
  2. Parse HTML: bytes → characters → tokens → nodes → DOM, incrementally as data arrives. A preload scanner runs ahead and starts downloads for images, scripts and styles it spots.
  3. Parse CSS into the CSSOM. Rendering waits until blocking CSS in the head is done (render-blocking), because painting unstyled content would flash.
  4. Run scripts (classic scripts stop the parser; they also wait for pending CSS).
  5. Style + render tree: combine DOM and computed styles; skip display:none and <head>.
  6. Layout (reflow): compute geometry for every box. Triggered again by size or position changes and by reading layout properties after writing (layout thrashing).
  7. Paint: convert boxes into draw instructions, per layer. Includes image decode.
  8. Composite: the compositor thread places layers on the GPU, which makes scrolling and transforms smooth even when the main thread is busy.

How to speed it up (and what each fixes)

Inline critical CSS, load the rest async (media trick or rel=preload)FCP, LCPkeep CSS small; avoid @import chains

How to measure

  • Lab: Chrome DevTools Performance panel (main thread, long tasks, layout, LCP marker), Lighthouse, WebPageTest (filmstrip, waterfall, real devices).
  • Field (real users): the web-vitals library to your analytics (RUM), CrUX / Search Console (28-day, 75th percentile).
  • Thresholds (good, p75): LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1.
  • Avoid unmeasured claims like “this massively reduces FCP”. Say what you would measure and the expected effect.

Traps

  • Saying “put scripts at the bottom of the body”. Outdated: use defer in the head.
  • Saying CSS blocks HTML parsing. It blocks rendering and later synchronous scripts, not parsing.
  • Skipping the second half of the question: the interviewer asks for speed-ups and measurement.
  • Forgetting layout, paint and composite and stopping at the DOM.

Likely follow-ups

What triggers a reflow?
Changing geometry (size, position, content), adding/removing elements, and reading properties such as offsetHeight or getBoundingClientRect() after a write.
What is a layer / will-change?
A hint that an element will change, so the browser may promote it to its own compositor layer. Overuse costs memory; use briefly.
FCP vs LCP vs TTI?
FCP: first content painted. LCP: largest content element painted. TTI is deprecated in favour of INP and TBT.

Server HTML paints early, but the page is not interactive until JS downloads and hydrates; use streaming SSR, Server Components and selective hydration to shrink that gap.

Say this first (30 seconds)

“An iframe isolates third-party content in its own browsing context, but it still has cost and risk. For safety I use sandbox with the minimum permissions, allow for specific features, a strict referrerpolicy, and I set a CSP frame-ancestors on my own pages to prevent clickjacking. For performance I add loading="lazy", set dimensions to avoid shift, and use a facade (a thumbnail that loads the real embed on click) for heavy players. For accessibility every iframe needs a meaningful title.”

Attributes that matter

AttributeEffect
sandboxWith no value: scripts, forms, popups, same-origin access all blocked. Add back only what is needed: allow-scripts, allow-forms, allow-popups. Never combine allow-scripts and allow-same-origin for untrusted content from your own origin: it can remove the sandbox.
allowPermissions Policy for the frame: allow="fullscreen; payment; camera 'none'".
loading="lazy"Defers offscreen iframes (maps, videos).
referrerpolicyLimits referrer data sent (strict-origin-when-cross-origin is the browser default).
titleAccessible name; screen readers list frames by it. Required (WCAG 4.1.2 / 2.4.1).
width/height or aspect-ratioPrevents layout shift when the embed loads.
srcdoc, credentiallessInline document; cookie-less embedding mode check status.

Protecting your own pages

  • Clickjacking: send Content-Security-Policy: frame-ancestors 'self' (or an allow-list). X-Frame-Options is the older equivalent.
  • postMessage: always check event.origin against an allow-list and validate the data; send to a specific targetOrigin, not "*".
  • CSP frame-src / child-src to limit which origins can be embedded.
  • Third-party cookies are being restricted; embedded auth and payment flows need explicit support (Storage Access API) verify current browser state.

Performance patterns

<!-- facade: load the heavy player only on click -->
<button class="yt" data-id="abc123" aria-label="Play video: Release demo">
  <img src="thumb.webp" width="560" height="315" alt="" loading="lazy">
</button>
<script type="module">
  document.querySelector('.yt').addEventListener('click', e => {
    const f = document.createElement('iframe');
    f.src = 'https://www.youtube-nocookie.com/embed/' + e.currentTarget.dataset.id + '?autoplay=1';
    f.title = 'Release demo'; f.allow = 'autoplay; fullscreen'; e.currentTarget.replaceWith(f);
  }, { once: true });
</script>

Other tools: lazy-load maps; use preconnect only if the embed is above the fold; run heavy scripts with Partytown/Web Worker; budget third parties (they often account for most of the main-thread time on marketing pages).

Traps

  • Embedding with no title, sandbox or size.
  • postMessage with "*" or no origin check.
  • Calling iframe isolation “secure” without sandbox or CSP.
  • Loading five tag-manager vendors synchronously in the head.

Likely follow-ups

Iframe vs Web Component for a widget?
Iframe: strongest isolation (security, separate JS/CSS), higher cost, awkward sizing and a11y. Web Component: lighter and integrated, but shares the JS realm and cookies.
How does an iframe resize to its content?
The child sends its height with postMessage (validated), parent sets the iframe height; or use a ResizeObserver in the child.
What does noopener protect against?
A link opened in a new tab getting access to window.opener and redirecting your page (tabnabbing).

Q17Added

Progressive enhancement and feature detection

“How do you approach cross-browser compatibility in HTML (and beyond)?”

Say this first (30 seconds)

“I build in layers. A baseline of semantic HTML that works everywhere, CSS that improves the layout, and JavaScript that adds behaviour, so a failure in one layer does not break the page. I decide support from data: a browserslist from our analytics, Baseline status from MDN and web-platform-dashboard for new features. I use feature detection and @supports rather than user-agent sniffing, add polyfills only where needed, and run cross-browser tests in CI with Playwright across Chromium, Firefox and WebKit, plus real devices for what matters most.”

HTML-level examples

  • Input types (date, email, number) fall back to text. Add pattern and a visible format hint.
  • <picture> falls back to the inner <img>; video multiple <source>; <noscript> for content that needs JS.
  • <dialog>, <details>, popover: now broadly supported, but check Baseline for newer attributes check MDN. Provide a fallback or polyfill if your support matrix needs it.
  • Unknown elements/attributes are ignored by browsers, which is why progressive enhancement is safe by design.
  • Forms should work with a plain POST and full page reload; JS upgrades to fetch.
/* CSS: fallback first, enhancement inside @supports */
.grid { display: flex; flex-wrap: wrap; gap: 1rem; }
@supports (display: grid) { .grid { display: grid; grid-template-columns: repeat(auto-fit, minmax(240px, 1fr)); } }

// JS: detect the feature, not the browser
if ('IntersectionObserver' in window) lazyLoadWithObserver(); else loadAll();
if (!HTMLDialogElement.prototype.showModal) await import('./dialog-polyfill.js');

Real-world cross-browser pain

  • Safari / iOS WebKit: all iOS browsers use WebKit; viewport units with dynamic toolbar (dvh, svh), form control styling, date inputs, autoplay rules, storage limits, newer features arrive later or differently.
  • Firefox: scrollbar styling, some CSS (:has arrived later), subpixel differences.
  • Chromium-only APIs: Speculation Rules, some Web APIs (Bluetooth, USB). Do not depend on them for core features.
  • Rendering differences: default styles (reset or normalize), font rendering, line-height: normal, form control appearance. Use a reset.
  • Interop effort: “Interop” yearly project aligns browsers on tests; web-platform-tests is the shared test suite.

Process an L4 candidate describes

  1. Define the support matrix with product and data (analytics), and write it down.
  2. Choose tooling to enforce it (browserslist, linters, transpile/polyfill by target).
  3. Automate cross-engine tests; keep a short manual checklist for visual and touch behaviour.
  4. Monitor in production: error tracking by browser, RUM by browser, a feature flag to disable a risky enhancement.
  5. Document known gaps and decisions (ADR) so the team does not re-litigate.

Traps

  • Listing tools without a strategy. Start with the support matrix and the layering principle.
  • User-agent sniffing, or assuming “Chrome = the web”.
  • Polyfilling everything for everyone; ship polyfills only to browsers that need them.
  • Forgetting accessibility tree differences between browsers and screen readers.

Likely follow-ups

Graceful degradation vs progressive enhancement?
Degradation starts from the full experience and patches down; enhancement starts from a baseline and adds. The second is more robust.
What is Baseline?
A shared label that says when a feature works across the core browsers (newly available, widely available).
How do you decide to drop a browser?
Traffic share and revenue from analytics, support cost, security (no updates), and legal or contractual requirements.
How would you test Safari without a Mac?
Playwright WebKit in CI approximates it; BrowserStack or real devices for final checks on iOS.
