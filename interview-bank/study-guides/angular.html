Angular architecture and comparison with React

“What is Angular and how does it differ from React? Explain the main building blocks, the CLI, standalone components versus NgModules, and when you would choose Angular over React.”

Say this first (30 seconds)

“Angular is a full, opinionated TypeScript framework from Google for building applications, whereas React is a UI library you assemble into a stack. Angular ships routing, forms, HTTP client, dependency injection, testing tools and a CLI, and uses templates with directives, classes decorated for components and services, RxJS for async streams and, in recent versions, signals for fine-grained reactivity. Modern Angular uses standalone components instead of NgModules. React gives flexibility and a huge ecosystem with more choices to make; Angular gives consistency and structure, which suits large teams and long-lived enterprise applications. Both are component-based with one-way data flow in practice; they differ in templating, state and change detection models, and in how much the framework decides for you.”

Details interviewers probe

  • Standalone components: since Angular 14 and default from 17, components, directives and pipes can be standalone: true (default in recent versions) and import what they need directly, replacing most NgModules; applications bootstrap with bootstrapApplication and provide services via provideRouter, provideHttpClient. NgModules remain in legacy code and some libraries; migration schematics exist verify version defaults.
  • Decorators and metadata: @Component (selector, template, styles, imports, changeDetection), @Directive, @Pipe, @Injectable, @Input/@Output (or signal-based input()/output()), @ViewChild, @HostListener. Angular compiles templates ahead of time (AOT) into efficient code.
  • Data binding syntax: interpolation {{ }}, property binding [prop]="expr", event binding (click)="handler()", two-way [(ngModel)] or model(), structural logic with @if/@for; one-way data flow with explicit two-way sugar.
  • Conceptual mapping from React: component ≈ component; props ≈ @Input/input(); callbacks ≈ @Output/output(); children ≈ content projection (<ng-content>); hooks ≈ lifecycle hooks and inject(); context ≈ dependency injection; useMemo ≈ computed(); useEffect ≈ effect() and lifecycle hooks; Redux ≈ NgRx; React Query ≈ RxJS + HttpClient or signal resources; Next.js ≈ Angular SSR/Analog.
  • Opinionated structure: consistent file layout (*.component.ts, .html, .scss, .spec.ts), style guide, CLI schematics, strict TypeScript, and formal patterns reduce decision fatigue and make large codebases uniform.
  • Release and support policy: major version every six months, each supported for about 18 months (including LTS), automated migrations via ng update; predictable upgrades are a selling point for enterprises verify the policy.
  • Ecosystem: Angular Material and CDK for UI primitives, NgRx for state, Nx for monorepos, ngx-translate or built-in i18n, Storybook, Cypress and Playwright, Analog for meta-framework features; fewer choices than React but more standardised.
  • When to choose Angular: large teams and long-lived products needing consistency, strong typing and conventions; organisations with Java/.NET backgrounds used to DI and layered structure; projects that value built-in features and predictable upgrades. When React: flexible UIs, rich ecosystem needs, Next.js features, smaller teams wanting control, and talent availability.
  • Honest trade-offs: Angular’s learning curve (RxJS, DI, decorators), historically verbose boilerplate (reduced in recent versions), and less flexibility; React’s ecosystem fragmentation and governance burden. Neither is universally better.
  • Related frameworks: Vue (progressive, template-based with reactivity like signals), Svelte (compiler), Solid (signals, JSX); Angular’s signals and control flow show convergence across frameworks.
  • Interview approach: do not criticise the framework you do not use; explain concepts via mappings, show you can pick up Angular quickly, and give a balanced decision framework.

Traps

  • Calling Angular “just an old AngularJS”. Angular 2+ is a different, TypeScript-based framework.
  • Describing Angular only as it was with NgModules and zone.js; modern Angular is standalone with signals.
  • Saying React is better or worse in general instead of by context.
  • Claiming Angular has no ecosystem choices; state and UI libraries still require decisions.
  • Mixing up AngularJS (1.x) and Angular.

Likely follow-ups

Library versus framework?
A library offers pieces you call; a framework defines the structure and calls your code; Angular includes routing, forms, DI and HTTP out of the box.
What are standalone components?
Components that declare their own dependencies via imports without an NgModule, simplifying structure and enabling better tree shaking.
How would you migrate a React skill set to Angular?
Map concepts (components, props, state, context) to inputs, signals and DI, then learn RxJS, the router and forms; the architecture ideas transfer directly.
Why do enterprises choose Angular?
Consistency, opinionated structure, built-in capabilities, TypeScript-first design and predictable long-term upgrades.

Components, templates and control flow

“Explain Angular components: inputs and outputs, templates, lifecycle hooks, content projection, view queries, directives, pipes and the new built-in control flow (@if, @for, @defer).”

Say this first (30 seconds)

“An Angular component is a TypeScript class with a template and styles, selected by a tag. Data flows in through inputs and out through outputs; in recent versions these are signal-based input() and output() functions. The template uses bindings for properties, events and two-way sync, pipes to transform values and, since Angular 17, built-in control flow blocks @if, @for with a required track expression, and @switch, replacing the older *ngIf and *ngFor directives. Lifecycle hooks such as ngOnInit and ngOnDestroy let me react to creation and destruction. Content projection with ng-content is the equivalent of React’s children, and @defer lazy-loads parts of a template with triggers.”

Details interviewers probe

  • Inputs and outputs: classic @Input() properties and @Output() event = new EventEmitter<T>(); signal-based input(), input.required(), output() and model() (two-way) in newer versions; input transforms (booleanAttribute); child never mutates the parent’s data directly: it emits events.
  • Templates: property binding ([disabled]="busy()"), attribute and class bindings ([class.active], [attr.aria-label]), event binding, template reference variables (#ref), safe navigation (?.), nullish coalescing, pipes (| date, | async, custom pipes), and template-local variables (@let in new versions verify). Templates are type-checked in strict mode.
  • Control flow blocks: @for (x of xs; track x.id) requires track (like React keys) for efficient DOM reuse; @empty handles empty lists; @if (cond; as value) aliases; @switch; they reduce the need for ng-container and structural directive imports.
  • @defer: declarative lazy loading of a template section with triggers (on viewport, on idle, on interaction, on hover, on timer, when cond), @placeholder, @loading, @error blocks, and prefetching; similar to React.lazy + Suspense but in templates.
  • Content projection: <ng-content> (default and selected slots) for composing components, ngTemplateOutlet with ng-template for render-prop-like customisation, @ContentChild to query projected content.
  • View queries: @ViewChild/viewChild(), viewChildren(), contentChild() to access elements or child components after the view initialises; signal-based queries update reactively.
  • Directives: attribute directives change behaviour or appearance ([appTooltip]), structural directives (legacy *ngIf) alter DOM structure, host bindings/listeners via host metadata, and directive composition API (hostDirectives) to reuse behaviour.
  • Pipes: pure by default (re-run when input reference changes), so cheap and cacheable; async pipe subscribes to observables and promises and unsubscribes automatically; impure pipes run every cycle and should be avoided; prefer computed signals for derived values.
  • Styles and encapsulation: emulated view encapsulation by default (scoped via attributes), ShadowDom or None modes; component styles apply only to their template; global styles in styles.scss; ::ng-deep is deprecated; design tokens via CSS variables work well.
  • Component communication: parent to child via inputs, child to parent via outputs, siblings via a shared service (signals or observables), and routing params; avoid reaching into other components through @ViewChild for logic.
  • Smart versus presentational components: container components inject services and manage state; presentational ones take inputs and emit outputs, often with OnPush change detection; the same idea as React’s container/presentational split.
  • Accessibility and CDK: Angular CDK provides accessibility primitives (focus trap, overlay, listbox, a11y utilities) similar to headless React libraries (E8).
  • Gotchas: forgetting track or using a poor key, heavy logic in template expressions (function calls run every cycle in default change detection), mutating inputs, and forgetting to unsubscribe from manual subscriptions.

Traps

  • Calling expensive functions in templates, which run on every change detection pass.
  • Using @for without a meaningful track expression.
  • Mutating an input object instead of emitting an event, hiding data flow.
  • Doing component setup in the constructor that needs input values (use ngOnInit or signals).
  • Leaving manual subscriptions open past ngOnDestroy.

Likely follow-ups

constructor versus ngOnInit?
The constructor wires dependencies (inject()) and runs before inputs are set; ngOnInit runs once after the first input values are available.
What is the async pipe for?
It subscribes to an observable or promise in the template, renders the latest value and unsubscribes on destroy, avoiding manual subscription management.
How does @defer help performance?
It code-splits and loads a template section on a trigger such as viewport entry, reducing initial bundle size and work.
How do you customise a child’s rendering?
Content projection with named slots, or template outlets passing ng-template with context, comparable to render props.

Dependency injection

“Explain Angular’s dependency injection system: injectors, providers, tokens, providedIn, hierarchical injection, inject() versus constructor injection, and how DI helps testing and architecture. How does it compare with React context?”

Say this first (30 seconds)

“Dependency injection is how Angular provides classes and values to the code that needs them: I declare a dependency, and the injector creates or finds an instance. A service is marked @Injectable({ providedIn: 'root' }) to be a tree-shakable singleton for the app, or provided at a component, route or environment level to scope its lifetime. Injectors form a hierarchy: a request is resolved from the nearest injector upward, so a component can override a service for its subtree. I request dependencies with inject(Service) or constructor parameters, and tokens, InjectionToken, let me inject configuration and interfaces. DI decouples code from implementations, which makes testing easy by providing fakes; React’s context covers part of this need but without constructors, scopes and lifecycle management.”

Details interviewers probe

  • Why DI: decouples consumers from implementations (program to interfaces and tokens), centralises construction, enables scoping and lifetimes, makes testing simple, and supports the dependency inversion principle (S8). Angular’s injector instantiates classes lazily on first request.
  • providedIn options: 'root' (application-wide, tree-shakable), 'platform', or specific environment injectors; services only included in the bundle if used. Alternative: list in providers of a component, route, or bootstrapApplication config.
  • Provider types: useClass (substitute implementation), useValue (constant or mock), useFactory (computed with deps or inject()), useExisting (alias); multi: true for collecting several providers under one token (HTTP interceptors in the legacy API, validators).
  • inject() function: works in injection contexts (constructor, field initialisers, factory functions, route guards, resolvers); enables functional guards and composable utility functions (injectUser()) similar to React hooks; preferred in modern code over constructor parameters for brevity and inheritance friendliness.
  • Scoping examples: a form-state service provided in a component to give each instance its own copy; a feature service provided on a lazy route so it exists only while that route is loaded; root singletons for auth and configuration.
  • Injection tokens for config and interfaces: TypeScript interfaces vanish at runtime, so use InjectionToken for abstractions (API_BASE_URL, FEATURE_FLAGS), optionally with a factory default.
  • Hierarchy and modifiers: @Self, @SkipSelf, @Optional, @Host (or inject(Token, { optional: true, skipSelf: true })) control lookup; used in directive and component library design.
  • Environment versus node injectors: environment injectors (root, route-level, EnvironmentInjector) hold services for app and lazy features; node injectors belong to the component tree; runInInjectionContext runs code with an injector programmatically.
  • Interceptors, guards and resolvers use DI: functional interceptors (HttpInterceptorFn) and guards use inject() to access services, avoiding class boilerplate.
  • Compared with React context: context passes values down at runtime and triggers re-renders; it is not a general object factory; DI constructs services with their own dependencies, supports hierarchical overrides and tree-shaking, and works outside the view tree. React achieves similar goals with props, context and module-level singletons, hooks for composition, and dependency injection patterns by convention (S8).
  • Common mistakes: circular dependencies between services, providing a service in multiple places and getting several instances unintentionally, heavy logic in constructors, and using services as global mutable bags without structure.
  • State in services: a root service with signals or BehaviorSubject is the standard lightweight state store; scale up to NgRx or signal stores when needed (NG9).

Traps

  • Providing a “singleton” service in a component’s providers and getting a new instance per component.
  • Injecting an interface type directly; interfaces do not exist at run time, so use a token or abstract class.
  • Circular dependencies between services.
  • Putting a lot of work in constructors rather than lifecycle hooks or factories.
  • Treating DI as only a testing convenience rather than an architectural tool for scope and decoupling.

Likely follow-ups

What does providedIn: 'root' mean?
The service is registered in the root injector as a tree-shakable application-wide singleton, created on first injection.
How do you get a new service instance per component?
Add it to the component’s providers, creating an instance for that component and its subtree.
How do you mock a service in a test?
Override its provider with useClass or useValue in TestBed.
Constructor injection or inject()?
Both work; inject() is concise, works in functions such as guards, and plays well with inheritance and composition.

Change detection and zoneless

“How does Angular detect changes and update the DOM? What are zone.js, the default and OnPush strategies, and how do signals and zoneless change detection change this? How does it compare with React’s rendering model?”

Say this first (30 seconds)

“Change detection is how Angular knows when to refresh templates. Traditionally zone.js patches browser APIs such as events, timers and promises, so whenever async work completes Angular runs change detection from the root, checking each component’s template bindings against previous values and updating the DOM where they differ. The default strategy checks every component; OnPush checks a component only when its inputs change by reference, an event originates in it, an observable bound with async emits, or it is marked dirty, which is a major optimisation. Signals refine this: a template that reads a signal is updated precisely when that signal changes, and with zoneless change detection Angular drops zone.js and relies on signals and explicit notifications. Compared with React, Angular tracks bindings and dependencies rather than re-running component functions.”

Details interviewers probe

  • zone.js: a library that patches async APIs (setTimeout, event listeners, promises, XHR/fetch) to tell Angular’s NgZone when tasks finish. After each, Angular calls ApplicationRef.tick(), running change detection top-down. Downsides: patching overhead, larger bundle, tricky stack traces, and unneeded checks.
  • Default strategy: every component’s bindings are compared on every cycle (dirty checking of template expressions), cheap per binding but costly in large trees or with expensive template functions. In development mode Angular runs a second pass to catch ExpressionChangedAfterItHasBeenChecked errors.
  • OnPush strategy: set changeDetection: ChangeDetectionStrategy.OnPush. The component’s view is checked only when marked dirty (see the diagram). Combine with immutable data (new object references) and observables with the async pipe or signals. Mutating an input object in place will not update an OnPush child.
  • Manual control: ChangeDetectorRef.markForCheck() (mark this and ancestors for the next cycle), detectChanges() (run now), detach()/reattach(); NgZone.runOutsideAngular() for high-frequency events (scroll, animation, third-party libs) that should not trigger detection.
  • Signals and fine-grained reactivity: reading a signal in a template registers a dependency; when it changes, Angular marks only that view for refresh, making OnPush-like behaviour automatic and enabling precise updates (NG5).
  • Zoneless: experimental then stable in newer versions verify the version; remove zone.js from polyfills and use provideZonelessChangeDetection(); code must notify Angular through signals, async pipe, or markForCheck; libraries must be compatible. Benefits: smaller bundles, simpler mental model, better performance.
  • Performance tips: OnPush everywhere, track in @for, avoid heavy template function calls (use computed or pure pipes), virtual scrolling (cdk-virtual-scroll), @defer, detach rarely changing parts, avoid deep object watching, and profile with Angular DevTools (change detection profiler).
  • Comparison with React in an interview: React re-renders components and relies on referential equality and memoisation to skip work; Angular compares bound values and can skip OnPush subtrees; signals bring Angular closer to Solid/Vue-style fine-grained reactivity, while React’s compiler automates memoisation (R5).
  • Common bugs: UI not updating because of in-place mutation under OnPush, updates from outside the zone (some third-party callbacks), ExpressionChangedAfterItHasBeenChecked caused by changing state during the check, and performance problems from impure pipes or getter-heavy templates.
  • Testing change detection: fixture.detectChanges() in tests; ComponentFixtureAutoDetect; zoneless testing helpers verify.
  • Migrating towards signals: replace @Input with input(), observables in templates with toSignal, derived getters with computed, and adopt OnPush then zoneless incrementally.

Traps

  • Mutating objects passed to OnPush components and wondering why the view is stale.
  • Calling expensive methods in templates under the default strategy.
  • Believing zone.js is part of the language; it is a library that Angular is moving away from.
  • Running high-frequency listeners inside the zone, triggering constant change detection.
  • Ignoring ExpressionChangedAfterItHasBeenChecked errors instead of fixing the data flow.

Likely follow-ups

What triggers change detection?
With zone.js, any completed async task in the zone (events, timers, HTTP); in zoneless, signal changes and explicit notifications.
When does an OnPush component update?
On input reference change, an event from it or its children, an async pipe emission, markForCheck, or a signal change in its template.
How do you run code without triggering change detection?
NgZone.runOutsideAngular() (or zoneless), then re-enter or update a signal when a UI update is needed.
Why is Angular’s model different from React’s?
Angular keeps compiled templates and checks or tracks bindings; React re-executes component functions and diffs element trees.

Signals and reactivity

“What are Angular signals? Explain signal, computed, effect, signal inputs, model, toSignal and toObservable. When do you use signals versus RxJS?”

Say this first (30 seconds)

“A signal is a reactive value container: I read it by calling it, count(), and write with set or update. Reading a signal inside a computed, an effect or a template automatically registers a dependency, so when the signal changes, only the derived values and views that depend on it update, with lazy and memoised computation. computed creates read-only derived state; effect runs side effects when dependencies change. Angular also offers signal-based inputs, outputs, two-way model and view queries. I use signals for synchronous state and derived values, and RxJS for asynchronous event streams that need operators such as debouncing, cancellation and combination; toSignal and toObservable bridge the two.”

Details interviewers probe

  • Writable signals: signal(initial); read with (); set(value), update(fn); for objects and arrays update immutably (update(list => [...list, item])) so equality checks detect changes; custom equal option available.
  • computed(): pure derived value, lazily evaluated, memoised until dependencies change; dependencies are tracked automatically at run time (including conditional branches); no side effects inside.
  • effect(): runs after change detection when its dependencies change; used for logging, syncing to localStorage, imperative DOM or third-party library updates; avoid using effects to propagate state (use computed); writing signals inside effects requires care (allowSignalWrites in some versions) verify; cleanup via the onCleanup callback; requires an injection context.
  • Signal inputs, outputs and models: input() returns a read-only signal, making derived values easy with computed; model() gives writable two-way bound signals; signal queries viewChild() update reactively.
  • Interop with RxJS: toSignal(observable$, { initialValue }) subscribes (and unsubscribes on destroy) and exposes the latest value as a signal; toObservable(signal) emits changes asynchronously; takeUntilDestroyed() for manual subscriptions. Prefer the async pipe or toSignal in templates.
  • Async data with signals: resource()/httpResource() (newer APIs) provide signal-based async state (value, status, error, reload) similar to TanStack Query-lite; evolving verify current API status.
  • Why signals matter: fine-grained updates reduce work, remove many ExpressionChanged issues, make OnPush/zoneless natural, and provide a simpler alternative to BehaviorSubject boilerplate for state.
  • Signals and RxJS division of labour: HTTP calls, user input streams, websockets, and anything with time-based operators remain observable-based; local UI state, derived values, and shared service state become signals. They complement each other.
  • State management with signals: a service with private writable signals and public readonly accessors (asReadonly()), derived computed selectors, and methods as actions; NgRx SignalStore offers structure (state, computed, methods, entities) for larger features.
  • Comparison with other frameworks: similar to Solid signals, Vue refs, Preact signals; React’s hooks re-render the component rather than tracking fine-grained dependencies; React’s compiler and useSyncExternalStore approach differ. TC39 has a signals proposal verify status.
  • Debugging and testing: Angular DevTools shows signal graphs in newer versions; tests set signals directly and call fixture.detectChanges(); effects can be flushed with TestBed.flushEffects() verify.
  • Gotchas: forgetting to call the signal (count versus count()), mutating arrays in place, creating effects outside an injection context, and using effects for derived state.

Traps

  • Forgetting the parentheses when reading a signal in templates or code.
  • Mutating an array or object held in a signal in place; equality does not change.
  • Using effect() to compute derived state instead of computed().
  • Claiming signals replace RxJS entirely.
  • Creating effects dynamically in places without an injection context.

Likely follow-ups

Signal versus BehaviorSubject?
A signal is synchronous with an always-available value and automatic dependency tracking; a BehaviorSubject is an observable with a current value, using subscriptions and operators.
Why is computed lazy and memoised?
It recalculates only when read after a dependency changed, avoiding unnecessary work and giving glitch-free derived values.
How do signals help change detection?
Templates that read signals are updated only when those signals change, enabling OnPush-like precision and zoneless apps.
When would you still choose RxJS?
For debounced search, cancellation with switchMap, merging event sources, retries, polling and websocket streams.

RxJS essentials

“What is RxJS and why does Angular use it? Explain observables, subscriptions, hot versus cold, subjects, the key operators (map, switchMap, mergeMap, concatMap, exhaustMap, debounceTime, combineLatest), error handling and avoiding memory leaks.”

Say this first (30 seconds)

“RxJS is a library for composing asynchronous and event-based programs with observables: lazy streams of values over time that I can transform with operators and subscribe to. Angular uses it for HTTP, router events, form value changes and reactive state. An observable does nothing until subscribed, and each subscription runs the producer again, which is a cold observable; subjects multicast to many subscribers. The operators I reach for are map and filter for transforming, debounceTime and distinctUntilChanged for input, combineLatest for joining streams, and the flattening operators for streams of requests: switchMap cancels the previous inner request, ideal for typeahead; concatMap queues; mergeMap runs in parallel; exhaustMap ignores new ones until done, good for submit buttons. I avoid leaks with the async pipe, takeUntilDestroyed and by always completing or unsubscribing.”

Details interviewers probe

  • Observable basics: lazy push-based collections that emit next values, then error or complete; subscribe() returns a Subscription with unsubscribe(); observables can be unicast (cold) or multicast. Differences from promises: multiple values, lazy, cancellable, operators, synchronous or asynchronous delivery.
  • Creation and conversion: of, from, interval, fromEvent, defer, timer, EMPTY; firstValueFrom/lastValueFrom convert to promises (needed for await); toSignal for templates.
  • Subjects: Subject (multicast, no replay), BehaviorSubject (current value, replays latest), ReplaySubject (replays N), AsyncSubject; commonly used for service state and event buses; expose as observables (asObservable()) to prevent outside next calls.
  • Transformation and filtering: map, tap (side effects), filter, take, takeUntil, first, distinctUntilChanged, debounceTime, throttleTime, scan (reducer), startWith.
  • Combination: combineLatest (latest of each, emits when any emits after all have emitted), forkJoin (waits for all to complete, last values; like Promise.all), merge, concat, zip, withLatestFrom, race.
  • Error handling and retry: catchError (return a fallback observable or rethrow), retry with delay/backoff config, finalize; errors terminate the stream, so catch inside the inner observable (as in the typeahead example) to keep the outer stream alive.
  • Sharing and caching: shareReplay({ bufferSize: 1, refCount: true }) to share an HTTP call among subscribers; be careful with stale caches and memory; share without replay for hot streams.
  • Memory leaks: forgetting to unsubscribe from long-lived observables (router events, intervals, subjects, valueChanges) in components leaves handlers and closures alive; fixes: async pipe, takeUntilDestroyed(destroyRef), takeUntil(destroy$) pattern, or converting to signals (J25).
  • Schedulers and testing: marble tests with TestScheduler (cold, hot, expectObservable) verify time-based logic; fakeAsync and tick in Angular tests.
  • Angular integration: HttpClient returns cold observables (one request per subscription); Router.events, ActivatedRoute.paramMap, FormControl.valueChanges, EventEmitter (observable-like) all use RxJS.
  • Comparison with React: React uses promises, async functions, effects and libraries for the same problems; RxJS gives a uniform operator toolkit. In React, TanStack Query handles caching and cancellation for requests; RxJS can be used but is not idiomatic (J19, E4).
  • Common mistakes: nested subscribes (“callback hell”) instead of flattening operators, wrong operator choice causing race conditions or duplicate requests, unhandled errors killing streams, and subscribing in templates and components twice.
  • Style guidance: keep pipelines readable, name streams with a trailing $, split complex pipelines into named observables, and keep side effects in tap or subscribers deliberately.

Traps

  • Nested subscribe calls instead of switchMap/mergeMap.
  • Using mergeMap for typeahead and getting out-of-order or stale results.
  • Letting an inner error complete the outer stream; catch inside the inner pipe.
  • Assuming every observable needs manual unsubscription (HTTP completes) or that none do (intervals and subjects need it).
  • Using BehaviorSubject everywhere when a signal is simpler.

Likely follow-ups

switchMap versus mergeMap?
switchMap cancels the previous inner observable when a new value arrives; mergeMap keeps all inner observables running concurrently.
combineLatest versus forkJoin?
combineLatest emits whenever any source emits (after each has emitted once); forkJoin waits for all to complete and emits the last values once.
Observable versus promise?
Observables are lazy, cancellable, can emit many values and have operators; promises are eager, single-valued and not cancellable.
How do you avoid duplicate HTTP calls from multiple subscribers?
Share the observable with shareReplay or cache in a service, or convert to a signal once.

Routing, guards and lazy loading

“How does the Angular router work? Define routes, nested routes, route parameters, guards, resolvers, lazy loading, preloading strategies and component input binding. How do you protect routes and structure large applications?”

Say this first (30 seconds)

“The Angular router maps URLs to components using a route configuration; <router-outlet> renders the matched component, nested routes use child outlets, and parameters are read from the route or bound directly to component inputs. Functional guards such as canActivate decide whether navigation proceeds, for authentication and authorisation; canDeactivate warns about unsaved changes; resolvers fetch data before activation. For performance I lazy-load feature routes with loadComponent or loadChildren so code downloads on demand, and use a preloading strategy to fetch likely routes in the background. Guards are a UX layer; authorisation must still be enforced by the backend.”

Details interviewers probe

  • Configuration and navigation: provideRouter(routes, ...features); routerLink directive and Router.navigate/navigateByUrl; routerLinkActive for active styles; wildcard route for 404; redirects (redirectTo with pathMatch); route titles (title), data and static data property; relative navigation.
  • Parameters: path params (:id), query params, fragments; read via ActivatedRoute.paramMap observables (they update when the same component is reused), snapshot for static reads, or with withComponentInputBinding() bind route params, query params and resolver data directly to component input()s.
  • Guards (functional): canActivate, canActivateChild, canDeactivate (unsaved changes), canMatch (decide whether a route config applies, enabling role-based route variants and avoiding loading code), and legacy canLoad. They use inject(), can return observables, promises, booleans or a UrlTree for redirects.
  • Resolvers: ResolveFn fetches data before the route activates, avoiding empty states but delaying navigation; modern alternatives: load in the component with signals and show skeletons; choose by UX.
  • Lazy loading: loadComponent for a single standalone component, loadChildren for route trees; code-split per route with the builder automatically; combine with @defer for in-page splitting. Preloading strategies (withPreloading(PreloadAllModules) or custom) trade bandwidth for speed.
  • Nested routes and outlets: child routes render in the parent’s <router-outlet>; named outlets for secondary routes (modals, side panels); layout components with shared headers and sidebars.
  • Route-level providers: providers on a route create an environment injector for that subtree, scoping services to the feature (NG3).
  • State and URL: keep shareable state (filters, pagination) in query parameters; queryParamsHandling: 'merge'; avoid storing large state in the URL; use Router.navigate with replaceUrl for incremental changes.
  • Security: guards improve UX but can be bypassed by calling APIs directly; enforce authorisation on the server; avoid exposing admin routes in navigation for unauthorised users but never rely on hiding; handle token expiry with interceptors (NG9) (N11).
  • Scroll and focus: withInMemoryScrolling for scroll restoration and anchor scrolling; manage focus and title for accessibility after navigation (R13).
  • Application structure: feature folders with their own routes files; shared core services and UI libraries; avoid circular imports between features; use Nx module boundaries for large repos (A3).
  • Router events and loading indicators: subscribe to NavigationStart/NavigationEnd/NavigationError to show progress; withViewTransitions() for view transition API support verify.
  • Testing routes: RouterTestingHarness or RouterTestingModule; test guards as functions with TestBed.runInInjectionContext.
  • SSR considerations: guards and resolvers run on the server too; avoid browser-only APIs; redirects become HTTP redirects (NG10).

Traps

  • Treating route guards as security rather than UX.
  • Reading route.snapshot.params in a component reused across different ids, so it never updates.
  • Eagerly importing lazy feature modules elsewhere, which pulls them into the main bundle.
  • Resolvers that block navigation on slow requests with no feedback.
  • Route order mistakes: the wildcard route placed before specific routes.

Likely follow-ups

canActivate versus canMatch?
canMatch decides whether a route configuration is considered at all (and avoids loading its code); canActivate runs after matching to allow or block activation.
How do you get route params in a component?
Inject ActivatedRoute and observe paramMap, or bind them to inputs with component input binding.
How do you lazy load a feature?
loadChildren: () => import('./feature/routes').then(m => m.ROUTES); the build creates a separate chunk.
How do you warn about unsaved changes?
A canDeactivate guard that checks the component’s dirty state and asks for confirmation.

Forms

“Compare template-driven and reactive forms in Angular. How do typed forms, FormGroup, FormArray, validators, async validators and custom form controls (ControlValueAccessor) work? How do they compare with React Hook Form?”

Say this first (30 seconds)

“Angular offers two forms approaches. Template-driven forms use directives like ngModel in the template and are quick for simple forms. Reactive forms define the form model in code with FormControl, FormGroup and FormArray; they are explicit, testable, strongly typed in recent versions, and the better choice for complex forms with dynamic fields and custom validation. The model exposes values, validity, dirty and touched state, and observables such as valueChanges. Validators are functions, sync or async, applied to controls or groups, and custom inputs integrate through ControlValueAccessor. Compared with React Hook Form, Angular’s forms are built in and model-driven, whereas RHF registers uncontrolled inputs and relies on a schema library.”

Details interviewers probe

  • Reactive building blocks: FormControl (single value), FormGroup (named controls), FormArray (dynamic list), FormBuilder (fb.group), FormRecord (dynamic keys). Since v14 forms are strictly typed: the model type is inferred, nonNullable avoids null resets, and getRawValue() includes disabled controls.
  • Template binding: [formGroup], formControlName, [formControl], formArrayName, formGroupName; display errors with @if (form.controls.email.errors?.['required'] && touched); ngSubmit on the form; novalidate to use Angular’s validation UI.
  • Validators: synchronous ValidatorFn returns an error map or null; group-level cross-field validators; asynchronous AsyncValidatorFn with a pending status; compose with Validators.compose; updateOn: 'blur' | 'submit' reduces noise; validators should be pure and fast.
  • Dynamic forms: add and remove controls (formArray.push, removeAt), build forms from JSON schemas or metadata, conditionally enable/disable controls with valueChanges, and keep the model and template in sync with @for and track.
  • Custom form controls: implement ControlValueAccessor for rating inputs, date pickers or wrappers over third-party widgets; provide NG_VALUE_ACCESSOR with forwardRef; also provide NG_VALIDATORS if the control validates itself; Angular Material components already implement this.
  • Template-driven forms: FormsModule, [(ngModel)], ngForm template references, validation attributes (required, pattern), simple but model is created asynchronously and harder to type and test.
  • UX and accessibility: show errors after touch or submit, associate messages with inputs (aria-describedby, aria-invalid), focus the first invalid control on submit, avoid disabling the submit button as the only feedback, and use autocomplete attributes (R8, R13).
  • Server integration: map server validation errors back to controls with control.setErrors({ server: 'msg' }); avoid duplicating rules by sharing schemas or generating validators from OpenAPI where practical (E6, T11).
  • Performance: big forms with many controls can be slow under default change detection; use OnPush, avoid heavy validators, updateOn: 'blur', and unsubscribe from valueChanges (use takeUntilDestroyed).
  • Comparison with React Hook Form: Angular owns the form model (a tree of controls with state) and integrates with templates and DI; RHF uses uncontrolled inputs, a resolver for Zod/Yup, and minimal re-renders. Angular’s reactive forms are more verbose but more structured; both support field arrays, async validation and custom controls (Controller ≈ ControlValueAccessor).
  • Testing: unit-test the form model and validators without the DOM; component tests set values and assert error display; test custom controls through a host component.
  • Signal forms: the Angular team has been developing signal-based forms to complement or replace the current API verify the current status.

Traps

  • Choosing template-driven forms for complex, dynamic forms and fighting the lack of explicit model.
  • Forgetting to unsubscribe from valueChanges and leaking subscriptions.
  • Putting heavy logic in validators that run on every keystroke.
  • Mutating form values directly instead of using setValue/patchValue.
  • Hiding validation messages from assistive technology by not associating them with fields.

Likely follow-ups

setValue versus patchValue?
setValue requires the whole model shape; patchValue updates only the provided fields.
How do you validate that two fields match?
A validator on the parent FormGroup that compares the controls and sets an error on the group or a control.
How do you build a custom date picker as a form control?
Implement ControlValueAccessor and register it with NG_VALUE_ACCESSOR so it works with formControlName.
Reactive or template-driven?
Reactive for anything beyond trivial forms; template-driven for quick, simple cases.

HTTP, state management and testing

“How do you make HTTP calls in Angular? Interceptors, error handling, caching. How do you manage state: services, NgRx, signal stores? How do you test components, services and routes? Compare with the React approach.”

Say this first (30 seconds)

“Angular’s HttpClient returns typed observables; I provide it with provideHttpClient() and add functional interceptors for cross-cutting concerns such as attaching auth tokens, refreshing on 401, logging and error mapping. For state, I start with services holding signals or BehaviorSubjects, and move to NgRx, with its store, actions, reducers, selectors and effects, or the lighter NgRx SignalStore, when state is shared widely and needs structure, devtools and predictable flows. I keep server data caching in mind, since Angular has no built-in TanStack Query equivalent. For testing I use TestBed with Jasmine and Karma or Jest and Vitest, component harnesses, HttpTestingController to mock HTTP, and Playwright or Cypress for end-to-end tests.”

Details interviewers probe

  • HttpClient basics: this.http.get<User[]>(url, { params, headers }) returns a cold observable (request starts on subscribe); typed generics are compile-time only (validate at boundaries, T11); observe: 'response' for headers and status; withFetch() to use the Fetch API; progress events for uploads; JSONP and XSRF support built in (cookie to header token).
  • Interceptors: functional HttpInterceptorFn chain registered with withInterceptors; common uses: add auth headers, refresh tokens on 401 (single-flight), global error handling and logging, loading indicators, caching, retry with backoff, request ids; order matters; avoid infinite loops on refresh calls.
  • Error handling: catchError in streams to map errors to user messages, global error handler via ErrorHandler provider for uncaught errors, retry strategies, distinguishing client, server and network errors; show errors in UI state, not only the console (J21).
  • Caching: simple in-service caches with shareReplay or a Map plus TTL; interceptor-based caches for GETs; TransferState to avoid duplicate requests during SSR hydration; for rich needs use TanStack Query’s Angular adapter or the newer resource APIs (E4).
  • NgRx: store (single state tree), actions (events), reducers (pure), selectors (memoised, composable), effects (side effects with RxJS), entity adapter for collections, router store, DevTools. Benefits: predictability, testability, tooling; costs: boilerplate and learning curve. createFeature, createActionGroup and signal selectors reduce boilerplate.
  • NgRx SignalStore and alternatives: signalStore(withState, withComputed, withMethods, withEntities) is lightweight and composable; alternatives include Akita (legacy), NGXS, Elf, and plain services. Do not adopt a global store by default: colocate state and promote it when sharing demands it (E1).
  • Service-based state pattern: private writable signals, readonly exposure, computed selectors, methods mutating state; async methods use HttpClient with toSignal or subscribe inside takeUntilDestroyed.
  • Testing tools: TestBed configures a testing module/environment; component fixtures with detectChanges; HttpTestingController expects and flushes requests; fakeAsync/tick/waitForAsync for async; component harnesses abstract DOM details (CDK HarnessLoader); Spectator and Testing Library for Angular improve ergonomics; Jest or the experimental Vitest builder replace Karma in many projects verify the current default runner.
  • What to test: behaviour through the template (inputs, outputs, rendered text), services’ logic, guards and interceptors as functions, form validators, route configs; avoid over-mocking; use real DI with fake providers (NG3).
  • End-to-end: Playwright or Cypress against the built app; mocking APIs with MSW or intercepts; visual tests with Storybook (Angular supported) (E10).
  • Comparison with React: Angular’s testing utilities and DI make unit testing services straightforward; React favours Testing Library and MSW for behaviour; both aim for user-centric tests.
  • Tooling and code generation: OpenAPI generators produce typed Angular services; schematics scaffold features consistently.

Traps

  • Subscribing to an HTTP observable twice and sending the request twice.
  • Adding a global store (NgRx) to a small app where services with signals suffice.
  • Refresh-token interceptors that trigger parallel refresh calls or infinite loops.
  • Testing implementation details (private methods, internal observables) instead of behaviour.
  • Assuming the generic type on http.get<T> validates the response.

Likely follow-ups

How do you attach an auth token to every request?
A functional HTTP interceptor that clones the request with an Authorization header, registered through provideHttpClient(withInterceptors([...])).
When is NgRx justified?
Large apps with complex, widely shared state, strict predictability needs and team familiarity; otherwise services with signals or a SignalStore are simpler.
How do you test a service that calls HTTP?
Use HttpTestingController to assert the request and flush a mock response, without a real network.
How do you cancel an in-flight request?
Unsubscribe or use switchMap; takeUntilDestroyed cancels on component destruction.

Performance, SSR and migration

“How do you optimise an Angular application? Bundle size, lazy loading, @defer, OnPush, virtual scrolling, SSR and hydration. How do you upgrade between versions or migrate from AngularJS or to standalone and signals? When would you choose Angular or React?”

Say this first (30 seconds)

“For Angular performance I work on four fronts. Load: lazy-load routes, use @defer for heavy template sections, optimise images with NgOptimizedImage, and analyse bundles. Runtime: OnPush and signals, track in @for, avoid heavy template calls, virtual scrolling for long lists, and running noisy code outside the zone. Rendering: server-side rendering with hydration and incremental hydration for faster first paint and SEO. Build: the modern esbuild and Vite builder and zoneless apps reduce size and time. For upgrades I follow the six-month release cadence with ng update migrations, moving incrementally to standalone components, new control flow, signals and zoneless. I choose Angular for large, long-lived team projects and React for flexibility and ecosystem reach.”

Details interviewers probe

  • Bundle size and loading: route-level lazy loading, @defer triggers, removing unused imports from standalone components, avoiding large libraries (moment, whole lodash), budgets in angular.json that fail builds, analysing with source-map-explorer or esbuild metafile, differential loading is obsolete for modern targets; check Material and CDK imports.
  • Images and assets: NgOptimizedImage (ngSrc) provides lazy loading, priority for LCP, required dimensions, srcset and CDN loaders, and warnings for common mistakes (F3).
  • Runtime performance: OnPush, signals, trackBy/track, pure pipes or computed over method calls in templates, virtual scrolling (cdk-virtual-scroll-viewport), batching updates, debouncing inputs, detaching change detection, and profiling with Angular DevTools plus the browser Performance panel (F4, F5).
  • Server-side rendering: ng add @angular/ssr (Angular Universal merged); renders on the server to HTML, transfers state, and hydrates instead of re-rendering; non-destructive hydration is stable; incremental hydration with @defer (hydrate on ...) hydrates parts on demand verify the current status; prerendering (SSG) for static routes; route-level render modes (server, prerender, client) in newer versions. Avoid direct window/document access (use isPlatformBrowser, afterNextRender) (N8).
  • Hydration pitfalls: mismatched DOM between server and client (manual DOM manipulation, random values), third-party libraries using the DOM directly (use ngSkipHydration for them), and time-dependent output.
  • Build system: the application builder uses esbuild and Vite (faster builds, dev server HMR), replacing the webpack-based browser builder; configure budgets, source maps, and optimisation; Nx or Turborepo for monorepos with caching.
  • Upgrading Angular: follow update.angular.io, update one major version at a time, use ng update @angular/core @angular/cli and ng update for Material and other libraries, run unit and e2e tests, adopt schematics (standalone, control flow, inject, signal inputs), and keep dependencies compatible; major releases come about every six months, with 18 months support.
  • Migrating from AngularJS: ngUpgrade hybrid apps to run both frameworks and migrate component by component, or a strangler approach with micro-frontends; AngularJS has long been end-of-life, so security is a driver; plan data, routing and styling carefully (A4).
  • Migrating between frameworks: prefer gradual strangler migration behind a shell or micro-frontends, share the design system as web components or CSS tokens, and avoid big-bang rewrites (A2, S9).
  • Choosing Angular versus React as a lead: evaluate team skills and hiring market, application size and lifetime, need for consistency and governance, ecosystem needs (Next.js, React Native), build tooling preferences, existing codebase, backend alignment (Angular often pairs with .NET/Java teams), and total cost. State a recommendation with trade-offs; avoid dogma.
  • Interview posture for an optional skill: be honest about depth: explain concepts through mappings from React, demonstrate you understand DI, RxJS, change detection and signals, and show you could be productive within weeks.
  • Resources and ecosystem to cite: Angular Material and CDK, Nx, NgRx, Angular DevTools, Storybook, Analog (meta-framework), Playwright, Cypress; official docs at angular.dev.

Traps

  • Skipping major versions during upgrades, then facing huge breaking changes.
  • Using browser globals in code that also runs on the server.
  • Calling a migration “done” while still depending on zone.js patterns and NgModules without a plan.
  • Optimising with OnPush but mutating objects, causing missing updates.
  • Advocating a framework switch without considering team and migration cost.

Likely follow-ups

How do SSR and hydration improve performance?
The server sends rendered HTML for fast first paint and SEO, and hydration attaches behaviour to the existing DOM instead of rebuilding it.
How do you find what makes an Angular app slow?
Profile with Angular DevTools’ change detection profiler and the browser Performance panel, inspect bundles, and check long tasks and template functions.
How do you upgrade a large Angular app safely?
One major at a time with ng update, schematics for standalone and new control flow, strong tests, and incremental adoption of signals.
Angular or React for a new enterprise dashboard?
Angular if the team values structure, built-in forms/DI and long-term consistency; React if flexibility, Next.js and ecosystem breadth matter more; decide with team and hiring context.
