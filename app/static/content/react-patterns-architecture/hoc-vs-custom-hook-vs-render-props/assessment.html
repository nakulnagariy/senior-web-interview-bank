QUESTIONS
Q1theorymust-know
All three patterns solve the same problem. Explain precisely what that problem is, why React's model makes it hard, and how each pattern attacks it differently at the structural level.
Senior expectation: Must articulate that the problem is cross-cutting stateful logic. Must explain why inheritance fails in React and how each pattern achieves reuse through composition instead.
The core problem: logic like "track window size", "fetch data with loading/error", "detect online status" doesn't belong to one component — yet many components need it. You can't extract it into a plain utility because it involves React state and lifecycle. Inheritance (the class-based OOP solution) doesn't compose well — a component can only extend one class, and mixins caused silent method collisions in early React.

Each pattern's structural attack:

HOC — wraps at the component tree level. Takes a component, returns an enhanced version that injects computed values as props. The wrapped component stays unaware of the logic source. Reuse = import and apply the HOC at the module level.

Render props — inverts control at the JSX level. A provider component manages state and passes it back to a consumer function that decides what to render. Logic and rendering are decoupled by making rendering a parameter.

Custom hooks — extract logic at the function level. The component calls the hook like any function and gets back values. No extra nodes in the tree, no props juggling — pure function composition.

Hooks won because they add zero structural overhead. HOC and render props both add wrapper nodes to the component tree; hooks add none. They also compose trivially: const { data } = useFetch(url); const { theme } = useTheme(); — two lines, no nesting.
Q2gotchamust-know
This HOC has four serious problems. Identify all of them and explain how each breaks real applications.
function withLogger(WrappedComponent) { return function(props) { const [logs, setLogs] = useState([]); useEffect(() => { setLogs(prev => [...prev, `render at ${Date.now()}`]); }); // no dep array return <WrappedComponent logs={logs} {...props} />; }; } const Enhanced = withLogger(Button); const DoubleEnhanced = withLogger(withLogger(Button));
Senior expectation: Must catch all four — missing displayName, prop collision, infinite render loop from missing deps, and how composition doubles every problem.
Problem 1 — Missing displayName. React DevTools shows the wrapper as "Component" or anonymous. In a tree with 5 HOCs you cannot identify anything. Fix: set WithLogger.displayName = `withLogger(${WrappedComponent.displayName || WrappedComponent.name})`.

Problem 2 — Prop name collision. If Button already accepts a logs prop for its own purpose, the HOC silently overwrites it. HOCs inject props with no awareness of the wrapped component's API. This causes invisible bugs that are nearly impossible to trace. Fix: namespace injected props or use a unique symbol key.

Problem 3 — Infinite render loop. useEffect with no dep array runs after every render. It calls setLogs, which triggers a re-render, which fires the effect again — infinite loop. Fix: add a dep array. But the deeper issue is that this pattern is architecturally wrong — logging is a side effect that should not live in state.

Problem 4 — Composition multiplies all bugs. DoubleEnhanced has two anonymous wrappers in DevTools, two logs props (outer overwrites inner), and two infinite loops running simultaneously. HOC problems are not additive — they compound.
HOC rules you must always follow: copy static methods with hoistNonReactStatics, always set displayName, always forward refs via React.forwardRef, never mutate the WrappedComponent directly.
Q3codingmust-know
Implement "data fetching with loading/error state" three ways — as an HOC, a render prop component, and a custom hook. Then say which you'd ship to production and exactly why.
Senior expectation: All three implemented correctly. The hook version adds the cancelled flag for unmount safety. Production answer is the hook with specific structural reasons — not just "hooks are modern."
// HOC version function withFetch(WrappedComponent, url) { function WithFetch(props) { const [data, setData] = useState(null); const [loading, setLoading] = useState(true); const [error, setError] = useState(null); useEffect(() => { fetch(url).then(r => r.json()).then(setData) .catch(setError).finally(() => setLoading(false)); }, []); return <WrappedComponent data={data} loading={loading} error={error} {...props} />; } WithFetch.displayName = `withFetch(${WrappedComponent.name})`; return WithFetch; } // Render prop version function Fetch({ url, children }) { const [state, setState] = useState( { data: null, loading: true, error: null } ); useEffect(() => { fetch(url).then(r => r.json()) .then(data => setState({ data, loading: false, error: null })) .catch(err => setState({ data: null, loading: false, error: err })); }, [url]); return children(state); } // Usage: <Fetch url="/api">{({ data, loading }) => ...}</Fetch> // Custom hook version — ship this function useFetch(url) { const [data, setData] = useState(null); const [loading, setLoading] = useState(true); const [error, setError] = useState(null); useEffect(() => { let cancelled = false; setLoading(true); fetch(url).then(r => r.json()) .then(d => { if (!cancelled) setData(d); }) .catch(e => { if (!cancelled) setError(e); }) .finally(()=> { if (!cancelled) setLoading(false); }); return () => { cancelled = true; }; }, [url]); return { data, loading, error }; }
Ship the custom hook. Specific reasons: (1) Zero component tree overhead — no extra node in DevTools. (2) Consumer controls rendering completely — no prop namespace risk. (3) Composes trivially: const a = useFetch('/a'); const b = useFetch('/b'); — two lines vs nested wrappers. (4) Testable with renderHook in isolation. (5) The cancelled flag for unmount safety is clean in a hook — in an HOC it would require additional lifecycle wiring.
The render prop version still has value as a library API — headless UI libraries like Downshift use it so consumers have full rendering control without knowing the library's internals.
Q4architecture
A colleague says "just make a custom hook" for a VirtualList component that manages scroll position, visible item range, and item measurement internally. Why is render props actually correct here? What is the general rule for when render props still win over hooks?
Senior expectation: Must articulate that render props win when the provider must own a DOM node that coordinates with consumer rendering. A hook cannot render a scroll container — it has no JSX. This is the surviving use-case for render props in modern React.
A custom hook can only return values and functions — it cannot render a DOM node. VirtualList needs to own its scroll container: attach a ref, measure height, listen to scroll events, and compute visible indices — all tied to a specific DOM element it controls. If you extract this to a hook, the consumer is forced to wire up the scroll container themselves, breaking the abstraction and duplicating the setup in every consumer.

With render props: <VirtualList items={items}>{({ visibleItems, itemStyle }) => visibleItems.map(i => <div style={itemStyle(i)}>...</div>)}</VirtualList> — the list owns its DOM, the consumer owns item rendering. This is exactly why react-window and react-virtual use this pattern.

General rule: hook = pure logic. Render prop = logic that must own rendering infrastructure (a scroll container, a drag surface, a canvas, a portal mount point). If the shared logic requires a specific DOM node to exist and be controlled by the abstraction, render props or a compound component is correct.
Q5gotcha
You need to protect 20 routes so only authenticated users can access them. Junior proposes a hook: const {'{'}isAuth{'}'} = useAuth() inside each page with an early redirect. You propose an HOC. Who is right — and how does the answer change with React Router v6?
Senior expectation: Must identify the flash-of-content problem with the hook approach. Must know the HOC fixes it by never mounting the component. Must know React Router v6 layout routes make both approaches redundant.
The hook approach has a critical flaw: on the render where isAuth resolves to false, the component body executes briefly before the redirect — potentially triggering data fetches, subscriptions, or visible UI flicker. For 20 pages this is 20 places to get it wrong.

The HOC solves this: it checks auth before mounting the wrapped component at all. If unauthed, it redirects — the component body never runs. This is structurally safer.

But in React Router v6, the correct answer is neither. Use a layout route:
<Route element={<RequireAuth />}> <Route path="/dashboard" element={<Dashboard />} /> <Route path="/settings" element={<Settings />} /> </Route> // RequireAuth.jsx function RequireAuth() { const { isAuth } = useAuth(); return isAuth ? <Outlet /> : <Navigate to="/login" replace />; }
RequireAuth renders <Outlet /> if authed — child routes never mount if not. No HOC wrapper hell, no per-page hook check, no flicker. The senior signal here: know what the framework gives you before reaching for a pattern.
Q6designmust-know
Give your decision framework: how do you choose between these three patterns in a real codebase today? The interviewer will push back if your answer is just "always use hooks."
Senior expectation: A nuanced framework that acknowledges legitimate surviving uses for HOC and render props. Must not be dogmatic. Should frame it as a decision tree, not a ranking.
PatternUse whenAvoid when
Custom hook Logic is purely stateful or computational. Data fetching, timers, subscriptions, form state, media queries. Covers ~90% of cases. Trivially testable with renderHook. Logic requires a DOM node to exist — hooks have no JSX.
Render prop Logic must own a DOM node (scroll container, drag surface, portal). Also ideal for headless library APIs where consumers need full rendering control. Simple stateful logic with no DOM ownership — a hook is cleaner.
HOC Enhancing third-party components you can't modify. Class component codebases. Applying the same enhancement declaratively at import time across many components. New code where hooks are available. Never stack more than 2 HOCs.
The meta-principle: default to custom hooks. Reach for render props when the logic needs to own DOM infrastructure. Reach for HOCs when you need to enhance components at the declaration site rather than inside their body — or when dealing with class components or third-party component APIs. Note that React.memo and React.forwardRef are HOCs from React itself — so HOCs are not deprecated, just no longer the first tool you reach for.
Interview closer: "In practice I use all three in the same codebase. Custom hooks for data and state logic, render props for our virtualized table internals, and HOCs for wrapping third-party chart components with our error boundary and loading skeleton."
Score guide: Q1 is the foundation — if shaky here, Q6 will fall apart. Q2 is the HOC gotcha most people partially answer. Q3 tests if you can implement, not just describe. Q4+Q5 are the questions that prove real-world experience. Q6 is the synthesis — a dogmatic "always use hooks" answer is a red flag to senior interviewers.
