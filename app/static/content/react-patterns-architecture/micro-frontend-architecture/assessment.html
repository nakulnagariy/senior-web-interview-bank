Questions
Q1 architecture must-know
Compare the four main micro-frontend integration strategies â€” build-time (npm packages), runtime via Module Federation, iframes, and Web Components. For each, give one real production scenario where it is the correct choice and one where it fails badly.
Senior expectation: Must go beyond surface-level definitions. Must articulate the deployment coupling problem with npm packages, the shared singleton problem with Module Federation, the iframe communication overhead, and the browser support / SSR limitations of Web Components. Each "fails badly" case should be a real scenario, not a vague trade-off.
Build-time (npm packages):
Correct for: a shared design system â€” Button, Input, Modal â€” consumed by multiple teams. These components change infrequently and all teams can align on a release cycle. Type safety and tree-shaking benefits outweigh the coordination cost.
Fails badly when: teams need independent deployment. A patch to fix a checkout MFE bug requires every consuming team to update and redeploy simultaneously. One team's release schedule blocks another's hotfix â€” the core deployment coupling problem.

Runtime via Module Federation:
Correct for: large product suites where teams need truly independent deploy cadences. The checkout team ships at 2pm, the catalog team ships at 4pm â€” the shell loads both at their latest URL without rebuilding. Zero coordination required.
Fails badly when: shared singletons are mismanaged. If React is not declared as a singleton shared dependency, each remote bundles its own React copy. Two React instances = two Context registries = Provider in remote A invisible to consumer in remote B.

Iframes:
Correct for: embedding third-party or legacy content with guaranteed style and script isolation â€” a payment widget, a legacy CRM screen. Hard security boundary is the feature, not the limitation.
Fails badly when: UX requires seamless integration. Iframes cannot share DOM, modal dialogs are clipped at the iframe boundary, cross-origin postMessage communication is required for every interaction, and keyboard navigation and accessibility patterns break.

Web Components:
Correct for: framework-agnostic components shared across a mixed-framework estate â€” a Vue team consuming a component from a React team. The Custom Element API is framework-neutral by design.
Fails badly when: SSR is required. Web Components render as empty shells during SSR, creating large CLS and blank initial states. React's synthetic event system does not bubble through Shadow DOM boundaries, breaking standard event patterns.
Q2 architecture must-know
Explain exactly how Webpack Module Federation works under the hood â€” what the host and remote webpack configs look like, how the runtime resolves remote modules, and what "singleton" sharing means and why it's critical for React.
Senior expectation: Must show both webpack configs with correct plugin syntax. Must explain the remoteEntry.js bootstrap file mechanism. Must explain singleton sharing â€” React must be a singleton across all MFEs or Context, hooks, and reconciliation break. Should mention version negotiation and what happens on version mismatch.
Module Federation generates a remoteEntry.js for each remote â€” a manifest + runtime that declares exposed modules and shared dependencies. The host loads this file at runtime via dynamic script injection.

Remote webpack config (Checkout MFE):
// checkout/webpack.config.js new ModuleFederationPlugin({ name: 'checkout', filename: 'remoteEntry.js', exposes: { './CheckoutPage': './src/CheckoutPage', './CartSummary': './src/CartSummary', }, shared: { react: { singleton: true, requiredVersion: '^18.0.0' }, 'react-dom': { singleton: true, requiredVersion: '^18.0.0' }, }, })
Host (shell app) webpack config:
// shell/webpack.config.js new ModuleFederationPlugin({ name: 'shell', remotes: { checkout: 'checkout@https://checkout.myapp.com/remoteEntry.js', }, shared: { react: { singleton: true, requiredVersion: '^18.0.0' }, 'react-dom': { singleton: true, requiredVersion: '^18.0.0' }, }, })
Consuming a remote module in the shell:
const CheckoutPage = lazy(() => import('checkout/CheckoutPage')); function App() { return ( <Suspense fallback={<PageSkeleton />}> <Route path="/checkout" element={<CheckoutPage />} /> </Suspense> ); }
Why singleton: true is critical for React: Without it, if the shell has React 18.2.0 and checkout has React 18.0.0, Module Federation loads both. Two separate React instances = two reconcilers, two Context registries, two hook state systems. A useContext(AuthContext) in checkout reads from a different registry than the Provider in the shell â€” silently returns the default value. With singleton: true, version negotiation picks one React version and shares it across all MFEs.
Version mismatch warnings from Module Federation in prod are often ignored. They shouldn't be â€” a remote expecting React 18 hooks behaviour running on React 17 will silently break features. Pin requiredVersion ranges tightly and treat version warnings as build failures in CI.
Q3 gotcha must-know
Cross-MFE communication is one of the hardest problems in micro-frontend architecture. A user logs in via the Auth MFE â€” the Header MFE needs to show their name, and the Cart MFE needs their userId to load their cart. Design a communication architecture that keeps MFEs decoupled. Give at least three approaches with their trade-offs.
Senior expectation: Must identify that the core tension is decoupling vs coordination. Must give at least three concrete patterns with real trade-offs. Should explain why shared Redux store is a coupling trap and why the URL is underrated as a communication channel.
Approach 1 â€” Custom event bus (pub/sub on window):
// Auth MFE â€” emits after login window.dispatchEvent(new CustomEvent('mfe:auth:login', { detail: { userId: '123', name: 'Alice', token: 'jwt...' } })); // Header MFE â€” listens window.addEventListener('mfe:auth:login', (e) => { setUser(e.detail); }); // Cart MFE â€” listens window.addEventListener('mfe:auth:login', (e) => { loadCart(e.detail.userId); });
Trade-offs: completely decoupled â€” MFEs don't import each other. Events are fire-and-forget â€” no guarantee a listener is registered when the event fires (race condition on slow-loading MFEs). No type safety without a shared event schema contract.

Approach 2 â€” Shared state store via Module Federation:
// shell exposes a Zustand store exposes: { './store': './src/store' } // Remote MFE consumes it import { useAuthStore } from 'shell/store'; const { user } = useAuthStore();
Trade-offs: strongly typed, reactive, works like a normal store. Creates a hard runtime dependency on the shell â€” the MFE cannot run standalone. Tightly couples MFE lifecycle to shell version. Good for auth/session state; bad for feature-specific state.

Approach 3 â€” URL as the source of truth:
// After login, shell navigates to: /dashboard?userId=123&sessionId=abc // Each MFE reads what it needs from the URL independently const userId = new URLSearchParams(location.search).get('userId');
Trade-offs: zero coupling â€” each MFE is completely independent. Deep-linkable, bookmarkable, survives page refresh. Limitation: sensitive data (tokens) must not go in the URL. Complex state is cumbersome to encode.

Approach 4 â€” BroadcastChannel API: For cross-tab or cross-iframe communication without a shared window: new BroadcastChannel('mfe-auth') posts messages to all MFEs on any tab. Survives iframe boundaries unlike CustomEvent.

Production recommendation: URL for persistent shared state, CustomEvents for transient notifications (login, logout, cart updated), shared Zustand store (via MF) only for truly global reactive state.
Q4 gotcha
CSS isolation is a silent killer in micro-frontend apps. Describe every way styles can leak between MFEs and for each one explain the correct isolation technique â€” including the trade-offs of each approach.
Senior expectation: Must cover global class name collisions, CSS custom property leakage, CSS-in-JS style tag injection ordering, and reset/normalise stylesheet conflicts. Must evaluate Shadow DOM, CSS Modules, BEM namespacing, and CSS-in-JS isolation. Must know that Shadow DOM breaks global portals and React modals.
Problem 1 â€” Global class name collisions: MFE-A defines .button { background: blue }. MFE-B defines .button { background: red }. Whichever loads last wins, breaking the other MFE's styles randomly.
Fix: CSS Modules (generates .button_a3f2k scoped hashes at build time) or strict BEM namespacing (.checkout__button). CSS Modules is better â€” enforced by tooling, not convention.

Problem 2 â€” Global reset/normalise conflicts: Both MFEs include their own normalize.css. They stack â€” the last loaded reset wins for each property.
Fix: The shell owns the global reset. MFEs never include their own global resets â€” only scoped component styles.

Problem 3 â€” CSS custom property leakage: MFE-A sets :root { --color-primary: blue }. Since :root is the document root, MFE-B inherits this, overriding its own design tokens.
Fix: Scope custom properties to a container: [data-mfe="checkout"] { --color-primary: green }. Each MFE wraps itself in a container with its own scope.

Problem 4 â€” CSS-in-JS style injection ordering: Emotion and styled-components inject <style> tags into document head. Two MFEs using different library versions interleave style tags unpredictably â€” specificity ordering becomes non-deterministic.
Fix: All MFEs must use the same CSS-in-JS library version (Module Federation singleton). Or use CSS Modules â€” build-time scoping has no runtime injection ordering problem.

Shadow DOM â€” the nuclear option:
const shadow = document.getElementById('mfe-checkout').attachShadow({ mode: 'open' }); const root = ReactDOM.createRoot(shadow); root.render(<CheckoutApp />);
Trade-offs of Shadow DOM: global CSS (Tailwind, design tokens, fonts) does not penetrate Shadow DOM â€” must be duplicated inside each shadow root. React portals render outside the shadow root into the light DOM â€” modal overlays escape their style scope. Third-party components that rely on global styles break.
Pragmatic production choice: CSS Modules for all component styles + BEM namespace prefix for any unavoidable global classes + shell owns global resets and design tokens. Shadow DOM only for true third-party widget isolation.
Q5 architecture
Design the deployment and CI/CD pipeline for a micro-frontend system with one shell app and four feature MFEs. Address: independent deployability, versioning strategy, rollback, feature flags for MFEs, and how you handle the "chunk hash mismatch" problem when the shell caches a stale remoteEntry.js URL.
Senior expectation: Must design truly independent pipelines. Must address the remoteEntry.js caching problem specifically â€” the most common production incident in MFE systems. Must cover rollback without requiring shell redeploy and feature flags at the MFE loading level.
Independent CI/CD pipelines: Each MFE has its own pipeline triggered by commits to its own repository. The pipeline: test â†’ build â†’ deploy assets to CDN â†’ update a central manifest. The shell reads this manifest at runtime and has no knowledge of individual MFE deployments.
// manifest.json â€” served with Cache-Control: no-store, updated by each MFE's pipeline { "checkout": "https://cdn.myapp.com/checkout/v2.4.1/remoteEntry.js", "catalog": "https://cdn.myapp.com/catalog/v1.9.0/remoteEntry.js", "cart": "https://cdn.myapp.com/cart/v3.1.0/remoteEntry.js", "auth": "https://cdn.myapp.com/auth/v1.2.3/remoteEntry.js" }
The remoteEntry.js caching problem: If the shell hardcodes a URL without a version, the CDN caches the old file. New deployment is invisible until cache expires. Fix: version the remoteEntry.js URL itself â€” each build deploys to /checkout/v2.4.1/remoteEntry.js. The manifest file is served with Cache-Control: no-store. Asset chunks are content-hashed and cached aggressively (1 year).

Rollback strategy: Rollback = update the manifest to point to the previous version URL. Old assets remain on CDN for 30 days. Rollback time: seconds. No shell redeploy required.
// Rollback checkout to v2.3.9 â€” update manifest.json only: "checkout": "https://cdn.myapp.com/checkout/v2.3.9/remoteEntry.js" // Shell picks it up on next manifest fetch (~30s)
Feature flags for MFEs: The manifest becomes a feature flag system. The shell checks a feature flag service and loads either the new MFE remote or falls back to the current stable version. Dark launches, canary deployments (10% of users get v2.4.1), and A/B tests all become manifest-level decisions with zero code changes in MFEs.
The manifest-driven architecture gives you runtime control over which version of each MFE the shell loads â€” without any code change or redeploy. It is effectively a feature flag system for entire micro-frontends.
Q6 architecture must-know
The hardest micro-frontend question: when should you NOT use micro-frontends? A startup CTO asks you to evaluate whether their 8-engineer frontend team should adopt MFE architecture for their React monolith. Give a structured recommendation framework including the specific signals that mean "yes, now" vs "not yet."
Senior expectation: Must push back on the premise â€” most teams adopting MFEs are not at the scale that justifies them. Must give concrete team/org size thresholds. Must identify the two genuine problems MFEs solve (team autonomy at scale, tech heterogeneity) and show that neither applies to an 8-engineer team.
Micro-frontends solve exactly two problems: (1) team deployment autonomy at scale, (2) technology heterogeneity. For an 8-engineer team, neither problem exists yet.

Signals: "not yet" â€” current state (8 engineers):
deploymentno8 engineers can coordinate a release in a standup. Deployment blocking is not real pain yet â€” it is hypothetical future pain.
team ownershipnoClear feature ownership in a monorepo with good folder structure solves 90% of team autonomy problems without runtime complexity.
build timenoBuild times become a problem at much larger codebase scale. Module Federation adds build complexity â€” you are solving a problem you don't have.
tech debtnoMFEs do not reduce existing tech debt â€” they add an integration layer on top of it. "Our code is messy" is not a MFE problem.
Signals: "yes, now" â€” typically 50+ engineers, multiple product teams:
release blockingyesTeam A's broken PR is blocking Team B's hotfix weekly. The shared deployment pipeline is the bottleneck.
team scaleyes5+ independent product teams, each with their own roadmap. Coordinating a shared frontend release across 5 teams is a project management nightmare.
tech diversityyesAn acquired company's Angular app must be embedded in your React shell. Or one team legitimately needs to migrate frameworks while others stay on the old one.
owned verticalsyesTeams own full vertical slices with different SLAs and deployment frequencies. Monolith coupling actively prevents this ownership.
The correct path for 8 engineers:
1. Strong monorepo structure with clear package boundaries (packages/checkout, packages/catalog)
2. Separate CI jobs per package with affected-only builds (Nx, Turborepo)
3. Strict interface contracts between packages â€” import only from public API, never internals
4. This gives you 80% of MFE's team-autonomy benefits with 10% of the operational complexity

Revisit MFEs when the team triples and deployment coordination becomes a measurable productivity drag. The monorepo package boundaries make migration to MFEs straightforward â€” the interfaces are already defined.
MFEs increase your operational surface area significantly: multiple build pipelines, a manifest service, shared dependency version negotiation, cross-MFE debugging, and local dev requiring multiple running servers. These costs are worth it at scale. They are not worth it for 8 engineers.
