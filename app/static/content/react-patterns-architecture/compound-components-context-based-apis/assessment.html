Compound components & Context-based APIs

6 questions covering pattern theory, implementation, Context re-render traps, and headless library design. All reveal buttons work.

MENTAL MODEL

QUESTIONS
Q1theorymust-know
Explain the compound component pattern — what problem it solves, how it differs from a monolithic props-driven component, and why Context is better than React.cloneElement as the implementation mechanism. Show the API surface of both approaches.
Senior expectation: Must articulate "flexible composition vs rigid configuration." Must know cloneElement only reaches direct children — breaks with fragments, wrappers, or arrays. Must contrast both API surfaces concretely.
The problem: a Tabs widget needs shared state (which tab is active) distributed across tab triggers, content panels, and a list wrapper. A monolithic approach solves this with configuration props:
<Tabs tabs={[{ label: 'Profile', content: <Profile /> }]} defaultTab={0} onTabChange={fn} />
This breaks the moment a designer wants a badge on one tab label, a divider between tabs, or panels in a different DOM location. Every edge case becomes a new prop — the component grows without limit.

The compound API inverts control — consumer owns structure, parent owns state:
<Tabs defaultTab="profile"> <Tabs.List> <Tabs.Tab id="profile">Profile <Badge>New</Badge></Tabs.Tab> <Tabs.Tab id="settings">Settings</Tabs.Tab> </Tabs.List> <Tabs.Panel id="profile"><Profile /></Tabs.Panel> <Tabs.Panel id="settings"><Settings /></Tabs.Panel> </Tabs>
Why Context over cloneElement: cloneElement can only inject props into direct children — wrap a Tabs.Tab in a div, fragment, or custom component and the injected props never arrive. Context broadcasts to any descendant at any depth with no structural constraint. Sub-components opt into the contract explicitly by calling useContext, rather than receiving surprise props from above.
Q2codingmust-know
Implement a fully working Tabs compound component with Tabs, Tabs.List, Tabs.Tab, and Tabs.Panel. Support both controlled and uncontrolled modes. Guard against sub-components being used outside the parent.
Senior expectation: Must implement controlled (activeTab + onTabChange) AND uncontrolled (defaultTab + internal state) modes. Must guard context with a null-check that throws a useful error. Must useMemo on the context value. Must add ARIA attributes.
const TabsContext = createContext(null); function useTabs() { const ctx = useContext(TabsContext); if (!ctx) throw new Error( 'Tabs sub-components must be used inside <Tabs>' ); return ctx; } function Tabs({ defaultTab, activeTab, onTabChange, children }) { const isControlled = activeTab !== undefined; const [internal, setInternal] = useState(defaultTab ?? null); const current = isControlled ? activeTab : internal; const setTab = useCallback((id) => { if (!isControlled) setInternal(id); onTabChange?.(id); }, [isControlled, onTabChange]); const value = useMemo( () => ({ current, setTab }), [current, setTab] ); return ( <TabsContext.Provider value={value}> {children} </TabsContext.Provider> ); } Tabs.List = function TabsList({ children }) { return <div role="tablist">{children}</div>; }; Tabs.Tab = function Tab({ id, children }) { const { current, setTab } = useTabs(); return ( <button role="tab" aria-selected={current === id} aria-controls={`panel-${id}`} onClick={() => setTab(id)} > {children} </button> ); }; Tabs.Panel = function Panel({ id, children }) { const { current } = useTabs(); if (current !== id) return null; return ( <div role="tabpanel" id={`panel-${id}`}> {children} </div> ); };
The controlled/uncontrolled duality mirrors how native HTML inputs work and how every well-designed library (Radix, Headless UI) exposes its API. The useMemo on context value is critical — without it, every Tabs render creates a new object reference, causing all consumers to re-render even when current and setTab haven't changed.
The guard pattern — if (!ctx) throw new Error(...) — turns a cryptic "cannot read property of null" into an actionable developer error message. Every compound component system should have this on its context hook.
Q3gotchamust-know
This Context setup causes every consumer to re-render on every keystroke in the search input — even ProductCard which only uses selectedItem. Identify the root cause and give two progressively better fixes.
const AppContext = createContext(); function AppProvider({ children }) { const [selectedItem, setSelectedItem] = useState(null); const [searchQuery, setSearchQuery] = useState(''); return ( <AppContext.Provider value={{ selectedItem, setSelectedItem, searchQuery, setSearchQuery, }}> {children} </AppContext.Provider> ); } function ProductCard({ id }) { const { selectedItem, setSelectedItem } = useContext(AppContext); // re-renders on every keystroke — why? }
Senior expectation: Root cause is a new object literal on every render failing referential equality. Must know Context has no built-in selector mechanism. Fix 1: split contexts. Fix 2: useMemo to stabilise the value. Must explain why splitting is architecturally superior.
Root cause: value={{ selectedItem, setSelectedItem, searchQuery, setSearchQuery }} creates a brand-new object literal on every render of AppProvider. React Context uses referential equality (===) — since the reference always changes, ALL consumers re-render on every state update regardless of which slice they use. A keystroke updates searchQuery, AppProvider re-renders, new object is created, every useContext(AppContext) consumer fires.

Fix 1 — Split contexts by update frequency (preferred):
const SelectionContext = createContext(); const SearchContext = createContext(); function AppProvider({ children }) { const [selectedItem, setSelectedItem] = useState(null); const [searchQuery, setSearchQuery] = useState(''); return ( <SelectionContext.Provider value={{ selectedItem, setSelectedItem }}> <SearchContext.Provider value={{ searchQuery, setSearchQuery }}> {children} </SearchContext.Provider> </SelectionContext.Provider> ); } // ProductCard uses useContext(SelectionContext) only // Keystrokes only trigger SearchContext consumers
Fix 2 — Stabilise with useMemo (when splitting isn't practical):
const selectionVal = useMemo( () => ({ selectedItem, setSelectedItem }), [selectedItem] ); const searchVal = useMemo( () => ({ searchQuery, setSearchQuery }), [searchQuery] );
Critical insight: Context has no built-in selector mechanism. Unlike Redux's useSelector — which re-renders only when the selected slice changes — useContext is all-or-nothing. You get the entire context value on every change. If you find yourself wanting selectors inside a large single context, that is the signal to reach for Zustand or Redux instead.
A codebase with 10+ split contexts is harder to reason about than a single Zustand store. Context is excellent for scoped compound-component state. For genuinely global, high-frequency, or cross-cutting state — use an external store.
Q4gotcha
A colleague reports that useContext(AuthContext) returns undefined intermittently in production but works fine in development. Walk through every possible cause and how you would diagnose each one.
Senior expectation: Must cover: missing default value in createContext, component renders before Provider mounts, Provider at wrong tree level, and — the principal-level answer — multiple React instances in a monorepo or microfrontend setup.
Cause 1 — Missing default value: createContext() with no argument means the default is undefined. Any consumer rendered outside a Provider gets undefined. Fix: createContext(null) and guard with the null-check hook pattern from Q2.

Cause 2 — Component renders before Provider mounts: in async or streaming SSR setups, a child can render before its Provider tree is in place. Fix: ensure Provider wraps the entire subtree at the correct level in the tree.

Cause 3 — Provider at the wrong tree level: the Provider is inside a sibling branch rather than an ancestor. Classic mistake when restructuring routes — the Provider moves to a new route file but a consumer is still in the old location outside it.

Cause 4 (the production-only culprit) — Multiple React instances: in a monorepo where a component library ships its own copy of React instead of declaring it as a peer dependency, createContext() in the library and createContext() in the app create two completely separate Context registries. A Provider from one React instance is invisible to a consumer subscribed to the other. The context silently returns undefined with no error.

Diagnosis: console.log(require.resolve('react')) in both the app and the library — they must resolve to the exact same file path. If they differ, you have two Reacts. Fix: add React to peerDependencies in the library package.json and deduplicate in the bundler:
// vite.config.js resolve: { dedupe: ['react', 'react-dom'] } // webpack.config.js resolve: { alias: { react: path.resolve('./node_modules/react') } }
This is why it only appears in production — dev builds often skip deduplication optimisations that expose the split-instance problem.
Q5architecture
A junior architect proposes using Context for all shared state in a large 80-component dashboard. Give your specific decision criteria for when Context is sufficient versus when you need an external state manager like Zustand or Redux.
Senior expectation: Concrete thresholds — not vague "it depends." Must name Context's specific failure modes at scale: no selector subscriptions, all-or-nothing re-renders, no middleware, no DevTools. Must acknowledge Context's genuine strengths for scoped state.
Use Context when:
scopegood fitState genuinely belongs to a subtree — theme, auth session, compound component internals. Not truly global.
frequencygood fitLow-to-medium update rate. Tab selection, modal open/close, user preferences. Not keystrokes, scroll position, or animation frames.
consumersgood fitBounded, known set of consumers. Compound component sub-components. Not 40+ components scattered across the app.
toolinggood fitNo need for DevTools, middleware, time-travel debugging, or undo/redo.
Switch to Zustand or Redux when:
selectorscontext failsYou need consumers to re-render only when their specific slice changes. Context is all-or-nothing — useSelector is not.
frequencycontext failsState updates on keystrokes, drag, scroll, or animation. Every update re-renders all consumers — unacceptable at this frequency.
middlewarecontext failsYou need logging, persistence, optimistic updates, or undo/redo. Context has no middleware layer.
complexitycontext failsYou find yourself splitting into 8+ contexts or writing useMemo on every provider. The workarounds cost more than an external store.
Compound components are the sweet spot for Context — the context is strictly scoped to the component tree, the consumers are known and bounded, and update frequency is driven by direct user interaction. This is exactly what Context was designed for.
Q6architecturedesign
Your design system needs a Select component. The designer says "make it headless so teams can fully style it." Explain what headless means architecturally, how you implement it with compound components and Context, and show the consumer-facing API contract.
Senior expectation: Must clearly separate the state machine (logic layer) from rendering (DOM + styles). Must show Context distributing state to sub-components. Must show how a styled wrapper is built on top of the headless layer. Must mention keyboard navigation and ARIA as things the headless layer handles.
Headless means the component ships zero CSS and zero DOM opinions — it only manages the state machine and exposes state + handlers through Context. The consumer decides every rendering detail.

Three layers:

Layer 1 — state machine (internal to Select): isOpen, selectedValue, highlightedIndex, toggle(), select(value), highlightNext(), highlightPrev(). Owned by the Select root, distributed via SelectContext.

Layer 2 — headless sub-components (what you ship):
const SelectContext = createContext(null); function Select({ value, onChange, children }) { const [isOpen, setIsOpen] = useState(false); const [highlighted, setHighlighted] = useState(0); const ctx = useMemo(() => ({ isOpen, selected: value, toggle: () => setIsOpen(o => !o), select: (v) => { onChange(v); setIsOpen(false); }, highlighted, setHighlighted, }), [isOpen, value, onChange, highlighted]); return ( <SelectContext.Provider value={ctx}> {children} </SelectContext.Provider> ); } Select.Trigger = function({ children, ...props }) { const { toggle, isOpen, selected } = useContext(SelectContext); return ( <button aria-haspopup="listbox" aria-expanded={isOpen} onClick={toggle} {...props} > {children ?? selected} </button> ); }; Select.Options = function({ children, ...props }) { const { isOpen } = useContext(SelectContext); if (!isOpen) return null; return <ul role="listbox" {...props}>{children}</ul>; }; Select.Option = function({ value, children, ...props }) { const { select, selected } = useContext(SelectContext); return ( <li role="option" aria-selected={selected === value} onClick={() => select(value)} {...props} > {children} </li> ); };
Layer 3 — styled wrapper built by a consuming team:
function StyledSelect({ value, onChange, options }) { return ( <Select value={value} onChange={onChange}> <Select.Trigger className={styles.trigger}> {value || 'Choose an option'} </Select.Trigger> <Select.Options className={styles.dropdown}> {options.map(o => ( <Select.Option key={o} value={o} className={styles.option} > {o} </Select.Option> ))} </Select.Options> </Select> ); }
The key principle: the headless layer handles everything hard — keyboard navigation, ARIA, click-outside detection, focus management — and exposes everything easy to customise via className, children, and spread props. This is precisely why Radix UI, Headless UI, and react-aria exist: they solved the hard parts once so every team can build their own styled layer on top without reimplementing accessibility logic.
Interview signal: mention that the headless pattern pairs naturally with compound components because the Context scope is bounded — it only exists within the Select tree. There is no global state pollution, no Provider at the app root needed.
