useReducer — when to choose over useState

6 questions. Most engineers know useReducer exists — few can articulate precisely when it earns its complexity cost, or implement it correctly under interview conditions.

MENTAL MODEL

useReducer signature

usageconst [state, dispatch] = useReducer(reducer, initialState)
reducer(state, action) => newState — must be pure
dispatchSends an action object to the reducer

vs useState

useStateOne value, one setter — caller decides next value
useReducerState machine — reducer decides next value from action
key diffLogic lives in reducer, not at the call site

When reducer wins

fieldsMultiple related state fields updated atomically
actionsMany distinct user actions → same state shape
testingLogic needs unit tests without mounting React

Reducer rules

pureNo side effects — same input always same output
immutableNever mutate state — always return new object
defaultAlways return current state for unknown actions
QUESTIONS
Q1theorymust-know
A tech lead asks: "Give me the exact decision criteria you use to choose useReducer over useState. Not 'when state is complex' — give me specific, testable signals that tell you it's time to switch." What do you say?
Senior expectation: Must give 4–5 specific, concrete signals — not vague adjectives like "complex" or "large." Must explain the core insight: useState puts transition logic at the call site (scattered), useReducer centralises it in the reducer (co-located, named, testable).
The core mental model shift: useState asks "what is the new value?" — the caller decides. useReducer asks "what happened?" — the reducer decides the new value from the action. When you find yourself answering "what happened?" rather than "what is the next value?", that is the signal to switch.

The specific signals:
signal 1atomic fieldsYou have 3+ state fields that must change together. Setting them via multiple useState setters risks partially-updated state between renders. One dispatch = one atomic transition.
signal 2named actionsThe same state shape is produced by 5+ distinct user actions. Named action types (FETCH_START, FETCH_SUCCESS, SUBMIT_FORM, RESET) are self-documenting. Anonymous setters are not.
signal 3next depends on currentThe new state value requires reading and branching on the current state — not just accumulating it. Complex conditional logic belongs in a reducer, not inline at a call site.
signal 4testabilityYou want to unit-test state transitions without mounting a component. A reducer is a pure function — test it directly with input/output assertions.
signal 5shared dispatchMultiple deeply nested child components need to trigger state changes. Pass dispatch down (stable reference — never changes) instead of 5 separate callback props.
The practical threshold: if you have more than two useState setters being called together in the same handler, that is the first signal. If you write the same state-reset logic in three different handlers, that is the second. At that point a reducer almost always produces cleaner code.
useReducer does not replace useState — it complements it. Simple, independent values (a modal open flag, a search string, a toggle) stay as useState. Related state with named transitions moves to useReducer. Both patterns live in the same component.
Q2codingmust-know
Refactor this useState-based fetch state into useReducer. The useState version has three problems — identify them, then implement the correct reducer version with proper TypeScript action types.
// useState version — 3 problems function useUserData(userId) { const [isLoading, setIsLoading] = useState(false); const [data, setData] = useState(null); const [error, setError] = useState(null); async function fetchUser() { setIsLoading(true); try { const d = await api.getUser(userId); setData(d); // isLoading still true here momentarily } catch(e) { setError(e); // data not reset } finally { setIsLoading(false); } } return { isLoading, data, error, fetchUser }; }
Senior expectation: Must identify all 3 problems — inconsistent intermediate state between setter calls, error doesn't reset data, success doesn't reset error. Must produce a typed reducer with discriminated union action types. Must show that one dispatch = one atomic, consistent transition.
The 3 problems in the useState version:
1. Between setData(d) and setIsLoading(false), React 17 renders with data=result, isLoading=true — inconsistent state visible to consumers.
2. On error: setError(e) is called but setData(null) is not — stale data remains alongside a new error.
3. On success: setData(d) is called but setError(null) is not — stale error remains alongside new data.

Reducer version:
type State<T> = | { status: 'idle'; data: null; error: null } | { status: 'loading'; data: null; error: null } | { status: 'success'; data: T; error: null } | { status: 'error'; data: null; error: Error }; type Action<T> = | { type: 'FETCH_START' } | { type: 'FETCH_SUCCESS'; payload: T } | { type: 'FETCH_ERROR'; error: Error } | { type: 'RESET' }; function fetchReducer<T>( state: State<T>, action: Action<T> ): State<T> { switch (action.type) { case 'FETCH_START': return { status: 'loading', data: null, error: null }; case 'FETCH_SUCCESS': return { status: 'success', data: action.payload, error: null }; case 'FETCH_ERROR': return { status: 'error', data: null, error: action.error }; case 'RESET': return { status: 'idle', data: null, error: null }; default: return state; } } function useUserData<T>(userId: string) { const [state, dispatch] = useReducer( fetchReducer<T>, { status: 'idle', data: null, error: null } ); async function fetchUser() { dispatch({ type: 'FETCH_START' }); try { const d = await api.getUser(userId); dispatch({ type: 'FETCH_SUCCESS', payload: d }); } catch(e) { dispatch({ type: 'FETCH_ERROR', error: e as Error }); } } return { ...state, fetchUser }; }
Each dispatch produces one atomic state transition — no intermediate inconsistent states. The discriminated union on State means TypeScript enforces exhaustive handling: in a component, if status === 'success', TypeScript knows data is non-null. This eliminates a whole class of null-check bugs.
The discriminated union state type is the TypeScript killer feature that pairs with useReducer. Instead of data: T | null, error: Error | null, isLoading: boolean (7 possible combinations, most invalid), you get exactly 4 valid states. The impossible states become unrepresentable.
Q3gotchamust-know
This reducer has three bugs that will cause silent failures in production. Find all of them.
function cartReducer(state, action) { switch (action.type) { case 'ADD_ITEM': state.items.push(action.item); // bug? return state; case 'REMOVE_ITEM': return { ...state, items: state.items.filter(i => i.id !== action.id) }; case 'CLEAR': return { items: [] }; case 'UPDATE_QTY': const item = state.items.find(i => i.id === action.id); item.qty = action.qty; return { ...state }; } }
Senior expectation: Must find all three — direct mutation in ADD_ITEM (React won't re-render), direct mutation in UPDATE_QTY (same problem, shallow spread doesn't help), and missing default case (throws on unknown actions instead of returning current state). Must explain why shallow spread doesn't fix nested mutation.
Bug 1 — ADD_ITEM mutates state directly. state.items.push() modifies the existing array in place, then returns the same state reference. React uses referential equality to detect changes — same reference means no re-render is scheduled. The item is added to the array in memory but the component never updates. Additionally, this corrupts React's ability to compare previous vs next state for debugging and Strict Mode checks.

Bug 2 — UPDATE_QTY mutates a nested object. item.qty = action.qty mutates an object inside state.items. The shallow spread { ...state } creates a new top-level object, but items still points to the same array containing the same mutated item objects. React sees a new state reference and re-renders — but any component using React.memo or doing its own item equality checks will see the same item reference and bail out incorrectly.

Bug 3 — Missing default case. If any action type is dispatched that isn't handled (a typo, a future action, middleware actions), the function returns undefined. React replaces the entire state with undefined, breaking the app. Every reducer must have a default that returns the current state.

Fixed reducer:
function cartReducer(state, action) { switch (action.type) { case 'ADD_ITEM': return { ...state, items: [...state.items, action.item] }; case 'REMOVE_ITEM': return { ...state, items: state.items.filter(i => i.id !== action.id) }; case 'CLEAR': return { ...state, items: [] }; case 'UPDATE_QTY': return { ...state, items: state.items.map(i => i.id === action.id ? { ...i, qty: action.qty } : i ) }; default: return state; // always return current state for unknown actions } }
The shallow spread false-security trap: return { ...state } after mutating a nested value is the most dangerous reducer bug — it creates a new top-level reference (satisfying React's change detection) while leaving nested objects mutated. Components that do deep equality checks or use React.memo on nested data will behave incorrectly in hard-to-diagnose ways.
Q4coding
Implement a multi-step form wizard (3 steps: personal info → address → review) using useReducer. The state must track current step, all field values, per-field validation errors, and submission status. Show the complete reducer and explain why this is better than managing it with useState.
Senior expectation: Must model the full state shape as a single object. Must show named action types for every meaningful transition (NEXT_STEP, PREV_STEP, SET_FIELD, SET_ERRORS, SUBMIT_START, SUBMIT_SUCCESS, SUBMIT_ERROR, RESET). Must explain why centralised logic beats scattered useState calls for a flow this complex.
const STEPS = ['personal', 'address', 'review']; const initialState = { step: 0, fields: { name: '', email: '', // personal street: '', city: '', // address }, errors: {}, submitStatus: 'idle', // idle | submitting | success | error submitError: null, }; function wizardReducer(state, action) { switch (action.type) { case 'NEXT_STEP': return { ...state, step: Math.min(state.step + 1, STEPS.length - 1), errors: {}, // clear errors when advancing }; case 'PREV_STEP': return { ...state, step: Math.max(state.step - 1, 0), errors: {}, }; case 'SET_FIELD': return { ...state, fields: { ...state.fields, [action.field]: action.value }, errors: { ...state.errors, [action.field]: undefined }, }; case 'SET_ERRORS': return { ...state, errors: action.errors }; case 'SUBMIT_START': return { ...state, submitStatus: 'submitting', submitError: null }; case 'SUBMIT_SUCCESS': return { ...state, submitStatus: 'success' }; case 'SUBMIT_ERROR': return { ...state, submitStatus: 'error', submitError: action.error }; case 'RESET': return initialState; default: return state; } } // Usage in component: function WizardForm() { const [state, dispatch] = useReducer(wizardReducer, initialState); function handleNext() { const errors = validateStep(state.step, state.fields); if (Object.keys(errors).length) { dispatch({ type: 'SET_ERRORS', errors }); return; } dispatch({ type: 'NEXT_STEP' }); } async function handleSubmit() { dispatch({ type: 'SUBMIT_START' }); try { await api.submit(state.fields); dispatch({ type: 'SUBMIT_SUCCESS' }); } catch(e) { dispatch({ type: 'SUBMIT_ERROR', error: e.message }); } } }
Why useReducer beats useState here: the wizard has 15+ state-affecting user actions. With useState you'd have 6+ setters called in combination across every handler — step transitions must also clear errors, field changes must clear that field's error, submit must set loading and clear previous errors atomically. Each handler becomes a complex sequence of setter calls with easy-to-miss combinations. The reducer consolidates every rule in one place: "advancing a step always clears errors" is enforced in NEXT_STEP, not duplicated across every button handler.

Bonus: the entire reducer is a pure function — you can test every transition with a simple expect(wizardReducer(state, action)).toEqual(expectedState) without mounting a single component.
Q5gotcha
A colleague combines useReducer with useContext to replace Redux in a medium-scale app. Six months later, the app has serious performance issues. Explain precisely why this pattern fails at scale and what the correct architectural boundary is between "useReducer + Context" and a proper state manager.
Senior expectation: Must explain that useReducer solves the logic problem but Context solves the prop-drilling problem — neither solves the re-render problem. Any state change re-renders every Context consumer regardless of whether they use that slice. Must know the specific threshold where this breaks down and what the alternatives are.
The pattern works initially because it solves two real problems elegantly: useReducer centralises state logic, Context distributes it without prop drilling. But it has a fundamental performance ceiling that Redux (with useSelector) doesn't have.

The re-render problem: every time dispatch is called and the reducer returns a new state object, the Context value changes. React re-renders every component that calls useContext(AppContext) — regardless of whether the slice of state they consume actually changed. A component that only reads state.user.name re-renders when state.cart.items changes. With 40+ consumers this becomes a significant performance problem on any frequent update (typing, drag, real-time data).

Redux's useSelector solves this with a subscription model: each selector runs after every dispatch and only triggers a re-render if its selected value changed. useContext has no equivalent mechanism — it's all-or-nothing.

The architectural boundary:
use reducer+ctxcorrectScoped state for a compound component or a specific feature subtree. Consumers are bounded and known. Update frequency is low. Example: a wizard form, a multi-select dropdown, a canvas editor's tool state.
use Redux/ZustandcorrectTruly global state with 10+ consumers across the app. High update frequency (search, real-time). Middleware needed (logging, persistence). Fine-grained subscription control required.
reducer+ctx as ReduxwrongReplacing Redux with useReducer+Context at app scale. Solves logic organisation but introduces worse re-render behaviour than the Redux it replaced.
The practical mitigation if you're stuck with this pattern: split the context into multiple contexts by update frequency (see compound components session). But at a certain scale, that workaround becomes harder to reason about than just adopting Zustand, which gives you a Redux-style subscription model with a fraction of the boilerplate.
The "useReducer + Context replaces Redux" pattern is well-intentioned but architecturally limited. It's a common source of performance regressions in mid-sized React apps that started small. Know this trade-off before recommending it to a team.
Q6architecture
You're building a real-time collaborative document editor (think Google Docs light). Users can type, select text, apply formatting, undo/redo, and see other users' cursors. Design the state management architecture — specifically which pieces use useState, which use useReducer, and which need an external store. Justify every decision.
Senior expectation: This is an architecture synthesis question. Must partition state by characteristics: update frequency, scope, transition complexity, undo requirements. Must not put everything in one bucket. Should identify undo/redo as a classic reducer use case (past/present/future state). Should identify real-time cursor positions as needing external store or ref-based approach to avoid re-render cascades.
Document content + undo/redo history → useReducer
Document content transitions are the clearest useReducer use case in existence: every keystroke, format operation, and selection is a named action with well-defined state transitions. Undo/redo is natively modelled as a reducer managing past/present/future stacks:
const docState = { past: [], // array of previous content snapshots present: { content, selection, formatting }, future: [], }; // UNDO: move present to future, pop past into present // REDO: move present to past, pop future into present // Any edit: push present to past, clear future, apply change
This is the canonical undo/redo pattern — impossible to implement cleanly with useState, natural with useReducer.

UI state → useState
Toolbar open/closed, active modal, selected formatting tool, sidebar visibility — simple independent values with no complex transitions. useState, kept close to the component that owns them. No global sharing needed.

Collaboration cursors → useRef + external subscription
Other users' cursor positions update at very high frequency (every mouse move or keystroke from every collaborator). Putting this in React state causes a re-render cascade on every update — unacceptable. Use a ref to store cursor positions and update the DOM directly via canvas/overlay, bypassing React's render cycle entirely for cursor painting. The WebSocket subscription lives outside React state.

User presence + permissions → External store (Zustand or Redux)
Who is online, their display names, their permission levels — this is genuinely global, consumed across many components (toolbar shows user avatars, sidebar shows presence, document title shows collaborator count), and updated by WebSocket events. An external store with fine-grained selectors prevents presence updates from re-rendering the document editor itself.
The architectural principle: match the state management tool to the state's characteristics — not to a single pattern applied everywhere. A document editor using only useState would have stale closure bugs and no undo. One using only useReducer+Context would have cursor-update re-render cascades. The right architecture uses all the tools for what they're each best at.
This partitioned architecture is how production collaborative editors are actually built. ProseMirror and Slate.js use reducer-like transaction models for document state. Cursor/presence data is kept out of the main render cycle entirely. Interview signal: showing you've thought about which state needs React's render cycle and which doesn't.

Q2 is the implementation proof — typed discriminated unions with useReducer is a senior-level pattern.
