useEffect — deps array, cleanup, common mistakes

6 questions covering lifecycle equivalents, the 3 deps array modes, cleanup timing, infinite loops, and race conditions. The most commonly failed hook topic in senior interviews.

QUESTIONS
Q1outputmust-know
Predict the exact console output — including order — when this component first mounts, when userId changes from 1 to 2, and when the component unmounts. Most engineers miss the cleanup ordering.
function UserProfile({ userId }) { useEffect(() => { console.log('effect run', userId); return () => { console.log('cleanup', userId); }; }, [userId]); console.log('render', userId); return <div>User {userId}</div>; }
Senior expectation: Must give the exact sequence for all three phases. The critical insight is that cleanup runs with the OLD dep value before the new effect runs with the NEW value — proving that cleanups close over their own render's values, not the latest ones.
Phase 1 — Initial mount (userId=1):
syncrender 1Component renders synchronously first
after painteffect run 1useEffect fires after browser has painted
Phase 2 — userId changes to 2:
syncrender 2Component re-renders with new userId
after paintcleanup 1Previous effect's cleanup runs FIRST — with old userId=1 captured in its closure
after painteffect run 2New effect runs with userId=2
Phase 3 — Unmount:
on unmountcleanup 2Final cleanup runs with userId=2 — the last rendered value
The critical insight: cleanup functions close over the values from their own render cycle. cleanup 1 logs userId=1 even though the component has already re-rendered with userId=2. This is what makes cleanup safe for cancelling the right request, removing the right listener — it always references what it set up.
In React Strict Mode (dev), the sequence on mount is: render → effect → cleanup → effect. React intentionally mounts, cleans up, and remounts to surface missing cleanup bugs. This double-fire is dev-only — never happens in production.
Q2gotchamust-know
This component has an infinite render loop. Identify every cause — there are two independent ones — and fix both.
function Dashboard({ config }) { const [data, setData] = useState(null); useEffect(() => { const options = { ...config, timestamp: Date.now() }; fetch('/api/data', { body: JSON.stringify(options) }) .then(r => r.json()) .then(setData); }, [config, data]); return <div>{JSON.stringify(data)}</div>; }
Senior expectation: Must catch BOTH causes independently. Cause 1: data in deps — setData triggers re-render, which re-runs effect, which calls setData again. Cause 2: config is likely an object — if the parent passes a new object reference on every render, Object.is comparison fails every time even with identical content. Must fix both.
Cause 1 — data in the deps array. The effect calls setData, which updates state, which triggers a re-render, which re-runs the effect (because data changed), which calls setData again — infinite loop. data is the effect's output, not its input. It should never be in the deps array of the effect that produces it.

Cause 2 — config is an object. If the parent component passes config as an inline object literal (<Dashboard config={{ theme: 'dark' }} />), a new reference is created on every parent render. Object.is(prevConfig, nextConfig) fails even if the content is identical — the effect re-runs on every parent render regardless of whether config actually changed.

Fixed version:
function Dashboard({ config }) { const [data, setData] = useState(null); // Stabilise config with useMemo if it's an object from parent // Better: destructure primitives from config instead const { theme, pageSize } = config; useEffect(() => { fetch(`/api/data?theme=${theme}&size=${pageSize}`) .then(r => r.json()) .then(setData); // data removed from deps }, [theme, pageSize]); // primitives — stable comparisons return <div>{JSON.stringify(data)}</div>; }
Two rules derived from this: (1) Never put a state setter's output in the deps of the effect that calls that setter. (2) Never put object/array/function references in deps unless you can guarantee their referential stability — destructure to primitives or use useMemo at the source.
The ESLint exhaustive-deps rule will catch the missing dep but won't catch the infinite loop from including data. Linters enforce completeness, not correctness of the dependency design. That judgment is yours.
Q3gotchamust-know
This effect has a race condition that causes stale data to overwrite fresh data when userId changes quickly. Explain precisely how the race occurs and implement the fix using both the cancellation flag pattern and AbortController.
function UserCard({ userId }) { const [user, setUser] = useState(null); useEffect(() => { fetchUser(userId).then(data => { setUser(data); }); }, [userId]); return <div>{user?.name}</div>; }
Senior expectation: Must describe the race precisely — two concurrent requests where the slower one (for an older userId) resolves after the faster one (for the newer userId), overwriting correct data with stale data. Must implement both fix patterns and explain which to prefer and when.
The race: user is on profile 1 (slow network). They quickly navigate to profile 2 (fast network). Profile 2 resolves first → setUser(profile2data). Then profile 1 resolves → setUser(profile1data) overwrites the correct result. The user sees profile 1's data on profile 2's page.

Fix 1 — Cancellation flag:
useEffect(() => { let cancelled = false; fetchUser(userId).then(data => { if (!cancelled) setUser(data); }); return () => { cancelled = true; }; }, [userId]);
When userId changes, cleanup runs first — setting cancelled = true on the old effect's closure. When the stale request resolves, it checks the flag and skips setUser. The network request still completes — it just discards the result.

Fix 2 — AbortController (preferred for fetch):
useEffect(() => { const controller = new AbortController(); fetch(`/api/users/${userId}`, { signal: controller.signal }) .then(r => r.json()) .then(data => setUser(data)) .catch(err => { if (err.name === 'AbortError') return; // ignore cancellation setError(err); }); return () => controller.abort(); }, [userId]);
AbortController actually cancels the in-flight network request — the browser stops receiving data and frees the connection. More efficient than the flag pattern for large responses. Limitation: only works with fetch — not axios (unless you pass the signal) or custom async logic.

Rule of thumb: use AbortController for fetch calls. Use the cancellation flag for non-fetch async operations (custom promises, third-party SDKs, sequential async logic).
React Query and SWR handle this race condition automatically — their caching layer discards responses for stale keys. If you're doing manual fetch-in-useEffect at scale, that's the signal to adopt a data-fetching library rather than writing cancellation logic in every component.
Q4gotcha
A junior engineer tries to make their useEffect async because they need to await a fetch call. They write this — it silently swallows errors and has a subtle memory leak. Explain both problems and show the correct pattern.
// Junior's version useEffect(async () => { const data = await fetchData(); setData(data); }, []);
Senior expectation: Must identify that async functions return a Promise — but useEffect expects either undefined or a cleanup function. React ignores the returned Promise, meaning: (1) async errors are unhandled silently, (2) cleanup is impossible since the Promise return value is discarded. Must show the IIFE pattern and the named async function pattern.
Problem 1 — Cleanup is impossible. useEffect expects its callback to return either undefined or a synchronous cleanup function. An async function always returns a Promise. React receives that Promise as the "cleanup" return value, does not recognise it as a function, and ignores it entirely. This means you can never return an AbortController.abort() or a cancellation flag from an async effect — your cleanup code simply never runs.

Problem 2 — Errors are silently swallowed. Because React ignores the returned Promise, any rejection from fetchData() or the await chain goes unhandled. No error boundary catches it. No .catch() is attached. In development you might see an unhandled rejection warning — in production it silently fails with no user feedback.

Fix 1 — Named async function inside effect (most readable):
useEffect(() => { const controller = new AbortController(); async function load() { try { const data = await fetchData(controller.signal); setData(data); } catch(err) { if (err.name !== 'AbortError') setError(err); } } load(); return () => controller.abort(); // cleanup works correctly }, []);
Fix 2 — IIFE pattern (compact but less readable):
useEffect(() => { (async () => { try { const data = await fetchData(); setData(data); } catch(err) { setError(err); } })(); }, []);
The named function pattern is preferred — it is easier to read, easier to attach the AbortController signal, and easier to test the async logic in isolation. The IIFE works but produces a harder-to-scan code structure as complexity grows.
Never write useEffect(async () => {...}). ESLint's react-hooks/exhaustive-deps rule does not catch this mistake. The only indication is a React warning in development: "Warning: An effect function must not return anything besides a function, which is used for clean-up."
Q5gotcha
This component registers a window event listener. It works correctly on first mount but causes a detectable memory leak and bugs after the parent re-renders. Identify all the problems and produce the correct implementation.
function KeyTracker({ onKeyPress }) { useEffect(() => { window.addEventListener('keydown', onKeyPress); }, []); return null; }
Senior expectation: Must catch all three problems: missing cleanup (listener accumulates on every mount), empty deps suppressing onKeyPress updates (stale closure — always calls the original prop value), and if the parent passes a new function reference on every render the effect still won't re-run due to the empty array. Must produce a correct fix.
Problem 1 — No cleanup. Every time this component mounts (including Strict Mode double-mount), a new keydown listener is added to window with no corresponding removal. If the component mounts and unmounts multiple times (route transitions, conditional rendering), listeners accumulate — each one still firing, still holding a reference to onKeyPress and the component's closure. Classic memory leak.

Problem 2 — Stale closure on onKeyPress. The empty deps array means the effect runs once and never again. The onKeyPress captured in the listener's closure is the prop value from the first render. If the parent passes a new function (e.g. it changed what the callback does), the listener still calls the old one — stale prop reference forever.

Problem 3 — ESLint violation. onKeyPress is used inside the effect but absent from deps. The exhaustive-deps rule flags this — and it's right to. The empty array is a lie about this effect's dependencies.

Correct implementation:
function KeyTracker({ onKeyPress }) { // Stabilise with useRef so we always call the latest prop // without adding it to deps (which would re-register listener) const onKeyPressRef = useRef(onKeyPress); useEffect(() => { onKeyPressRef.current = onKeyPress; }, [onKeyPress]); useEffect(() => { function handler(e) { onKeyPressRef.current(e); // always calls latest version } window.addEventListener('keydown', handler); return () => window.removeEventListener('keydown', handler); }, []); // empty deps correct now — handler never changes return null; }
The ref pattern decouples two concerns: (1) keeping the callback current (the first small effect, runs whenever prop changes) and (2) registering/unregistering the listener (the second effect, runs once). The listener always calls the latest onKeyPress via the ref, without needing to re-register on every prop change.
This is the "event handler ref" pattern — a well-known solution for stable event listeners with unstable callbacks. React's own useEffectEvent hook (RFC stage as of 2024) formalises this pattern: const stableHandler = useEffectEvent(onKeyPress) — a ref-backed stable function reference that always calls the latest prop.
Q6architecturemust-know
A tech lead asks you: "Give me the complete mental model you use when writing a useEffect. Walk me through every decision point before you write a single line of the effect body." Give a production-grade answer that would satisfy a principal engineer.
Senior expectation: Must go beyond "I check the deps array." Should present a structured decision process covering: whether useEffect is even needed, what the effect synchronises, what cleanup it requires, how deps are composed, and what failure modes to check. This answer reveals whether you've truly internalised the hook's purpose or just memorised its API.
Step 1 — Ask: does this need to be an effect at all?
useEffect is for synchronising with external systems — the DOM, network, timers, subscriptions, browser APIs. If the code derives state from props/state (filtering a list, computing a total, formatting a string), it belongs in the render body or useMemo — not an effect. Most over-use of useEffect comes from reaching for it when a derived value would suffice.

Step 2 — Identify what external system this effect owns.
Name it explicitly: "this effect owns the WebSocket connection," "this effect owns the scroll event listener," "this effect owns the data fetch for userId." An effect should own exactly one external resource. If it owns two, split into two effects — they'll have different deps and different cleanup requirements.

Step 3 — Write the cleanup before the effect body.
Ask: what does this external system need to release when the effect stops? Write the return function first. If you cannot name a cleanup, ask whether the effect has a side effect that outlives the component. Timer? Clear it. Listener? Remove it. Fetch? Abort it. Subscription? Unsubscribe.

Step 4 — Determine deps precisely.
List everything the effect reads from the component scope: props, state, context values, functions. Every one of them goes in deps — no exceptions, no suppressions. Then audit for stability:
primitivessafeStrings, numbers, booleans — compared by value. Always stable if the underlying data hasn't changed.
objects/arraysriskyNew reference on every render unless stabilised with useMemo. Destructure to primitives where possible.
functionsriskyNew reference on every render unless stabilised with useCallback. Consider the event handler ref pattern for callbacks.
Step 5 — Check for failure modes:
— Does the effect call a setter whose output is in its deps? (infinite loop)
— Is there an async operation without a cancellation mechanism? (race condition, stale setState on unmount)
— Is the effect async? (wrap in named function — never make the effect callback itself async)
— Does React Strict Mode's double-invoke expose a cleanup bug? (it will in dev — fix it)

Step 6 — Consider extraction.
If the effect is more than ~10 lines, or if the same effect pattern appears in multiple components, extract it into a custom hook. The hook name (useWebSocket, useDocumentTitle, useIntersectionObserver) becomes the documentation. A well-named custom hook makes the component's intent obvious without reading the effect internals.
The one-line heuristic: if you can describe your effect as "synchronise X with Y," it belongs in useEffect. If you can describe it as "compute Z from A and B," it belongs in useMemo or the render body. If you cannot describe it simply, the effect is probably doing too much.
Score guide: Q1 is the cleanup ordering baseline — missing that cleanup fires with the OLD value is extremely common. Q2 catches the two most frequent infinite loop causes. Q3 is the race condition — asked in nearly every UBS-style round. Q4 is the async effect mistake that every junior makes and many seniors don't know to avoid. Q5 combines missing cleanup + stale closure in a real-world event listener. Q6 is the architecture question — a mechanical "check the deps" answer fails; a structured decision process passes.
