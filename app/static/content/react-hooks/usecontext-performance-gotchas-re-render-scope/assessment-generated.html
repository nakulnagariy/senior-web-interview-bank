Questions
Q1 theory must-know
A React component renders every time a parent's state changes, even though it only reads one field from a large context object and that field hasn't changed. Explain exactly why this happens and give two different architectural solutions.
Senior expectation: Must explain referential equality — not just "context changed." Must know that useContext has no selector mechanism. Both solutions (context splitting and stable value with useMemo) must be explained with trade-offs.
Root cause — referential equality. useContext compares the previous and next context value using Object.is. When the Provider renders (because its parent's state changed), it evaluates its value prop. If that prop is an inline object literal value={{ user, theme, query }}, a brand-new object reference is produced every render — even if user, theme, and query are identical. Object.is(prevValue, nextValue) is false. Every consumer re-renders.

Solution 1 — Stabilise the value with useMemo. Wrap the value object in useMemo with the actual data as deps. The reference only changes when data changes:
// ❌ New object every render <Context.Provider value={{ user, theme }}> // ✅ Stable reference — only new when user/theme change const value = useMemo(() => ({ user, theme }), [user, theme]); <Context.Provider value={value}>
Solution 2 — Split contexts by update frequency. Separate the frequently-changing values from the rarely-changing ones into distinct contexts. A component subscribing to AuthContext won't re-render when SearchContext (updated on every keystroke) changes.
const AuthContext = createContext(); // low frequency const SearchContext = createContext(); // high frequency // UserAvatar only subscribes to AuthContext // → never re-renders from search keystrokes function UserAvatar() { const { user } = useContext(AuthContext); return <div>{user?.name}</div>; }
Context has no built-in selector mechanism — unlike Redux's useSelector which only re-renders when the selected slice changes. If you need per-consumer subscription granularity, use Zustand or Redux.
Q2 gotcha must-know
Predict whether ProductCard re-renders on every keystroke in the search bar. Then identify every problem in this Provider and produce a corrected version.
const AppContext = createContext(); function AppProvider({ children }) { const [cart, setCart] = useState([]); const [query, setQuery] = useState(''); return ( <AppContext.Provider value={{ cart, setCart, query, setQuery }}> {children} </AppContext.Provider> ); } function ProductCard({ id }) { const { cart, setCart } = useContext(AppContext); // only uses cart return <div>...</div>; }
Senior expectation: Yes, ProductCard re-renders on every keystroke. Must identify the inline object literal as the root cause, and produce a corrected version using either context splitting or useMemo — with the split-context approach as the preferred architectural solution.
Yes — ProductCard re-renders on every keystroke. Every time the user types, setQuery is called → AppProvider re-renders → a new value object is created → all consumers including ProductCard re-render, even though cart hasn't changed.

Fix — split contexts:
const CartContext = createContext(); // low frequency const SearchContext = createContext(); // high frequency function AppProvider({ children }) { const [cart, setCart] = useState([]); const [query, setQuery] = useState(''); const cartVal = useMemo(() => ({ cart, setCart }), [cart]); const searchVal = useMemo(() => ({ query, setQuery }), [query]); return ( <CartContext.Provider value={cartVal}> <SearchContext.Provider value={searchVal}> {children} </SearchContext.Provider> </CartContext.Provider> ); } // Now only re-renders when cart changes — never on keystrokes function ProductCard({ id }) { const { cart, setCart } = useContext(CartContext); return <div>...</div>; }
A codebase with 10+ split contexts becomes harder to reason about than a single Zustand store. Context splitting solves the re-render problem for 3–5 related groups. Beyond that, adopt an external store with selector subscriptions.
Q3 coding must-know
Implement a production-quality AuthContext with login/logout async actions, correct TypeScript types, a guard hook, and no unnecessary re-renders. The context must handle loading and error states atomically.
Senior expectation: Must use useReducer for atomic state transitions (never three separate useState setters). Must useMemo to stabilise the context value. Must implement the guard hook pattern. Must type the discriminated union state correctly. Login/logout must be stable useCallback references.
// auth/AuthContext.tsx type AuthState = | { status: 'idle'; user: null; error: null } | { status: 'loading'; user: null; error: null } | { status: 'success'; user: User; error: null } | { status: 'error'; user: null; error: string }; type AuthAction = | { type: 'LOGIN_START' } | { type: 'LOGIN_SUCCESS'; payload: User } | { type: 'LOGIN_ERROR'; error: string } | { type: 'LOGOUT' }; function authReducer(state: AuthState, action: AuthAction): AuthState { switch (action.type) { case 'LOGIN_START': return { status: 'loading', user: null, error: null }; case 'LOGIN_SUCCESS': return { status: 'success', user: action.payload, error: null }; case 'LOGIN_ERROR': return { status: 'error', user: null, error: action.error }; case 'LOGOUT': return { status: 'idle', user: null, error: null }; default: return state; } } const AuthContext = createContext<AuthContextValue | null>(null); export function AuthProvider({ children }) { const [state, dispatch] = useReducer(authReducer, { status: 'idle', user: null, error: null }); const login = useCallback(async (credentials) => { dispatch({ type: 'LOGIN_START' }); try { const user = await api.login(credentials); dispatch({ type: 'LOGIN_SUCCESS', payload: user }); } catch(e) { dispatch({ type: 'LOGIN_ERROR', error: e.message }); } }, []); const logout = useCallback(() => { dispatch({ type: 'LOGOUT' }); }, []); const value = useMemo( () => ({ ...state, login, logout }), [state, login, logout] // login/logout are stable refs ); return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>; } // Guard hook — self-documenting errors export function useAuth() { const ctx = useContext(AuthContext); if (!ctx) throw new Error( 'useAuth() must be used inside <AuthProvider>' ); return ctx; }
The discriminated union on AuthState makes impossible states unrepresentable. When status === 'success', TypeScript knows user is non-null. This eliminates a whole class of null-check bugs downstream.
Q4 gotcha must-know
A colleague reports that useContext(AuthContext) returns undefined intermittently in production — but never in development. Walk through every possible cause and how you would diagnose each.
Senior expectation: Must cover at minimum: missing default value, component renders before Provider mounts, Provider at wrong tree level, and the multiple React instances trap (the production-only cause). The last one is the principal-level answer.
Cause 1 — Missing default value. createContext() with no argument sets the default to undefined. Any consumer outside a Provider silently receives undefined. Fix: createContext(null) and guard with a null-check hook.

Cause 2 — Provider at wrong tree level. The Provider is inside a sibling branch rather than an ancestor. Common when restructuring routes — the Provider moves but some consumers remain outside it.

Cause 3 — Component renders before Provider mounts. In async/streaming SSR, a child can render before its Provider tree is established.

Cause 4 (the production-only culprit) — Multiple React instances. In a monorepo, a library bundled with its own copy of React creates a separate context registry. The Provider from one React instance is invisible to consumers in the other.
// Diagnose: both must resolve to the SAME path console.log(require.resolve('react')); // app: /app/node_modules/react/index.js ✅ // library: /app/node_modules/react/index.js ✅ // library: /library/node_modules/react/index.js ❌ — two Reacts! // Fix in Vite: resolve: { dedupe: ['react', 'react-dom'] } // Fix in Webpack: resolve: { alias: { react: path.resolve('./node_modules/react') } }
This is why the bug appears only in production — dev builds often skip the deduplication optimisations that split the React instance. Always check peer dependencies in shared libraries.
Q5 coding
Implement the state + dispatch split context pattern. Explain why CountControls (which only dispatches actions) should never re-render after mount — and verify your implementation achieves this.
Senior expectation: Must use two separate contexts — one for state, one for dispatch. Must know that dispatch from useReducer is always the same reference (never changes). Must wrap CountControls in React.memo. Must explain why this pattern is structurally superior to passing both in one context.
const StateContext = createContext(null); const DispatchContext = createContext(null); function countReducer(state, action) { switch (action.type) { case 'INC': return { count: state.count + 1 }; case 'DEC': return { count: state.count - 1 }; case 'RESET': return { count: 0 }; default: return state; } } function CountProvider({ children }) { const [state, dispatch] = useReducer(countReducer, { count: 0 }); // dispatch is ALWAYS the same reference — DispatchContext // consumers will NEVER re-render from state changes return ( <DispatchContext.Provider value={dispatch}> <StateContext.Provider value={state}> {children} </StateContext.Provider> </DispatchContext.Provider> ); } // ✅ Re-renders ONLY when count changes const CountDisplay = React.memo(function() { const { count } = useContext(StateContext); console.count('CountDisplay render'); return <p>Count: {count}</p>; }); // ✅ Renders ONCE on mount — never again from count changes const CountControls = React.memo(function() { const dispatch = useContext(DispatchContext); console.count('CountControls render'); // should only fire once return ( <div> <button onClick={() => dispatch({ type: 'DEC' })}>-</button> <button onClick={() => dispatch({ type: 'INC' })}>+</button> <button onClick={() => dispatch({ type: 'RESET' })}>Reset</button> </div> ); });
dispatch from useReducer is guaranteed stable by React — it's the same function reference for the entire lifetime of the component. This makes it safe in an empty-deps useCallback or as a stable context value.
Q6 theory
Can React.memo prevent re-renders caused by useContext? A colleague wraps an expensive component in React.memo expecting it to bail out when context changes. What actually happens and why?
Senior expectation: No — React.memo cannot prevent context-driven re-renders. Must explain why precisely: React.memo only compares props, but useContext creates a direct subscription that bypasses prop comparison entirely. Must give the correct solutions.
No. React.memo cannot prevent re-renders caused by useContext.

React.memo wraps a component and bails out of re-rendering when its props haven't changed. But useContext creates a direct subscription to the Context — this subscription is independent of props. When the context value changes, React marks the component for re-render at the subscription level, before prop comparison ever happens. React.memo's bailout never fires.

Think of it this way: React.memo guards the component's door (props). useContext has a direct phone line into the component that bypasses the door entirely.
// This does NOT prevent context-driven re-renders: const MyComponent = React.memo(function() { const value = useContext(SomeContext); // direct subscription return <div>{value.data}</div>; // Re-renders whenever SomeContext value changes // regardless of React.memo wrapper }); // ✅ Correct approach: separate the subscribed component // from the expensive rendering component function ContextReader() { const { data } = useContext(SomeContext); return <ExpensiveRenderer data={data} />; // passes primitive/stable ref } const ExpensiveRenderer = React.memo(function({ data }) { // Now React.memo works — only re-renders if data prop changes return <div>...expensive render...</div>; });
The "container and presenter" split: a thin context-reading container passes stable primitive values as props to a React.memo-wrapped presenter. The presenter only re-renders when its specific props change — achieving the selector-like granularity that Context lacks natively.
Q7 architecture must-know
Your team proposes replacing Redux with useReducer + useContext across a 60-component e-commerce app (cart, user, product filters, real-time stock, notifications). Give a precise evaluation: which pieces work with this pattern, which will fail, and what the correct architecture is.
Senior expectation: Must not give a binary "yes" or "no." Must partition the state by characteristics and assign the right tool to each. Must identify real-time stock and notifications as unsuitable for Context. Must articulate why Context lacks selector subscriptions and what that means at 60+ components.
The pattern works for some pieces and fails for others. The evaluation by state type:
Auth / user Context ✅ Low update frequency (login/logout). Small, bounded consumers. Atomic state transitions with useReducer. Ideal Context use case.
Cart state Context ✅ Changes on add/remove/clear — not high frequency. Bounded consumers (cart icon, cart page, checkout). Works well with split CartContext.
Product filters Caution ⚠ If filter state changes on every keystroke and 20+ components consume it, Context re-renders all of them. Splitting helps, but selector-based store is cleaner at this scale.
Real-time stock Fails ❌ Updates every few seconds from WebSocket. 60 components subscribing to one Context = 60 re-renders per WebSocket message. Use Zustand with selectors — each ProductCard selects only its own stock level.
Notifications Fails ❌ High frequency, cross-cutting concern. Needs middleware (persistence to localStorage, batching). Context has no middleware layer.
Correct architecture: Use Context (with useReducer) for auth and cart — scoped, bounded, low-frequency. Use Zustand for product filters, real-time stock, and notifications — needs selector subscriptions and middleware. The two patterns coexist in the same app; the mistake is using one pattern for everything.
The 10-consumer rule: Context with useMemo handles up to ~10 consumers cleanly. Beyond that, or whenever consumers need granular subscription (re-render only when their specific slice changes), reach for Zustand. It gives you Redux-style selectors with a fraction of the boilerplate.
