useState — batching, functional updates, stale closure

6 questions. The most failed category in React senior interviews — most engineers use useState daily but have never traced through what React actually does with multiple setX calls in one event handler.

MENTAL MODEL

useState contract

returnsA snapshot of state for this render + a setter
setterSchedules a re-render with new state value
key ruleState is immutable per render — setX never mutates current

Batching

whatReact groups multiple setState calls into one re-render
React 17Only in event handlers
React 18Everywhere — async, setTimeout, promises too

Functional update

syntaxsetX(prev => newValue)
whenNew value depends on previous state
whyprev is always the latest state, not a snapshot

Stale closure

whatA closure captures state from a previous render
risksetTimeout, event listeners, async callbacks
fixFunctional update or useRef for latest value
QUESTIONS
Q1outputmust-know
Predict exactly what renders after the button is clicked. Most senior engineers get this wrong — and then get the fixed version wrong too.
function Counter() { const [count, setCount] = useState(0); function handleClick() { setCount(count + 1); setCount(count + 1); setCount(count + 1); } return <button onClick={handleClick}>{count}</button>; }
Senior expectation: Must say the counter shows 1, not 3. Must explain that count is a snapshot — it is 0 for the entire duration of this render's handleClick. All three setCount calls schedule a re-render with the same value (0+1=1). Must know the fix is functional updates and explain why they work differently.
after clickshows 1Not 3. count is a constant (0) for this entire render. All three setCount(count+1) calls are setCount(0+1) = setCount(1). React batches them into one re-render with state=1.
The fix — functional updates:
function handleClick() { setCount(prev => prev + 1); setCount(prev => prev + 1); setCount(prev => prev + 1); }
Now the counter shows 3. Each functional update receives the latest pending state as prev — not the render snapshot. React processes the queue in order: 0→1→2→3. The key distinction: setCount(count + 1) captures the snapshot. setCount(prev => prev + 1) receives the accumulated pending value.
Mental model: setCount(value) replaces. setCount(fn) transforms. When the new value depends on the previous value — always use the functional form. No exceptions.
Q2outputmust-know
React 17 vs React 18 batching. Predict the number of re-renders in each version for this code, and explain exactly what changed in React 18.
function App() { const [count, setCount] = useState(0); const [flag, setFlag] = useState(false); function handleClick() { fetchData().then(() => { setCount(c => c + 1); setFlag(f => !f); }); } console.log('render'); return <button onClick={handleClick}>Go</button>; }
Senior expectation: React 17 = 2 renders (no batching outside event handlers). React 18 = 1 render (automatic batching everywhere via createRoot). Must explain the mechanism: React 18's scheduler accumulates all state updates in the current microtask before flushing. Must know the escape hatch: flushSync.
React 172 rendersBatching only worked inside React event handlers. Inside a Promise .then() callback, React 17 flushed each setState immediately — two separate re-renders, two 'render' logs.
React 181 renderAutomatic batching via createRoot. React 18's scheduler batches all setState calls in the same event loop task or microtask into one flush — one re-render, one 'render' log.
React 18 automatic batching covers: Promise callbacks, setTimeout, native event listeners, setInterval — anywhere state updates are called in the same task. This was a significant performance win for apps doing multiple state updates in async callbacks.

The escape hatch when you need synchronous flushing:
import { flushSync } from 'react-dom'; flushSync(() => setCount(c => c + 1)); // renders immediately flushSync(() => setFlag(f => !f)); // renders immediately // Use when you need DOM to update between two state changes
If you're upgrading a React 17 app to React 18, code that relied on two-render behaviour inside async callbacks will silently change to one render. Rare but real breakage — audit any code that reads DOM state between two setState calls in async contexts.
Q3gotchamust-know
This component has a stale closure bug that only manifests after the first click. Identify exactly when and why it occurs, and give two different fixes with trade-offs.
function Timer() { const [count, setCount] = useState(0); useEffect(() => { const id = setInterval(() => { setCount(count + 1); }, 1000); return () => clearInterval(id); }, []); return <p>{count}</p>; }
Senior expectation: Must trace the stale closure precisely — the effect runs once, capturing count=0 in its closure. Every setInterval tick calls setCount(0+1)=setCount(1) forever — count never advances past 1. Must give both fixes and explain their trade-offs.
The bug: the effect runs once (empty deps array) and the interval callback closes over count at that moment — which is 0. React state is a snapshot per render. When the component re-renders with count=1, a new count binding exists for that render — but the old interval callback still holds a reference to the original count=0 binding. Every tick forever calls setCount(0+1). The display shows 1, then stays at 1.

Fix 1 — functional update (preferred):
useEffect(() => { const id = setInterval(() => { setCount(prev => prev + 1); }, 1000); return () => clearInterval(id); }, []);
The functional form receives the latest pending state — it does not close over the render snapshot. No stale closure. The empty deps array is now legitimate because the callback no longer references any external state.

Fix 2 — useRef to hold latest value:
const countRef = useRef(count); useEffect(() => { countRef.current = count; }, [count]); useEffect(() => { const id = setInterval(() => { setCount(countRef.current + 1); }, 1000); return () => clearInterval(id); }, []);
The ref is mutable and not tied to render snapshots — it always holds the latest value. More verbose but necessary when you need the latest state value inside a long-lived callback that can't use functional updates (e.g. needs to read state to make a decision, not just increment it).

Trade-offs: functional update is simpler and correct for pure accumulation. useRef is required when the callback needs to read and branch on state, not just transform it.
Q4gotcha
This code attempts to update an object in state correctly, but it has a subtle mutation bug that causes React to skip re-renders intermittently. Find it and explain why React misses the update.
function Profile() { const [user, setUser] = useState({ name: 'Alice', age: 30 }); function birthday() { user.age += 1; setUser(user); } function rename(newName) { setUser({ ...user, name: newName }); } return ( <div> <p>{user.name}, {user.age}</p> <button onClick={birthday}>Birthday</button> </div> ); }
Senior expectation: Must identify that user.age += 1 mutates the existing state object in place. setUser(user) passes the same object reference. React uses Object.is() to compare previous and next state — same reference = no re-render scheduled. Must explain that React's state immutability contract is referential, not deep structural.
user.age += 1 mutates the state object directly — the same object reference that React is holding as current state. Then setUser(user) passes that same reference back. React compares with Object.is(prevState, nextState): they are the same object → same reference → React bails out and schedules no re-render. The age incremented in memory, but the component never re-renders to show it.

The mutation is also dangerous for a second reason: if React ever reads the previous state for reconciliation, time-travel debugging, or Strict Mode double-invocation, the mutated object gives it incorrect historical data.

Correct fix:
function birthday() { setUser(prev => ({ ...prev, age: prev.age + 1 })); }
Spread creates a new object with a new reference. Object.is(prev, next) returns false — React schedules a re-render. The functional form also prevents the stale closure issue if birthday were ever called from an async context.
The mutation bug is particularly insidious because it can appear to work intermittently — if anything else triggers a re-render (a parent re-render, another state update), the mutated value will appear, making the bug look like a timing issue rather than a mutation.
Q5gotcha
Predict what the alert shows when the button is clicked, then clicked again 3 seconds later. Explain the stale closure mechanism and the correct architectural fix.
function Messenger() { const [message, setMessage] = useState('hello'); function handleSend() { setTimeout(() => { alert('Sending: ' + message); }, 3000); } return ( <div> <input value={message} onChange={e => setMessage(e.target.value)} /> <button onClick={handleSend}>Send in 3s</button> </div> ); }
Senior expectation: Must predict that the alert shows the message value at the time the button was clicked — not what it is when the alert fires. This is intentional React behaviour (snapshot semantics), not a bug. Must distinguish when this is correct behaviour vs when it needs a fix, and know the useRef solution for the "always latest" case.
scenariostepsUser types 'hello', clicks Send. Then types 'world'. After 3s the alert fires.
alert shows'hello'Not 'world'. The setTimeout callback closed over the message binding from the render when Send was clicked. That render's message was 'hello' — it stays 'hello' inside that closure forever.
This is actually correct behaviour for a messaging app — you want to send what the user had typed when they hit Send, not what they typed afterwards. Snapshot semantics prevent "message changed under me" bugs.

But if your use case genuinely needs the latest value at the time the async callback fires (e.g. a save-draft function that should always save the current content), use a ref:
function Messenger() { const [message, setMessage] = useState('hello'); const latestMessage = useRef(message); useEffect(() => { latestMessage.current = message; }, [message]); function handleSave() { setTimeout(() => { alert('Saving latest: ' + latestMessage.current); }, 3000); } }
The ref is not part of React's render cycle — it always holds the current value regardless of which render's closure is executing. Use this pattern when you explicitly want the "whatever it is right now" semantics rather than "what it was when this event fired."
The React docs call this distinction "snapshot vs latest." State gives you snapshots — predictable, debuggable, what React was built on. Refs give you mutable escape hatches — reach for them only when snapshot semantics are genuinely wrong for your use case.
Q6architecture
A senior engineer reviews your code and asks: "When should you use useState versus useReducer? Give me the exact criteria you use to make that call — not just 'when state is complex.'" Give a precise, production-grounded answer.
Senior expectation: Must go beyond "useReducer for complex state." Must give specific, concrete criteria — number of related state fields, state transition logic, testability, debugging needs. Must show a concrete example of when useState becomes painful and useReducer solves it cleanly.
The precise criteria — use useReducer when any of these are true:

1. Multiple state fields that change together as a unit. If you have isLoading, data, error, and you always update all three atomically (fetch starts: loading=true, data=null, error=null; fetch succeeds: loading=false, data=x, error=null), that is a state machine — not three independent values. Managing it with three separate useState calls forces you to call three setters in sequence, risking partial state between renders.

2. Next state depends on previous state in non-trivial ways. Functional updates (prev => ...) handle simple accumulation. When the transformation involves branching logic based on current state (e.g. a toggle that also resets other fields, a paginator that clamps to bounds), that logic belongs in a reducer where it is co-located, named, and testable.

3. You want to test state transition logic in isolation. A reducer is a pure function — you can unit test every transition without mounting a component. useState transitions are anonymous inline functions scattered across event handlers.

4. Multiple actions produce the same state shape. If ten different user actions all produce valid state updates, a reducer with named action types is self-documenting. Ten separate setX calls are not.

Concrete example where useState breaks down:
const [status, setStatus] = useState('idle'); const [data, setData] = useState(null); const [error, setError] = useState(null); async function fetchUser() { setStatus('loading'); setData(null); setError(null); try { const d = await api.getUser(); setStatus('success'); setData(d); } catch(e) { setStatus('error'); setError(e); } }
Six setter calls — and between each pair, a render could theoretically show an inconsistent state (loading=true but error still set from last time). The reducer version:
const [state, dispatch] = useReducer(fetchReducer, { status: 'idle', data: null, error: null }); function fetchReducer(state, action) { switch(action.type) { case 'FETCH_START': return { status: 'loading', data: null, error: null }; case 'FETCH_SUCCESS': return { status: 'success', data: action.payload, error: null }; case 'FETCH_ERROR': return { status: 'error', data: null, error: action.error }; default: return state; } }
One dispatch call. One atomic state transition. Testable without React. State shape is always consistent — no intermediate partial states between fields.
The short version for interviews: useState for independent, simple values. useReducer when you have a state machine — multiple fields that transition together, or logic that needs naming and testing. If you find yourself writing more than two related useState setters in the same handler, that is the signal to reach for useReducer.
