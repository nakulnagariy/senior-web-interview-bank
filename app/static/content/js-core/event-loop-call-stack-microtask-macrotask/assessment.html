Event loop — call stack, microtask, macrotask

6 questions. Output prediction is the most common interview format here — work every answer before revealing. All buttons functional.

Key rule: after each macrotask, the entire microtask queue drains completely before the next macrotask runs. A microtask that queues another microtask keeps draining — it does not wait for a macrotask.
QUESTIONS
Q1outputmust-know
Predict the exact output in order. Then explain the precise state of the call stack, microtask queue, and macrotask queue at each step.
console.log('A'); setTimeout(() => console.log('B'), 0); Promise.resolve() .then(() => console.log('C')) .then(() => console.log('D')); console.log('E');
Senior expectation: Must give A→E→C→D→B and explain why. Must articulate that setTimeout(fn, 0) does not mean "immediately" — it means "after current sync + all microtasks." Must walk the queue state at each transition point.
step 1ASynchronous. console.log('A') pushed onto call stack, runs, pops.
step 2—setTimeout callback registered with browser timer API. Even with 0ms delay it goes to macrotask queue — never runs before sync code finishes.
step 3—Promise.resolve() settles immediately. First .then callback queued in microtask queue.
step 4ESynchronous. console.log('E') runs. Call stack now empty.
step 5CCall stack empty — event loop drains microtask queue. First .then fires, logs C. This .then returns undefined, which schedules the next .then as a new microtask.
step 6DMicrotask queue not yet empty — second .then fires, logs D. Queue now empty.
step 7BMicrotask queue drained. Event loop picks next macrotask — setTimeout callback runs, logs B.
Final output: A E C D B. The critical insight: setTimeout(fn, 0) does not mean "run immediately after this line." It means "schedule this as a macrotask, run after current sync AND after the entire microtask queue drains." The 0ms is the minimum delay, not the actual delay.
Q2outputmust-know
This is the question most seniors get wrong. Predict the exact output and explain the two-tick penalty that causes 'D' to appear after 'E'.
Promise.resolve() .then(() => { console.log('A'); return Promise.resolve('inner'); }) .then(v => console.log('B', v)); Promise.resolve() .then(() => console.log('C')) .then(() => console.log('D')) .then(() => console.log('E'));
Senior expectation: Output is A→C→D→E→B inner. Must explain the two-tick penalty: returning Promise.resolve() from inside a .then() handler causes two extra microtask ticks before the next .then fires — due to the PromiseResolveThenableJob introduced by the spec to handle potentially synchronous thenables. This is the most commonly missed senior-level output question on promises and the event loop combined.
Both chains register their first .then as microtasks simultaneously. The microtask queue starts with: [chain1.then1, chain2.then1].

Tick 1 — chain1.then1 runs → logs A → returns Promise.resolve('inner') (a thenable). The spec mandates a PromiseResolveThenableJob to assimilate this — costs one extra microtask tick. Queue: [chain2.then1, resolveThenableJob]

Tick 2 — chain2.then1 runs → logs C. Schedules chain2.then2. Queue: [resolveThenableJob, chain2.then2]

Tick 3 — resolveThenableJob runs → resolves the outer promise with 'inner' → schedules chain1.then2. Queue: [chain2.then2, chain1.then2]

Tick 4 — chain2.then2 runs → logs D. Schedules chain2.then3. Queue: [chain1.then2, chain2.then3]

Tick 5 — chain1.then2 runs → logs B inner. Queue: [chain2.then3]

Tick 6 — chain2.then3 runs → logs E.
final outputA C D B ENot A C D E B — the two-tick penalty from returning Promise.resolve() lets chain2 advance two more steps before chain1's second .then fires.
Production implication: returning Promise.resolve(value) from inside a .then() adds latency versus returning a plain value. In tight async pipelines this two-tick gap is measurable. Return plain values unless you specifically need a new Promise.
Q3outputgotcha
Predict the output. The tricky part is the interaction between async/await and the event loop — trace exactly what happens when the engine hits each await.
async function foo() { console.log('B'); await Promise.resolve(); console.log('D'); } console.log('A'); foo(); console.log('C');
Senior expectation: Output is A→B→C→D. Must explain that async functions run synchronously until the first await — they are not deferred entirely. The await suspends the function and schedules the remainder as a microtask, returning control to the caller. Must explain await as syntactic sugar over Promise.then.
step 1ASynchronous. console.log('A') runs.
step 2Bfoo() is called. The async function body runs synchronously until the first await. console.log('B') executes immediately.
step 3—await Promise.resolve() suspends foo(). The rest of foo() (after the await) is scheduled as a microtask. foo() returns a pending Promise to the caller.
step 4CControl returns to the call site. console.log('C') runs synchronously. Call stack empties.
step 5DMicrotask queue drains. foo() resumes after the await. console.log('D') runs.
Final output: A B C D. The key mental model: async function does not defer the entire function — it runs synchronously until the first await. At that point, it suspends, schedules its continuation as a microtask, and returns control to whoever called it. await x is equivalent to Promise.resolve(x).then(resume) — it always costs at least one microtask tick even when awaiting an already-resolved promise.
Q4outputgotcha
This is a harder async/await + setTimeout interaction. Predict the full output in order and explain the queue state after each transition.
async function bar() { console.log('2'); await null; console.log('4'); await null; console.log('6'); } console.log('1'); bar(); setTimeout(() => console.log('7'), 0); console.log('3');
Senior expectation: Output is 1→2→3→4→6→7. Must show that each await null costs one microtask tick, so '4' and '6' fire before the setTimeout macrotask. A common wrong answer is 1→2→3→4→7→6 — getting this right proves deep understanding of microtask queue draining.
sync phase1, 2, 3'1' logs. bar() called: '2' logs, hits first await null, suspends. setTimeout registered as macrotask. '3' logs. Call stack empty.
microtask 14First await null resolves — bar() resumes, logs '4', hits second await null, suspends again. New microtask scheduled.
microtask 26Second await null resolves — bar() resumes, logs '6', function completes. Microtask queue now empty.
macrotask7Microtask queue fully drained. Event loop picks setTimeout callback — logs '7'.
Final output: 1 2 3 4 6 7. Each await suspends and resumes via the microtask queue — so both resumptions ('4' and '6') fire before the macrotask ('7'). The rule holds: the full microtask queue — including microtasks spawned by microtasks — drains completely before any macrotask gets to run.
Common wrong answer: 1 2 3 4 7 6 — this would only be correct if each await pushed continuation to the macrotask queue. It does not. await always uses microtasks. If you said 7 before 6, you confused microtask and macrotask scheduling.
Q5gotchamust-know
A junior engineer writes a "sleep" utility using setTimeout and is confused why the code after it runs before the UI updates. Then they switch to a queueMicrotask-based sleep and the app hangs. Explain both failure modes and what the correct tool is for each use case.
function sleepMacro(ms) { return new Promise(resolve => setTimeout(resolve, ms)); } function sleepMicro() { return new Promise(resolve => queueMicrotask(resolve)); } async function runA() { await sleepMacro(0); console.log('after macro sleep'); } async function runB() { while(true) { await sleepMicro(); processNextItem(); } }
Senior expectation: Must explain that setTimeout(0) yields to the browser for rendering but adds ~4ms minimum delay. queueMicrotask never yields — a microtask loop starves the macrotask queue indefinitely, freezing rendering and I/O. Must know the correct tool: scheduler.yield() or MessageChannel for cooperative yielding without minimum delay.
sleepMacro(0) issue: setTimeout has a minimum clamped delay of ~4ms (spec-enforced, ~1ms in some environments). If the engineer wants to yield to the browser to allow a paint/reflow, this works — but it adds non-trivial latency in tight loops. If they want to simply defer to after the current microtask queue, setTimeout is heavier than needed.

sleepMicro() hang: queueMicrotask queues in the microtask queue. The while loop awaits a microtask — which resolves, which schedules the next iteration as a microtask, which resolves, infinitely. The microtask queue never empties. The browser's rendering pipeline and all setTimeout/setInterval callbacks live in the macrotask queue — they never get a turn. The tab freezes completely: no repaints, no user input, no network callbacks.

The correct tools by use case:
yield to rendersetTimeout(0)Guarantees a rendering opportunity before continuation. Use for chunked heavy work that must not block paint.
cooperative yieldscheduler.yield()New browser API — yields to the browser without the 4ms setTimeout tax. Falls back to MessageChannel hack in older browsers.
post-render checkrequestAnimationFrameFires after the browser has committed a paint. Use for animation-synchronised work.
idle workrequestIdleCallbackRuns when the browser has spare time between frames. Use for non-urgent background processing.
The MessageChannel trick for zero-delay macrotask yielding (without setTimeout's 4ms clamp): const {port1, port2} = new MessageChannel(); port1.onmessage = resolve; port2.postMessage('') — posts a message to itself, which fires as a macrotask with no artificial delay.
Q6architecture
Production scenario: your React app processes large CSV uploads (100k rows) synchronously on the main thread. The UI freezes for 3–5 seconds during processing. Using your knowledge of the event loop, design two different solutions — one that stays on the main thread, one that leaves it — and explain the trade-offs of each.
Senior expectation: Solution 1 must use chunked processing with setTimeout/scheduler.yield to cooperatively yield between chunks — keeping the main thread responsive. Solution 2 must use a Web Worker to fully offload processing. Must give concrete trade-offs: Workers have serialization cost, can't touch the DOM; chunking keeps UI responsive but processing takes longer overall.
Solution 1 — Chunked processing on main thread: Split the 100k rows into chunks of ~500 rows. Process one chunk, then yield to the browser for a render opportunity, then process the next chunk. This keeps the UI responsive (user can see a progress bar update) at the cost of slightly longer total processing time.
async function processCSV(rows) { const CHUNK = 500; const results = []; for (let i = 0; i < rows.length; i += CHUNK) { const chunk = rows.slice(i, i + CHUNK); results.push(...chunk.map(transform)); const progress = Math.round((i / rows.length) * 100); setProgress(progress); await new Promise(r => setTimeout(r, 0)); } return results; }
Solution 2 — Web Worker offload: Spin up a Worker, post the full dataset, receive the processed result. The main thread is completely free during processing — zero UI jank. Worker runs on a separate OS thread with its own event loop.
const worker = new Worker('/csv-worker.js'); worker.postMessage({ rows }); worker.onmessage = ({ data }) => { setResults(data.results); setProgress(100); }; worker.onerror = (err) => setError(err.message);
Trade-offs side by side:
chunkedprosNo serialization cost. Can access DOM/React state directly. Progress bar updates naturally. Works in all browsers.
chunkedconsTotal processing time is ~10-20% longer (yield overhead). UI still processes on main thread — other JS (animations, user input handlers) competes for ticks.
web workerprosTrue parallelism. Main thread completely free. Total processing time is faster — dedicated thread with no competition.
web workerconsData must be serialized/deserialized via postMessage (structured clone — costs time for 100k rows). No DOM/React access from Worker. Requires separate file or blob URL. Progress requires messaging back each chunk result.
Optimal production choice: Web Worker for pure data transformation (no DOM needed), with chunk-based progress messages posted back. For the 100k row case, use SharedArrayBuffer + Atomics to share memory directly and avoid serialization cost entirely — though this requires secure context (HTTPS + COOP/COEP headers).
