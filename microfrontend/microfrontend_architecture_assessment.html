QUESTIONS
Q1architecturemust-know
Compare the four main micro-frontend integration strategies — build-time (npm packages), runtime via Module Federation, iframes, and Web Components. For each, give one real production scenario where it is the correct choice and one where it fails badly.
Senior expectation: Must go beyond surface-level definitions. Must articulate the deployment coupling problem with npm packages, the shared singleton problem with Module Federation, the iframe communication overhead, and the browser support / SSR limitations of Web Components. Each "fails badly" case should be a real scenario, not a vague trade-off.
Build-time (npm packages):
Correct for: a shared design system — Button, Input, Modal — consumed by multiple teams. These components change infrequently and all teams can align on a release cycle. The type safety and tree-shaking benefits of a proper npm package outweigh the coordination cost.
Fails badly when: teams need independent deployment. Publishing a patch to fix a checkout MFE bug requires every consuming team to update and redeploy their app simultaneously. One team's release schedule blocks another's hotfix. This is the core deployment coupling problem that makes npm packages wrong for independently-deployed features.

Runtime via Module Federation:
Correct for: large product suites where teams need truly independent deploy cadences. The checkout team ships at 2pm, the product catalog team ships at 4pm — the shell app loads both at their latest URL without rebuilding. Zero coordination required for feature releases.
Fails badly when: shared singletons are mismanaged. If React is not declared as a singleton shared dependency, each remote bundles its own React copy. Two React instances = two Context registries = Provider in remote A invisible to consumer in remote B. Entire feature trees silently break with no obvious error.

Iframes:
Correct for: embedding third-party or legacy content with guaranteed style and script isolation — a payment widget, a legacy CRM screen, a third-party analytics dashboard. Hard security boundary is the feature, not the limitation.
Fails badly when: UX requires seamless integration. Iframes cannot share DOM, cannot overflow their boundaries (modal dialogs are clipped), have complex cross-origin postMessage communication for every interaction, and break keyboard navigation and accessibility patterns. Any feature requiring "feels like one app" behaviour cannot live in an iframe.

Web Components:
Correct for: framework-agnostic components shared across a mixed-framework estate — a team using Vue consuming a component from a React team, or embedding widgets in a CMS. The Custom Element API is framework-neutral by design.
Fails badly when: SSR is required. Web Components have no server rendering story in most frameworks — they render as empty shells during SSR and hydrate on the client, creating large CLS and blank initial states. Also: React's synthetic event system does not bubble through Shadow DOM boundaries, breaking standard React event patterns inside Web Components.
Q2architecturemust-know
Explain exactly how Webpack Module Federation works under the hood — what the host and remote webpack configs look like, how the runtime resolves remote modules, and what "singleton" sharing means and why it's critical for React.
Senior expectation: Must show both webpack configs with correct plugin syntax. Must explain the remoteEntry.js bootstrap file mechanism. Must explain singleton sharing — React must be a singleton across all MFEs or Context, hooks, and reconciliation break. Should mention version negotiation and what happens on version mismatch.
Module Federation works via a special webpack plugin that generates a remoteEntry.js file for each remote. This file is a manifest + runtime that declares what modules the remote exposes and what shared dependencies it has. The host loads this file at runtime (a dynamic script tag injection) and uses it to resolve module requests.

Remote webpack config (e.g. Checkout MFE):
// checkout/webpack.config.js new ModuleFederationPlugin({ name: 'checkout', filename: 'remoteEntry.js', exposes: { './CheckoutPage': './src/CheckoutPage', './CartSummary': './src/CartSummary', }, shared: { react: { singleton: true, requiredVersion: '^18.0.0' }, 'react-dom': { singleton: true, requiredVersion: '^18.0.0' }, }, })
Host (shell app) webpack config:
// shell/webpack.config.js new ModuleFederationPlugin({ name: 'shell', remotes: { checkout: 'checkout@https://checkout.myapp.com/remoteEntry.js', }, shared: { react: { singleton: true, requiredVersion: '^18.0.0' }, 'react-dom': { singleton: true, requiredVersion: '^18.0.0' }, }, })
Consuming a remote module in the shell:
// In shell — dynamically imported, code-split automatically const CheckoutPage = lazy(() => import('checkout/CheckoutPage')); function App() { return ( <Suspense fallback={<PageSkeleton />}> <Route path="/checkout" element={<CheckoutPage />} /> </Suspense> ); }
Why singleton: true is critical for React: Without it, if the shell has React 18.2.0 and checkout has React 18.0.0, Module Federation loads both. Two separate React instances means two separate reconcilers, two Context registries, two hook state systems. A useContext(AuthContext) in checkout reads from a different registry than the Provider in the shell — silently returns the default value. useState calls in checkout components are tracked by a different reconciler — hooks break in unpredictable ways.

With singleton: true, Module Federation's version negotiation picks one React version (the highest compatible one) and shares it across all MFEs. If versions are incompatible, it logs a warning but still shares one instance — the consuming app gets the host's version.
Version mismatch warnings from Module Federation in prod are often ignored. They shouldn't be — a remote expecting React 18 hooks behaviour running on React 17 will silently break features. Pin requiredVersion ranges tightly and treat version warnings as build failures in CI.
Q3gotchamust-know
Cross-MFE communication is one of the hardest problems in micro-frontend architecture. A user logs in via the Auth MFE — the Header MFE needs to show their name, and the Cart MFE needs their userId to load their cart. Design a communication architecture that keeps MFEs decoupled. Give at least three approaches with their trade-offs.
Senior expectation: Must identify that the core tension is decoupling vs coordination. Must give at least three concrete patterns with real trade-offs — not just "use an event bus" vaguely. Should explain why shared Redux store is a coupling trap and why the URL is underrated as a communication channel.
Approach 1 — Custom event bus (pub/sub on window):
MFEs communicate through browser native CustomEvents — zero shared library required:
// Auth MFE — emits after login window.dispatchEvent(new CustomEvent('mfe:auth:login', { detail: { userId: '123', name: 'Alice', token: 'jwt...' } })); // Header MFE — listens window.addEventListener('mfe:auth:login', (e) => { setUser(e.detail); }); // Cart MFE — listens window.addEventListener('mfe:auth:login', (e) => { loadCart(e.detail.userId); });
Trade-offs: completely decoupled — MFEs don't import each other. Events are fire-and-forget — no guarantee a listener is registered when the event fires (race condition on slow-loading MFEs). No type safety without a shared event schema contract. Hard to debug — events leave no trace in React DevTools.

Approach 2 — Shared state store via Module Federation:
Expose a singleton store from the shell, consumed by all MFEs:
// shell exposes a Zustand store exposes: { './store': './src/store' } // Remote MFE consumes it import { useAuthStore } from 'shell/store'; const { user } = useAuthStore();
Trade-offs: strongly typed, reactive, works like a normal store. But it creates a hard runtime dependency on the shell — the MFE cannot run standalone without the shell's store being present. Tightly couples MFE lifecycle to shell version. Good for auth/session state that all MFEs genuinely share. Bad for feature-specific state.

Approach 3 — URL as the source of truth:
Encode shared state in the URL — query params, path segments, or hash. All MFEs read from the URL independently:
// After login, shell navigates to: // /dashboard?userId=123&sessionId=abc // Each MFE reads what it needs from the URL const userId = new URLSearchParams(location.search).get('userId');
Trade-offs: zero coupling — each MFE is completely independent. Deep-linkable and bookmarkable state for free. Survives page refresh. Limitation: sensitive data (tokens) must not go in the URL. Complex state (arrays, nested objects) is cumbersome to encode. Not suitable for ephemeral UI state (tooltip open, animation progress).

Approach 4 — BroadcastChannel API (tabs + iframes):
For cross-tab or cross-iframe communication without a shared window: const ch = new BroadcastChannel('mfe-auth') — posts messages to all MFEs on any tab. Survives iframe boundaries unlike CustomEvent.

Production recommendation: use the URL for persistent shared state (user session, selected entity ID), CustomEvents for transient notifications (login, logout, cart updated), and a shared Zustand store (via MF) only for truly global reactive state that every MFE depends on.
Q4gotcha
CSS isolation is a silent killer in micro-frontend apps. Describe every way styles can leak between MFEs and for each one explain the correct isolation technique — including the trade-offs of each approach.
Senior expectation: Must cover global class name collisions, CSS custom property leakage, CSS-in-JS style tag injection ordering, and reset/normalise stylesheet conflicts. Must evaluate Shadow DOM, CSS Modules, BEM namespacing, and CSS-in-JS isolation. Must know that Shadow DOM breaks global portals and React modals.
Problem 1 — Global class name collisions: MFE-A defines .button { background: blue }. MFE-B defines .button { background: red }. Both inject into the same document — whichever loads last wins, breaking the other MFE's styles randomly depending on load order.
Fix: CSS Modules (generates .button_a3f2k scoped hashes at build time) or strict BEM namespacing (.checkout__button, .catalog__button). CSS Modules is better — namespacing is enforced by tooling, not convention.

Problem 2 — Global reset/normalise conflicts: Both MFEs include their own normalize.css or CSS reset. They stack — margin resets apply twice, font-size resets conflict. The last loaded reset wins for each property.
Fix: The shell owns the global reset. MFEs never include their own global resets — only scoped component styles.

Problem 3 — CSS custom property leakage: MFE-A sets :root { --color-primary: blue }. Since :root is the document root, MFE-B inherits this — overriding its own design tokens if they share variable names.
Fix: Scope custom properties to a container element, not :root: [data-mfe="checkout"] { --color-primary: green }. Each MFE wraps itself in a container with its own scope.

Problem 4 — CSS-in-JS style injection ordering: Emotion and styled-components inject <style> tags into the document head. If two MFEs use different versions of the same CSS-in-JS library, their style tags interleave unpredictably — specificity ordering becomes non-deterministic.
Fix: All MFEs must use the same CSS-in-JS library version (Module Federation singleton). Or use CSS Modules instead — build-time scoping has no runtime injection ordering problem.

Shadow DOM — the nuclear option: Attach each MFE's React root inside a Shadow DOM element — complete style isolation, nothing leaks in or out.
const shadow = document.getElementById('mfe-checkout') .attachShadow({ mode: 'open' }); const root = ReactDOM.createRoot(shadow); root.render(<CheckoutApp />);
Trade-offs of Shadow DOM: global CSS (Tailwind, design tokens, fonts) does not penetrate Shadow DOM — must be duplicated inside each shadow root. React portals (ReactDOM.createPortal) render outside the shadow root into the light DOM — modal overlays escape their style scope. Third-party components that rely on global styles break. Shadow DOM is correct for true third-party widget isolation; it is usually too aggressive for same-company MFE architectures.
The pragmatic production choice: CSS Modules for all component styles + BEM namespace prefix for any unavoidable global classes + shell owns global resets and design tokens. Shadow DOM only for third-party embeds.
Q5architecture
Design the deployment and CI/CD pipeline for a micro-frontend system with one shell app and four feature MFEs. Address: independent deployability, versioning strategy, rollback, feature flags for MFEs, and how you handle the "chunk hash mismatch" problem when the shell caches a stale remoteEntry.js URL.
Senior expectation: Must design truly independent pipelines — not "deploy everything together." Must address the remoteEntry.js caching problem specifically (this is the most common production incident in MFE systems). Must cover rollback without requiring shell redeploy and feature flags at the MFE loading level.
Independent CI/CD pipelines:
Each MFE has its own pipeline triggered by commits to its own repository (or monorepo package). The pipeline: test → build → deploy assets to CDN → update a manifest registry. The shell has no knowledge of individual MFE deployments — it reads a central manifest at runtime.
// Central manifest — updated by each MFE's pipeline // manifest.json (served by your infrastructure) { "checkout": "https://cdn.myapp.com/checkout/v2.4.1/remoteEntry.js", "catalog": "https://cdn.myapp.com/catalog/v1.9.0/remoteEntry.js", "cart": "https://cdn.myapp.com/cart/v3.1.0/remoteEntry.js", "auth": "https://cdn.myapp.com/auth/v1.2.3/remoteEntry.js" }
The shell fetches this manifest on startup (or on each navigation) and uses the URLs to load remotes. A MFE deployment = update one entry in the manifest. Shell never needs to rebuild or redeploy.

The remoteEntry.js caching problem:
If the shell hardcodes checkout@https://cdn.myapp.com/checkout/remoteEntry.js (no version in URL), the CDN/browser caches the old file. New checkout deployment is invisible until cache expires. The fix: version the remoteEntry.js URL itself. Each build of checkout deploys to /checkout/v2.4.1/remoteEntry.js. The manifest is the only file with no version in its URL — served with Cache-Control: no-store or very short TTL (30s). Asset chunks are content-hashed and cached aggressively (1 year).

Rollback strategy:
Rollback = update the manifest to point to the previous version's URL. The old assets are still on the CDN (never delete old versions for 30 days). Rollback time: seconds. No shell redeploy required.
// Rollback checkout to v2.3.9: // Just update manifest.json: "checkout": "https://cdn.myapp.com/checkout/v2.3.9/remoteEntry.js" // Shell picks it up on next manifest fetch
Feature flags for MFEs:
The manifest itself becomes a feature flag system. Rather than loading checkout/CheckoutPage directly, the shell checks a feature flag service and either loads the new MFE remote or falls back to the current stable version. Dark launches (load but don't render), canary deployments (10% of users get v2.4.1), and A/B tests all become manifest-level decisions with zero code changes in MFEs.

Monitoring:
Each MFE remote load is a network request — instrument with custom performance marks. Track: remote load time, module resolution failures (chunk 404s), and MFE error boundary activations. Alert on any MFE's error rate rising independently — isolates which team's deploy caused a production incident.
The manifest-driven architecture is the production-grade evolution of hardcoded Module Federation URLs. It gives you runtime control over which version of each MFE the shell loads — without any code change or redeploy. It is effectively a feature flag system for entire micro-frontends.
Q6architecturemust-know
The hardest micro-frontend question: when should you NOT use micro-frontends? A startup CTO asks you to evaluate whether their 8-engineer frontend team should adopt MFE architecture for their React monolith. Give a structured recommendation framework — including the specific signals that mean "yes, now" vs "not yet" vs "never for this team."
Senior expectation: Must push back on the premise — most teams adopting MFEs are not at the scale that justifies them. Must give concrete team/org size thresholds and specific engineering costs. Must identify the two genuine problems MFEs solve (team autonomy at scale, tech heterogeneity) and show that neither applies to an 8-engineer team. Must articulate the correct scaling path.
Micro-frontends solve exactly two problems: (1) team deployment autonomy at scale — when teams are blocked on each other's release schedules, (2) technology heterogeneity — when different parts of the product legitimately need different frameworks or versions.

For an 8-engineer frontend team, neither problem exists yet. The recommendation: do not adopt MFEs now. Here is the framework:

Signal: "not yet" (current state — 8 engineers):
deploymentno8 engineers can coordinate a release in a standup. Deployment blocking is not a real pain yet — it is hypothetical future pain.
team ownershipnoClear feature ownership in a monorepo with good folder structure solves 90% of team autonomy problems without runtime complexity.
build timenoBuild times become a problem at much larger codebase scale. Module Federation adds build complexity — you are solving a problem you don't have.
tech debtnoMFEs do not reduce existing tech debt — they add an integration layer on top of it. "Our code is messy" is not a MFE problem.
Signal: "yes, now" (typically 50+ engineers, multiple product teams):
release blockingyesTeam A's broken PR is blocking Team B's hotfix from shipping. This is happening weekly. Shared deployment pipeline is the bottleneck.
team scaleyes5+ independent product teams, each with their own roadmap and sprint cadence. Coordinating a shared frontend release across 5 teams is a project management nightmare.
tech diversityyesAn acquired company's Angular app must be embedded in your React shell. Or one team legitimately needs to migrate to a new framework while others stay on the old one.
owned verticalsyesTeams own full vertical slices (checkout, catalog, auth) with different SLAs, different deployment frequencies, and different tech stacks. Monolith coupling actively prevents this ownership.
The correct path for 8 engineers:
1. Strong monorepo structure with clear package boundaries (packages/checkout, packages/catalog)
2. Separate CI jobs per package with affected-only builds (Nx, Turborepo)
3. Strict interface contracts between packages — import only from public API, never internals
4. This gives you 80% of MFE's team-autonomy benefits with 10% of the operational complexity

Revisit MFEs when: the team triples and deployment coordination becomes a measurable productivity drag. At that point, the monorepo package boundaries make migration to MFEs straightforward — the interfaces are already defined.
MFEs increase your operational surface area significantly: multiple build pipelines, a manifest service, shared dependency version negotiation, cross-MFE debugging complexity, and local development requiring multiple running servers. These costs are worth it at scale. They are not worth it for 8 engineers — they will slow the team down and produce no meaningful benefit.
