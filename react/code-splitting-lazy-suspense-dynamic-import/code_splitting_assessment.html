Code splitting — React.lazy, Suspense, dynamic import

6 questions across internals, gotchas, coding patterns, and architecture. This topic covers both how it works under the hood and how it fails in production.

QUESTIONS
Q1theorymust-know
Explain exactly what happens — at the bundler level, the network level, and the React rendering level — from the moment a user navigates to a lazy route until the component appears on screen. Walk through every step.
Senior expectation: Must cover all three layers — not just "React shows a fallback". Must explain the Promise-throwing mechanism (how Suspense actually works internally), the bundler chunk emission, and the network waterfall. Should mention that React re-renders the tree once the chunk resolves.
Step 1 — Build time (bundler). When Webpack or Vite encounters import('./Dashboard'), it treats this as a split point and emits Dashboard.[hash].js as a separate chunk. The main bundle gets a small stub that knows how to fetch this chunk by its hashed filename.

Step 2 — User navigates. React renders the lazy component for the first time. The lazy wrapper calls the factory function () => import('./Dashboard'). The Promise is pending — the chunk is not loaded yet.

Step 3 — React's Suspense mechanism. React.lazy throws the pending Promise. This is not a regular error — React's reconciler catches thrown Promises specifically. It walks up the tree to find the nearest <Suspense> boundary and renders its fallback prop instead.

Step 4 — Network. The browser requests Dashboard.[hash].js. This is a real network round-trip — subject to latency, CDN caching, and connection speed.

Step 5 — Chunk resolves. The Promise settles. React re-renders from the Suspense boundary downward, this time successfully rendering the now-available component. The fallback is replaced with the real UI.

Step 6 — Failure path. If the network request fails (404, timeout, offline), React.lazy's Promise rejects. Suspense does NOT handle rejections — the error propagates to the nearest Error Boundary. Without one, the entire tree crashes.
The thrown-Promise mechanism is not public API — it's an internal React convention called "Suspense for data". React 18 formalised this with the use() hook, which can throw any Promise, not just lazy component loads.
Q2gotchamust-know
This code has three mistakes that will cause real production problems. Identify all three and fix them.
import React, { lazy } from 'react'; const Dashboard = lazy(() => import('./Dashboard')); const Settings = lazy(() => import('./Settings')); function App() { return ( <Suspense> <Router> <Route path="/dashboard" element={<Dashboard />} /> <Route path="/settings" element={<Settings />} /> </Router> </Suspense> ); }
Senior expectation: Must catch missing fallback prop (Suspense renders nothing during load), missing Error Boundary (chunk load failure crashes the app), and lazy definitions inside the component (they'd be recreated on every render). Should provide the corrected version.
Problem 1 — Missing fallback prop on Suspense. Without a fallback, React renders nothing (null) while the chunk loads. Users see a blank screen with no indication anything is happening. Always provide a meaningful fallback — at minimum a spinner, ideally a skeleton that matches the page layout to prevent layout shift.

Problem 2 — No Error Boundary. If Dashboard.js fails to load (network blip, deploy with new hashes, user offline), the thrown rejection is uncaught. React unmounts the entire tree and shows a blank screen in production. Wrap with an Error Boundary that shows a "Failed to load — retry" UI.

Problem 3 — Lazy definitions are fine here (they're at module level), but a common variant of this mistake is defining lazy inside the component function body — that recreates the lazy reference on every render, triggering a new import() and destroying Suspense's ability to cache the result.

Corrected version:
const Dashboard = lazy(() => import('./Dashboard')); const Settings = lazy(() => import('./Settings')); function App() { return ( <ErrorBoundary fallback={<ChunkLoadError />}> <Suspense fallback={<PageSkeleton />}> <Router> <Route path="/dashboard" element={<Dashboard />} /> <Route path="/settings" element={<Settings />} /> </Router> </Suspense> </ErrorBoundary> ); }
Never define React.lazy() inside a component function body. The reference is recreated on every render, causing the component to remount on every parent re-render — destroying state, triggering redundant network requests, and flickering the fallback continuously.
Q3codingmust-know
React.lazy only supports default exports. Your team has a component library where everything is named export. Without changing the library, implement a pattern that makes lazy loading work for named exports — and explain why the constraint exists.
// component-library/index.js export { HeavyChart } from './HeavyChart'; export { DataGrid } from './DataGrid'; // You cannot modify the library. // How do you lazy load HeavyChart?
Senior expectation: Must know the re-export wrapper pattern. Must explain WHY React.lazy requires default exports (it looks for module.default on the resolved module object). Bonus: mention that React's future versions and some bundler plugins are relaxing this constraint.
Why the constraint exists: React.lazy() resolves the Promise and accesses module.default directly — it assumes a single default export represents the component. This is a deliberate simplicity choice, not a technical limitation.

The re-export wrapper pattern — create a thin proxy file:
// lazy-wrappers/HeavyChart.js export { HeavyChart as default } from '../component-library'; // In your app: const HeavyChart = lazy( () => import('./lazy-wrappers/HeavyChart') );
Alternatively, inline the re-export directly in the lazy call:
const HeavyChart = lazy(() => import('../component-library').then(mod => ({ default: mod.HeavyChart })) );
The .then(mod => ({ default: mod.HeavyChart })) pattern constructs a synthetic module object that satisfies React.lazy's expectation. This is the idiomatic solution — no extra files needed. The trade-off: every lazily-loaded named export still pulls in the full library barrel unless your bundler's tree-shaking can isolate the chunk, which barrel files often defeat. The proxy file approach gives the bundler a cleaner split point.
Barrel files (index.js re-exporting everything) are the silent enemy of code splitting. Even with React.lazy, if the library barrel isn't tree-shakeable, the entire library lands in one chunk. Use direct imports or sideEffects: false in package.json to help bundlers split correctly.
Q4gotcha
A user deploys a new version of the app. An existing user's browser still has the old HTML cached, which references old chunk filenames like Dashboard.abc123.js. The new deployment replaced that chunk with Dashboard.xyz789.js. What happens when the old user navigates to the dashboard, and how do you handle this in production?
Senior expectation: This is a real production outage scenario called "chunk hash mismatch" or "stale chunk" problem. Must identify that the old chunk 404s, React.lazy rejects, and without an Error Boundary the app crashes. Must know at least two recovery strategies.
What happens: the old HTML requests Dashboard.abc123.js. That file no longer exists on the CDN/server — it was replaced with Dashboard.xyz789.js in the new deployment. The browser gets a 404. React.lazy's Promise rejects. Without an Error Boundary, the entire React tree unmounts and the user sees a blank screen with no way to recover.

Strategy 1 — Error Boundary with reload. Catch the chunk load failure and offer a "click to refresh" button. On click, call window.location.reload() — the browser fetches the new HTML with correct chunk references, and the new chunk loads successfully. This is the most user-friendly approach.
class ChunkErrorBoundary extends React.Component { state = { hasError: false }; static getDerivedStateFromError(error) { const isChunkError = error?.name === 'ChunkLoadError' || error?.message?.includes('Loading chunk'); return { hasError: true, isChunkError }; } render() { if (this.state.hasError && this.state.isChunkError) { return ( <div> <p>A new version is available.</p> <button onClick={() => window.location.reload()}> Refresh to update </button> </div> ); } return this.props.children; } }
Strategy 2 — Keep old chunks alive. Configure your CDN/deployment to retain previous chunk versions for a rolling window (e.g. 24 hours). Old sessions can still load their expected chunks. New sessions get new chunks. This is the most robust solution but adds storage cost.

Strategy 3 — Vite's vite-plugin-chunk-rename or Webpack's runtimeChunk. Separate the chunk manifest from the main bundle so only changed chunks get new hashes — stable chunks keep stable filenames and remain cached across deploys.
This is one of the most common production incidents in SPAs with code splitting. Every app that lazy-loads routes needs a chunk error boundary with reload logic. Without it, a deployment can silently strand users on broken sessions.
Q5architecture
Your React app has 40 routes. A colleague says "lazy load every route." Another says "only lazy load heavy routes." Who is right? Design a code splitting strategy for a large enterprise dashboard — explain what to split, where to place Suspense boundaries, and what NOT to split.
Senior expectation: Must avoid the dogmatic "lazy everything" trap. Must explain the cost of splitting (extra network round trips, waterfall risk) vs the benefit (smaller initial bundle). Should give a concrete decision framework with specific Suspense boundary placement strategy.
Don't lazy-load everything. Each split point is a potential network waterfall. If a user lands on /dashboard and the dashboard chunk triggers a data fetch inside it, you get: chunk load → render → data fetch → render. Two waterfalls where one would do. For small components (<20KB gzipped), the network overhead of an extra request often exceeds the savings.

What to split — apply these criteria:
SplitHeavy routesAnalytics dashboards, map views, rich text editors, PDF viewers — anything pulling in large third-party libraries (chart.js, monaco-editor, pdf.js)
SplitRole-gated routesAdmin panels, super-user tools — routes most users will never see. No reason to ship that code to all users.
SplitBelow-fold modalsComplex modals, drawers, wizard flows — load them on user interaction, not on page load
Don't splitShell componentsNav, sidebar, layout — always needed immediately. Splitting them adds latency with no benefit.
Don't splitLanding / loginFirst thing the user sees. Any loading delay here kills perceived performance metrics (LCP).
Don't splitSmall componentsIf the gzipped chunk is under 10-15KB, the HTTP overhead is not worth it. Bundle it.
Suspense boundary placement strategy: One global boundary at the router level handles route transitions. Additionally, place boundaries at the feature level for within-page lazy components (modals, tabs, sidepanels) — this prevents a loading modal from blanking the entire page. Nest boundaries intentionally: outer = route-level skeleton, inner = component-level spinner.
Use your bundler's bundle analyzer (webpack-bundle-analyzer or vite-bundle-visualizer) to identify what's actually large before splitting. Premature splitting without data adds complexity with no measurable benefit.
Q6codingarchitecture
Implement a lazyWithPreload utility — a wrapper around React.lazy that exposes a preload() method. Use it to preload a route's chunk on hover over its nav link, so it's already cached when the user clicks. Explain why this dramatically improves perceived performance.
Senior expectation: Must know that dynamic import() is idempotent — calling it twice for the same chunk hits the module cache the second time, not the network. Must implement preload() by calling the factory function early and caching the Promise. The hover → preload pattern is a real production technique used in large SPAs.
The key insight: import('./Dashboard') called multiple times for the same module is idempotent — Webpack/Vite cache the Promise internally. The second call returns the same (already-resolved) Promise. So calling the factory function early just "warms" the cache — when React.lazy needs it, the chunk is already there.
function lazyWithPreload(factory) { let cachedPromise = null; const LazyComponent = React.lazy(() => { if (!cachedPromise) cachedPromise = factory(); return cachedPromise; }); LazyComponent.preload = () => { if (!cachedPromise) cachedPromise = factory(); return cachedPromise; }; return LazyComponent; } // Usage: const Dashboard = lazyWithPreload( () => import('./Dashboard') ); // In nav component: <NavLink to="/dashboard" onMouseEnter={() => Dashboard.preload()} > Dashboard </NavLink>
Why this works: hover intent gives you ~100–300ms of user deliberation time before the click. On a fast connection, a JS chunk typically loads in 50–150ms. By the time the user clicks, the chunk is already cached — Suspense shows its fallback for near-zero time or skips it entirely.

Extended strategy: also preload on onFocus (keyboard navigation) and on touchstart (mobile — fires before tap resolves). You can further preload predictively based on the current route — if the user is on /dashboard, preload /settings during idle time using requestIdleCallback(() => Settings.preload()).
React Router v6.4+ has a loader API that handles data preloading alongside route transitions. Combining route-level data loaders with chunk preloading eliminates both the chunk waterfall and the data waterfall — the two biggest perceived-performance killers in SPAs.
